## summary

`@polymarket-bot/event-bus` moves normalized §7.1 envelopes from the gateway to
the trader through the four capabilities handoff §9.1 names — publish,
subscribe, consumer checkpoint, bounded retention — with Redis Streams as the
v1 implementation behind the interface (ADR-003 §1).

**The interface carries no storage vocabulary.** `src/transport.ts` declares
`MarketEventTransport`, `EventSubscription`, `StreamCheckpoint`,
`HardResyncCondition`, and `RetentionPolicy` in transport-neutral terms. A
checkpoint's `token` is opaque: it carries the issuing `transport` and its
`stream` so it cannot be replayed into the wrong place, and its internals — a
stream-instance marker, a position, and that position's publication ordinal —
are parsed only inside `src/redis/`. The marker is an implementation detail of
where a position is valid, not a new concept a consumer handles: the type is
still `{ transport, stream, token }`, and a consumer still only stores the token
and hands it back. ADR-003's Consequences make this substantive
("if consumer-group names, `XADD` ids, or `MAXLEN` trimming appear in a
consumer's types … this ADR has been violated in substance while satisfied in
form"), so `src/transport-vocabulary.test.ts` strips comments from
`transport.ts`, `metrics.ts`, `index.ts`, and `redis/index.ts` and fails on any
of twenty implementation terms appearing in a declaration. The client type is
not exported at all: it is an `ioredis` type, and a consumer able to name it
would hold the F8 grant this package reserves.

**Ordering is per gateway epoch and is never synthesised.** Events are appended
in publish order and read back in that order; nothing sorts, groups, or
renumbers. `ingestSeq` is compared as `BigInt`, never as `number` — the
integration suite publishes `9007199254740992..9007199254740995`, four values
that collapse onto one JavaScript number, and asserts they arrive in order.
`EpochOrderTracker` keeps one cursor per epoch, so a restarted gateway's epoch
restarting `ingestSeq` at 1 is not a regression and two epochs are never one
sequence. The publisher **refuses** a non-advancing `(gatewayEpoch, ingestSeq)`
pair, because an event with no defined position (ADR-002 §2) must not enter the
stream; the cursor advances only after a successful publish, so retrying a
publish that failed is not locked out. The check and the append are **one
serialized step per epoch** (`src/serial-queue.ts`), so two overlapping
publishes cannot both pass the same cursor value and land in the stream in the
order their round trips happened to finish — the later-arriving `ingestSeq` is
refused before anything is appended.

**Hard resync is exact, and it blocks.** The publish script assigns the next
publication ordinal and appends the entry in one server-side step, stamping
each entry with a contiguous ordinal. A script is isolated but not
transactional, so the two mutations are ordered and compensated rather than
merely co-located: key types and the safe-integer ceiling are checked before
anything is written, the append is guarded, and the counter write is undone by
removing the entry if it fails. A publish that fails therefore consumes no
ordinal — which matters because an ordinal with no entry behind it would read,
to the next consumer, as an event retention removed.

A consumer therefore knows precisely how many events retention removed
before it read them, instead of inferring loss from "my position is older than
everything retained" — which is equally true of a consumer that is simply caught
up. When the ordinals are not consecutive, `receive` returns
`{ status: "resync-required", condition }` with `reason: "retention-exceeded"`,
an exact `missedEventCount`, and `requiresAuthoritativeSnapshot: true` pinned to
the literal. It **keeps** returning it, and `checkpoint` is refused, until the
caller calls `acknowledgeHardResync({ authoritativeSnapshotApplied: true, … })`.
There is no code path from that state back to delivering that does not go
through the acknowledgement, so a subscription that has seen a gap cannot
resume from it silently (ADR-003 §3.3). The acknowledged position is recorded
durably, so a crash right after it does not demand a second snapshot for the
same loss.

That statement is about a *subscription*, and it is deliberately not a claim
about the whole system: a caller may still open a **new** subscription with a
different consumer id and an explicit `{ at: "newest" }`, which starts at the
end without acknowledging anything. That is explicit rather than silent — it
requires a new durable identity and a named start position — but it is why
`WP-120` must keep one stable consumer id per role (see
[`follow_up`](#follow_up) 2).

**Checkpoints are explicit, durable, and judged.** `checkpoint(position)`
records the position under the consumer id, so a restarted trader resumes where
it stopped rather than from "now" (ADR-003 §3.4). `start` **does** have a
default — `{ at: "stored-checkpoint", whenMissing: "oldest-retained" }` — and it
is the conservative one: it resumes what the consumer stored and otherwise
replays what retention still holds. `newest` is never reached by omission;
naming the `stored-checkpoint` variant explicitly requires saying what happens
when there is nothing to resume, and `whenMissing` has no default of its own.

A checkpoint that regresses, names an undelivered event, or belongs to another
stream or transport is refused — and so is one that names a position the stream
does not hold. Every start position and every stored position is checked
against the server's own state before it is used: a token carries the marker of
the stream instance it was minted in, and the server confirms that the entry
exists, that it carries exactly that publication ordinal, and that the marker is
this stream's. A token from another server or key namespace, from a stream that
was destroyed and recreated, or naming an entry in the future, one beyond the
newest entry, or one that never existed is refused rather than resumed from.
Syntax alone is never enough, because each of those decodes into a position
delivery would happily start at, skipping everything between it and the
consumer's real position with no gap for the continuity arithmetic to find.

**Every §8.3 metric is a real, moving value.** `streamMetrics` reports current
depth, maximum depth (the configured bound), oldest message age against the
*server's* clock, messages dropped (what retention removed), producer blocked
time (cumulative time spent inside `publish`), and consumer lag per durable
consumer. `ConsumerMetrics` nests that set and adds delivered/uncheckpointed
counts, hard-resync and missed-event totals, non-monotonic deliveries, unreadable
entries, and receive wait time. Nothing here touches Prometheus:
`packages/observability` does not exist and the export arrives with `WP-140`.

**Nothing is dropped silently (§8.3).** Publication either lands or throws a
typed, coded error — invalid envelope, non-advancing `ingestSeq`, unencodable
payload, closed transport, unreachable transport. The stream never refuses an
event for being full; retention removes the oldest and the loss becomes a
consumer's hard resync. An entry that cannot be read back stops delivery after
the valid events before it, and the error names the offending position so a
caller that has opened a data-quality incident can step over exactly that entry
and nothing else. Two interleaved reads on one subscription are refused rather
than allowed to advance the position past events neither returned.

**A transport outage is a trading outage, by design.** Publication raises
`EventBusUnavailableError` instead of buffering indefinitely, so the caller's
halt path runs (ADR-003 §4). No fallback data path exists in this package.

**No latency claim is made.** Handoff §9.1's under-5 ms p99 is an unmeasured
target; ADR-003 §5 records that no benchmark has been run, and nothing in this
package measures, asserts, or implies it.

## assumptions

1. **`ingestSeq` is strictly increasing within a gateway epoch.** §7.1 calls it
   "monotonic within epoch" and states that `gatewayEpoch + ingestSeq` "defines
   the exact order"; a non-strict sequence could not define an exact order, so
   the publisher enforces strict increase. If a producer legitimately needs to
   repeat an `ingestSeq`, that is an ADR-002 question, not a transport setting.
2. **Retention is bounded by event count.** §9.1 requires "bounded retention"
   without naming a unit, and a count is the unit the hard-resync rule is
   expressed in (events missed). Trimming is exact rather than approximate so
   the bound is a guarantee — ADR-003's Consequences call retention "a safety
   parameter, not a tuning knob", and an approximate safety parameter cannot be
   sized against the worst tolerated restart.
3. **The transport validates the envelope but not the payload.** ADR-003 §2 says
   it carries normalized envelopes; the payload's contract belongs to the
   producer and consumer. Envelope validation uses the frozen
   `UnknownPayloadEventEnvelopeSchema`, so provenance and strictness are enforced
   exactly as `packages/domain` defines them and nowhere re-implemented.
4. **A checkpoint is cumulative.** There is no per-event or out-of-order
   acknowledgement, because `(gatewayEpoch, ingestSeq)` is a total order within
   an epoch and a consumer that skipped one event would have no way to say so.
5. **One process publishes any one gateway epoch.** ADR-002 §2.1: `gatewayEpoch`
   is "a UUID assigned at gateway startup", and ADR-002's Consequences require
   two gateways sharing a stream to use distinct epochs. Ordering *within* an
   epoch is therefore a within-process question, and the publisher answers it
   within the process: the check and the append are one serialized step per
   epoch (`src/serial-queue.ts`), not a check-then-act that two overlapping
   calls can both pass.

   The round-1 review **rejected** the earlier version of this assumption, which
   cited §8.1's deterministic core loop as a reason not to serialize at all;
   §8.1 describes the *trader's* loop and says nothing about the gateway
   publisher. The assumption now rests on ADR-002's definition of an epoch, and
   the serialization is present regardless — it is what makes concurrent
   publishes safe rather than merely unlikely. What remains outside this
   package's reach is two *processes* sharing one epoch, which ADR-002 already
   forbids (`known_risks` 10).
6. **`ioredis@^6` is the current `ioredis`.** Handoff §2.1 names `ioredis`
   without a version; 6.0.0 is the registry's `latest`. Its dependency set is the
   v5 family minus the `lodash.*` helpers, and every API this package uses is
   exercised by the integration suite against a real server.
7. **`redis:7.4.2-alpine` is the version to test against**, because that is what
   `docker-compose.yml` runs — the `WP-040` precedent for pinning the test image
   to the developer's local server.

## deviations

1. **`newest` is offered as a start position.** ADR-003 §3.4 rules out resuming
   from "now" *on a restart*, and this package keeps that out of reach by
   omission: `start` defaults to `{ at: "stored-checkpoint", whenMissing:
   "oldest-retained" }`, so a caller that says nothing resumes its stored
   position and otherwise replays what retention holds. `newest` remains
   reachable for a consumer's genuine first start and for a deliberate
   post-snapshot skip, both of which require naming it. (Round-1 review, L1: an
   earlier draft claimed there was *no* default. There is one; it is the
   conservative one.)
2. **`messagesDropped` counts what retention removed**, rather than being pinned
   to zero as in `WP-050`'s queue. The WAL queue refuses instead of trimming, so
   zero is a true statement about it; a bounded retention stream removes events
   by design, and reporting zero would hide the number an operator most needs.
   It is not a *silent* drop — the consumer that had not read those events gets
   a hard resync — and the integration suite asserts both facts together.
3. **`producerBlockedTimeMs` is process-local and fractional.** It measures time
   spent inside `publish` in the reporting process; a pure consumer reports `0`
   because it published nothing. Documented on the field rather than left to be
   inferred.
4. **A read-exclusivity guard was added.** Not requested by the packet, but two
   interleaved `receive` calls on one subscription would advance the shared read
   position past events neither returned — a silent drop, which §8.3 forbids.
   The guard refuses the second call; callers needing concurrency use two
   subscriptions, which have separate positions by construction.
5. **`test:integration` is wired at the package level only.** Root
   `package.json` is orchestrator-owned at merge; see `follow_up` 1.
6. **A fourth key per stream holds the instance marker.** Added in remediation
   round 1. A checkpoint token that names only a position cannot be shown to
   belong to *this* stream, so a marker is minted once per stream key space and
   carried in every token. It costs one key, one round trip per `subscribe`, and
   the operational rule in `known_risks` 6.
7. **`StreamQueueMetrics.unreadableCheckpoints` was added.** Also round 1: a
   stored position the transport cannot read is neither a lag number nor
   something to leave out of the metric set, because omitting it would make a
   consumer disappear from `consumerLag` without a word.

## known_risks

1. **`ioredis@6` is a recent major.** Its behaviour under this package is
   verified by 73 integration tests against a real server, but the repository has
   no prior production experience with it. If a defect surfaces, pinning to
   `^5.11` is a contained change: no API this package uses differs between the
   two in the paths exercised here.
2. **The publisher's ordering guard is not a distributed lock.** Within a
   process it is now airtight: the check and the append are one serialized step
   per epoch, so two overlapping `publish` calls cannot both pass the same
   cursor value — the later-arriving `ingestSeq` is refused before anything is
   appended. Across processes there is no lock, and none is meaningful for
   ordering: one epoch belongs to one gateway process by ADR-002 §2.1. What is
   *not* prevented is two processes wrongly sharing an epoch (risk 10), which
   would produce duplicate ordering identities rather than a reordered epoch,
   and which the consumer reports (risk 3).
3. **A duplicate ordering identity is reported, not refused.** An ambiguous
   publish failure followed by a successful retry, or two processes sharing one
   `gatewayEpoch`, can put two entries with the same `(gatewayEpoch, ingestSeq)`
   in the stream. The subscription counts that as `nonMonotonicDeliveries` and
   still delivers both, because stopping a trader on a legitimate at-least-once
   duplicate would be worse than reporting it.

   **Consumers must deduplicate on `(gatewayEpoch, ingestSeq)`** — the ordering
   identity (ADR-002 §2, `WP-050`) — and not on `eventId`. The two duplicates
   above carry *different* `eventId` values, so an `eventId` comparison would
   treat them as two distinct events and act on both; `eventId` is at most a
   secondary idempotency key for the case where the same envelope was
   republished byte-for-byte. (Round-1 review, M2: an earlier draft instructed
   `WP-120` to deduplicate on `eventId`. `test/integration/event-bus/metrics.test.ts`
   now demonstrates the failing case positively.)
4. **Delivery is at-least-once across a restart.** A consumer that crashes
   between delivery and checkpoint re-reads from its last checkpoint. This is
   the correct trade for never losing an event, and it is why 3 matters.
5. **An idle `receive` costs a second round trip.** After a read returns nothing,
   the subscription inspects the stream state to distinguish "nothing to read"
   from "what you had not read is gone" — the two must not look alike. A tight
   zero-wait polling loop therefore does two round trips per empty poll; a caller
   in that shape should use `waitMs`.
6. **A stream is four keys, and they are one unit.** The stream, the publication
   counter, the consumer positions, and the instance marker. Deleting some and
   not others is an operator action with a defined outcome, and every outcome is
   loud: a stream without its counter gives consumers
   `transport-sequence-inconsistent`; a stream whose marker was removed and
   re-minted refuses every position taken before, at `subscribe` and at
   `checkpoint`, and reports the stored ones as `unreadableCheckpoints`. None of
   these resumes from a position the transport cannot vouch for — but backup,
   restore, and migration must treat the four as one unit or an ordinary restart
   turns into a refusal.
7. **Publication ordinals are `number`.** They are validated as safe integers and
   the transport refuses to publish once the counter reaches
   `Number.MAX_SAFE_INTEGER`, **before** appending anything, rather than losing
   precision silently or refusing an event that already landed. At 100 000
   events/second that bound is roughly 2 850 years away, but the refusal is real
   code, not a comment.
8. **`oldestMessageAgeMs` derives from the entry id's timestamp.** That is the
   server's clock at append time, compared against the same server's clock at
   read time, so client skew cannot distort it — but a server clock step
   backwards would; the value is clamped at zero rather than reported negative.
9. **The vocabulary test strips comments with regular expressions.** The scanned
   files hold no string literal containing `//` or `/*`, so this is accurate
   today. A self-check asserts the stripper still finds real declarations, so the
   test cannot silently become vacuous, but a future author adding such a literal
   to `transport.ts` should extend the check rather than work around it.
10. **Two gateways publishing into one stream are not prevented here.** ADR-002's
    Consequences note that they must use distinct `gatewayEpoch` values; this
    package keeps their sequences separate and never merges them, but it cannot
    detect two gateways sharing an epoch. Each publisher's ordering cursor is
    its own, so a second publisher reusing an epoch's `ingestSeq` values is
    accepted at publish and surfaces at the consumer as
    `nonMonotonicDeliveries` (risk 3). That remains a gateway concern.
11. **A checkpoint is judged, not authenticated.** The instance marker makes a
    position from another server, key namespace, or destroyed-and-recreated
    stream refusable, and the server confirms that the position exists and that
    its two halves describe the same event. What it does not do is prove *who*
    minted a token: a caller holding a genuine token for a real, retained,
    later position can still choose to resume there, exactly as it could by
    passing `{ at: "newest" }`. That is an explicit start position, not a silent
    skip. Making it unforgeable would need key material this package
    deliberately does not have (§0.2, ADR-010) and would still not stop a caller
    from starting wherever it says it wants to.

    The bound on what an accepted position can hide is worth stating exactly.
    Against a stream that retains anything, every accepted position either names
    a real entry (its ordinal must match) or is older than everything retained —
    and in the second case the ordinal drives gap detection, so an inflated one
    surfaces as `retention-exceeded` at subscribe or as
    `transport-sequence-inconsistent` on the first delivery. The one residue is
    a stream that retains *nothing* while its counter says events were
    published, which only an external deletion produces: there is no newest
    entry to compare against, so a position whose id lies within the current
    millisecond is accepted, and delivery could begin after an entry appended in
    that same millisecond. One millisecond, on a stream an operator has already
    destroyed.
12. **A stored position is refused, not repaired.** If a consumer's durable
    position becomes unreadable — the marker was re-minted, or something wrote
    into the position hash — `subscribe` throws instead of falling back to a
    default start. That is the safe direction (a new start position is an
    operator's decision, not a library's), but it means an operator who wipes a
    marker must give each affected consumer an explicit start.

## follow_up

1. **Root `test:integration` wiring (orchestrator, at merge).** Root
   `package.json` currently runs only the postgres suite. `WP-060`'s suite is
   reachable as `pnpm --filter @polymarket-bot/event-bus test:integration`; the
   root script should run both once the orchestrator edits the root manifest.
2. **`WP-120` (data gateway / trader).** Four obligations:

   - **Deduplicate on `(gatewayEpoch, ingestSeq)`**, the ordering identity
     (ADR-002 §2, `WP-050`) — not on `eventId`, which differs between two
     publications of the same identity (risk 3). Treat `eventId` as a secondary
     idempotency key at most.
   - **Keep one stable durable consumer id per role, for the process's
     lifetime and across restarts.** The checkpoint, the resync state, and the
     lag metric are all keyed by it. A fresh id is a fresh consumer with no
     history: with an explicit `{ at: "newest" }` it may start at the end
     without acknowledging a resync another id is blocked on. That is explicit,
     not silent — but a generated-per-boot id would make it routine.
   - **Route a `resync-required` result to the halt path**, plus a
     `DataQualityIncidentOpened` and an authoritative snapshot before
     acknowledging. `EventBusUnavailableError` is the trading-halt signal.
   - **Give one gateway process one `gatewayEpoch`** (ADR-002 §2.1). Publishes
     within an epoch may overlap — the transport serializes them and refuses a
     non-advancing one — but two processes sharing an epoch is outside what any
     transport can order (risk 10).
3. **`WP-140` (observability).** `StreamQueueMetrics` and `ConsumerMetrics` are
   the typed source for the §8.3 and §14.3 metric families; no Prometheus naming
   is assumed here, so the exporter is free to choose it.
4. **Retention sizing is a deployment decision with a safety consequence.**
   ADR-003's Consequences: retention shorter than the worst tolerated trader
   restart turns an ordinary restart into a hard resync plus a snapshot cycle.
   The operational runbook should state the chosen bound and its justification.
5. **The 5 ms p99 target is still unmeasured.** `WP-120`/`WP-140` own the
   benchmark. If measurement shows it unreachable, ADR-003 §5 requires an ADR
   amendment with evidence, not a quiet relaxation.
6. **Schema-version upgrade ordering.** ADR-002's Consequences leave the
   producer/consumer upgrade runbook owed. This transport rejects an envelope its
   `packages/domain` build does not accept, so a dual-publish or ordering plan is
   a real deployment concern for `WP-120`.
7. **Multi-stream retention.** One `RetentionPolicy` applies to every stream a
   transport publishes. If market and reference feeds ever need different bounds,
   that is a second transport instance today; a per-stream policy would be a
   small, cited extension.
