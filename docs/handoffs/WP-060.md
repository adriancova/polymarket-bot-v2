## summary

`@polymarket-bot/event-bus` moves normalized §7.1 envelopes from the gateway to
the trader through the four capabilities handoff §9.1 names — publish,
subscribe, consumer checkpoint, bounded retention — with Redis Streams as the
v1 implementation behind the interface (ADR-003 §1).

**The interface carries no storage vocabulary.** `src/transport.ts` declares
`MarketEventTransport`, `EventSubscription`, `StreamCheckpoint`,
`HardResyncCondition`, and `RetentionPolicy` in transport-neutral terms. A
checkpoint's `token` is opaque: it carries the issuing `transport` and its
`stream` so it cannot be replayed into the wrong place, and its internals are
parsed only inside `src/redis/`. ADR-003's Consequences make this substantive
("if consumer-group names, `XADD` ids, or `MAXLEN` trimming appear in a
consumer's types … this ADR has been violated in substance while satisfied in
form"), so `src/transport-vocabulary.test.ts` strips comments from
`transport.ts`, `metrics.ts`, `index.ts`, and `redis/index.ts` and fails on any
of twenty implementation terms appearing in a declaration. The client type is
not exported at all: it is an `ioredis` type, and a consumer able to name it
would hold the F8 grant this package reserves.

**Ordering is per gateway epoch and is never synthesised.** Events are appended
in publish order and read back in that order; nothing sorts, groups, or
renumbers. `ingestSeq` is compared as `BigInt`, never as `number` — the
integration suite publishes `9007199254740992..9007199254740995`, four values
that collapse onto one JavaScript number, and asserts they arrive in order.
`EpochOrderTracker` keeps one cursor per epoch, so a restarted gateway's epoch
restarting `ingestSeq` at 1 is not a regression and two epochs are never one
sequence. The publisher **refuses** a non-advancing `(gatewayEpoch, ingestSeq)`
pair, because an event with no defined position (ADR-002 §2) must not enter the
stream; the cursor advances only after a successful publish, so retrying a
publish that failed is not locked out.

**Hard resync is exact, and it blocks.** The publish script performs
`INCR` + append atomically, stamping each entry with a contiguous publication
ordinal. A consumer therefore knows precisely how many events retention removed
before it read them, instead of inferring loss from "my position is older than
everything retained" — which is equally true of a consumer that is simply caught
up. When the ordinals are not consecutive, `receive` returns
`{ status: "resync-required", condition }` with `reason: "retention-exceeded"`,
an exact `missedEventCount`, and `requiresAuthoritativeSnapshot: true` pinned to
the literal. It **keeps** returning it, and `checkpoint` is refused, until the
caller calls `acknowledgeHardResync({ authoritativeSnapshotApplied: true, … })`.
There is no code path from that state back to delivering that does not go
through the acknowledgement, so "silent catch-up from an incomplete stream"
(ADR-003 §3.3) is unrepresentable rather than merely discouraged. The
acknowledged position is recorded durably, so a crash right after it does not
demand a second snapshot for the same loss.

**Checkpoints are explicit and durable.** `checkpoint(position)` records the
position under the consumer id, so a restarted trader resumes where it stopped
rather than from "now" (ADR-003 §3.4). A first-ever consumer has no default
start at all: `{ at: "stored-checkpoint", whenMissing: … }` forces the caller to
say what happens when no checkpoint exists, and `"newest"` is only ever
reachable by asking for it. A checkpoint that regresses, names an undelivered
event, or belongs to another stream or transport is refused.

**Every §8.3 metric is a real, moving value.** `streamMetrics` reports current
depth, maximum depth (the configured bound), oldest message age against the
*server's* clock, messages dropped (what retention removed), producer blocked
time (cumulative time spent inside `publish`), and consumer lag per durable
consumer. `ConsumerMetrics` nests that set and adds delivered/uncheckpointed
counts, hard-resync and missed-event totals, non-monotonic deliveries, unreadable
entries, and receive wait time. Nothing here touches Prometheus:
`packages/observability` does not exist and the export arrives with `WP-140`.

**Nothing is dropped silently (§8.3).** Publication either lands or throws a
typed, coded error — invalid envelope, non-advancing `ingestSeq`, unencodable
payload, closed transport, unreachable transport. The stream never refuses an
event for being full; retention removes the oldest and the loss becomes a
consumer's hard resync. An entry that cannot be read back stops delivery after
the valid events before it, and the error names the offending position so a
caller that has opened a data-quality incident can step over exactly that entry
and nothing else. Two interleaved reads on one subscription are refused rather
than allowed to advance the position past events neither returned.

**A transport outage is a trading outage, by design.** Publication raises
`EventBusUnavailableError` instead of buffering indefinitely, so the caller's
halt path runs (ADR-003 §4). No fallback data path exists in this package.

**No latency claim is made.** Handoff §9.1's under-5 ms p99 is an unmeasured
target; ADR-003 §5 records that no benchmark has been run, and nothing in this
package measures, asserts, or implies it.

## assumptions

1. **`ingestSeq` is strictly increasing within a gateway epoch.** §7.1 calls it
   "monotonic within epoch" and states that `gatewayEpoch + ingestSeq` "defines
   the exact order"; a non-strict sequence could not define an exact order, so
   the publisher enforces strict increase. If a producer legitimately needs to
   repeat an `ingestSeq`, that is an ADR-002 question, not a transport setting.
2. **Retention is bounded by event count.** §9.1 requires "bounded retention"
   without naming a unit, and a count is the unit the hard-resync rule is
   expressed in (events missed). Trimming is exact rather than approximate so
   the bound is a guarantee — ADR-003's Consequences call retention "a safety
   parameter, not a tuning knob", and an approximate safety parameter cannot be
   sized against the worst tolerated restart.
3. **The transport validates the envelope but not the payload.** ADR-003 §2 says
   it carries normalized envelopes; the payload's contract belongs to the
   producer and consumer. Envelope validation uses the frozen
   `UnknownPayloadEventEnvelopeSchema`, so provenance and strictness are enforced
   exactly as `packages/domain` defines them and nowhere re-implemented.
4. **A checkpoint is cumulative.** There is no per-event or out-of-order
   acknowledgement, because `(gatewayEpoch, ingestSeq)` is a total order within
   an epoch and a consumer that skipped one event would have no way to say so.
5. **One transport process publishes each epoch sequentially.** §8.1's core loop
   is sequential, so the publisher's ordering guard is a check-then-act against
   its own cursor rather than a distributed lock. See `known_risks` 2.
6. **`ioredis@^6` is the current `ioredis`.** Handoff §2.1 names `ioredis`
   without a version; 6.0.0 is the registry's `latest`. Its dependency set is the
   v5 family minus the `lodash.*` helpers, and every API this package uses is
   exercised by the integration suite against a real server.
7. **`redis:7.4.2-alpine` is the version to test against**, because that is what
   `docker-compose.yml` runs — the `WP-040` precedent for pinning the test image
   to the developer's local server.

## deviations

1. **`newest` is offered as a start position.** ADR-003 §3.4 rules out resuming
   from "now" *on a restart*, and this package makes that unrepresentable: a
   stored checkpoint is always resumed when it exists, and `whenMissing` has no
   default, so a caller cannot fall back to "now" by omission. `newest` remains
   reachable for a consumer's genuine first start and for a deliberate
   post-snapshot skip, both of which require naming it.
2. **`messagesDropped` counts what retention removed**, rather than being pinned
   to zero as in `WP-050`'s queue. The WAL queue refuses instead of trimming, so
   zero is a true statement about it; a bounded retention stream removes events
   by design, and reporting zero would hide the number an operator most needs.
   It is not a *silent* drop — the consumer that had not read those events gets
   a hard resync — and the integration suite asserts both facts together.
3. **`producerBlockedTimeMs` is process-local and fractional.** It measures time
   spent inside `publish` in the reporting process; a pure consumer reports `0`
   because it published nothing. Documented on the field rather than left to be
   inferred.
4. **A read-exclusivity guard was added.** Not requested by the packet, but two
   interleaved `receive` calls on one subscription would advance the shared read
   position past events neither returned — a silent drop, which §8.3 forbids.
   The guard refuses the second call; callers needing concurrency use two
   subscriptions, which have separate positions by construction.
5. **`test:integration` is wired at the package level only.** Root
   `package.json` is orchestrator-owned at merge; see `follow_up` 1.

## known_risks

1. **`ioredis@6` is a recent major.** Its behaviour under this package is
   verified by 57 integration tests against a real server, but the repository has
   no prior production experience with it. If a defect surfaces, pinning to
   `^5.11` is a contained change: no API this package uses differs between the
   two in the paths exercised here.
2. **The publisher's ordering guard is not a distributed lock.** It reads its
   cursor, then publishes, then advances. Two concurrent `publish` calls for one
   epoch can both pass the check; the *stream* order still matches the atomic
   append order, but `ingestSeq` order within the stream would then reflect the
   producer's concurrency rather than its intent. §8.1's core loop is sequential,
   so this is a guard against a producer bug, not a concurrency primitive.
   `WP-120` must publish sequentially per epoch.
3. **A duplicate delivery is reported, not refused.** An ambiguous publish
   failure followed by a successful retry can put two entries with the same
   `ingestSeq` in the stream. The subscription counts that as
   `nonMonotonicDeliveries` and still delivers both, because stopping a trader on
   a legitimate at-least-once duplicate would be worse than reporting it.
   Consumers must be idempotent on `eventId`.
4. **Delivery is at-least-once across a restart.** A consumer that crashes
   between delivery and checkpoint re-reads from its last checkpoint. This is
   the correct trade for never losing an event, and it is why 3 matters.
5. **An idle `receive` costs a second round trip.** After a read returns nothing,
   the subscription inspects the stream state to distinguish "nothing to read"
   from "what you had not read is gone" — the two must not look alike. A tight
   zero-wait polling loop therefore does two round trips per empty poll; a caller
   in that shape should use `waitMs`.
6. **The publication counter is a second key per stream.** If an operator deletes
   the stream but not the counter (or the reverse), consumers see
   `transport-sequence-inconsistent` and must resynchronize. That is the intended
   outcome — a consumer that cannot know what it missed must not continue — but
   it means the two keys are one unit for backup and migration purposes.
7. **Publication ordinals are `number`.** They are validated as safe integers and
   the transport refuses to continue above `Number.MAX_SAFE_INTEGER` rather than
   losing precision silently. At 100 000 events/second that bound is roughly
   2 850 years away, but the refusal is real code, not a comment.
8. **`oldestMessageAgeMs` derives from the entry id's timestamp.** That is the
   server's clock at append time, compared against the same server's clock at
   read time, so client skew cannot distort it — but a server clock step
   backwards would; the value is clamped at zero rather than reported negative.
9. **The vocabulary test strips comments with regular expressions.** The scanned
   files hold no string literal containing `//` or `/*`, so this is accurate
   today. A self-check asserts the stripper still finds real declarations, so the
   test cannot silently become vacuous, but a future author adding such a literal
   to `transport.ts` should extend the check rather than work around it.
10. **Two gateways publishing into one stream are not prevented here.** ADR-002's
    Consequences note that they must use distinct `gatewayEpoch` values; this
    package keeps their sequences separate and never merges them, but it cannot
    detect two gateways sharing an epoch. That remains a gateway concern.

## follow_up

1. **Root `test:integration` wiring (orchestrator, at merge).** Root
   `package.json` currently runs only the postgres suite. `WP-060`'s suite is
   reachable as `pnpm --filter @polymarket-bot/event-bus test:integration`; the
   root script should run both once the orchestrator edits the root manifest.
2. **`WP-120` (data gateway / trader).** Publish sequentially per epoch (risk 2),
   be idempotent on `eventId` (risk 3), and route a `resync-required` result to
   the halt path plus a `DataQualityIncidentOpened` and an authoritative snapshot
   before acknowledging. `EventBusUnavailableError` is the trading-halt signal.
3. **`WP-140` (observability).** `StreamQueueMetrics` and `ConsumerMetrics` are
   the typed source for the §8.3 and §14.3 metric families; no Prometheus naming
   is assumed here, so the exporter is free to choose it.
4. **Retention sizing is a deployment decision with a safety consequence.**
   ADR-003's Consequences: retention shorter than the worst tolerated trader
   restart turns an ordinary restart into a hard resync plus a snapshot cycle.
   The operational runbook should state the chosen bound and its justification.
5. **The 5 ms p99 target is still unmeasured.** `WP-120`/`WP-140` own the
   benchmark. If measurement shows it unreachable, ADR-003 §5 requires an ADR
   amendment with evidence, not a quiet relaxation.
6. **Schema-version upgrade ordering.** ADR-002's Consequences leave the
   producer/consumer upgrade runbook owed. This transport rejects an envelope its
   `packages/domain` build does not accept, so a dual-publish or ordering plan is
   a real deployment concern for `WP-120`.
7. **Multi-stream retention.** One `RetentionPolicy` applies to every stream a
   transport publishes. If market and reference feeds ever need different bounds,
   that is a second transport instance today; a per-stream policy would be a
   small, cited extension.
