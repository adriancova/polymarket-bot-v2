## summary

1. **The commands:**

   | Command | What it does |
   |---|---|
   | `cancel-order <id>` | Cancels one order |
   | `cancel-market <condition-id> [--asset]` | Cancels a market's orders |
   | `cancel-all` | Uses venue truth and the emergency credential only, then a by-id sweep for anything still listed |
   | `account-snapshot` | Reads Data API `/v2` only |
   | `reconcile` | Runs WP-290's coordinator, read-only |
   | `stop-heartbeat` | Revokes the fencing lease through `FencingLeaseStore.revoke`, and prints the documented 10–15 s cancellation timing |

   Every command prints PLAN, CONFIRMATION, RESULT, UNKNOWN, AUDIT and OUTCOME, and exits with one of 18 distinct codes.
2. **The acceptance criteria:**
   - **`cancel-all` needs no trader state.** It never touches the trader process, its memory, its database or the lease store.
   - **The audit.** An append-only local JSON Lines log gets three records: INVOKED, then ACTING before any cancel or revoke, then OUTCOME.
     - Each record is one `O_APPEND`/`O_NOFOLLOW` write, fsynced, with its directory synced too, mode 0600.
     - A record that cannot be written stops the command before it acts.
     - Records are redacted with WP-260's redactor, and mirrored, best effort, to `ops.config_change_audit`.
   - **Scoped confirmation.** The operator types the scope, or passes `--confirm` naming it: `cancel-all:<account>`, `stop-heartbeat:<account>:<lease-id>` and so on. A bare `--yes` is refused, and `--dry-run` never acts.
3. **The obligations:**
   - **WP-310:** cancels at `EMERGENCY_CANCEL` and reads at `RECONCILIATION_READ`; `canceledCount` is always passed; batches are at most the burst minus headroom (never over 1,000); D-21 debt is printed and waited out.
   - **WP-290:** `reconcile` never resumes, never releases a quarantine and books nothing.
   - **V3-E15:** `/v2` only.
   - **§15:** a separate credential port.
   - **Time bounds:** every venue call is bounded.
4. **The shell-runnable bundle** (the orchestrator's grant, 2026-10-05). `apps/ops-cli/dist/main.mjs` is an ADR-018 esbuild ESM bundle.
   - It reuses the pinned esbuild with the trader's `createRequire` banner, which `pg` needs.
   - `app-bundles-load.test.ts` runs it in PAPER and pins each command's refusal, and its INVOKED and OUTCOME records.
   - Running it exposed two defects, both fixed and pinned: an EPIPE crash on a closed stdout, and a symlinked entry that silently did nothing.

## known_risks
- **CX330-R5-01 (LOW).** The audit log's newline check and its append are separate operations, so two concurrent invocations can interleave. A completed command's `ACTING` or `OUTCOME` record can then join another invocation's fragment, on a line that does not parse. Round 5 opened split: astra returned CHANGES REQUIRED with this item at MEDIUM, and Opus returned ACCEPT. The reconciliation agreed LOW and a joint ACCEPT. It also agreed that `docs/runbooks/emergency.md` over-claimed ("records nothing done"); `RECORDS-W3` corrected the runbook.
  Corrected 2026-10-06 (`RECORDS-W3`, `CLOSEOUT-3` L2): was '**CX330-R5-01 (LOW).** The audit log's newline check and its append are separate operations, so two concurrent invocations can interleave.'
- **WP330-V5-01 (LOW).** `O_NONBLOCK` and `O_NOFOLLOW` on the read descriptor are unpinned.
