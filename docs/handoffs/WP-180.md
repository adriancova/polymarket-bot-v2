## summary

`packages/capital-allocator` and `packages/risk` replace their `WP-010`
placeholders with handoff §9.7 and §9.8. Both are pure layer-1 libraries: no
I/O, no clock, no network, no credential, no signer, no order-placement surface,
and exact decimal arithmetic for every monetary and size value.

1. **The allocator tracks commitments from BOTH positions and open orders
   (§9.7).** Every exposure entry publishes `openOrderCommitted` and
   `positionCommitted` as separate exact decimals plus their sum, and every cap
   compares against the sum. A position contributes its `costBasis`; an open BUY
   order contributes `price × shares` because it can fill at any moment; an
   applied live BUY reservation contributes its cost (§9.10). Open SELL orders
   reserve *outcome tokens*, tracked by instance-scoped inventory accounting
   rather than the pUSD table.
2. **Caps are user-defined (§9.7), and the safety floors are not.**
   `globalAccountCap` and `perStrategyCap` are required with no default — this
   package invents no example number. The per-scope caps (market, series,
   underlying, resolution window) are optional; a configured scope cap on an
   unattributable request **fails closed** (`CAPITAL_SCOPE_KEY_MISSING`). The two
   live-micro caps default to exactly `"0"`, mirroring `AGENTS.md`, so any
   positive-notional commitment in `EXECUTION_PROBE`, `LIVE_MICRO`, or `LIVE` is
   refused as shipped.

   > **Corrected 2026-09-02 (remediation round 1).** The last sentence was true
   > "as shipped" and *insufficient*: review round 1 (HIGH) established that
   > defaulting to `"0"` while accepting any caller-supplied value made this
   > package a **weakening vector** for defaults `AGENTS.md` declares
   > non-weakenable. The caps are now **fenced**, not defaulted: any live-micro
   > value other than the exact canonical `"0"` is refused
   > (`CAPITAL_LIVE_MICRO_CAP_NOT_PERMITTED`) at the schema, at
   > `parseAllocatorCaps`, and at the reservation gate. See remediation round 1,
   > HIGH.
3. **V1 does not net opposing strategy intents (§9.7, ADR-011).** A LIVE
   commitment requires the requesting instance to be the recorded live owner;
   a conflicting owner — or **no owner at all** — is a typed refusal.
   `SHADOW` commitments keep an independent per-instance book that never touches
   live collateral, inventory, or caps, in either direction.
4. **The risk engine implements the §9.8 twenty checks in §9.8's order**, and
   does not short-circuit: a rejection that named one reason would hide the
   others an operator has to fix. Refusals accumulate in check order; a check
   whose input is *absent* does not silently pass — the absence is itself a
   refusal.
5. **Worst-case contractual loss is the PRIMARY hard limit.** Three structural
   expressions, not a comment: `limits.maxWorstCaseContractualLoss` is the only
   **required** limit in the policy while every secondary cap is optional; the
   check runs and the assessment is returned on *both* arms of the result; and
   `PRIMARY_RISK_REASON_CODES` names its codes so a consumer can separate
   primary from secondary refusals without string matching.
6. **The measure is grounded in WP-110's payoff models.** Both tokens, per
   outcome: `YES_WIN` pays a YES share `1` and a NO share `0`, `NO_WIN` the
   reverse, `SPLIT_50_50` pays `0.5` for a share of either token
   (`packages/settlement/src/payout.ts`, venue-verified 2026-08-28). The
   constants are **mirrored, not imported** (no §2.1 edge exists) and pinned by a
   cross-package test that imports both packages and fails if they diverge.
7. **`CANCELLED` is bounded, never valued** — see `assumptions` 1.
8. **Structured reason codes are a package-owned, documented vocabulary.**
   `RISK_REASON_CODES` (56 codes) and the allocator's `CapitalRefusalCode` (18
   codes) are enumerated at runtime and documented with meanings in each
   package's `README.md`. A test asserts the vocabulary has **no dead entries**
   (every declared code is reachable), emits **no undeclared code**, and that
   every code fits the frozen `CodeString` grammar so it is safe as a §14.3
   metric label.

   > **Corrected 2026-09-02 (remediation round 1).** Two false claims in the
   > paragraph above, both found by review round 1 (MEDIUM). (a) The count
   > **was never 56** — the exported list held **61** at the reviewed commit;
   > with `RISK_EXPOSURE_ENTRY_MISSING` added by the BLOCKER-2 fix the vocabulary
   > is now **62**, pinned as `RISK_REASON_CODE_COUNT` and asserted against both
   > the list and the README's own table. (b) The allocator's codes were **not**
   > enumerated at runtime — `CapitalRefusalCode` was a type union with no
   > runtime list. `CAPITAL_REFUSAL_CODES` (**19** codes after the HIGH fix),
   > `CAPITAL_REFUSAL_CODE_COUNT`, `isCapitalRefusalCode`, and a compile-time
   > exhaustiveness proof now make the claim true.
9. **Incident actions are RECOMMENDATIONS, never actions.** §9.9 says "the
   Incident Controller—not the ordinary risk gate—originates operational safety
   actions", and that controller is a later package. This package emits the §9.9
   ladder verbatim as `kind: "RECOMMENDATION"` data, mapped row for row from the
   §9.9 default-action table with each row quoted, carrying no callable.
10. **A resize creates a new approved-intent record (§7.7).** Records are deeply
    frozen (an in-place edit throws); `resizeApprovedIntent` returns a new record
    with a new id, `lineage: "RESIZED"`, `supersedesApprovedIntentId`, and
    `rootApprovedIntentId`. Reusing an id in the lineage is refused, and a resize
    may only strictly reduce magnitude without flipping side.

## assumptions

1. **`CANCELLED` is bounded, never valued (WP-110 register row U-10).** The
   venue documents winning, losing, and 50/50 redemption and **no** cancellation,
   void, or refund path; `payoutPerShare("CANCELLED")` refuses with
   `SETTLEMENT_CANCELLED_PAYOUT_UNVERIFIED`. This package invents no payout
   either. The assumption it *does* make is one-directional and stated in code:
   **an outcome token is an asset, so no redemption path can charge its holder,
   every unverified redemption is `≥ 0`, and the loss across all terminal
   outcomes is therefore bounded by a zero-redemption floor.** That is what
   `maximumContractualLoss` computes, and it is deliberately conservative — a
   fully hedged YES/NO pair is *not* credited its verified hedge value in the
   primary measure, because crediting it would rely on the undocumented
   cancellation payout. `worstCaseResolutionLoss` is the separate,
   verified-outcomes-only measure that *does* credit the hedge. Every assessment
   carries `cancelledOutcomeTreatment: "ZERO_REDEMPTION_FLOOR_UNVERIFIED_U10"`.
2. **Disposition is derived from the intent TYPE alone.** `POSITION`, `QUOTE`,
   and `BASKET` are `ENTRY`; `REDUCE_POSITION` is `EXIT`; `CANCEL` is `CANCEL`.
   A `POSITION` intent whose delta happens to reduce a holding is therefore
   treated as an entry and gets the **stricter** treatment. This fails closed —
   entry treatment can only refuse more, and refusing to place a new order is the
   safe direction (§6 invariant 12 makes cancel-and-reconcile, not action, the
   mandated response to unknown state). A strategy that means "exit" has
   `REDUCE_POSITION`.
3. **Capacity limits gate entries, not exits.** Exposure caps, per-order
   notional, participation, the economic floor, expected net edge, rate-limit
   headroom, and time-to-close are enforced on entries only. An exit *reduces*
   exposure, so enforcing a cap against it would block exactly the action that
   brings the account back inside the cap. The worst-case and scenario measures
   are still **computed and returned** for exits, so an operator sees them; they
   are simply not the reason a reduction is refused. An **explicit** allocator
   refusal still binds on any disposition.
4. **A `QUOTE` level names no outcome token.** §7.7's `QuoteLevel` is price plus
   size, so a quote's bought shares are UNASSIGNED and the worst-case builder
   places them on whichever token settles **worse** for the holder, per market,
   using the same exact per-outcome arithmetic. Never split, never averaged.
5. **A `REDUCE_POSITION` on a market the supplied portfolio does not describe is
   unknown position state**, not "flat": it is refused with
   `RISK_POSITION_STATE_UNKNOWN` and cancel-and-reconcile recommendations (§6
   invariant 12). A caller that genuinely knows the account is flat has nothing
   to reduce.
6. **The engine never approves a real-order-mode intent.** Beyond check 2 (run
   mode within the process maximum, default `PAPER`), check 3 refuses any mode in
   `RUN_MODE_PLACES_REAL_ORDERS` outright, because this package owns no signer,
   no fencing token, and no venue connection and therefore cannot establish that
   §6 invariants 16 and 17 hold. This is a floor, not a policy knob.
7. **`Date.parse` on a caller-supplied string is not a clock read.** Deadline
   comparison goes through the parsed epoch value because ISO-8601 strings are
   not lexicographically comparable across UTC offsets. This follows WP-110's
   `packages/settlement/src/time.ts` precedent verbatim; `Date.now()` and
   `new Date()` appear nowhere, and a test asserts it over the whole package.
8. **The approved-intent record shape is package-owned.** `packages/domain`
   defines no `ApprovedIntent` and is frozen and forbidden to this work package,
   so the record lives in `packages/risk`. Its identity/lineage fields reuse the
   frozen domain shapes (`IntentId`, `IsoTimestamp`, `RunMode`, `Intent`). If a
   later package needs this shape in the shared contract, that is an ADR.
9. **A resize copies the strategy's ceilings unchanged.** `maximumTotalCost`,
   `maximumBuyPrice`, `minimumSellPrice`, and `validUntil` are not rescaled — a
   ceiling stays valid under a smaller size, and scaling one would invent a
   number the strategy did not supply.
10. **Refusals accumulate; they do not short-circuit.** §9.8's "cheapest first"
    is honoured as the *order* of evaluation and of the returned refusals, not as
    an early exit. A rejection that named one reason would hide the others.

## known_risks

1. **`QuoteIntent` carries no expected-edge field.** §9.8 check 12 requires a
   declared edge, and §7.7's `QuoteIntent` has none, so under the default
   `requirePositiveNetEdgeForEntries: true` **every quote intent is refused**
   with `RISK_EDGE_INPUTS_MISSING`. That is the fail-closed answer and it is
   correct as a default, but it means a quoting strategy cannot run until an
   operator sets the flag false for it or the domain gains an edge field (which
   is an ADR, since `packages/domain` is frozen). See `follow_up` 1.
2. **The structural allocator port is not a compiled contract.** `packages/risk`
   mirrors the allocator's exposure-snapshot and verdict shapes because no §2.1
   edge exists. `test/unit/risk/ports.test.ts` pins it three ways — `tsc`-checked
   field names via `satisfies readonly (keyof …)[]`, a runtime parse of real
   allocator output, and an end-to-end pass — but a *semantic* change on the
   allocator side that keeps the field names (say, `positionCommitted` starting
   to mean mark-to-market rather than cost basis) would not be caught.
3. **Scenario shocks are supplied, not modelled.** This package marks a supplied
   scenario and enforces the loss; it invents no volatility, time, or liquidity
   shock. A caller that supplies mild scenarios gets a mild check. The
   fail-closed half is real (a missing required kind or a partially-marked
   portfolio blocks), but the *severity* of the shocks is the caller's
   responsibility and is not verifiable here.
4. **Participation is a per-intent share cap only.** §9.8 check 13 says
   "Requested quantity respects participation limits"; depth-fraction
   participation needs the book, which this package does not have. The v1 floor
   is a hard `maxOrderShares`; real depth-aware slicing belongs to WP-190's
   execution planner (§9.10).
5. **Self-trade detection sees only the portfolio view it is given.** It
   compares the intent's legs against the resting orders in
   `portfolio.openOrders`. Orders the caller omits are invisible, and a
   `QUOTE`'s token-less legs are compared per market across both tokens
   (conservative, but it can flag a pair that could not actually cross).
6. **`RISK_ALLOCATION_REFUSED` carries the allocator's codes as opaque strings.**
   The risk package cannot import the allocator's `CapitalRefusalCode` union, so
   a typo or a renamed allocator code would ride through as data rather than
   failing a type check. The `ports.test.ts` end-to-end case asserts one real
   code survives the hop.
7. **Exposure attribution for pre-existing positions is the caller's.** A
   position supplied without a scope attribution does not appear in the series /
   underlying / resolution-window tables. The request side still fails closed
   (`RISK_SCOPE_KEY_MISSING` / `CAPITAL_SCOPE_KEY_MISSING`), so no new commitment
   is admitted under an unmeasurable cap, but a historical position can sit
   outside a scope total.

**The one gate a cancel cannot bypass, and why.** `RISK_INPUT_INVALID` is
returned before the intent is normalized. Until the input parses there is no
disposition to privilege, and an unparseable request names no orders to cancel:
this is a limit of knowledge, not a risk gate. Pinned by the test *"the only
thing a CANCEL cannot bypass is input validation itself"*. Flagged explicitly
for review round 2 as the one residual.

### Fix

The rule is now **structural**, not per-gate. One choke point at the end of
`evaluateIntent`: if the disposition is `CANCEL`, every refusal the pipeline
accumulated — from any gate, **including gates added later** — becomes a
non-blocking observation on the new approved-arm field
`cancelPriorityOverrides`, and the cancel is approved carrying its typed
`ApprovedIntentRecord`, its recommendations, and its worst-case measure.

Per-gate conditions were deliberately **not** used: they are exactly what a
later edit forgets, and two of the four findings were gates whose authors
simply did not think about cancels. The choke point carries a loud
do-not-narrow comment naming the test that fails if it is narrowed.

`cancelPriorityOverrides` is **not** a refusal list — the result is approved.
It exists so the observability is not lost: an operator and the §9.9 controller
still see that, say, the allocator refused, even though the cancel proceeded.

### Judgment calls

1. **`RISK_UUID_NOT_CANONICAL` is overridden, not enforced, on a cancel.**
   ADR-016 §2 rules that a UUID-shaped non-canonical identifier is *refused,
   never case-folded*. It is still never case-folded — the id rides through
   exactly as supplied, and the ADR-016 observation is reported. What changed is
   that it no longer **blocks the cancel**, because ADR-016 governs
   normalization, not whether a safety cancellation may be trapped. §6 invariant
   13 is the stronger rule here. Flagged for the reviewer.
2. **The cancel record honestly names the requested run mode.** A cancel
   evaluated with `runMode: "LIVE"` under `maxRunMode: "PAPER"` is approved and
   its record says `runMode: "LIVE"`, with the mismatch on the overrides. This
   package places no orders, so approving a cancel creates no real-order
   surface; misreporting the mode would be worse than reporting it.
3. **The overrides live on the approved arm only.** A rejected result overrode
   nothing by definition, so the field would always be empty there.

## BLOCKER 2 — a missing exposure entry was read as zero (fail-open bypass)

**Finding.** `packages/risk/src/exposure-limits.ts:45` returned `"0"` for an
absent entry, and `packages/risk/src/inputs.ts:105` permits sparse scope maps.
With a per-market or per-scope cap configured, an omitted current exposure was
silently accepted as zero — the cap passed against exposure nobody had measured.

### Fix

- `committed()` **has no `undefined` arm any more**. It takes a present entry,

- Every query site — instance, market, series, underlying, resolution window —

  declares it will query. This is the "represent every queried scope with

  merely break the integration, since `exposureSnapshot` is sparse by
  construction. The zeros are exact and honest — only the *snapshot* is sparse;
  the allocator *state* is complete, so a key it does not mention genuinely
  holds nothing.
- `packages/risk/src/inputs.ts` now documents on the schema itself why sparse
  maps remain structurally legal and where completeness is enforced instead:
  the query set is not known until the intent is normalized, so the schema
  cannot express it.

## BLOCKER — a contract-invalid approved record could be emitted for a CANCEL

**Finding (review round 2).** `engine.ts:181-188` refused a UUID-shaped,
NON-CANONICAL `approvedIntentId` as a pipeline refusal; `engine.ts:951-975` — the
§6 invariant 13 cancel choke point — then converted that refusal into a
non-blocking `cancelPriorityOverrides` observation, approved the cancel, and
copied the id **verbatim** into the emitted `ApprovedIntentRecord`. The
reviewer's targeted product test confirmed `approved: true`, a typed
`RISK_UUID_NOT_CANONICAL` override, and the non-canonical id present in the
record.

**The ruling on the question round 1 referred up** (`known_risks` 1 of round 1,
now annotated with it): ADR-016 §2 requires a **typed refusal at an input
surface** and explicitly forbids accepting uppercase UUIDs for lookup or
persistence. `evaluateIntent(policy, input: unknown)` **is** such a surface.
"Safety cancellation outranks new order placement" does **not** authorize
emitting a contract-invalid approved record. So the two invariants do not
collide: §6 invariant 13 protects a **valid** cancel from being trapped by risk
policy; it does not require accepting a malformed identity. Round 1's judgment
call 1 is superseded.

### Fix — the check moves to the side of the line round 1 itself drew

Round 1 documented that a cancel cannot bypass input validation and called that
"the one residual… a limit of knowledge, not a risk gate". This round puts the
identity check on that side of the line, structurally:

1. **`inputs.ts` gains `validateEvaluationInput(input: unknown)` — one door.**
   It parses `RiskEvaluationInputSchema` **and** applies ADR-016 §2 identity
   validation, and it answers **before `buildIntentView`**, so no disposition
   exists, nothing has been normalized, and the choke point has nothing to
   override. `evaluateIntent`'s body is now `if (!validated.ok) return
   rejected(...)` — the same standing the schema refusal already had.
2. **NOTHING IS CASE-FOLDED.** ADR-016 §2 is refuse-not-normalize; producing a
   canonical id from a non-canonical one would be a worse defect than the one

## assumptions (remediation round 2)

1. **ADR-016 §2 governs REPOSITORY identifiers, not venue-supplied opaque
   ones.** The amendment's premise ("every UUID in these contracts is generated
   in-process") is what makes a mixed-case arrival evidence of a caller defect;
   it does not hold for a `VenueOrderId`, and the amendment says the ruling
   "does not touch any venue wire format". Stated explicitly because the
   allocator is stricter on its own `orderId` field, and because a reviewer may
   prefer the uniform reading.
2. **`evaluateIntent`'s two arguments have different standing.** `policy` is a
   `RiskPolicy` produced by `parseRiskPolicy`; `input` is `unknown` and is the
   external surface. Identity validation belongs to the second.
3. **An identity refusal is not a risk decision**, so short-circuiting at the
   door does not violate the package's no-short-circuit rule (§9.8 refusals
   still accumulate). All identity violations are reported together, so nothing
   is hidden *within* input validation either.
4. **`resizeApprovedIntent`'s `record` argument is input.** It is typed, not
   parsed; a hand-built record is reachable at runtime, so its inherited
   identity fields are validated rather than trusted.

## known_risks (remediation round 2)

1. **A caller can still persist a non-canonical id it never showed this
   package.** The engine refuses what it is given and copies nothing else, but
   a consumer that mints its own id after approval is outside this package's
   reach. The `ApprovedIntentRecord` shape is package-owned (`assumptions` 8),
   so nothing here can constrain that.
2. **The venue-id exclusion is a judgment on ADR-016's scope.** If a future
   ruling extends the UUID rule to venue-supplied identifiers, this package must
   change with it — and, unlike today, that change could refuse a cancel, which
   is why it should be an ADR decision rather than a package choice. Recorded as
   `follow_up` R2-3.
3. **`CodeString` admits only UUIDs that start with a letter**, so a
   `strategyInstanceId` of `"01890000-…"` is refused by the schema
   (`RISK_INPUT_INVALID`) rather than by the identity check. Both refuse; the
   code differs by the shape of the field. The tests use `f1890000-…` for that
   field so the identity path is genuinely exercised.

   > **Confirmed 2026-09-03 (review round 3, NOTE — not a finding).** The
   > reviewer verified this and explicitly did **not** classify it as a
   > valid-cancel trap or a regression, because no current authority establishes
   > UUIDs as valid `strategyInstanceId` values. It nonetheless needs contract
   > alignment before any composition root chooses UUID strategy-instance ids.
   > Recorded as `follow_up` R3-1 below, owned by the contract owner, with the
   > `db/migrations/0004_strategy.up.sql` evidence.
4. **The binding-property test walks emitted records with an allowlist of one
   path.** If a future record field legitimately carries a second venue-supplied
   identifier, the allowlist must grow, and a reviewer should treat any growth
   of it as a finding rather than a mechanical edit.
5. Round 1's `known_risks` 2-5 stand unchanged.

## THE LESSON THIS ROUND WAS SET, AND HOW IT IS DISCHARGED

Round 2 was asked to fix one field; its sweep found five plus a duplicate guard.
Round 3 found a **sixth** the sweep still missed. The instruction for this round
was therefore explicit: *enumerating fields does not establish the property* —
prove it **structurally**.

So the field list is **gone**. What replaces it:

1. **One boundary.** `sealApprovedIntentRecord`
   (`packages/risk/src/approved-intent.ts`) is the only place an
   `ApprovedIntentRecord` is frozen and returned. All three record-emitting
   paths go through it: `evaluateIntent`'s cancel arm, its ordinary arm, and
   `resizeApprovedIntent`. Freezing lives inside it, so "emit a record" and
   "validate the record being emitted" are one act.
2. **A walk, not a list.** The boundary walks the record it is about to emit —
   every string, at every depth, at any nesting — and refuses any value that is
   UUID-shaped but not canonical lowercase (ADR-016 §2), carrying the **raw**
   value. `resizeApprovedIntent` walks the record it INHERITS and the parsed
   request the same way, *before* constructing anything.
3. **Default is CHECKED; the exceptions are a closed, contract-anchored set.**
   `NON_IDENTITY_KEYS` = `orderId`/`orderIds` (§7.2 `VenueOrderId` — opaque
   venue strings, which ADR-016 §2 excludes explicitly), `reason` /
   `resizeReason` / `rationale` (`DetailString`: "bounded human-readable text …
   never parsed, only displayed or logged"), and `tags` (§7.7 free-form strategy
   tags). Every entry names the contract type that makes it a non-identifier,
   and two of them ride the `CANCEL` path where an over-refusal would trap a
   position — the exact error class the MEDIUM warns about.
4. **The inherited intent is PARSED**, because the resize computes on it. That
   closed a second defect the probe found: a hand-built `targetShares` threw
   `InvalidDecimalStringError` out of a function whose whole contract is to
   return a typed refusal.

**How a SEVENTH field is caught automatically — the answer this round owes.**
Three independent mechanisms, none of which is a list anyone maintains:

> **CORRECTED 2026-09-03 (adversarial review round 4).** The three bullets below
> are true of a field *name* and false of a field *shape*. The first two both
> rest on `Object.entries`, which reports only enumerable own properties — so a
> non-enumerable, prototype-placed or accessor-backed identity was neither walked
> by the product nor visible to the suite, and an accessor is not skipped by that
> primitive but INVOKED, so a throwing getter escaped `resizeApprovedIntent` as
> an exception. The enumeration primitive had become the list. The original text
> is preserved; what replaces the mechanism is the data-record boundary described
> in the round-4 section below.

- **In the product code**, the walk enumerates the record's own *values*, not
  field *names*. A field added to `ApprovedIntentRecord` (or to any object it
  contains, at any depth) is walked the moment it exists, because the walk
  recurses over `Object.entries`. There is no place to forget to add it. The
  only way to opt out is to name the field `orderId`, `orderIds`, `reason`,
  `resizeReason`, `rationale` or `tags` — a closed set whose growth is a visible
  source edit with an ADR citation attached.
- **In the suite**, the new test *"THE STRUCTURAL PROPERTY: every string
  position of a hand-built record, generated from its shape"* obtains its case
  list by **walking a real emitted record** and driving every string position
  hostile in turn. A seventh field becomes a new position, hence a new
  assertion, with **no test edit**. It also asserts the *complement*: positions
  under the excluded keys must be ACCEPTED and round-tripped byte-for-byte, so
  the exclusion set cannot quietly grow either.
- **In the boundary itself**, the seal re-walks the constructed draft. Mutation
  M-R3b (below) demonstrates this is load-bearing rather than decorative: with
  the round-2 field list restored in the resize, the seal alone still prevents
  every contract-invalid emission — only the refusal's *quality* degrades.

## MEDIUM — escalated, not applied: the allocator's `orderId` is repository-generated

**Finding and ruling (review round 3).**
`packages/capital-allocator/src/state.ts:177` applies the ADR-016
repository-identity check to `openOrders[].orderId`. The reviewer ruled: "risk's
exclusion is faithful to ADR-016 and avoids a cancellation trap. The allocator
behavior is the inconsistent side… Either remove `orderId` from the allocator's
repository-identity check or obtain a superseding ADR backed by evidence that
this `orderId` is not venue-supplied."

**The task packet required verifying provenance first**, and stopping if the
field proved repository-generated. It does. The check is therefore **left
exactly as it was** — `packages/capital-allocator` is byte-identical to
`49246d6`, source and test — and the question is referred up.

### The evidence, in the repository's own contracts

1. **`db/migrations/0005_execution.up.sql:213`** —
   `order_id internal.uuid_v7 primary key default internal.uuid_generate_v7()`.
   The repository *generates* this identifier, in-process, as a canonical
   UUIDv7.
2. **`db/migrations/0005_execution.up.sql:234` and `:345-348`** — the same table
   carries a **separate** `venue_order_id internal.identifier` column, with its
   own unique index. This repository does not call the venue's identifier
   `orderId`; it calls it `venueOrderId`, in the schema and in
   `packages/storage-postgres/src/repositories/orders.ts` (`InsertOrderInput`
   carries both).
3. **`packages/storage-postgres/src/repositories/orders.ts:195`** —
   `const orderId = uuidV7();`. Minted in-process, which is precisely ADR-016
   §2's stated premise ("every UUID in these contracts is generated
   in-process") — the premise the round-2 record argued is *false* for venue
   strings.
4. **`db/migrations/0006_accounting.up.sql:514` and `:531-532`** — the
   accounting layer this allocator mirrors keys reservations by
   `order_id internal.uuid_v7 references execution.orders (order_id)`, and the
   §9.14 "prevent double reservation" unique index is `(order_id, asset_id)` —
   the same rule `packages/capital-allocator/src/state.ts` implements and cites.
   If the allocator accepted an uppercase spelling of that key it would create
   the "second accepted spelling" ADR-016 §2 forbids, and the join to
   `execution.orders` would silently miss.
5. **§7.2 (handoff line 477)** types the venue identifier as
   `VenueOrderId = string; // order hash/string`. §7.2 contains no plain
   `OrderId` entry at all, so "`orderId` is §7.2 `VenueOrderId`" is an
   inference, not a citation.
6. The allocator's sibling field `positionId` is unambiguously
   repository-internal (§7.2 defines no venue position id) and is treated
   identically by the same check.

### What the reviewer's cross-package evidence actually compares

The reviewer's risk-engine probe round-trips a UUID-shaped uppercase id on a
`CANCEL`. That value sits in **`CancelIntent.orderIds`**, which the frozen
domain contract types `VenueOrderIdSchema` — genuinely venue-supplied, and
correctly excluded (refusing it would trap a position, §6 invariant 13). The
allocator's `openOrders[].orderId` is a **different field** with no contract
annotation. So the two behaviours the reviewer compared are not the same field,
and the asymmetry that does exist is between the allocator's
`openOrders[].orderId` (checked) and **risk's** `portfolio.openOrders[].orderId`
(not checked) — and risk's laxity there is independently defensible, because
risk's check runs at a door that binds cancels.

### What this means for the ruling

- Removing the check would weaken a fail-closed boundary on what the evidence
  says is a repository-generated UUIDv7, on the strength of a premise the
  repository's own schema contradicts. It is not in the "stricter is not
  automatically safe" class the reviewer described, because no legitimate opaque
  venue value is rejected: a venue string reaches this repository as
  `venueOrderId`.
- The remaining defensible reading is that a future composition root will
  populate the allocator's `openOrders[].orderId` from `venue_order_id` rather
  than `order_id`. **No such producer exists yet** — both packages are pure and
  the composition root is unwritten — so the meaning is genuinely undetermined
  by any producer, and determined only by the naming the persistence contract
  fixes.
- The clean resolution is a **one-line contract annotation** on the allocator's
  and risk's port shapes stating which of the two identifiers they carry. That
  is a `docs/contracts` / ADR change, outside this package's allowed paths.
  Recorded as `follow_up` R3-2.

**Nothing was changed for this finding.** No allocator test assertion was
"corrected", because correcting it would have encoded a conclusion the evidence
does not support.

## assumptions (remediation round 3)

1. **ADR-016 §2 governs the CONTENT of an emitted record, not only the arguments
   of an input function.** That is the round-2 ruling ("a contract-invalid
   approved record may not be emitted") applied where it is cheapest to enforce:
   at the point of emission.
2. **A repository identifier is any string in a record that the frozen contract
   does not type as a venue identifier, free prose, or a strategy tag.** That is
   the inversion this round rests on. It is deliberately over-inclusive — it
   checks decimals and enums too — because a UUID-shaped decimal is a defect in
   any case, and because being over-inclusive fails in the safe direction for
   everything except the excluded classes, which are excluded precisely because

## THE LESSON THIS ROUND WAS SET, AND HOW IT IS DISCHARGED

Round 2 fixed one field and its sweep found five. Round 3 replaced the list with
a WALK. Round 4 found the walk's **enumeration primitive** was the new list —
and, worse, that the property TEST walked with the same primitive, so it could
not have failed where the product failed. **A property proved with the
implementation's own primitive is not proved.**

So the answer this round owes is not a better walk. It is that **a JavaScript
object is not a data record**. An object can hide state behind enumerability,
inherit it from a prototype, compute it on read, answer differently on a second
read, or throw when asked. Round 3's boundary checked a caller's object and then
emitted *that same object* — two different acts, with a gap between them wide
enough for all three reviewer probes.

What replaces it: **a data-record boundary**, `packages/risk/src/plain-data.ts`.
It READS a value into plain own data — a fresh tree of plain objects, arrays and
primitives — before anything looks at it, and everything downstream (identity
validation, arithmetic, emission) uses only that snapshot.

**The route was chosen deliberately, and here is the argument.** The reviewer
offered two: reconstruct through a complete runtime schema (stronger), or
typed-refuse the exotic shapes (cheaper). This round takes the **materialize**
route — the same class of answer the sibling package WP-170 landed on, but
argued independently here and adapted in one important way:

1. **Materializing is what makes the guarantee structural.** Refusing exotic
   shapes alone leaves the emitted record aliasing the caller's objects, so
   "deeply immutable" would still mean "we called `Object.freeze` on the objects
   we could see". Reading the record into a fresh tree makes it plain own data
   BY CONSTRUCTION, which closes the deep-immutability half of the BLOCKER at
   the same time — the round-4 probe's post-return prototype edit has nothing
   left to reach.
2. **It removes the check-then-emit gap entirely.** A getter that answers
   cleanly when validated and hostile when emitted is not a possible bug once
   the validated bytes *are* the emitted bytes. (The probe recorded the old code
   reading one property **twice**; the new code reads everything **once**, from
   descriptors.)
3. **But the deep read is SHAPE-AGNOSTIC, not schema-driven.** A "complete
   runtime schema" for the whole record would have to restate the domain's
   `Intent` union inside `packages/risk` — a second copy of a frozen contract
   this package may not edit, and a strict copy would REFUSE the day
   `packages/domain` adds a field. That boundary also runs on the `CANCEL`
   emission path, where a false refusal traps a position (§6 invariant 13). A
   shape-agnostic read has neither problem: a field added to any contract is
   materialized and checked the moment it exists.
4. **The record's OWN shape does get a complete schema.**
   `ApprovedIntentRecordSchema` covers every field of `ApprovedIntentRecord`,
   with `intent: IntentSchema` — the domain contract itself, not a copy. That is
   what closes the reviewer's other sentence: `resizeApprovedIntent` "accepts
   the record directly without parsing its complete runtime shape". It does not
   any more.

**What the boundary refuses, and why each is not record data** (the source
comments carry the same list):

| Refused | Because |
| --- | --- |
| a non-plain prototype | an inherited property is state the container does not own, and `Object.freeze` cannot reach it — probe P2 changed a "frozen" record after it was returned |
| an accessor property | a getter is code, not data: it can throw (probe P3), can answer differently on a second read, and cannot be frozen. Values come from **descriptors**, so no caller code runs inside the boundary at all |
| functions, symbols, symbol-keyed properties | none can be a field of a persisted record, and dropping one silently is the failure mode this whole chain is about |
| cycles, sparse arrays, nesting past 64 | a record is a finite tree |
| any reflective operation that throws | a hostile `Proxy` may not turn a typed-result contract into an exception |

**What it does NOT refuse: a non-enumerable own DATA property is READ.** Hiding
a field from enumeration does not remove it from the value, so materializing it
is what lets the identity rules see it — probe P1's uppercase market id comes
back as `RISK_UUID_NOT_CANONICAL` naming `record.worstCase.perMarket[0].marketId`
and carrying the raw value, which is a better answer than a shape refusal.

**And there is now exactly ONE traversal primitive in the emission path.** The
read returns an inventory of every string it materialized, with paths; the
ADR-016 §2 check consumes that inventory instead of walking again. There is no
second walk left to be blind in a different way.

## assumptions (remediation round 4)

1. **A record is a finite tree of plain own data.** Everything in this round
   follows from that: what cannot be read as such is refused, and what is
   emitted is what was read. It is a stronger claim than "the record's fields
   have the right types", and it is the one the reviewer's three probes falsify
   in a checkable way.

   close the TOCTOU gap, but it runs caller code inside a boundary whose whole

   removing; reading it produces the precise ADR-016 refusal instead of a vague

   shape is not.** The record type is this package's; `Intent` is the frozen

## BLOCKER 1 — `__proto__` was not materialized as an own data property

**Finding (review round 5).** `plain-data.ts:238`/`:243`. `out[key] = …` is
`Set`, which walks the prototype chain; for `key === "__proto__"` it found
`Object.prototype`'s accessor and invoked its **setter**, so the value became
the emitted object's PROTOTYPE and no own property was created.
`sealApprovedIntentRecord` returned `ok=true` with `plainPrototype=false` and
`prototypeFrozen=false`, and adding an uppercase-UUID `marketId` to that
prototype after the call changed `record.marketId` — bypassing identity
validation and deep immutability at once.

### Fix

1. **`defineDataProperty`** — every property of the materialized tree is created
   with `Object.defineProperty` (`CreateDataProperty` semantics), which defines
   on the object itself and consults no setter, inherited or otherwise.
2. **`__proto__` is refused as a property NAME.** Materializing it honestly is
   necessary but not sufficient, and the reason was *measured*, not assumed:
   **`zod`'s `strictObject` is blind to exactly this one key.** With the
   property created by `defineProperty` so it is genuinely own and enumerable:

   ```text
   KEY __proto__:        success=true   parsed output keys = ["a"]   (silently dropped)
   KEY constructor:      success=false  Unrecognized key: "constructor"
   KEY prototype:        success=false  Unrecognized key: "prototype"
   KEY toString:         success=false  Unrecognized key: "toString"
   KEY hasOwnProperty:   success=false  Unrecognized key: "hasOwnProperty"
   KEY valueOf:          success=false  Unrecognized key: "valueOf"
   KEY __defineGetter__: success=false  Unrecognized key: "__defineGetter__"
   KEY then / length / name: success=false  Unrecognized key
   ```

   A field under that one name is the one field a strict schema in this
   repository cannot report — and this package's contract since round 4 is that
   an unexpected field is **refused, never dropped**. So the name is refused at

## assumptions (remediation round 5)

1. **The intrinsics are genuine.** Proposition 1 assumes `Object`, `Reflect`,
   `Array.prototype` and `util.types` are the real ones. A process that has
   replaced them has already lost; that is a different threat model from the one
   this boundary answers, and it is written into the source rather than left
   implicit.
2. **`util.types.isProxy` is trap-free.** Verified directly rather than assumed
   (a `Proxy`-wrapped handler records zero reads; it also answers for revoked
   and cross-realm proxies). If a future Node changed that, M-R5f shows the
   remaining mechanics still contain the failure as a typed refusal.
3. **A `node:util` type predicate is permissible in layer 1.** Argued from the
   dependency contract and the gate, both quoted above, and pinned by a test.
   The argument is package-scoped by construction and establishes nothing about
   any other package's import budget.
4. **`__proto__` is never a legitimate record field.** No shape in this
   repository declares one; `JSON.parse` is the only ordinary producer, and a
   payload carrying one is not a record this package should emit.
5. **Refusing is better than containing.** Where both are available the input is
   REFUSED before caller code runs; the containment guard is the floor under
   that, not a substitute for it. The tests assert `invoked === 0`, not merely
   "did not throw", so a regression from refusal to containment is a failure.
6. Rounds 1–4's assumptions stand, except round 4's assumption 2's phrase "no
   `Proxy` trap … executes during validation at all", which was the false claim
   this round fixes and which is superseded here.

## BLOCKER 1 — an inherited property authorized a live reservation

**Finding (review round 6).** `reserve.ts:239` read
`state.liveOwners[req.marketId]` — `Get`, which walks the prototype chain — so
an INHERITED owner satisfied the ADR-011 live-ownership gate and a LIVE BUY was
`permitted=true, refusals=[]` where `CAPITAL_LIVE_OWNERSHIP_MISSING` was owed.
`reserve.ts:293/:294` and `exposure.ts:155` are the same class; the reviewer's
inventory probe put a TWO-ANSWER GETTER on the composite inventory key and a
SELL with **zero holdings** saw `held=1000, reserved=0`.

**The second probe is why this round does not stop at the four sites.** The
state in it was created by `createAllocatorState` — this library's own
constructor, from valid input — and a single non-enumerable `Object.prototype`
property spelled as the market's UUID flipped its verdict. There was no hostile
input. So the class is not "a caller handed us a hostile value"; it is
**`Object.prototype` is reachable state, and this package kept asking it
questions**.

### Fix — the four sites, and then the class

1. **The four reported sites are own reads**: `ownEntry(state.liveOwners, …)`,
   `ownEntry(heldSharesByKey(state), key)`,
   `ownEntry(reservedSharesByKey(state), key)`,
   `ownEntry(finalize(tables.global), GLOBAL_KEY)`.
2. **Every other computed access in both packages** was found by the census and
   converted or registered: `reserve.ts` `entryOf` (now an own read for the
   DIMENSION as well as the key), the `RUN_MODE_PLACES_REAL_ORDERS` lookups in
   `reserve.ts` and `engine.ts` (new `ownFlag`), `exposure-limits.ts`'s scope
   read and dimension read, `caps.ts`'s `caps[field]`, `exposure.ts`'s
   `entry[component]` and `worst-case.ts`'s `perOutcome[outcome]` (both written
   out by name rather than registered).
3. **The materialized tree has NO PROTOTYPE** (`Object.create(null)`), and every
   door re-hardens the SCHEMA'S OUTPUT the same way. This is the half that
   closes DOTTED reads, which no syntactic rule can police. Measured on the
   pinned `zod`:

   ```text
   schema = z.strictObject({ a: z.string(), b: z.string().optional() })
   Object.defineProperty(Object.prototype, "b", { value: "inherited", enumerable: false })

   schema.safeParse({ a: "x" })                    → { a: "x", b: "inherited" }   ← ADOPTED
   schema.safeParse(nullPrototypeObject{ a: "x" }) → { a: "x" }
   ```

   An absent `venueEligibility` would have arrived as `"ELIGIBLE"` and §9.8
   check 4 would have passed on a fact nobody supplied.
4. **A door refuses a parse output that LOST a field** (`hardenParsed` /
   `lostKeyPaths`). An inherited GET-ONLY accessor makes an assignment inside
   the validator fail, so a field vanishes from the output while the parse still
   reports success. Measured consequences before the fix: a configured
   `perMarketCap` silently not enforced, and — worse —
   `resizeApprovedIntent` emitting a record whose own `approvedIntentId` was
   `"0"`, the inherited getter's second answer.

**What was NOT done, deliberately.** The internally-built tables (`liveOwners`,
the exposure tables) keep `Object.prototype`; every read of them goes through
`ownEntry`, which is what the census enforces. Making them prototype-free as
well would be a second mechanism for the same invariant, and the reviewer has
twice observed that a boundary resting on two overlapping mechanisms is where
this package stops being able to say which one is load-bearing.

## BLOCKER 3 — the totality claim was about the wrong noun

**Finding (review round 6).** Round 5 wrote that "no public function throws for
any input" (`packages/risk/README.md` §4.5 proposition 2;
`docs/handoffs/WP-180.md` line 3069). The reviewer's matrix:

```text

```

**The reviewer required a choice, argued. Here it is, and it is a split.** The
question that decides each case is: *what would a contained failure have to
RETURN?*

**Contained, because the answer is a refusal the caller already handles:**

| Export | Why containment is right |
| --- | --- |
| `validateEvaluationInput` | Non-negotiable per the reviewer, and correct: it already returns a typed union, and a door that answers with an exception has no defined behaviour for the caller standing in it |
| `riskRefusal` / `capitalRefusal` | These are HOW the packages say no. | `nonFloorLiveMicroCapFields` / `liveMicroCapRefusals` | An `AGENTS.md` floor. Total AND fail-closed: anything that cannot be read as an own data value at the exact floor is reported as NON-floor, so an unreadable caps object refuses rather than passing |
| `withLiveOwner` | Found by the new matrix, not by the reviewer. It returns a `CapitalResult`, so an ownership question it cannot answer must be a refusal |

**Propagating, because containment would have to INVENT a measurement:**
`assessWorstCase`, `exposureSnapshot`, `exposureSnapshotCovering`,
`shadowExposureSnapshot`, `heldSharesByKey`, `reservedSharesByKey`,
`buildWorstCaseLots`, `assessScenarios`, `assessFreshness`, `buildIntentView`,
`heldShares`, `checkExposureLimits`, `recommendIncidentActions`,
`settlementValueUnderOutcome`.

Their result types cannot express a refusal, and the only inventable value is
the empty one: a worst-case loss of `"0"`, an EMPTY exposure snapshot, an EMPTY
inventory table. Each of those is a fail-OPEN — an empty snapshot reads as zero
committed exposure, which is precisely what `RISK_EXPOSURE_ENTRY_MISSING` (round
1, BLOCKER 2) exists to prevent, and an empty reserved-shares table under-states
what is already reserved, which is the direction that permits an oversell. **A
crash is the fail-closed answer here, and every in-repository call site runs
inside `contained`, so no public ANSWER of either package is ever an exception.**

**The claim is now a classification, not a sentence**, and it is enumerated from
the module namespace by `test/unit/risk/public-surface.test.ts`: an export added
without a classification fails the build, a `total` classification is checked by
running the hostile call, and a `propagates` classification is checked by
requiring that call to throw — so the table cannot quietly become aspirational.
`packages/risk/README.md` §4.5 and `packages/capital-allocator/README.md` §7
carry the corrected text with the old sentence quoted and dated.

## BLOCKER — a valid CANCEL was trapped by the parse-output loss check

### The route, argued (the reviewer asked for the argument, not just the fix)

Round 6 discovered that the schema library's output is not trustworthy: it
ADOPTS an inherited field, and with a get-only inherited accessor it DROPS a
field during output assembly while still reporting success. Round 6 answered the
second by REFUSING any output smaller than the input. That refusal is right for
an ordinary entry and wrong for a cancel, and the reviewer ruled it a BLOCKER.

The clean answer is not a narrower refusal. **It is to stop treating the
validator's constructed output as the value at all.** Each door already builds a
prototype-free materialized tree BEFORE parsing; the schema is then asked a
QUESTION — is this acceptable? — and the DATA is taken from our own tree. That
sidesteps adoption and loss in one move and removes the need for the loss check
on that path entirely.

**Does it work everywhere? Yes for five of the seven schemas, and the other two
needed one more idea rather than an exception.** The route is exact only while a
schema contributes NOTHING of its own. Measured across every door schema, the
only value-producing construct in either package is `.default()`:

| Door schema | Value-producing nodes |
| --- | --- |
| `RiskEvaluationInputSchema` | none |
| `ResizeRequestSchema` | none |
| `ApprovedIntentRecordSchema` | none |
| `AllocatorStateInputSchema` | none |
| `ReservationRequestSchema` | none |
| `RiskPolicySchema` | 5 `.default()` |
| `AllocatorCapsSchema` | 2 `.default()` (both `AGENTS.md` floors) |

For the five, the validated value IS the read, verbatim. For the two, the
default cannot come from the read — the caller did not supply it — and PROBE C
line 3 shows why it must not come from the output either. So each of those two
doors declares its defaults in a table (`RISK_POLICY_DEFAULTS`,
`ALLOCATOR_CAPS_DEFAULTS`) and `withSchemaDefaults` applies them to the tree it
already owns, with `undefined` counting as absent exactly as `zod` does. That is
what closed the three fail-opens above, which round 6's loss check could not
even see: the field is missing from the INPUT too, so nothing was "lost".

### Does the loss check survive anywhere? No — and that is deliberate

The reviewer asked for a deliberate decision. `lostKeyPaths` and `hardenParsed`
are **deleted from both copies of `plain-data.ts`**, and no door has a loss arm.
The reasoning: after the change, the value's data comes from a tree this package
built, so there is nothing for a loss check to compare and nothing that can go
missing. The only content that does NOT come from the read is a schema default,
and a lost default is now impossible rather than detected — the table is applied
by us, and `withSchemaDefaults` FAILS CLOSED (`unfilled`, a typed refusal) if a
default's container is missing, a state a successful parse should make
unreachable. Keeping a loss check "just in case" would re-introduce exactly the
cancel trap the reviewer reported, for a condition that can no longer occur.

`ownDataTree` goes with them: nothing needs to re-harden a foreign object any
more. What remains of that machinery is `copyPlainData`, used only to copy a
default VALUE this repository declared, so two parses never share one mutable
array.

## BLOCKER — an inherited SETTER trapped a valid CANCEL

### The route, argued

Round 7's rule — *a schema answers a question, it does not hand you the value* —
is necessary and **not sufficient**, exactly as the reviewer put it. Discarding
the output does not stop the library BUILDING it, and it builds it by
ASSIGNMENT: `newResult[key] = value`, onto an object it created with `{}`. An
ordinary object inherits from `Object.prototype`, so that assignment consults
the chain and invokes an inherited setter. A throwing one aborts the parse; an
accepting one is handed every validated field this package holds.

Three routes were considered, and two rejected with evidence:

1. **Tolerate the throw and answer "valid".** REJECTED — PROBE B above: the
   abort leaves every later key unvalidated, so the answer would admit an
   invalid input. (The reviewer offered this as a leading candidate "unless you
   can better it"; the transcript is the reason it was bettered rather than
   taken.)
2. **Complete the verdict by re-parsing with the hostile names removed.**
   REJECTED after analysis: removing a key changes the verdict wherever a
   sibling depends on it, and the reviewer's own matrix contains such a key —
   `type` is the DISCRIMINATOR of `IntentSchema`, so with it removed no branch
   matches and the rest of the intent is never validated by anything. That route
   is unsound at exactly the case the acceptance test names.
3. **Make the assembly unable to reach a polluted prototype.** ADOPTED. It is
   the reviewer's own second suggestion, and it is the only one that is both
   complete and sound.

### The fix

`packages/risk/src/schema-arena.ts` (NEW, mirrored byte-identically in
`packages/capital-allocator/src/`) exports `prototypeFreeParser(schema)`, which
returns a **PARSING COPY**:

- every node is built by the library itself, from the library's own definition,
  so the copy's VERDICT is the library's verdict — not one validation rule is
  reimplemented;
- each node runs on a payload whose `value` is an accessor: when the library
  assigns a FRESH, EMPTY ordinary container (how it starts assembling an object,
  a record or an array) the arena substitutes a **prototype-free** one, so every
  `payload.value[key] = ...` that follows creates an own property on an object
  with no chain to walk;
- the parse CONTEXT is a **null-prototype copy** of the library's, which is what
  closes PROBE F;
- the copy forces `ctx.jitless`, because the library has two object parsers and
  only the interpreted one assembles into `payload.value`. That is a documented
  per-parse option, not a monkey-patch;
- the walk **fails closed**: a node type outside `ARENA_NODE_TYPES` throws at
  module load, so a future `.transform()`, `.pipe()`, `.catch()` or `z.lazy()`
  is a loud build failure rather than an unprotected assembly.

**The library's own schemas are cloned, never mutated.** A process-wide patch of
`IntentSchema` — a frozen domain contract other packages share — would be a
worse defect than the one being fixed. `schema-arena.test.ts` asserts the
original still has the library's behaviour (it still throws, with
`setterCalls=1`) while the copy does not.

## assumptions (remediation round 8)

1. **A library that ASSEMBLES an output is a side effect, not just an answer.**
   Round 7's rule is extended: it is not enough to ignore the value a library
   hands back; the library must not be able to produce effects the caller does
   not consume. Here the effect is a property write, and the fix removes the one
   thing that made it observable — a prototype chain on the target.
2. **The arena's copy is the library's own semantics.** Not assumed —
   `schema-arena.test.ts` asserts it differentially over every door schema and a
   corpus of valid and broken values, with non-vacuity in both directions.
3. **Three `zod@4.4.3` internals and one documented option are load-bearing:**
   `_zod.def`, `_zod.constr`, `_zod.run`, and `ctx.jitless`. This is a
   version-pinned coupling, taken deliberately: the alternative is to
   reimplement object, array, record and union semantics in this package, which
   is the larger risk by far. A version bump that changes them fails the arena's
   own non-vacuity tests first, loudly.
4. **Prototype AUGMENTATION remains in scope; REPLACEMENT remains out.** Rounds
   1-7's assumptions otherwise stand, except round 7's assumption 1, which this
   round CORRECTS: "if a future `zod` assembled its output with `defineProperty`
   this design would be belt-and-braces" was written as though the assembly were
   harmless today. It is not, and this round measures why.

## known_risks (remediation round 8)

1. **The arena is pinned to one library version.** If a future `zod` changes
   `_zod.run`, `_zod.constr`, `_zod.def` or the meaning of `ctx.jitless`, the
   copy could stop being built — loudly (the build throws) — or, in the worst
   case, silently stop protecting the assembly. The differential test compares
   verdicts, not assembly targets, so the test that would catch a silent loss of
   protection is the sweep's ZERO-setter rule. That is the one to keep green on
   a version bump.
2. **Array-INDEX names stay excluded from the sweep**, with round 6's measured
   reason. An `Object.prototype["0"]` accessor breaks array indexing everywhere
   in the process, including inside the test runner and `decimal.js`; the arena
   substitutes a null-prototype array for the library's assembly, so the
   library's own index writes are covered, but this is not a claim about
   third-party array machinery.
3. **A dotted WRITE is not detected syntactically** (exclusion item 1). Every
   one in these packages is onto an object the package built in the same
   function, and the behavioural sweep is the gate; a syntactic gate is
   follow-up R8-2.
4. **The census's rule is syntactic**, and its boundary is stated in full with
   both round-8 corrections. It still does not reason about call sites or data
   flow.
5. **The pollution sweep proves its property for the scenarios it runs.**
   Unchanged from round 7.
6. **Emitted values have a `null` prototype** (README 6.1 / 2.1). Unchanged.
7. Rounds 1-7's known risks stand.
