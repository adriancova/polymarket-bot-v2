## summary

`packages/capital-allocator` and `packages/risk` replace their `WP-010`
placeholders with handoff §9.7 and §9.8. Both are pure layer-1 libraries: no
I/O, no clock, no network, no credential, no signer, no order-placement surface,
and exact decimal arithmetic for every monetary and size value.

1. **The allocator tracks commitments from BOTH positions and open orders
   (§9.7).** Every exposure entry publishes `openOrderCommitted` and
   `positionCommitted` as separate exact decimals plus their sum, and every cap
   compares against the sum. A position contributes its `costBasis`; an open BUY
   order contributes `price × shares` because it can fill at any moment; an
   applied live BUY reservation contributes its cost (§9.10). Open SELL orders
   reserve *outcome tokens*, tracked by instance-scoped inventory accounting
   rather than the pUSD table.
2. **Caps are user-defined (§9.7), and the safety floors are not.**
   `globalAccountCap` and `perStrategyCap` are required with no default — this
   package invents no example number. The per-scope caps (market, series,
   underlying, resolution window) are optional; a configured scope cap on an
   unattributable request **fails closed** (`CAPITAL_SCOPE_KEY_MISSING`). The two
   live-micro caps default to exactly `"0"`, mirroring `AGENTS.md`, so any
   positive-notional commitment in `EXECUTION_PROBE`, `LIVE_MICRO`, or `LIVE` is
   refused as shipped.

   > **Corrected 2026-09-02 (remediation round 1).** The last sentence was true
   > "as shipped" and *insufficient*: review round 1 (HIGH) established that
   > defaulting to `"0"` while accepting any caller-supplied value made this
   > package a **weakening vector** for defaults `AGENTS.md` declares
   > non-weakenable. The caps are now **fenced**, not defaulted: any live-micro
   > value other than the exact canonical `"0"` is refused
   > (`CAPITAL_LIVE_MICRO_CAP_NOT_PERMITTED`) at the schema, at
   > `parseAllocatorCaps`, and at the reservation gate. See remediation round 1,
   > HIGH.
3. **V1 does not net opposing strategy intents (§9.7, ADR-011).** A LIVE
   commitment requires the requesting instance to be the recorded live owner;
   a conflicting owner — or **no owner at all** — is a typed refusal.
   `SHADOW` commitments keep an independent per-instance book that never touches
   live collateral, inventory, or caps, in either direction.
4. **The risk engine implements the §9.8 twenty checks in §9.8's order**, and
   does not short-circuit: a rejection that named one reason would hide the
   others an operator has to fix. Refusals accumulate in check order; a check
   whose input is *absent* does not silently pass — the absence is itself a
   refusal.
5. **Worst-case contractual loss is the PRIMARY hard limit.** Three structural
   expressions, not a comment: `limits.maxWorstCaseContractualLoss` is the only
   **required** limit in the policy while every secondary cap is optional; the
   check runs and the assessment is returned on *both* arms of the result; and
   `PRIMARY_RISK_REASON_CODES` names its codes so a consumer can separate
   primary from secondary refusals without string matching.
6. **The measure is grounded in WP-110's payoff models.** Both tokens, per
   outcome: `YES_WIN` pays a YES share `1` and a NO share `0`, `NO_WIN` the
   reverse, `SPLIT_50_50` pays `0.5` for a share of either token
   (`packages/settlement/src/payout.ts`, venue-verified 2026-08-28). The
   constants are **mirrored, not imported** (no §2.1 edge exists) and pinned by a
   cross-package test that imports both packages and fails if they diverge.
7. **`CANCELLED` is bounded, never valued** — see `assumptions` 1.
8. **Structured reason codes are a package-owned, documented vocabulary.**
   `RISK_REASON_CODES` (56 codes) and the allocator's `CapitalRefusalCode` (18
   codes) are enumerated at runtime and documented with meanings in each
   package's `README.md`. A test asserts the vocabulary has **no dead entries**
   (every declared code is reachable), emits **no undeclared code**, and that
   every code fits the frozen `CodeString` grammar so it is safe as a §14.3
   metric label.

   > **Corrected 2026-09-02 (remediation round 1).** Two false claims in the
   > paragraph above, both found by review round 1 (MEDIUM). (a) The count
   > **was never 56** — the exported list held **61** at the reviewed commit;
   > with `RISK_EXPOSURE_ENTRY_MISSING` added by the BLOCKER-2 fix the vocabulary
   > is now **62**, pinned as `RISK_REASON_CODE_COUNT` and asserted against both
   > the list and the README's own table. (b) The allocator's codes were **not**
   > enumerated at runtime — `CapitalRefusalCode` was a type union with no
   > runtime list. `CAPITAL_REFUSAL_CODES` (**19** codes after the HIGH fix),
   > `CAPITAL_REFUSAL_CODE_COUNT`, `isCapitalRefusalCode`, and a compile-time
   > exhaustiveness proof now make the claim true.
9. **Incident actions are RECOMMENDATIONS, never actions.** §9.9 says "the
   Incident Controller—not the ordinary risk gate—originates operational safety
   actions", and that controller is a later package. This package emits the §9.9
   ladder verbatim as `kind: "RECOMMENDATION"` data, mapped row for row from the
   §9.9 default-action table with each row quoted, carrying no callable.
10. **A resize creates a new approved-intent record (§7.7).** Records are deeply
    frozen (an in-place edit throws); `resizeApprovedIntent` returns a new record
    with a new id, `lineage: "RESIZED"`, `supersedesApprovedIntentId`, and
    `rootApprovedIntentId`. Reusing an id in the lineage is refused, and a resize
    may only strictly reduce magnitude without flipping side.

## assumptions

1. **`CANCELLED` is bounded, never valued (WP-110 register row U-10).** The
   venue documents winning, losing, and 50/50 redemption and **no** cancellation,
   void, or refund path; `payoutPerShare("CANCELLED")` refuses with
   `SETTLEMENT_CANCELLED_PAYOUT_UNVERIFIED`. This package invents no payout
   either. The assumption it *does* make is one-directional and stated in code:
   **an outcome token is an asset, so no redemption path can charge its holder,
   every unverified redemption is `≥ 0`, and the loss across all terminal
   outcomes is therefore bounded by a zero-redemption floor.** That is what
   `maximumContractualLoss` computes, and it is deliberately conservative — a
   fully hedged YES/NO pair is *not* credited its verified hedge value in the
   primary measure, because crediting it would rely on the undocumented
   cancellation payout. `worstCaseResolutionLoss` is the separate,
   verified-outcomes-only measure that *does* credit the hedge. Every assessment
   carries `cancelledOutcomeTreatment: "ZERO_REDEMPTION_FLOOR_UNVERIFIED_U10"`.
2. **Disposition is derived from the intent TYPE alone.** `POSITION`, `QUOTE`,
   and `BASKET` are `ENTRY`; `REDUCE_POSITION` is `EXIT`; `CANCEL` is `CANCEL`.
   A `POSITION` intent whose delta happens to reduce a holding is therefore
   treated as an entry and gets the **stricter** treatment. This fails closed —
   entry treatment can only refuse more, and refusing to place a new order is the
   safe direction (§6 invariant 12 makes cancel-and-reconcile, not action, the
   mandated response to unknown state). A strategy that means "exit" has
   `REDUCE_POSITION`.
3. **Capacity limits gate entries, not exits.** Exposure caps, per-order
   notional, participation, the economic floor, expected net edge, rate-limit
   headroom, and time-to-close are enforced on entries only. An exit *reduces*
   exposure, so enforcing a cap against it would block exactly the action that
   brings the account back inside the cap. The worst-case and scenario measures
   are still **computed and returned** for exits, so an operator sees them; they
   are simply not the reason a reduction is refused. An **explicit** allocator
   refusal still binds on any disposition.
4. **A `QUOTE` level names no outcome token.** §7.7's `QuoteLevel` is price plus
   size, so a quote's bought shares are UNASSIGNED and the worst-case builder
   places them on whichever token settles **worse** for the holder, per market,
   using the same exact per-outcome arithmetic. Never split, never averaged.
5. **A `REDUCE_POSITION` on a market the supplied portfolio does not describe is
   unknown position state**, not "flat": it is refused with
   `RISK_POSITION_STATE_UNKNOWN` and cancel-and-reconcile recommendations (§6
   invariant 12). A caller that genuinely knows the account is flat has nothing
   to reduce.
6. **The engine never approves a real-order-mode intent.** Beyond check 2 (run
   mode within the process maximum, default `PAPER`), check 3 refuses any mode in
   `RUN_MODE_PLACES_REAL_ORDERS` outright, because this package owns no signer,
   no fencing token, and no venue connection and therefore cannot establish that
   §6 invariants 16 and 17 hold. This is a floor, not a policy knob.
7. **`Date.parse` on a caller-supplied string is not a clock read.** Deadline
   comparison goes through the parsed epoch value because ISO-8601 strings are
   not lexicographically comparable across UTC offsets. This follows WP-110's
   `packages/settlement/src/time.ts` precedent verbatim; `Date.now()` and
   `new Date()` appear nowhere, and a test asserts it over the whole package.
8. **The approved-intent record shape is package-owned.** `packages/domain`
   defines no `ApprovedIntent` and is frozen and forbidden to this work package,
   so the record lives in `packages/risk`. Its identity/lineage fields reuse the
   frozen domain shapes (`IntentId`, `IsoTimestamp`, `RunMode`, `Intent`). If a
   later package needs this shape in the shared contract, that is an ADR.
9. **A resize copies the strategy's ceilings unchanged.** `maximumTotalCost`,
   `maximumBuyPrice`, `minimumSellPrice`, and `validUntil` are not rescaled — a
   ceiling stays valid under a smaller size, and scaling one would invent a
   number the strategy did not supply.
10. **Refusals accumulate; they do not short-circuit.** §9.8's "cheapest first"
    is honoured as the *order* of evaluation and of the returned refusals, not as
    an early exit. A rejection that named one reason would hide the others.

## known_risks

1. **`QuoteIntent` carries no expected-edge field.** §9.8 check 12 requires a
   declared edge, and §7.7's `QuoteIntent` has none, so under the default
   `requirePositiveNetEdgeForEntries: true` **every quote intent is refused**
   with `RISK_EDGE_INPUTS_MISSING`. That is the fail-closed answer and it is
   correct as a default, but it means a quoting strategy cannot run until an
   operator sets the flag false for it or the domain gains an edge field (which
   is an ADR, since `packages/domain` is frozen). See `follow_up` 1.
2. **The structural allocator port is not a compiled contract.** `packages/risk`
   mirrors the allocator's exposure-snapshot and verdict shapes because no §2.1
   edge exists. `test/unit/risk/ports.test.ts` pins it three ways — `tsc`-checked
   field names via `satisfies readonly (keyof …)[]`, a runtime parse of real
   allocator output, and an end-to-end pass — but a *semantic* change on the
   allocator side that keeps the field names (say, `positionCommitted` starting
   to mean mark-to-market rather than cost basis) would not be caught.
3. **Scenario shocks are supplied, not modelled.** This package marks a supplied
   scenario and enforces the loss; it invents no volatility, time, or liquidity
   shock. A caller that supplies mild scenarios gets a mild check. The
   fail-closed half is real (a missing required kind or a partially-marked
   portfolio blocks), but the *severity* of the shocks is the caller's
   responsibility and is not verifiable here.
4. **Participation is a per-intent share cap only.** §9.8 check 13 says
   "Requested quantity respects participation limits"; depth-fraction
   participation needs the book, which this package does not have. The v1 floor
   is a hard `maxOrderShares`; real depth-aware slicing belongs to WP-190's
   execution planner (§9.10).
5. **Self-trade detection sees only the portfolio view it is given.** It
   compares the intent's legs against the resting orders in
   `portfolio.openOrders`. Orders the caller omits are invisible, and a
   `QUOTE`'s token-less legs are compared per market across both tokens
   (conservative, but it can flag a pair that could not actually cross).
6. **`RISK_ALLOCATION_REFUSED` carries the allocator's codes as opaque strings.**
   The risk package cannot import the allocator's `CapitalRefusalCode` union, so
   a typo or a renamed allocator code would ride through as data rather than
   failing a type check. The `ports.test.ts` end-to-end case asserts one real
   code survives the hop.
7. **Exposure attribution for pre-existing positions is the caller's.** A
   position supplied without a scope attribution does not appear in the series /
   underlying / resolution-window tables. The request side still fails closed
   (`RISK_SCOPE_KEY_MISSING` / `CAPITAL_SCOPE_KEY_MISSING`), so no new commitment
   is admitted under an unmeasurable cap, but a historical position can sit
   outside a scope total.

**The one gate a cancel cannot bypass, and why.** `RISK_INPUT_INVALID` is
returned before the intent is normalized. Until the input parses there is no
disposition to privilege, and an unparseable request names no orders to cancel:
this is a limit of knowledge, not a risk gate. Pinned by the test *"the only
thing a CANCEL cannot bypass is input validation itself"*. Flagged explicitly
for review round 2 as the one residual.

### Fix

The rule is now **structural**, not per-gate. One choke point at the end of
`evaluateIntent`: if the disposition is `CANCEL`, every refusal the pipeline
accumulated — from any gate, **including gates added later** — becomes a
non-blocking observation on the new approved-arm field
`cancelPriorityOverrides`, and the cancel is approved carrying its typed
`ApprovedIntentRecord`, its recommendations, and its worst-case measure.

Per-gate conditions were deliberately **not** used: they are exactly what a
later edit forgets, and two of the four findings were gates whose authors
simply did not think about cancels. The choke point carries a loud
do-not-narrow comment naming the test that fails if it is narrowed.

`cancelPriorityOverrides` is **not** a refusal list — the result is approved.
It exists so the observability is not lost: an operator and the §9.9 controller
still see that, say, the allocator refused, even though the cancel proceeded.

### Judgment calls

1. **`RISK_UUID_NOT_CANONICAL` is overridden, not enforced, on a cancel.**
   ADR-016 §2 rules that a UUID-shaped non-canonical identifier is *refused,
   never case-folded*. It is still never case-folded — the id rides through
   exactly as supplied, and the ADR-016 observation is reported. What changed is
   that it no longer **blocks the cancel**, because ADR-016 governs
   normalization, not whether a safety cancellation may be trapped. §6 invariant
   13 is the stronger rule here. Flagged for the reviewer.
2. **The cancel record honestly names the requested run mode.** A cancel
   evaluated with `runMode: "LIVE"` under `maxRunMode: "PAPER"` is approved and
   its record says `runMode: "LIVE"`, with the mismatch on the overrides. This
   package places no orders, so approving a cancel creates no real-order
   surface; misreporting the mode would be worse than reporting it.
3. **The overrides live on the approved arm only.** A rejected result overrode
   nothing by definition, so the field would always be empty there.

## BLOCKER 2 — a missing exposure entry was read as zero (fail-open bypass)

**Finding.** `packages/risk/src/exposure-limits.ts:45` returned `"0"` for an
absent entry, and `packages/risk/src/inputs.ts:105` permits sparse scope maps.
With a per-market or per-scope cap configured, an omitted current exposure was
silently accepted as zero — the cap passed against exposure nobody had measured.

### Fix

- `committed()` **has no `undefined` arm any more**. It takes a present entry,

- Every query site — instance, market, series, underlying, resolution window —

  declares it will query. This is the "represent every queried scope with

  merely break the integration, since `exposureSnapshot` is sparse by
  construction. The zeros are exact and honest — only the *snapshot* is sparse;
  the allocator *state* is complete, so a key it does not mention genuinely
  holds nothing.
- `packages/risk/src/inputs.ts` now documents on the schema itself why sparse
  maps remain structurally legal and where completeness is enforced instead:
  the query set is not known until the intent is normalized, so the schema
  cannot express it.

## BLOCKER — a contract-invalid approved record could be emitted for a CANCEL

**Finding (review round 2).** `engine.ts:181-188` refused a UUID-shaped,
NON-CANONICAL `approvedIntentId` as a pipeline refusal; `engine.ts:951-975` — the
§6 invariant 13 cancel choke point — then converted that refusal into a
non-blocking `cancelPriorityOverrides` observation, approved the cancel, and
copied the id **verbatim** into the emitted `ApprovedIntentRecord`. The
reviewer's targeted product test confirmed `approved: true`, a typed
`RISK_UUID_NOT_CANONICAL` override, and the non-canonical id present in the
record.

**The ruling on the question round 1 referred up** (`known_risks` 1 of round 1,
now annotated with it): ADR-016 §2 requires a **typed refusal at an input
surface** and explicitly forbids accepting uppercase UUIDs for lookup or
persistence. `evaluateIntent(policy, input: unknown)` **is** such a surface.
"Safety cancellation outranks new order placement" does **not** authorize
emitting a contract-invalid approved record. So the two invariants do not
collide: §6 invariant 13 protects a **valid** cancel from being trapped by risk
policy; it does not require accepting a malformed identity. Round 1's judgment
call 1 is superseded.

### Fix — the check moves to the side of the line round 1 itself drew

Round 1 documented that a cancel cannot bypass input validation and called that
"the one residual… a limit of knowledge, not a risk gate". This round puts the
identity check on that side of the line, structurally:

1. **`inputs.ts` gains `validateEvaluationInput(input: unknown)` — one door.**
   It parses `RiskEvaluationInputSchema` **and** applies ADR-016 §2 identity
   validation, and it answers **before `buildIntentView`**, so no disposition
   exists, nothing has been normalized, and the choke point has nothing to
   override. `evaluateIntent`'s body is now `if (!validated.ok) return
   rejected(...)` — the same standing the schema refusal already had.
2. **NOTHING IS CASE-FOLDED.** ADR-016 §2 is refuse-not-normalize; producing a
   canonical id from a non-canonical one would be a worse defect than the one
   being fixed. The raw value rides back out on `details.value` and no
   lowercased form is ever constructed. A dedicated test asserts the canonical
   spelling appears **nowhere** in the result, and mutation M-R2b (below) is a
   fold-instead-of-refuse implementation that the suite kills.
3. **The refusal stays typed and evidential.** Same code
   (`RISK_UUID_NOT_CANONICAL`, so the vocabulary is unchanged at **62**), now
   carrying `{ field, value }` so an operator sees which identifier and what the
   caller actually sent.
4. **`resizeApprovedIntent` validates the identity it INHERITS.** That function
   is the second record-emitting path, and its `record` argument is *typed*
   rather than parsed, so a hand-built record could carry anything into
   `supersedesApprovedIntentId`, `rootApprovedIntentId`, `sourceIntentId`,

## assumptions (remediation round 2)

1. **ADR-016 §2 governs REPOSITORY identifiers, not venue-supplied opaque
   ones.** The amendment's premise ("every UUID in these contracts is generated
   in-process") is what makes a mixed-case arrival evidence of a caller defect;
   it does not hold for a `VenueOrderId`, and the amendment says the ruling
   "does not touch any venue wire format". Stated explicitly because the
   allocator is stricter on its own `orderId` field, and because a reviewer may
   prefer the uniform reading.
2. **`evaluateIntent`'s two arguments have different standing.** `policy` is a
   `RiskPolicy` produced by `parseRiskPolicy`; `input` is `unknown` and is the
   external surface. Identity validation belongs to the second.
3. **An identity refusal is not a risk decision**, so short-circuiting at the
   door does not violate the package's no-short-circuit rule (§9.8 refusals
   still accumulate). All identity violations are reported together, so nothing
   is hidden *within* input validation either.
4. **`resizeApprovedIntent`'s `record` argument is input.** It is typed, not
   parsed; a hand-built record is reachable at runtime, so its inherited
   identity fields are validated rather than trusted.

## known_risks (remediation round 2)

1. **A caller can still persist a non-canonical id it never showed this
   package.** The engine refuses what it is given and copies nothing else, but
   a consumer that mints its own id after approval is outside this package's
   reach. The `ApprovedIntentRecord` shape is package-owned (`assumptions` 8),
   so nothing here can constrain that.
2. **The venue-id exclusion is a judgment on ADR-016's scope.** If a future
   ruling extends the UUID rule to venue-supplied identifiers, this package must
   change with it — and, unlike today, that change could refuse a cancel, which
   is why it should be an ADR decision rather than a package choice. Recorded as
   `follow_up` R2-3.
3. **`CodeString` admits only UUIDs that start with a letter**, so a
   `strategyInstanceId` of `"01890000-…"` is refused by the schema
   (`RISK_INPUT_INVALID`) rather than by the identity check. Both refuse; the
   code differs by the shape of the field. The tests use `f1890000-…` for that
   field so the identity path is genuinely exercised.
4. **The binding-property test walks emitted records with an allowlist of one
   path.** If a future record field legitimately carries a second venue-supplied
   identifier, the allowlist must grow, and a reviewer should treat any growth
   of it as a finding rather than a mechanical edit.
5. Round 1's `known_risks` 2-5 stand unchanged.

## follow_up (remediation round 2)

1. **R2-1. Composition roots must round-trip identifiers byte-for-byte.** A
   caller whose pipeline re-cases an id now gets a typed refusal at the risk
   boundary rather than a silently-persisted variant. That is the ADR-016
   direction and it is a real behaviour change for a caller with such a
   pipeline.
2. **R2-2. `validateEvaluationInput` is exported** so a composition root can
   validate before evaluating (for example to reject at an API edge with the
   same typed code). It is additive and changes no existing signature.
3. **R2-3. A future ADR round may want to state the venue-identifier case
   once**, so `packages/risk` and `packages/capital-allocator` stop differing on
   whether a UUID-shaped `orderId` is refused. Neither behaviour is unsafe —
   the allocator is stricter — but one written rule would be better than two
   defensible readings. Not changed here: weakening the allocator is out of
   scope and out of direction, and strengthening risk would add a way to refuse
   a cancel.
4. Round 1's `follow_up` 1-4 stand unchanged.
