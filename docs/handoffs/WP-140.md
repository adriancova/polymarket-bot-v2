## summary

Four deliverables, zero new dependencies (`pnpm-lock.yaml` untouched):

1. **Metrics exporter** — `packages/observability/src/recorder/`, a pure,
   dependency-free layer-1 module. It declares **structural mirrors** of the
   metric shapes the producers already export (`DataGateway.metrics()` in
   `apps/data-gateway`; `ResearchWorkerMetrics` in `apps/research-worker`)
   and renders them to Prometheus text exposition. Why mirrors: the
   dependency-direction contract (§2, F10/F12) forbids `packages/observability`
   (layer 1) from importing layer-3 apps, so the types cannot be imported —
   instead the soak tree, where both sides are reachable, pins assignability
   against the REAL exported types at compile time
   (`test/soak/recorder/src/type-compat.ts`), so drift fails a typecheck
   with the field named. The canonical metric table
   (`metric-families.ts`, 120 `recorder_*` families with type, help,
   category, and label domains) is the single source of truth: the renderer
   refuses samples not in it, and every family is proven reachable by test.
   Also here: the WP-130 validator finding-class registry (drift-tested
   against `python/research/compaction/validate.py`'s actual source), the
   pure book snapshot comparator, and the soak-evidence schema + fail-closed
   evaluator.

2. **Dashboard and alert rules as code** — `infra/grafana/recorder/` and
   `infra/prometheus/`. **Acceptance 1 is machine-checked**, not eyeballed:
   `infra-consistency.test.ts` parses the dashboard JSON and the rules YAML
   and asserts (a) every referenced `recorder_*` series is one the exporter
   emits, (b) each of the six acceptance-1 categories — queue depth, lag,
   gaps, fsync, compaction, upload status — has at least one panel bound to
   a metric of that category, (c) the WP-120-obligated charts
   (`queueDepth`, `queueMaxDepthObserved`, `queueBytes`,
   `oldestQueuedAgeMs`, `admissionRefusals`) and alarms (recorder EXIT;
   oldest-queued-age BEFORE the bound; WAL refusals/drops; RTDS halt;
   publication halt; fsync overdue vs the data-loss bound; compaction lag;
   upload failure; validation findings) exist by name, and (d) the
   oldest-age alarm threshold stays early (≤ 30 s). The "recorder FAILED to
   exit" alarm is **documented as log-based** (the `cleanup deadline …
   expired` and `[disposal]` stderr lines) rather than faked as PromQL —
   a metric cannot observe the process that is wedged, and the test pins
   that documentation too.

3. **Soak harness** — `test/soak/recorder/`, self-contained
   (WP-020/WP-120/WP-130 test-tree precedent; root wiring is
   orchestrator-owned at merge). `run-soak.mjs` builds and runs the REAL
   gateway bundle (the exact WP-120 subprocess pattern from
   `test/integration/data-gateway/process-liveness.test.ts`; loopback-only
   by default — `wss://127.0.0.1:1`, `redis://127.0.0.1:1`, nothing leaves
   the machine) for a bounded window, observes it from outside (stderr
   signals, exit behavior, WAL manifests), and writes one evidence record
   per window. **Duration is first-class** (`startedAt`/`endedAt`/
   `elapsedMs`, recomputed and cross-checked at evaluation) and the record
   carries **no status field** — status exists only as the output of
   `evaluateSoakEvidence`, which fails closed: any malformed, contradictory,
   or future-dated record poisons the set to `INVALID`; short windows are
   `PENDING` with the arithmetic stated; `SATISFIED` requires ONE contiguous
   qualifying window ≥ the threshold in which the recorder demonstrably
   recorded, shut down cleanly on request, and reported zero
   unexplained-gap signals. A real soak is the SAME harness run longer with
   a reviewed config (`docs/runbooks/recorder.md` §7). The automated smoke
   runs the whole pipeline for ~4 s and asserts the result is honestly
   PENDING — and that a loopback window can never qualify at any length,
   because it records nothing.

4. **Snapshot comparison job** — the Wave 1 closeout item "Book
   reconstruction is checked against snapshots", shaped like the WP-130
   validator (findings returned, never raised). The pure comparator
   (`book-comparison.ts`) applies the venue's own recorded `price_change`
   deltas (absolute-size semantics, ADR-013) from one recorded authoritative
   `book` snapshot and requires the result to equal the NEXT recorded
   snapshot, per outcome token, per epoch, on **canonical decimal strings**
   (no float ever touches a price or size; a tiny string-space
   canonicalizer/comparator is implemented and tested in-module because
   observability cannot import `packages/decimal` without a package.json
   edit outside this package's paths — see deviations 3). The I/O driver
   (`soak:compare-books`) reads real WAL segments per epoch (epochs are
   never mixed — the WAL contract defines no cross-epoch order; WP-130
   precedent) and fails on any divergence.

5. **Recorder runbook** — `docs/runbooks/recorder.md`: the bidirectional
   exit contract (WP-120 rounds 2–6, in its final round-6 wording), the
   forced-exit operator signals with exact log-line substrings, alarm
   meanings for both failure directions (EXIT and FAILED-to-exit), the
   restart procedure **folded in** from `infra/compose/data-gateway/README.md`
   (per WP-120 follow-up; see deviations 2), the fsync interval written
   down as the data-loss bound (ADR-004 §3 — closing the WP-120 "runbook
   still owes" item), admission-bound sizing from soak data (explicitly
   pending, with the procedure for when data exists), the validator finding
   classes as an operational table with actions, and the full soak-evidence
   procedure (how to start, where evidence lands, what marks it complete).

## assumptions

1. **The soak threshold is 24 hours** (`SOAK_ELAPSED_EVIDENCE_THRESHOLD_MS =
   86_400_000`). Neither the handoff (§16.7, §17 Phase 1 "sustained
   recording soak") nor the work plan states a duration. 24 h is chosen
   conservatively (covers daily venue cycles and the ephemeral-market
   series) and is a one-line reviewed edit if the orchestrator rules
   otherwise. The runbook §7 recommends requesting 26 h so a qualifying
   24 h window survives operational slack.
2. **"No unexplained gaps" is enforced conservatively**: WAL recording
   failures AND any incident whose reason code contains `GAP` count as
   unexplained-gap signals, and a window carrying any cannot qualify — even
   a venue-side RTDS gap. A soak with venue gaps therefore stays PENDING
   until an operator reviews and either re-runs or documents the
   explanation in the completion record. The safe direction: harder to
   satisfy, never easier.
3. **Alert thresholds are reasoned, not measured** (5 s oldest-age, 80%
   headroom, 1 h compaction lag): no soak data exists to size them from
   (that is this package's own pending evidence). Each is annotated in the
   rules file; the runbook §5 records the sizing procedure for when data
   exists. The oldest-age threshold is pinned ≤ 30 s by test so it cannot
   quietly drift past "before the bound".
4. **Evidence honesty leans on the future-skew tolerance** (60 s) and the
   claimed-vs-recomputed elapsed tolerance (5 s): wall-clock ISO timestamps
   and monotonic elapsed legitimately disagree slightly. Both constants are
   exported and tested.
5. **The scrape ports (9464/9465) are placeholders** in a fragment that is
   explicitly disclosed as not-yet-served (follow-up 1); loopback-only
   either way.

## deviations

1. **No HTTP metrics endpoint was added.** The dispatch permitted "no new
   network server is required for tests: expose a pure render function and
   let the harness/app wire serving later" — that is exactly what was
   built. Consequence, stated plainly: **no process serves `/metrics`
   today**, so the Prometheus/Grafana artifacts are forward-looking code
   validated for internal consistency, and the scrape fragment says so in
   its header. Wiring the exporter into `apps/data-gateway` /
   `apps/research-worker` is a composition-root change in forbidden paths
   (follow-up 1).
2. **The restart procedure was subsumed, not moved.** The WP-120 follow-up
   said "fold the operator restart procedure into the WP-140 recorder
   runbook rather than duplicating it". The runbook now owns the procedure
   (§3), but `infra/compose/data-gateway/README.md` still contains its
   original copy because `infra/compose/**` is outside WP-140's allowed
   paths. Trimming the README to a pointer is follow-up 2 (WP-120-path
   owner). Until then two copies exist; the runbook is declared the
   authoritative one in both this hand-off and the runbook header.
3. **A minimal canonical-decimal comparator is implemented inside
   `book-comparison.ts`** instead of depending on `packages/decimal`
   (layer 0, a legal downward edge) — because declaring the dependency
   requires editing `packages/observability/package.json`, which is outside
   `packages/observability/src/recorder/**`. It is string-space only (strip
   leading/trailing zeros, length-then-lex compare), grammar-fail-closed,
   and covered by 14 dedicated test cases. If a later package-manifest edit
   is ratified, replacing it with `packages/decimal` is mechanical.
4. **The recorder module is not re-exported from the package entry point.**
   `packages/observability/src/index.ts` is the WP-010 placeholder and is
   outside the allowed `src/recorder/**` grant. In-repo consumers (the soak
   tree) import by path; the one-line `export * from "./recorder/index.js"`
   is follow-up 3.
5. **The soak tree carries a non-workspace `package.json` with no
   devDependencies**, resolving `vitest`/`tsc` from the root toolchain via
   directory walk-up — the same resolution every `test/**` tree already
   uses (their configs note "files under test/ sit outside every workspace
   package"). Unlike `test/integration/*`, no workspace package hosts this
   tree's scripts (WP-120 put them in `apps/data-gateway/package.json`,
   which WP-140 may not edit), so the scripts live in the tree itself and
   run via `pnpm --dir test/soak/recorder run <script>`. Verified working
   from a clean install. Root-script wiring (e.g. a `test:soak:recorder`
   alias, and adding the soak tree's typecheck to a root gate) is
   orchestrator-owned at merge (follow-up 4).
6. **`packages/observability` colocated tests import `vitest` without a
   local devDependency declaration** — same walk-up resolution, since the
   package manifest is outside the grant. Root `pnpm test` runs them (the
   root config includes `packages/**/src/**/*.test.ts`) and root `vitest`
   is the runner, so no phantom runtime dependency exists; still, declaring
   `vitest` in the package manifest for hygiene is part of follow-up 3.
7. **The evaluation and comparison "jobs" are vitest specs** run by
   dedicated scripts (`soak:evaluate`, `soak:compare-books`), not
   standalone binaries: the repository has no runtime-build story for

   open), and vitest is the established execution vehicle in test trees.
   They write their artifacts only under the (gitignored) evidence
   directory or an operator-supplied path.

## known_risks

1. **The exporter is unserved** (deviation 1). Until follow-up 1 lands, the
   dashboards/alerts cannot fire against a live process, and gateway health
   is read from stderr and in-process `metrics()` as before. The alert
   design anticipates this: `RecorderExited` fires on an absent target,
   which is exactly what an unwired deployment looks like — deliberate:
   silence is an alarm, not a pass.
2. **The FAILED-to-exit alarm depends on a log pipeline** that this
   repository does not ship. The signals are pinned (exact substrings in
   the runbook §2; the alerts-file header; a test asserts the
   documentation), but if no log alarm is wired at deployment, a wedged
   recorder pages only via the `RecorderExited`-after-shutdown-request
   procedure, which requires an operator to know a shutdown was requested.
3. **The structural mirrors are pinned only where the pin runs.** The
   type-compat check lives in the soak tree's typecheck, which is NOT yet
   part of any root gate (deviation 5 / follow-up 4). Until wired, a
   producer field rename would surface there and in the review, but not in
   root `pnpm typecheck`.
4. **The book comparator trusts recorded order within an epoch** (by
   `ingestSeq`), which is what the WAL guarantees; it does not verify
   payload digests (the WP-130 validator owns byte-exactness). A WAL that
   lies about order would produce divergence findings — the safe direction,
   but attribution would take the validator run too.
5. **`evaluateSoakEvidence` sums nothing and forgives nothing**, which
   means operational restarts during a soak (deploys, host reboots) reset
   the qualifying window. That is the correct reading of "sustained", and
   it makes a 24 h window a real operational bar. If the orchestrator later
   rules that N windows totalling T qualify, that is a reviewed evaluator
   change, not a harness change.
6. **Metric families for feed internals are a curated subset** — every
   §14.3 recorder-family entry and every WP-120/WP-130 obligation is
   covered (tested by name), but a few producer fields with no operational
   story (e.g. `transportObservations`, `highWaterMark` string) are
   deliberately not exported. Adding one later is a table row + a mapping
   line + the tests forcing panel/alert consistency.
