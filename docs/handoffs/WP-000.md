## summary

Verified current official Polymarket integration behavior against official
sources (all accessed 2026-08-24) and froze three deliverables, without
placing any order, loading any credential/signer, or making any
authenticated call:

1. **Verification report** `docs/venue/verified-2026-08-24.md` — every venue
   statement cites its official source with access date. Rules the unified
   SDK `@polymarket/client` (Node `>=24`) as the only permitted client and
   explicitly REJECTS archived CLOB/relayer/builder-signing clients. Covers
   order schemas and GTC/GTD/FOK/FAK expiration rules, delayed/unmatched
   responses, market and user WebSocket schemas (raw SDK wire layer vs
   normalized docs layer, frozen against `Polymarket/ts-sdk` reference
   commit `7fdbed42484b5d279c71aa36d3757d18968260da`), heartbeat protocol
   (empty-ID bootstrap, per-response ID rotation, 5 s cadence / 10 s
   timeout / 5 s cancellation sweep), fees and maker/taker/liquidity reward
   snapshots, per-market parameters (dynamic tick size, min size, negRisk,
   secondsDelay), IP and per-signer rate limits as configuration snapshots
   (all eight signer tiers; exact per-endpoint dual limits), matching-engine
   restricted modes (HTTP 425 restart with undocumented body; 503
   cancel-only/post-only with `error`/`code`/`retry_after_seconds` and
   `Retry-After`), geoblock, CTF split/merge/redeem with published Polygon
   contract addresses and `TransactionOutcome` handles, and Chainlink TWAP
   over RTDS (30 s/60 s, no replay after disconnect). Conflicts C-1..C-4
   and UNVERIFIED items U-1..U-9 (U-5, U-8 resolved) are explicit.
2. **Sanitized fixtures** `test/fixtures/venue/**` (17 JSON files + README
   with provenance and sanitization rules): market WS events (book,
   price-change incl. flagged zero-size removal, tick-size change, last
   trade, best bid/ask, lifecycle), raw user WS order lifecycle and trade
   settlement per the SDK raw schemas, REST trades with prefixed
   `TRADE_STATUS_*` constants (REST-only `MATCHED_NOT_BROADCASTED`), order
   placement responses incl. delayed and failure shapes, restricted modes,
   heartbeat rotation, fee/reward snapshots, rate-limit headers/tiers,
   geoblock, split/merge/redeem, RTDS TWAP.
3. **Verification CLI skeleton** `apps/ops-cli/src/verify-venue/`
   (`checks.ts`, `fixtures.ts`, `index.ts`, `fixtures.test.ts`): enumerates
   the handoff §1.2 checks; validates fixtures against source-specific
   schemas; scans for credential-shaped keys; validates the frozen report;
   reports PASS/FAIL/DOCUMENTED; exposes formatter and exit-code mapping.
   Never touches the network; never requires credentials. NOT wired into the
   CLI entry point (outside allowed paths; owned integration plan in report
   §15). Precisely, after the round-3 remediation:
   - **Payload schemas.** Each fixture check declares a `PayloadSpec` that is
     either a single `ObjectSpec` or a **discriminated** set of variants keyed
     on a payload field (`event_type`, `operation`) or on the example name
     (configuration snapshots that share no wire discriminator). An example
     whose discriminant has no declared variant fails, so a new example
     cannot pass unvalidated.
   - **Field kinds** are `string`, `decimal-string`, `price-string`,
     `empty-or-decimal-string`, `empty-or-price-string`, `digit-string`,
     `hex-string` (with length sets), `number`, `integer`, `boolean`,
     `object` (nested `fields`, map-valued `values`, `strict` key sets),
     `array` (recursive `items`), `union` (`oneOf`), and `unknown`.
     Optionality distinguishes SDK `.nullish()` (`optional`) from
     `.nullable()` (`nullable`).
   - **Nested contract-bearing structures are typed, not opaque objects:**
     fee/rebate tables and category maps, rate-limit response header bags
     (documented names, digit-string counters), `limits_per_10s`,
     `trading_dual_limits` inner burst/sustained pairs, published contract
     address maps, CTF request/`TransactionOutcome` shapes, negative-risk
     event flags, RTDS `subscriptions[]` entries, `clobRewards[]` entries,
     book levels, price-change entries, and maker orders.
   - **SDK fidelity.** Every SDK-derived schema is `strict` and enumerates the
     full field list of its source schema at the pinned reference commit
     `7fdbed42484b5d279c71aa36d3757d18968260da`, so an omitted SDK field
     cannot hide behind unknown-key acceptance. Modeled faithfully: optional
     decimals accept the wire empty string (`OptionalDecimalStringSchema`);
     `outcome_index`/`bucket_index` are integers on the websocket channel and
     `z.number()` on REST; epoch fields are `/^\d+$/` digit strings; the
     `matchtime` alias exists; `NewMarketEventSchema` and
     `MarketResolvedEventSchema` both require `id`; REST trades follow
     `ClobTradeSchema`/`MakerOrderSchema` (all fields required, no
     `outcome_index`), a different contract from the websocket trade event;
     order placement responses follow `OrderResponsePayloadSchema`.
     Deliberate narrowings (prices bounded to [0,1] and canonical per §7.3;
     documented enums where the SDK types a free string) are each marked
     NARROWING in `checks.ts`.
   - **Price bounds are exact.** `isCanonicalPriceString` decides the [0,1]
     range lexically on the canonical string with no binary floating point,
     so `"-0.<400 zeros>1"` and `"1.<400 zeros>1"` are rejected instead of
     underflowing to `-0` / rounding to `1`.
   - **Credential scanning** is case/separator-insensitive and combines an
     exact-name list with substring patterns, so documented names
     (`POLYMARKET_PRIVATE_KEY`, `POLYMARKET_WALLET_ADDRESS`,
     `POLY_API_KEY`/`PASSPHRASE`/`SIGNATURE`/`ADDRESS`/`TIMESTAMP`,
     `POLY_BUILDER_*`, `POLYMARKET_BUILDER_CODE`) and unenumerated variants
     (`*_PRIVATE_KEY`, any builder/API-key spelling) are all caught.
   - **Report evidence.** Every non-exempt required report section must carry
     its **own** official citation; `UNVERIFIED` is a status annotation and
     never counts as evidence. Exemptions are an enumerated table with
     rationales (`CITATION_EXEMPT_SECTIONS`), currently only §13 (safety
     attestation). Documented-absence venue facts (for example the
     undocumented HTTP 425 body, U-9) are NOT exempt: they are modeled as
     explicit strict variants that reject an invented body, and their report
     section still cites the page on which the body is absent. SDK links must
     be commit permalinks; `blob/main` is rejected.

## assumptions

  quoted text is as returned by those fetches.

  commit `7fdbed42484b5d279c71aa36d3757d18968260da` (committed 2026-08-24);

  shown in the docs; the fixture value is marked illustrative.

  in fixtures (no personal data).

  intended mechanism for the colocated test file; no config change was
  needed or made.
- Round 3: raw SDK sources were fetched read-only and unauthenticated from
  `raw.githubusercontent.com` at the pinned commit and read verbatim (not via
  a summarizing fetch), so the field lists and value types recorded here are
  transcriptions rather than paraphrases.
- Round 3: the fee/reward decimal strings were normalized to canonical form
  per handoff §7.3 (`"0.20"`→`"0.2"`, `"1.0"`→`"1"`, `"0.50"`→`"0.5"`,
  `"3.0"`→`"3"`, `"0.10"`/`"0.90"`→`"0.1"`/`"0.9"`). This changes
  representation only; the documented values are unchanged and the
  normalization is recorded in the fixture notes.
- Round 3: `orders/rest-trades.json` examples were completed to satisfy the
  SDK `ClobTradeSchema`, which requires every field. The added values
  (synthetic zero transaction hashes, zero maker address, `bucket_index: 0`,
  epoch-second `match_time`/`last_update`) are sanitized placeholders in
  fields whose SDK types they satisfy; no claim is made about the venue's
  real values for a not-yet-broadcast trade.
- Round 3: SDK layer narrowings that this repository applies on purpose are
  documented rather than silently adopted — prices are bounded to [0,1] and
  canonicalized per §7.3 where the SDK uses unbounded `DecimalString`;
  `side`/`status` are enumerated where the SDK types a free string;
  user-stream trade statuses are pinned to the plain spelling and REST to the
  prefixed spelling even though `TradeStatusSchema` normalizes both. Each is
  marked NARROWING in `checks.ts`.

## known_risks

- C-1/U-1: `price_change` absolute-size / zero-removal semantics are not
  explicitly documented; the handoff §23 assumption is provisional and the
  fixture example is flagged UNVERIFIED. WP-070 must confirm before WP-150

- C-2: official pages use USDC (fees) vs pUSD (rebates/rewards)
  denomination language; interpretation deferred to ledger/fee accounting
  packages.
- C-3: docs list `MATCHED_NOT_BROADCASTED` for the user stream while the
  SDK states it is REST-only; modeled per SDK (source precedence). WP-280
  must re-check.
- C-4: review-claimed archived-SDK references on quickstart/overview were
  not reproducible; re-check both pages at the next phase gate.
- U-4: order error-message strings beyond "not enough balance / allowance"
  are representative paraphrases; consumers must key on failure status.
- U-9: no HTTP 425 body is documented; clients must key on the status code.
- All limits, fees, tiers, and addresses are snapshots effective 2026-08-24
  and must be re-verified at each phase start (handoff §1.2).
- Structural validation is not domain validation: `packages/domain`
  (WP-020) will own canonical schemas; the verify-venue schemas are
  contract-shaped stand-ins only. They are now strict and SDK-enumerated, but
  they are hand-transcribed from the SDK rather than generated from it, so
  they can drift if the SDK changes; the pin plus the permalink test make
  drift detectable only at the next deliberate re-verification.
- The `hex-string` kind assumes the SDK's `isHexString` requires the `0x`
  prefix. This is inferred from `EvmAddressSchema` (`length === 42`, i.e.
  `0x` + 40 hex characters) rather than read from `@polymarket/types`
  directly; the condition-id lengths 64/66 are applied on the same basis.
- Fixture completion for `ClobTradeSchema` means the REST fixture now asserts
  a strictly larger contract than before. If the venue in practice omits a
  field the SDK marks required, the fixture would be stricter than reality;
  WP-280 should confirm against observation.
