## summary

Verified current official Polymarket integration behavior against official
sources (all accessed 2026-08-24) and froze three deliverables, without
placing any order, loading any credential/signer, or making any
authenticated call:

1. **Verification report** `docs/venue/verified-2026-08-24.md` — every venue
   statement cites its official source with access date. Rules the unified
   SDK `@polymarket/client` (Node `>=24`) as the only permitted client and
   explicitly REJECTS archived CLOB/relayer/builder-signing clients. Covers
   order schemas and GTC/GTD/FOK/FAK expiration rules, delayed/unmatched
   responses, market and user WebSocket schemas (raw SDK wire layer vs
   normalized docs layer, frozen against `Polymarket/ts-sdk` reference
   commit `7fdbed42484b5d279c71aa36d3757d18968260da`), heartbeat protocol
   (empty-ID bootstrap, per-response ID rotation, 5 s cadence / 10 s
   timeout / 5 s cancellation sweep), fees and maker/taker/liquidity reward
   snapshots, per-market parameters (dynamic tick size, min size, negRisk,
   secondsDelay), IP and per-signer rate limits as configuration snapshots
   (all eight signer tiers; exact per-endpoint dual limits), matching-engine
   restricted modes (HTTP 425 restart with undocumented body; 503
   cancel-only/post-only with `error`/`code`/`retry_after_seconds` and
   `Retry-After`), geoblock, CTF split/merge/redeem with published Polygon
   contract addresses and `TransactionOutcome` handles, and Chainlink TWAP
   over RTDS (30 s/60 s, no replay after disconnect). Conflicts C-1..C-4
   and UNVERIFIED items U-1..U-9 (U-5, U-8 resolved) are explicit.
   Round 4 additionally added §16 (documented credential, auth-header, and
   builder-attribution names with per-name citations and the round-3→round-4
   fact reversal) and corrected §7, §10.2, §10.3, and the §14 source index.
   Round 4b added §7.1, which records that the market-details page publishes
   the reward fields in two disagreeing layers — an SDK-parsed layer typing
   the amounts `DecimalString`/`Decimal` and a raw Gamma layer typing them
   `number` — quotes both verbatim, and shows the SDK's `DecimalishSchema`
   union that reconciles them. Round 5 added §17 (optionality versus
   nullability: what `.default([])`, `.nullish()`, and a published `| null`
   each mean, the complete list of documented nullables, and the narrowing a
   runtime parser must not inherit), completed the `MarketRewards` field list
   in §7/§7.1 with `holdingRewardsEnabled`, gave §2.1–§2.4 and §16 their own
   citations, and recorded the key-by-key re-audit of every SDK field list in
   §14.
2. **Sanitized fixtures** `test/fixtures/venue/**` (17 JSON files + README
   with provenance and sanitization rules): market WS events (book,
   price-change incl. flagged zero-size removal, tick-size change, last
   trade, best bid/ask, lifecycle), raw user WS order lifecycle and trade
   settlement per the SDK raw schemas, REST trades with prefixed
   `TRADE_STATUS_*` constants (REST-only `MATCHED_NOT_BROADCASTED`), order
   placement responses incl. delayed and failure shapes, restricted modes,
   heartbeat rotation, fee/reward snapshots, rate-limit headers/tiers,
   geoblock, split/merge/redeem, RTDS TWAP.
3. **Verification CLI skeleton** `apps/ops-cli/src/verify-venue/`
   (`checks.ts`, `fixtures.ts`, `index.ts`, `fixtures.test.ts`): enumerates
   the handoff §1.2 checks; validates fixtures against source-specific
   schemas; scans for credential-shaped keys; validates the frozen report;
   reports PASS/FAIL/DOCUMENTED; exposes formatter and exit-code mapping.
   Never touches the network; never requires credentials. NOT wired into the
   CLI entry point (outside allowed paths; owned integration plan in report
   §15). Precisely, after the round-3 remediation and as amended by round 4
   (nullable/optional corrections, whole-map validation, recursive catalog
   guards, corrected credential sources — see the round-4 history entry) and
   round 5 (optional no longer implies nullable, the complete `MarketRewards`
   field list, and a report evidence gate that covers every heading — see the
   round-5 history entry):
   - **Payload schemas.** Each fixture check declares a `PayloadSpec` that is
     either a single `ObjectSpec` or a **discriminated** set of variants keyed
     on a payload field (`event_type`, `operation`) or on the example name
     (configuration snapshots that share no wire discriminator). An example
     whose discriminant has no declared variant fails, so a new example
     cannot pass unvalidated.
   - **Field kinds** are `string`, `decimal-string`, `price-string`,
     `empty-or-decimal-string`, `empty-or-price-string`, `digit-string`,
     `hex-string` (with length sets), `number`, `integer`, `boolean`,
     `object` (nested `fields`, map-valued `values`, `strict` key sets),
     `array` (recursive `items`), `union` (`oneOf`), and `unknown`.
     **Optionality and nullability are separate axes (corrected in round 5).**
     `optional` means the key may be ABSENT and nothing else; `nullable` means
     the value may be `null`. Rounds 3–4b described `optional` as modelling SDK
     `.nullish()`, and the validator implemented that by accepting `null` for
     any `optional` field — which admitted four undocumented nulls. An explicit
     `null` is now accepted only where `nullable: true` is declared, every
     `nullable` in the catalog cites an official published type that documents
     `| null` (four in total), and a catalog guard fails if a fifth appears.
     Report §17 records the rule, the three source modifiers it maps
     (`.default([])`, `.nullish()`, `.nullable()`), and the fact that rejecting
     `null` for SDK `.nullish()` fields is a fixture-only narrowing that a
     runtime parser must not inherit.
   - **Nested contract-bearing structures are typed, not opaque objects:**
     fee/rebate tables and category maps, rate-limit response header bags
     (documented names, digit-string counters), `limits_per_10s`,
     `trading_dual_limits` inner burst/sustained pairs, published contract
     address maps, CTF request/`TransactionOutcome` shapes, negative-risk
     event flags, RTDS `subscriptions[]` entries, `clobRewards[]` entries,
     book levels, price-change entries, and maker orders.
   - **Every map entry is validated, including `null` and `undefined`**
     (round-4 HIGH (a)). A map value may be `null` only where its value spec
     declares `nullable`, and `undefined` only where it declares `optional`;
     otherwise both are errors. Previously such entries were skipped outright.
   - **Catalog guards are recursive** (round-4 LOW). `reachableObjectSpecs`
     walks variants, nested `fields`, array `items`, `union` alternatives, and
     map `values`, asserting at EVERY level that a schema is strict or
     map-typed, is non-vacuous, has at least one required field when it
     declares fields, and never declares an `unknown` map value spec. Two
     further tests guard the walker itself against regressing to
     top-level-only.
   - **Documented nullability/optionality corrections (round 4).** RTDS
     subscription `filters` is OPTIONAL (omit it to receive every symbol);
     `TransactionOutcome.transactionId` is NULLABLE; `clobRewards[].endDate`
     is NULLABLE. Each is cited in the report and frozen as a fixture example.
   - **SDK fidelity.** Every SDK-derived schema is `strict` and enumerates the
     full field list of its source schema at the pinned reference commit
     `7fdbed42484b5d279c71aa36d3757d18968260da`, so an omitted SDK field
     cannot hide behind unknown-key acceptance. **This claim was false until
     round 5** for the per-market reward schema, which omitted
     `MarketRewards.holdingRewardsEnabled` and so rejected a valid parsed
     object as carrying an unexpected key. The field is now declared (optional
     AND nullable, per the published `?: boolean | null`), and because one gap
     was found, every other source field list was re-read verbatim at the
     pinned commit and compared key-by-key: the six market-channel event
     schemas plus `PriceChangeSchema`, `MarketEventMessageSchema` and
     `OrderBookLevelSchema`, `UserOrderEventSchema` (19 keys),
     `UserTradeEventSchema` (23 keys), `TradeMakerOrderSchema`,
     `ClobTradeSchema` (18 keys), `MakerOrderSchema`,
     `OrderResponsePayloadSchema`, `ClobRewardsSchema`, and `MarketRewards`.
     No further gap was found; the re-audit and its date are recorded in the
     `checks.ts` header and report §14. Modeled faithfully: optional
     decimals accept the wire empty string (`OptionalDecimalStringSchema`);
     `outcome_index`/`bucket_index` are integers on the websocket channel and
     `z.number()` on REST; epoch fields are `/^\d+$/` digit strings; the
     `matchtime` alias exists; `NewMarketEventSchema` and
     `MarketResolvedEventSchema` both require `id`; REST trades follow
     `ClobTradeSchema`/`MakerOrderSchema` (all fields required, no
     `outcome_index`), a different contract from the websocket trade event;
     order placement responses follow `OrderResponsePayloadSchema`.
     Deliberate narrowings (prices bounded to [0,1] and canonical per §7.3;
     documented enums where the SDK types a free string) are each marked
     NARROWING in `checks.ts`.
   - **Price bounds are exact.** `isCanonicalPriceString` decides the [0,1]
     range lexically on the canonical string with no binary floating point,
     so `"-0.<400 zeros>1"` and `"1.<400 zeros>1"` are rejected instead of
     underflowing to `-0` / rounding to `1`.
   - **Credential scanning** is case/separator-insensitive and combines an
     exact-name list with substring patterns, so documented names
     (`POLYMARKET_PRIVATE_KEY`, `POLYMARKET_WALLET_ADDRESS`,
     `SIGNER_PRIVATE_KEY`,
     `POLY_API_KEY`/`PASSPHRASE`/`SIGNATURE`/`ADDRESS`/`TIMESTAMP`,
     `POLY_BUILDER_*`, `POLYMARKET_BUILDER_API_KEY`/`SECRET`/`PASSPHRASE`,
     `POLYMARKET_BUILDER_CODE`) and unenumerated variants (`*_PRIVATE_KEY`,
     any builder/API-key or secret spelling) are all caught. Round 4 corrected
     the per-name sources, added the `secret` pattern (round 3 missed
     `POLYMARKET_BUILDER_SECRET` entirely), and records the names in report
     §16 split into **secret material**, **account-identifying**, and **public
     builder attribution** — `POLYMARKET_BUILDER_CODE` is a public builder
     identifier, scanned so no real value is embedded, but it is not a secret.
   - **Report evidence.** Every non-exempt required report section must carry
     its **own** official citation; `UNVERIFIED` is a status annotation and
     never counts as evidence. Exemptions are an enumerated table with
     rationales (`CITATION_EXEMPT_SECTIONS`): §10 (a bare container heading
     whose facts all live in §10.1–§10.3), §13 (safety attestation), and §15
     (the in-repo integration plan). Documented-absence venue facts (for
     example the undocumented HTTP 425 body, U-9) are NOT exempt: they are
     modeled as explicit strict variants that reject an invented body, and
     their report section still cites the page on which the body is absent.
     SDK links must be commit permalinks; `blob/main` is rejected.
     **Coverage is now total (round 5).** The required-section list previously
     held only the check sections plus §11–§13, so §2.1–§2.4, §7.1, §14, §15
     and §16 were never gated at all and every URL could be stripped from any
     of them without failing validation. Subsections are gated INDIVIDUALLY —
     a section's evidence is its own text, so a parent may not borrow a
     citation from a child nor a child from its parent — and
     `validateVerificationReport` additionally fails if any `##`/`###` heading
     in the report is absent from both the required list and the exemption
     table, or carries no section number at all. The test file no longer keeps
     its own copy of the section list; it imports the real one, which is how
     the two drifted apart unnoticed for two rounds.
