**The signer boundary.** Building a secure client goes through four steps in order, and any failure stops it:
1. The run-mode gate runs first and fails closed. It lets through only EXECUTION_PROBE, LIVE_MICRO or LIVE, within the process maximum, with `allowRealOrders === true`. PAPER, BACKTEST, SHADOW, REPLAY, and any unknown or malformed context are refused.
2. The signer must be an opaque handle this package created.
3. The real SDK factory refuses the test mock signer.
4. Only then is the signer handed to the SDK.

Nothing in the package reads the environment or a key file. The mock signer holds no key, signs only its own fixture domain, and produces a signature that no verifier would accept.

**The narrow interface (`SecureVenueClient`).** It signs orders locally, posts one order or a batch of 1–15, cancels (single, up to 1,000 ids, by market, or all), and reads an order back. After construction no method throws; each returns an outcome of NOT_SENT, REFUSED, REJECTED, UNKNOWN or ACCEPTED.

**Error mapping.** Errors are classified by HTTP status and documented code only, never by the venue's text:
- A 503 without a documented code maps to TRADING_UNAVAILABLE, with cancels marked UNKNOWN. This holds for all three official strings in C-9.
- Undocumented codes are flagged but their value is not carried (U-4).
- Errors carry no venue text and no `cause`.

**One SDK behaviour you should know about.** The pinned SDK turns the venue's documented successful `unmatched` placement into a rejection and drops the order id. I map it to UNKNOWN, never REJECTED, so the order has to be reconciled by its signed identity.

**Runbook.** docs/runbooks/signer.md explains how the boundary works and why no key can reach a paper process, and records the fresh-check results.

### assumptions

- **Where the gate's input comes from.** The run-mode context is supplied by the composition root from its validated startup configuration, the same way the domain package's maximum-run-mode check is given its maximum. The gate cannot detect a root that lies about its own mode; the runbook says so plainly.
- **Which failures count as "not applied".** I class 401, 425, 429, and 503 with `post_only_mode` as NOT_APPLIED, because they are documented refusals. A bare 503 and every other status are UNKNOWN, a conservative reading of C-9 and U-4. Treating 401 as not applied is my reading of HTTP semantics, not a venue statement.
- **SDK rejection codes are trusted.** The pinned SDK sorts some failures into named codes by matching the venue's error text exactly. I treat that as current official SDK behaviour, so its eight named codes map to REJECTED.
- **Tests use a live-looking context.** The test-only factory still runs the gate, so the tests pass the literal context {LIVE_MICRO, LIVE_MICRO, allowRealOrders: true}. That context only ever reaches the fake SDK or a refusal.
- **How the contract hook reaches the SDK's response parser.** The 0.11.0 runtime root does not export the schemas its type declarations advertise (e.g. `OrderResponseSchema` is undefined at runtime). The test-only hook therefore finds `@polymarket/bindings/clob` from the SDK's own install location.

### deviations

- **Acceptance 1 is enforced by a test, not by editing the dependency checker.** sdk-import-boundary.test.ts scans the whole repo:
  - imports in every source file, including test/** and tools/**;
  - every package.json dependency field;
  - the lockfile's importers;
  - the archived clients anywhere (F7).
  The existing check:deps F6 rule already covers package source. The checker, its configuration and its allowlist are untouched.
- **No heartbeat method in the interface.** C-12 is unresolved, and an ADR is owed before WP-320.
- **No user stream or wallet operations.** Those belong to WP-280 and WP-300.
- **The new contract suite is not in the root `test:contract` chain.** That script lives in the protected root package.json, which is outside my allowed paths. Until it is added, the suite runs with `pnpm --filter @polymarket-bot/polymarket-secure test:contract`.
- **Venue error text is deliberately not carried.** Diagnostics lose the venue's message; that is the price of structural redaction.

### known_risks

- **The SDK drops the order id on `unmatched` (C-6).** @polymarket/client 0.11.0 turns the documented successful `unmatched` placement into {ok:false, code:"unmatched"} with no order id. I map it to UNKNOWN, but the OMS has only the signed identity (salt, maker, token) to reconcile with.
- **No expected order hash before sending.** ADR-007 step 3 wants it, but the SDK does not expose it and computing it by hand would need an ADR.
- **The static scan cannot see a non-literal dynamic import** of the SDK. check:deps has the same limit.
- **The redaction detector matches substrings only.** It checks each full fake secret and its 16-character prefix, so an encoded leak (for example base64 of a secret) would not be seen. Structural redaction is the primary defence.
- **The network tripwire covers fetch, WebSocket and net.Socket.connect.** A Node network path outside those would not be caught; none is known.
- **`SignerHandle.create` is a public static.** It throws unless called while this package is sealing a signer.

### assumptions

  - shares are rounded down to 2 decimals for every tick;

- **Maker/signer addresses are not cross-checked.** How the account wallet maps to the maker for each wallet type is not documented, so I did not invent it.
- **mapVenueError's operation argument is always a package-internal literal.** An invalid one produces only a fixed TypeError with no value in it.
