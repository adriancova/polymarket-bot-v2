## summary

`packages/binance-adapter` normalizes the two required Binance public streams —
`<symbol>@trade` and `<symbol>@bookTicker` — into the frozen domain events
`ReferenceTradeObserved` and `ReferenceTopOfBookChanged`, manages the connection
lifecycle with explicit subscription generations and feed-status events,
classifies duplicates and out-of-order updates against documented venue ids, and
exposes staleness as typed queryable values.

Seven design decisions carry the weight, each forced by a cited rule rather than
by preference:

1. **The adapter owns no socket, no timer, and no clock.** `BinanceReferenceFeed`
   is a state machine over (socket events, receipt stamps) that *returns* a
   `ConnectionDirective` telling the caller when to reconnect. Handoff §12.4 and
   §6 invariant 15 require a recorded run to be replayable in arrival order,
   which is impossible for a component that schedules its own reconnect and
   stamps its own frames. `systemClock` is the one wall-clock read in the
   package, and it is injectable.
2. **It assigns no gateway field.** ADR-002 §1 makes `gatewayEpoch` and
   `ingestSeq` required and §2.1 makes `(gatewayEpoch, ingestSeq)` the only
   ordering authority; handoff §9.1 assigns them, with `eventId`, to the
   gateway. `AdapterEmission` is the §7.1 envelope *minus* exactly those three
   fields, so the mistake is unrepresentable rather than merely avoided. A
   contract test adds the three fields and parses the result through
   `DOMAIN_EVENT_REGISTRY.parseEnvelope`.
3. **A reconnect is never a silent resumption.** Every open emits
   `FeedConnected` **and** a `FeedGapDetected` whose
   `requiresAuthoritativeSnapshot` is the contract's literal `true`, plus a
   `DataQualityIncidentOpened`. The package **never** emits `FeedResynchronized`:
   Binance publishes no authoritative snapshot on these streams and its
   documentation defines no replay, resume, or backfill for them, so ADR-002
   §2.4's "recorded as `FeedConnected` alongside the still-open gap" is exactly
   the state this adapter is in.
4. **Duplicate handling is grounded in documented ids, and stops there.** A trade
   `t` identifies one trade on one symbol (`GET /api/v3/historicalTrades` pages
   from a `fromId`), and the documented local-order-book procedure fixes what a
   *lower* update id means. Neither stream is documented to deliver *consecutive*
   ids, so a jump is never reported as a gap — handoff §9.4 forbids inventing a
   venue sequence number, and treating a non-contiguous id as contiguous is that
   invention with extra steps.
5. **A late trade is published; a stale quote is not.** A trade is a point
   observation, so dropping a late one would lose a real event (§8.3); top of
   book is versioned state, so applying an older version would overwrite newer
   state. Both are classified, counted, and returned to the caller.
6. **Nothing is dropped silently.** Every frame produces a `FrameOutcome` with a
   classification, the decoded frame, the raw text, and any emissions. Malformed,
   unknown, conflicting, and unrepresentable frames each open a
   `DataQualityIncidentOpened` with a bounded raw excerpt (ADR-002 §2.5, §7).
7. **Staleness is data, and the threshold is the caller's.** Binance documents no
   maximum interval between two market-data messages, so
   `stalenessThresholdMs` is a required constructor option with no default; a
   default here would be an invented venue fact. Staleness itself is measured on
   the monotonic clock, and `venueToReceiptLagMs` keeps its sign because a
   negative value is real clock-skew evidence.

### The ADR-004 §1 open item, answered

`docs/handoffs/WP-030.md` `follow_up` 7 and ADR-004 §1 assigned this package the
question "does Binance deliver binary payloads, in which case `payloadUtf8`
cannot hold them and ADR-004 needs an amendment?" The answer has three parts,
recorded as data in `BINANCE_FRAMING_RULING`:

1. **VERIFIED — the JSON stream endpoints carry JSON payloads** (V14).
2. **VERIFIED — a binary Binance market-data path exists, and it is a different,
   credential-gated host** (V15). This package refuses that host by construction,
   so **no binary payload can reach the WAL through this adapter and ADR-004
   needs no amendment for `WP-080`.**
3. **UNVERIFIED — the WebSocket *opcode* of a market-data event on
   `stream.binance.com` / `data-stream.binance.vision` is never stated**
   (`BNC-U1`). `SBE_STREAMS` says the JSON control traffic on the *SBE* host
   travels "in JSON in WebSocket **text frames**", which is strong but is a
   statement about the other host. This package therefore does **not** assert
   "text frame". The socket contract takes a string; the shipped WebSocket
   binding sets `binaryType = "arraybuffer"` and decodes a binary payload with a
   **fatal** `TextDecoder`, reporting an `ERROR` event if it cannot — which is
   exactly the right behavior, since a payload that cannot be represented as a
   UTF-8 string cannot be recorded in `payloadUtf8` either.

**This closes the `WP-080` half of the item as far as documentation can close
it.** The residual is an observation question, not a documentation question, and
is listed in `follow_up`.

### UNVERIFIED register (`BINANCE_UNVERIFIED` in `src/venue.ts`)

| id | Subject | Conservative behavior chosen instead of an assumption |
| --- | --- | --- |
| `BNC-U1` | WebSocket opcode of market-data events on the JSON stream endpoint | Socket contract takes a string; a binary frame is decoded as UTF-8 with a fatal decoder and reported if undecodable. Nothing claims the frames are text. |
| `BNC-U2` | Contiguity of `<symbol>@trade` trade ids | A jump in `t` is **never** a feed gap. Only equality is a duplicate; a non-consecutive step is reported as data. |
| `BNC-U3` | Monotonicity of `<symbol>@bookTicker` update ids | The *stale* reading of a lower `u` is applied (documented for `@depth`, not for `bookTicker`); the *contiguity* reading is not. A regressed quote is suppressed, counted, and returned — never silently discarded. |
| `BNC-U4` | How `bookTicker` spells an empty book side | A non-positive best price is **not** mapped to "absent" (ADR-001 §8.1: "an absent best bid is not a zero best bid"). **One** unusable side: that side is omitted with its raw value recorded and an incident opened, the other side is still published, and the frame is `NORMALIZED` and counted as a partial top of book. **Both** sides unusable: the frame is `UNREPRESENTABLE`, an incident is opened, and nothing is emitted. (The `src/venue.ts` register text was corrected in remediation round 1 — finding L1.) |
| `BNC-U5` | Which book side the frozen contract's `takerSide` names | `takerSide` is **omitted by default**. Binance documents `m` as "Is the buyer the market maker?"; the contract says only "Taker side when the venue reports it", and the two available readings map `m` to **opposite** values. ADR-002 §6's precedent applies: "a producer that cannot supply them must omit them rather than guess." A caller that owns the ruling opts into a named convention (`BOOK_SIDE_CONSUMED` or `TAKER_ORDER_DIRECTION`) and thereby records which one it meant. The raw `buyerIsMaker` boolean survives on the decoded frame either way. |
| `BNC-U6` | Precision of integer JSON fields (`t`, `u`, `E`, `T`) | A parsed integer outside the JavaScript safe range fails to parse rather than being carried as a silently rounded value that would print as a wrong `venueTradeId`. |

## assumptions

1. **`venueTimestamp` for a trade is `T` (trade time), not `E` (event time).** §7.1
   describes `venueTimestamp` as the time the source supplies for the event, and
   `T` is when the trade happened while `E` is when Binance generated the
   message. Both survive on the decoded frame, so a consumer that wants the
   difference has it. If a reviewer prefers `E`, it is a one-line change in
   `normalizeTrade` plus its tests.
2. **A first subscription emits `FeedGapDetected` too**, with its own reason code
   (`BINANCE_SUBSCRIPTION_START_NO_REPLAY`). §7.1 lists "a restart **or** detected
   gap" as triggering the snapshot obligation, and a process that has just
   started has observed nothing before its first frame. Emitting it can only make
   a consumer wait for a snapshot it was already required to have; omitting it
   would let a fresh subscription look like a continuous one. A reviewer who
   reads §7.1 more narrowly would suppress it at generation 0.
3. **One incident per reason code per connection generation.** A malformed-frame
   storm would otherwise become an incident storm and bury the first, most useful
   report. This is not a silent drop: every occurrence is counted in the metrics
   and returned on the `FrameOutcome`. The suppression set is cleared on each new
   connection, so a condition still true on a new socket gets its own incident.
4. **The package never emits `DataQualityIncidentClosed`.** It does not observe
   the resolution of a condition, and asserting a recovery it did not perform
   would be the mirror of the `FeedResynchronized` mistake ADR-002 §2.4 forbids.
   Closing incidents belongs to the gateway or an operator.
5. **`sourceChannel` for a connection-level event** is the constant
   `binance:stream-connection`. §7.1 requires a non-empty `sourceChannel`, and a
   feed-status event belongs to the socket rather than to one stream; picking a
   subscribed stream arbitrarily would be misleading and joining them all would
   exceed the field's bound.
6. **`FeedConnected.endpoint` is the query-free endpoint identifier**
   (`wss://data-stream.binance.vision/stream`), not the full URL. The full URL
   exceeds the domain's 200-character bound with a realistic subscription set,
   the subscription set is already recorded per event as `sourceChannel`, and the
   contract says of that field "Never contains credentials".
7. **Symbol validation is boundary hygiene, not a venue grammar.** Binance
   publishes no symbol grammar and explicitly contemplates non-ASCII symbol
   names, so only structural, whitespace, and control characters are refused,
   with a 64-character bound.
8. **The reconnect backoff carries no jitter.** Jitter needs randomness, and an
   adapter that reads unseeded entropy stops being replayable (§12.4). The
   trade-off is stated in `connection.ts`: several feeds in one process retry in
   lockstep. A caller that wants jitter adds it from its own seeded source.

## deviations

1. **The package builds a *combined*-stream URL, always.** The venue documents
   both raw and combined forms; `buildRawStreamUrl` exists, but
   `BinanceReferenceFeed` uses the combined one. Reason: a `bookTicker` payload
   carries no event-type field, so on a raw multi-stream connection the
   originating stream can only be *inferred* from the payload's shape, while the
   combined wrapper states it. The decoder still accepts unwrapped frames and
   records `channelSource: "RECONSTRUCTED"` when it had to reconstruct the
   channel name.
2. **Live `SUBSCRIBE`/`UNSUBSCRIBE` control messages are not sent.** Subscriptions
   are encoded in the URL, which needs no client message at all and therefore
   cannot breach the documented 5-messages-per-second limit. The *responses* to
   such messages are still decoded (`CONTROL_RESPONSE`, `CONTROL_ERROR`), so a
   future dynamic-subscription layer has the parsing already.
3. **`test/contract/binance/fixtures.ts` validates fixtures by hand rather than
   with `zod`.** This tree is not a workspace package and resolves only what the
   repository root installs; `zod` is a dependency of `packages/domain`, not of
   the root. Adding it to the root manifest to validate test data would edit a
   protected path for a test-only convenience.
4. **`unknownFields` reports keys the *venue documentation* does not describe,
   not keys this package does not model.** The trade payload's `M` is documented
   ("Ignore") and is therefore not reported; reporting it would open a
   data-quality incident on every single trade frame and bury the real
   schema-drift signal.
5. **No root wiring was added.** `test/vitest.config.ts`, `test/tsconfig.json`,
   and the root `package.json` are protected paths; the suite runs through the
   package-level `test:contract` script, the `WP-040`/`WP-050`/`WP-060` pattern.
   Registering it in a root script is orchestrator-owned at merge.

## known_risks

1. **`takerSide` is omitted by default, so a real venue fact does not cross the
   boundary** (`BNC-U5`). This is deliberate and cited, but it *is* information
   loss on the recorded path: a downstream consumer cannot tell trade direction
   from a `ReferenceTradeObserved` event until the contract owner rules on the
   convention. The raw `buyerIsMaker` is available on the decoded frame in the
   same process, but not in the recorded event. See `follow_up` 1.
2. **A permanently regressed `bookTicker` update id would stall top-of-book
   publication for that symbol.** If Binance ever reset `u` (undocumented, never
   observed here), every subsequent frame would classify `REGRESSED` and be
   suppressed. It would be visible — `staleUpdatesSuppressed` climbs, the
   per-stream `lastVenueSequenceId` sits still, and the feed would eventually go
   `stale` if nothing else arrived — but the adapter would not self-heal. A
   reconnect does not clear the tracker, deliberately, because clearing it would
   also lose duplicate detection across the reconnect (which
   `reconnect.test.ts` exercises).
3. **Sequence state is retained across reconnects and is bounded at 4096 keys by
   default.** Beyond the bound a key is `UNTRACKED` and cannot be deduplicated;
   this is counted (`untrackedSequenceObservations`) rather than silent, but a
   subscription set near the documented 1024-stream ceiling on many connections
   should raise the bound explicitly.
4. **The shipped `createWebSocketFactory` has never opened a real socket.** Tests
   run offline against an injected fake constructor, which covers the event
   mapping, the UTF-8 decode path, and the `close` forwarding — but not the real
   `WebSocket` semantics of Node 24 (`binaryType` acceptance, error-event shape,
   automatic pong replies). The first real connection belongs to `WP-120`.
5. **Venue facts are a dated snapshot** (`BINANCE_FACTS_VERIFIED_AT =
   "2026-08-27"`). Handoff §1.2 requires re-verification each phase. The contract
   suite ties every fixture's `accessedAt` to that constant, so a partial
   re-verification cannot pass unnoticed — but nothing forces the re-verification
   itself.
6. **`BNC-U1` (the frame opcode) is closed conservatively, not resolved.** If a
   Binance market-data frame on the JSON endpoint ever arrives as binary *and*
   is not valid UTF-8, this adapter reports an error and publishes nothing for
   that frame, which is correct but is a hard stop rather than a degradation.
7. **The `serverShutdown` advisory is surfaced, not acted on.** A caller that
   ignores `advisory: "ESTABLISH_NEW_CONNECTION"` will simply be disconnected
   shortly afterwards and reconnect through the ordinary path — correct, but it
   forfeits the seamless handover the venue's instruction makes possible.
8. **Incident ids are derived, not random** (`feedId:connectionId:ordinal`).
   Uniqueness therefore depends on the caller supplying a unique `connectionId`
   per connection. This is a deliberate trade for replay determinism, and the
   dependency is stated in `incidents.ts`, but it is a real obligation on
   `WP-120`.

### H1 — retired-socket callbacks were relabelled as the current connection

**Probe reproduced** against `be5d67a`, byte for byte as reported:

```json
{"probe":"retired_socket_message","classification":"NORMALIZED","emitted":[{"type":"ReferenceTradeObserved","connectionId":"conn-b","generation":1}]}
{"probe":"retired_socket_close","state":"IDLE","directive":{"kind":"RECONNECT_AFTER","delayMs":1000,"attempt":1},"emitted":[{"type":"FeedDisconnected","connectionId":"conn-b","generation":1}]}
```

A frame from the retired socket `conn-a` was published as `conn-b`/generation 1,
and `conn-a`'s late close disconnected the live feed and directed a reconnect.

**Fix.** Socket identity is now immutable and travels with every event.

1. `src/connection.ts` — `connectionId` is a required field on **all four**
   `BinanceSocketEvent` variants, not only `OPEN`; the transport's obligation to
   stamp it is stated in the module header. `MAX_CONNECTION_ID_LENGTH` and
   `isWellFormedConnectionId` moved here (they are part of the socket contract),
   and `ConnectionIdentityRelation` (`LIVE | RETIRED | UNKNOWN | INVALID`) is
   exported.
2. `src/websocket.ts` — the binding captures `request.connectionId` once, per
   socket, and stamps it on `open`, `message`, `error`, and `close`. Two
   overlapping sockets therefore produce distinguishable events.
3. `src/feed.ts` — `onFrame`, `onSocketError`, and `onClose` take the
   connection id as their first argument (`handleSocketEvent` reads it off the
   event), and the feed keeps `#liveConnectionId` plus a **bounded, FIFO** set of
   retired identities (`MAX_REMEMBERED_RETIRED_CONNECTIONS = 256`). Acceptance:
   - `MESSAGE` — only from the live socket.
   - `ERROR`/`CLOSE` — from the live socket, or from an identity the feed has
     never listened to **while nothing is live**. That second case is a
     connection attempt failing before it ever opened, which must still produce
     the reconnect directive; while a socket IS live, an unknown identity is
     another socket and is refused.
   - `OPEN` — only for an identity never listened to. A repeat open of the live
     id creates no generation; a retired id is never revived; a *new* id while
     one is live is a make-before-break reconnect and retires the previous
     socket.
   A refused event mutates nothing: no state, no sequence tracker, no staleness
   clock, no domain event. It returns `rejected: RejectedSocketEvent`, is counted
   (`frames.framesNotFromLiveConnection`,
   `connections.lifecycleEventsNotFromLiveConnection`), and opens a
   `BINANCE_RETIRED_CONNECTION_EVENT` incident. A refused **frame** is still
   decoded, so its raw text survives (§8.3), and is classified
   `STALE_CONNECTION`.

**Probe re-run against the fix:**

```json
{"probe":"retired_socket_message","classification":"STALE_CONNECTION","emitted":[{"type":"DataQualityIncidentOpened","connectionId":"conn-b","generation":1}]}
{"probe":"retired_socket_close","state":"OPEN","liveConnectionId":"conn-b","directive":{"kind":"NONE"},"emitted":[]}
```

### M1 — combined-wrapper channel provenance was trusted without validation

**Probe reproduced** against `be5d67a`: every wrapper below decoded as a `TRADE`
whose `streamName` was the wrapper's, unchecked —

```json
{"probe":"wrapper_channel","stream":"BTCUSDT@trade","kind":"TRADE","streamName":"BTCUSDT@trade","channelSource":"WRAPPER"}

{"probe":"wrapper_channel_mismatch","classification":"NORMALIZED","emitted":[{"type":"ReferenceTradeObserved","sourceChannel":"ethusdt@trade","symbol":"BTCUSDT"}]}
```

**Fix.** `src/frames.ts` `resolveChannel` now derives
`"<lowercase payload symbol>@<decoded suffix>"` and requires the wrapper to

never resolved by guessing which half of the frame to believe (ADR-002 §7). The

endpoint cannot smuggle in an unsubscribed symbol either.

value, `UNVERIFIED_WRAPPER`. It is preserved as data on the decoded frame but
never becomes an emission's `sourceChannel`: the feed falls back to
`binance:stream-connection` for those. A side effect worth stating: with the
subscription check in place the sequence tracker's key space is bounded by the
subscribed set rather than by venue-supplied symbols.

### M2 — delayed, non-adjacent duplicate trades were published twice

**Probe reproduced** against `be5d67a` (`100, 101, 100`):

```json
{"probe":"delayed_duplicate","classifications":["NORMALIZED","NORMALIZED","NORMALIZED"],"sequences":["FIRST","ADVANCED","REGRESSED"],"emitted":[{"id":"100"},{"id":"101"},{"id":"100"}]}
```

Trade `100` was published twice. Duplicate detection depended on the arrival
schedule rather than on the data.

**Fix.** `src/sequence.ts` keeps a **bounded per-key FIFO window** of recent
id→identity pairs (`maxRecentIdsPerKey`, default
`DEFAULT_MAX_RECENT_IDS_PER_KEY = 64`, surfaced as the feed option
`maxRecentIdsPerStream`) alongside `lastId`. An id already in the window is
`DUPLICATE` or `CONFLICTING_DUPLICATE` whether or not it is still the highest;
only an **unseen** lower id is `REGRESSED`, and a `REGRESSED` id is itself
remembered so its own repeat is recognised. `SequenceObservation` gained
`previouslySeen`, which is the "repeat vs. out-of-order" distinction as data.
This is the same bounded discipline as the accepted 4096-key bound, extended.

**The bound's consequence is documented, not hidden** (module header,
`known_risks` below): an id evicted from the window is no longer recognised as a
repeat, so a very late repeat of it is `REGRESSED` and — for a trade — published
again. Worst-case retained state is `maxTrackedStreams × maxRecentIdsPerStream`.
Both bounds and the per-stream `recentIdsTracked` are reported in the metrics, so
the window's real reach is observable rather than assumed.

**Probe re-run:**

```json
{"probe":"delayed_duplicate","classifications":["NORMALIZED","NORMALIZED","DUPLICATE_SUPPRESSED"],"sequences":["FIRST","ADVANCED","DUPLICATE"],"emitted":[{"id":"100"},{"id":"101"}]}
```

**Tests added** — `src/sequence.test.ts`: delayed duplicate, delayed conflict, a
late arrival's own repeat, the bounded window and its eviction consequence
asserted explicitly, and per-key window independence (cross-symbol isolation);
`src/feed.test.ts`: the `100, 101, 100` schedule end to end, the delayed-conflict
case, and a reconnect where a **newer** id arrives before the replayed one;
`test/contract/binance/reconnect.test.ts`: the same reconnect-delayed duplicate
at the contract level.

**Mutation check.** Restricting the window lookup to `id === lastId` → **6 tests
fail** across `sequence.test.ts` and `feed.test.ts`.

### L2 — MAX_FRAME_BYTES was enforced as a UTF-16 character count

**Probe reproduced** against `be5d67a`: a frame of 600 023 UTF-16 units /
1 200 023 UTF-8 bytes — 1.14× the claimed 1 MiB bound — passed the size check and
was parsed (`{"kind":"MALFORMED","reason":"SCHEMA_MISMATCH"}`, i.e. rejected for

`length > MAX` proves "too large" and `length × 3 ≤ MAX` proves "not too large",

now states the unit and why it matters (the venue documents non-ASCII symbol

### Review note — the off-state frame path

Reproduced: a frame arriving in a state with no decode branch threw
`BinanceStateError: a frame arrived while the feed was IDLE`.

**Terminal behavior, stated as the note asks: no socket-event path throws.**
`onFrame`, `onOpen`, `onSocketError`, and `onClose` are transport callbacks, and
a throw inside one surfaces in the driver's event loop where it destroys the
frame instead of recording it. Every transport-committable misuse is now a
classified outcome:

| Input | Outcome |
| --- | --- |
| Frame while no socket is live (`IDLE`, `CONNECTING`, `CLOSED`) | `FrameOutcome`, classification `STALE_CONNECTION`, incident `BINANCE_FRAME_WITHOUT_CONNECTION`, `directive: NONE`, nothing applied |
| Frame from a retired or foreign socket | `FrameOutcome`, classification `STALE_CONNECTION`, incident `BINANCE_RETIRED_CONNECTION_EVENT` |
| `OPEN` on a caller-closed feed | `FeedOutcome` with `rejected`, `directive: STOP/CLOSED_BY_CALLER` |
| `OPEN` with a malformed, live, or retired id | `FeedOutcome` with `rejected`, `directive: NONE` |
| `ERROR`/`CLOSE` from a socket that is not live | `FeedOutcome` with `rejected`, `directive: NONE` |

Direct caller misuse that is **not** a socket event still throws:
`new BinanceReferenceFeed({…})` with a bad option, and `connecting()` on a closed
feed. Those are programming errors on a path the caller controls, and a silent
value there would hide them.

## assumptions (round 1, additional)

1. **The newest `OPEN` wins.** When a socket opens while another is live, the new
   one becomes the live socket and the previous is retired. A driver only opens
   what it decided to open, so the later decision is the current one; the
   alternative (refusing the new socket) would strand a make-before-break
   reconnect, which is exactly what the documented `serverShutdown` advisory asks
   a client to perform.
2. **A connection id identifies exactly one connection.** Already an obligation
   for incident-id uniqueness (`incidents.ts`); it is now also what makes a
   retired socket recognisable. A repeated id is refused rather than silently
   treated as a new connection.
3. **64 remembered ids per stream is a chosen default, not a venue fact.** The
   venue documents nothing about reordering distance. It is exposed as an option
   and its bound is in the metrics.
4. **A wrapper name that cannot be derived from its payload is not provenance.**
   `!serverShutdown` is documented and preserved, but it is not used as a
   `sourceChannel`. The alternative — recording an unverifiable venue string as
   the origin of an event — is the class of claim `AGENTS.md` forbids.

## deviations (round 1, additional)

1. **The feed's socket-event methods changed signature.** `onFrame`,
   `onSocketError`, and `onClose` now take the connection id first. The identity
   cannot be optional without leaving the H1 hole open, and the package is
   unmerged, so no consumer exists yet. `handleSocketEvent` is unchanged for a
   driver that uses it, which is the documented entry point.
2. **`metrics.connectionId` now reports the LIVE connection**, so it is
   `undefined` between a close and the next open. It previously reported the last
   connection whenever the state was `OPEN`, which is the same value in every
   reachable case, but "the socket we are listening to" is the honest reading.

## known_risks (round 1, additional)

1. **The duplicate window has an edge.** An id evicted after 64 newer ids on the
   same stream is no longer recognised as a repeat: a very late repeat of it is
   `REGRESSED`, and for a trade that means a second publication. This is bounded,
   documented, and visible (`recentIdsTracked`, `maxRecentIdsPerStream`), and it
   replaces a hole that had no edge at all — but it is not "duplicates are
   impossible".
2. **The retired-connection set is bounded at 256.** An event from a socket
   retired more than 256 connections ago is classified `UNKNOWN` rather than
   `RETIRED`. It is still refused whenever a socket is live; only when nothing is
   live can it be accepted, and then the worst case is one extra
   `FeedDisconnected` and reconnect directive for an already-disconnected feed.
3. **Channel verification assumes the documented stream-name grammar.** If
   Binance ever wraps a `<symbol>@trade` payload in a stream name that is not
   `"<lowercase symbol>@trade"`, this package will classify it `MALFORMED` rather
   than publish it. That is the intended failure direction — the frame is
   preserved with an incident — but it is a behavior change that a venue-side
   naming change would surface as malformed traffic, not as a silent
   mislabelling.
4. **`framesReceived` counts refused frames too.** It is "what the transport
   delivered"; `framesNotFromLiveConnection` is the part that was not applied. A
   dashboard that reads `framesReceived` as "frames processed" would overcount
   during an overlapping-socket episode.
