## summary

`packages/strategy-sdk` and `packages/strategy-runtime` replace their `WP-010`
placeholders with the handoff §9.6 strategy runtime and the §7.6 strategy
surface. Both are layer-1 application modules under
`docs/contracts/dependency-direction.md` §2: pure logic over the frozen layer-0
contracts, owning **no connection**.

1. **The strategy interface is the handoff's, verbatim.** `Strategy<TParams,
   TState>` declares the nine §9.6 callbacks with the exact signatures §9.6
   prints, and `StrategyContext` / `SeededRandom` are exactly §7.6. Nothing was
   added to either shape. The SDK also owns the read-only view types ADR-005 §6
   assigns to WP-170 rather than to the frozen domain package (`MarketView`,
   `OrderBookView`, `FeatureSnapshot`, `VirtualPositionView`,
   `StrategyOrderView`, `StrategyFill`, `ResolutionView`, `RiskBudgetView`,
   `SourceEventRef`), each deliberately narrow: every field is a contract the
   composition root must populate, so every widening is a reviewable SDK change
   rather than an accident.
2. **Versioning is explicit in three independent places**, because §9.6
   requires "a new run for every code, config, model, feature, or state-schema
   change" and those are different things: `strategy.name`/`version` (code),
   `strategy.stateSchemaVersion` (state shape),
   `STRATEGY_SDK_CONTRACT_VERSION` (the interface itself), and
   `STRATEGY_STATE_CHECKPOINT_SCHEMA_VERSION` (the checkpoint envelope).
3. **Exactly one persisted `DecisionResult` per invoked callback** (§6
   invariant 3), on every path: a valid decision, a no-op decision, a throwing
   callback, an over-budget callback, a returned value that is not a §7.5
   `DecisionResult`, a decision naming a feature snapshot this evaluation did
   not see, a decision claiming a reserved `RUNTIME.*` reason code, and a
   `statePatch` that is not checkpointable JSON. The first case persists a
   **strategy**-attributed record; the rest are CONTAINED as exactly one
   **runtime**-attributed `skip` with a reserved reason code and no intents
   (ADR-005 §3), the strategy's returned value is discarded, the RNG is rolled
   back to its pre-invocation state, and the instance is paused.
4. **A no-op decision is persisted like any other.** §9.6 says "persist exactly
   one `DecisionResult` per evaluation" without exception, and ADR-005 §2
   spells out the consequence: `intents` may be empty, and "no action is a
   recorded fact, not an absence". A `hold` with zero intents therefore takes
   the ordinary DECIDED path — one record, one checkpoint — and this is pinned
   by a named test rather than left to inference.
5. **Refusal is separated from containment, and both are separated from
   halting**, because they are different facts about an evaluation:
   - `REFUSED` — the callback was **never invoked** (paused/stopped instance,
     re-entrant call, invalid input), so §6 invariant 3 does not bind and **no**
     record exists. Nothing was evaluated, so nothing decided.
   - `CONTAINED` — the callback ran and misbehaved: exactly one
     runtime-attributed record, instance paused, incident reported.
   - `HALTED` — a persistence port threw. The write was attempted **exactly
     once** and is deliberately **not retried** (a write of unknown fate must
     not be blindly repeated — the §6 invariant 6 reasoning); the instance
     pauses and the outcome names which port failed, so a `SAVE_CHECKPOINT`
     halt tells the operator the decision *is* durable and only the checkpoint
     is not.
   Nothing recoverable throws out of `evaluate()`; the caller branches on
   `kind`.
6. **The watchdog is honest about what it can and cannot do.** §9.6 callbacks
   are synchronous, so a callback that never returns cannot be preempted in
   process. What this runtime guarantees is that an **over-budget return** is
   discarded, recorded as a runtime skip, and pauses the instance. A genuinely
   wedged process is the composition root's process-level concern (WP-230
   health state). This is stated in the source, not only here.
7. **Determinism has no ambient inputs.** Time enters only as the injected
   logical `evaluatedAt` (which is what `ctx.now()` returns and what the record
   carries); randomness only through a per-run seeded generator (sfc32 over a
   cyrb128 fold of the run seed) whose state is carried in every checkpoint;
   and the watchdog's monotonic clock is an injected port whose readings live
   in `DecisionTelemetry`, never in `DecisionRecord`. That split is what lets
   the §12.4 byte-comparison be meaningful while still measuring evaluation
   latency (§10.3 `decisions.evaluation_duration_us` is nullable for exactly
   this reason).
8. **Checkpoints are versioned, and restore refuses rather than repairs.** A
   checkpoint pins the full run identity; restore returns a typed refusal on an
   unknown `checkpointSchemaVersion` and on every mismatch of run, instance,
   strategy name/version, state-schema version, config, or seed — and on
   non-canonical state bytes, because the store hashes those exact bytes (§10.3
   `state_checkpoints.state_hash`). State is also **rebuildable** without
   checkpoints: `rebuildStateFromPatches` is the fold of the persisted
   `statePatch` values, and a test asserts the fold reproduces the checkpointed
   bytes (§6 invariant 8 applied to strategy state).
9. **Persistence is a port, not a dependency** — see
   [`assumptions`](#assumptions) 1 for the §9.6/F12 justification of that
   boundary decision.

## assumptions

Every open semantic decision, with the justification it rests on. Each is a
place a reviewer can disagree.

1. **Persistence is a port the composition root binds — the boundary decision
   WP-170 was asked to record.** §9.6 requires the runtime to "persist exactly
   one `DecisionResult` per evaluation" and to "checkpoint strategy state after
   defined transitions", but the storage that satisfies those writes is
   `packages/storage-postgres`, which is **layer 2**
   (`dependency-direction.md` §2), and `packages/strategy-runtime` is **layer
   1**. A layer-1 → layer-2 edge is **F12**, forbidden always. The resolution
   §4 of that contract prescribes for exactly this shape ("if a layer-1
   application module ever needs the transport interface directly, the answer
   is to extract the interface … not to permit an upward edge") is applied
   here: the runtime declares `DecisionSink` and `CheckpointStore` as pure
   synchronous interfaces over plain data, and the trader app (WP-230, layer 3
   — the only layer where an adapter may meet an application module) implements
   them over the storage package and injects them. The runtime guarantees the
   exactly-once **call** discipline; the implementation guarantees durability;
   and the database's `unique (run_id, evaluation_seq)` key
   (`db/migrations/0004_strategy.up.sql`) backstops both. **Consequence to
   review:** WP-170 alone cannot prove a decision reached disk — only that
   `persist` was called exactly once. The database constraint and WP-230's
   binding complete the invariant.
2. **Both ports are synchronous.** §8.1: "The core loop must never wait on
   external I/O… The loop may synchronously append to a local journal/outbox
   only if benchmarked within the latency budget." An implementation needing
   slow I/O appends to a bounded local journal and drains it outside the loop.
   An `async` port would have forced `evaluate()` to be async, which would make
   the re-entrancy guard and the "exactly one" ordering far weaker claims.
3. **"Checkpoint after defined transitions" is read as: after every persisted
   decision record**, strategy- or runtime-attributed. This is a superset of
   any narrower "only when state actually changed" rule, and it keeps
   `checkpointSeq` aligned with `evaluationSeq` so a restore never re-uses an
   evaluation sequence number that already has a persisted decision. §9.6 does
   not enumerate the transitions; a narrower rule would have to invent them.
4. **`statePatch` is a shallow merge over a flat JSON object.** §7.5 types it
   `Record<string, unknown>` and calls it opaque to the domain; ADR-005 leaves
   the interpretation to the runtime. Shallow merge is chosen because it is the
   only rule under which `rebuildStateFromPatches` is a plain fold, which is
   what makes state rebuildable from the decision log. **Two consequences a
   strategy author must know:** a nested value must be rewritten whole, and
   **a key cannot be deleted** (the checkpointable grammar refuses `undefined`,
   so there is no tombstone). See [`known_risks`](#known_risks) 4.
5. **A decision must name the feature snapshot the evaluation actually saw.**
   `decision.featureSnapshotRef !== input.features.snapshotRef` is CONTAINED as
   an invalid decision. ADR-005 §2 makes `featureSnapshotRef` what "makes §6
   invariant 4's traceability chain complete"; a decision naming a different
   snapshot breaks the chain silently, which is worse than a loud skip.
6. **The `RUNTIME.` reason-code prefix is reserved in both directions.** A
   strategy-returned decision using it is CONTAINED. ADR-005 §3 forbids
   attributing a runtime action to the strategy; the mirror (a strategy
   impersonating the runtime) would corrupt decision analytics (§14.3) the same
   way. The four reserved codes satisfy the frozen `CodeString` grammar.
7. **`DecisionRecord.attribution` is a WP-170 field with no column in
   `strategy.decisions` today.** WP-040's table has no `attribution` column.
   The value is nonetheless recoverable from what *is* stored, because a
   runtime-attributed record always carries a reserved `RUNTIME.*` code in
   `reason_codes`. The composition root either maps it to reason codes or
   WP-040 adds a column. Recorded as [`follow_up`](#follow_up) 1 rather than
   assumed away.
8. **Run identifiers are bounded non-empty strings, not UUIDs.** §7.2 leaves
   `StrategyRunId` unformatted and ADR-005 §7 ratifies "bounded non-empty
   strings" for it, so inventing a format here would be a silent contract. But
   `strategy.runs.run_id` is `internal.uuid_v7`, so the *composition root* will
   supply UUIDs; the runtime therefore applies the ADR-016 rule to whatever it
   is given — a **UUID-shaped** value that is not canonical lowercase is
   refused with `RUN_IDENTITY_INVALID`, never case-folded. `run.runSeed` is
   validated strictly (`UnsignedBigIntStringSchema`), because §10.3 does pin
   `runs.run_seed` as `internal.uint_string`.
9. **`paramsSchema` is accepted structurally.** §9.6 says "JSON Schema/Zod" and
   types the field `unknown`. The runtime accepts anything exposing
   `safeParse(value) → { success, data?, error? }`, uses `data` when present and
   the raw params otherwise, and refuses anything else with
   `PARAMS_SCHEMA_UNSUPPORTED` rather than guessing. A JSON-Schema strategy
   wraps its validator in a two-line adapter.
10. **A contained failure PAUSES the instance permanently, from the runtime's
    point of view.** There is no `resume()`. §9.6 requires a new run for a code,
    config, model, feature, or state-schema change, and ADR-005 §3 requires the
    incident; resuming a paused instance is an operator decision, and expressing
    it as a runtime affordance would let a crash-looping strategy silently
    continue.
11. **A restored checkpoint restores its `status`.** Restoring a `PAUSED`
    checkpoint yields a paused instance that refuses to evaluate. The
    alternative — reviving it as `ACTIVE` — would erase the incident that paused
    it across a restart.
12. **Input validation is shallow and typed, not a re-validation of every view.**
    Identifiers, timestamps, the terminal-resolution vocabulary, and the
    per-callback payload are checked; book prices and position sizes are not
    re-parsed. Views are produced in-process by components that validated their
    own inputs against the frozen contracts, and §8.1 gives the core loop a
    latency budget; boundary re-validation belongs where untrusted bytes enter.
13. **Passing an `EvaluationInput` transfers ownership of the view objects.**
    The runtime deep-freezes them **in place** before the strategy can see them,
    which is how §7.6's "read-only" is made real rather than advisory. See
    [`known_risks`](#known_risks) 1 — this is the integration constraint most
    likely to surprise WP-230.
14. **A whitespace-only `onStop` reason is accepted.** Emptiness and the
    identifier length bound are enforced; blankness is not. Refusing the *input*
    would refuse the whole `onStop` evaluation and leave the instance unable to
    record its own stop, which is a worse outcome than a useless reason string.
    Pinned by a named test so it is a reviewed decision rather than a discovered
    one.
15. **An exactly-at-budget evaluation is not a timeout** (`durationUs >
    budget`, strictly). A budget is a limit, not an exclusive bound; pinned by a
    named test.
16. **The unit tests live in `test/unit/strategy-runtime/` and import each
    package through its own `exports` entry module by relative path.** This is
    the WP-150 precedent: the root test tree declares no dependency on workspace
    packages, and the root `package.json` is outside WP-170's `allowed_paths`.
    It is the entry point, not a deep import (F16). A consequence worth noting:
    the two packages take no `vitest` devDependency, which is why the lockfile
    delta contains workspace links only.
17. **`evaluationDurationUs` is truncated integer microseconds** from the
    injected nanosecond clock, and a non-monotonic clock reading yields `0`
    rather than a negative duration. It is telemetry, never part of the
    deterministic record.

## known_risks

1. **In-place deep-freezing of caller-supplied views is an integration
   constraint, not a local detail.** `buildStrategyContext` freezes the objects
   handed to it. If WP-230 (or the book/feature components) hands the runtime a
   view object it intends to keep mutating — an order-book instance updated in
   place, a reused snapshot buffer — the first evaluation will freeze the
   producer's own object and its next in-place write will throw in strict mode.
   The contract is stated in `input.ts` and in `assumptions` 13, but it is
   stated *here* too because it is the failure this package is most likely to
   cause somewhere else. *Mitigation for the composition root:* pass a fresh
   view per evaluation (what the tests do), or pass an explicit copy.
2. **The watchdog cannot preempt a non-returning callback.** Callbacks are
   synchronous by §9.6, so an infinite loop inside a strategy wedges the calling
   thread and no in-process budget can fire. Over-budget *returns* are contained
   and the instance is paused; a wedged process needs WP-230's process-level
   watchdog and health state. This is a real residual, stated in the source and
   not papered over.
3. **"Exactly one" is guaranteed at the call boundary, not at the disk.** A
   sink that silently retries internally, or a non-idempotent implementation,
   can still write twice; a sink that swallows its own error can write zero
   times and report success. The database's `unique (run_id, evaluation_seq)`
   is the backstop, and WP-230's binding is where it becomes end-to-end. WP-170
   pins the call discipline and the no-retry-on-throw rule.
4. **Strategy state cannot delete a key.** The shallow-merge fold plus the
   refusal of `undefined` (which does not survive a JSON round trip) means a key
   once written persists for the run unless overwritten with an explicit value —
   `null`, `false`, `""`. Strategies with a large or open-ended key space will
   accumulate state. A future tombstone convention is a checkpoint-schema
   version bump, which is exactly why the version exists.
5. **The purity pins are textual scans, not proofs.** The clock/randomness and
   dynamic-import pins in `package-boundaries.test.ts` are regexes over source
   with comments stripped; they catch the direct spellings, not an obfuscated
   acquisition. This is the same limitation the dependency contract states for
   its own check (§3, F14 consequence 2: "noisy, never silent"), and the
   authoritative mechanism for `packages/strategies/**` remains `check:deps`.
6. **The view contracts are a first cut and their producers do not exist yet.**
   `RiskBudgetView` (WP-180), `VirtualPositionView` (WP-200), `OrderBookView`
   (WP-150, merged), and `FeatureSnapshot` (WP-160) are consumed here as
   declarations. WP-160/180/200/220 will likely need fields that are not there.
   Each addition is an SDK change reviewed on its own merits; that is the
   intended cost of keeping the surface minimal, but it does mean WP-220 may
   land an SDK edit.
7. **`STRATEGY_SDK_CONTRACT_VERSION` is declared but nothing consumes it yet.**
   It is the hook for "a new run for every code change" at the interface level;
   until WP-230 records it in the run manifest, it documents rather than
   enforces.
8. **No golden replay artifact is produced by this package.** §12.4's CI golden
   replay is a cross-package concern (`pnpm test:replay` is still a
   `NOT IMPLEMENTED` placeholder). Determinism is pinned here by an in-process
   double run plus a seed-variation probe, which is strictly weaker than a
   committed golden artifact replayed across commits.

### H1.1 Reproduction (before any change)

### H1.2 Fix

`buildStrategyContext` now returns a `ScopedStrategyContext`
(`{ context, revoke }`) and `runtime.ts` revokes in a `finally` immediately
around the callback, so revocation happens on the returning path **and** the
throwing path:

```ts
try {
  returned = this.invokeCallback(input, scoped.context);
} catch (cause) {
  threw = true;
  thrown = cause;
} finally {
  scoped.revoke();
}
```

Every capability calls a shared guard **before** doing anything, including the
three RNG draw methods — so a refused draw cannot advance the generator. The
typed refusal is `StrategyContextRevokedError` in `outcomes.ts`, carrying
`code: "STRATEGY_CONTEXT_REVOKED"` and the `StrategyContextCapability` that was
reached for; both are exported from the package entry point.

**Why a throw, and why this code (the judgment call the reviewer asked for).**
This package's convention is that everything recoverable is a *returned* value.
That is impossible here: §7.6 freezes `SeededRandom.nextUint32(): number` and
every other context method as data-returning, so there is no return channel for
a refusal, and returning a fabricated number would *be* the defect. Throwing is
therefore the only fail-closed option, and it is now documented as the single
exception in the `outcomes.ts` header rather than left as a surprise. No new
reserved `RUNTIME.*` reason code was added, deliberately: a reserved code is for
attributing a *persisted decision record*, and the two places this throw can
land are already correctly modelled — inside a later callback the runtime's own
containment persists exactly one `RUNTIME.CALLBACK_THREW` skip whose detail
names the revoked capability (pinned by a test), and outside any callback there
is no evaluation in progress and therefore no record to attribute it to, so it
propagates to the out-of-band caller. Inventing a reason code for a situation
with no decision record would have made ADR-005 §3's vocabulary less honest,
not more.

### H1.3 Capability audit (the reviewer asked which others have the hazard)

Every capability on the context was audited for what it closes over:

| capability | closes over | hazard found | revoked |
| --- | --- | --- | --- |
| `rng`, `rng.nextUint32/nextFloat53/nextIntBelow` | the runtime's **mutable** `DeterministicRng` | **the determinism defect** — a post-return draw shifts the shared stream | yes |
| `state` | the state object as of context construction; the runtime *replaces* `this.state` on commit | silently **stale read** (a retained ctx answers with superseded state) | yes |
| `market`, `book`, `features`, `position`, `orders`, `riskBudget` | that evaluation's deep-frozen views | silently **stale read** of market data across evaluations | yes |
| `now` | that evaluation's logical `evaluatedAt` (immutable string) | silently **stale read** of logical time | yes |
| `params` | the instance's frozen params, identical for the run's whole life | **none found** | yes (uniformity) |

Only `rng` can perturb runtime state; the rest are read hazards. All ten are
revoked on the same discipline anyway, for two stated reasons: a stale read
should be loud rather than silent, and a capability added to this object later
inherits the guard instead of re-opening the hole. There is no checkpoint
capability on the context — `snapshot`/`restore` were never reachable from a
strategy, which the pre-existing `context.test.ts` already pins.

**Honest limit, recorded rather than glossed:** revocation withdraws the
*capability*, not copies of the immutable data already read through it. A
strategy may keep a frozen view object it obtained during its callback. That
object is deep-frozen plain data and cannot affect runtime state or the RNG
stream, so the determinism invariant holds; what it cannot prevent is a
strategy reasoning over data it knows to be old. Stated in `context.ts`.

End to end through the runtime, which the finding did not claim and which turns

```

[probe] runtime outcome: CONTAINED

[probe] contained detail: … did not return a valid §7.5 DecisionResult: [{ "code": "invalid_key", "origin": "record", …

```

So a *top-level* symbol key was already caught by the domain's
`z.record(z.string(), z.unknown())` (`invalid_key`), but a **nested** symbol key
passed the whole runtime: the evaluation was DECIDED, the symbol-keyed entry
rode the spread into live in-memory instance state, and the checkpoint bytes
dropped it. The live instance and any instance restored from that checkpoint
then disagree — a §12.4 replay divergence with no loud failure anywhere. M1 is
therefore a live runtime defect, not only a direct-caller hazard.

### M1.2 Rulings, one per form (all fail-closed)

| own-property form | ruling | reason |
| --- | --- | --- |
| symbol key (object or array, any depth) | **REFUSE** | invisible to `Object.keys`; dropped silently |
| non-enumerable property | **REFUSE** | same |
| accessor (getter and/or setter) | **REFUSE** | `JSON.stringify` persists a *computed* value that returns as a plain data property; a getter over mutable state can serialize differently on two passes over the same object — the exact §12.4 divergence these functions exist to prevent |
| non-index own property on an array | **REFUSE** | arrays serialize positionally; dropped silently |
| array hole | already refused (kept) | reading the index yields `undefined`, already rejected — and it must stay rejected: the canonical serializer emits the invalid text `[1,,3]`, which is now pinned by a test that `JSON.parse` throws on it |
| `length` on an array | allowed | the intrinsic, never a serialized key |

Implementation: the object walk enumerates with `Reflect.ownKeys` (not
`Object.keys`) and checks each own property's descriptor **before reading its
value**, so validating strategy state never invokes a getter; arrays get an
equivalent own-key check. `canonicalJsonStringify` is unchanged — its
documented precondition ("the caller must have validated first") is what makes
`Object.keys` sufficient there, and the header now says so explicitly instead
of leaving it implicit.

Over-refusal was checked, not assumed: ordinary state, `deepFreeze`d state,
`Object.create(null)`, frozen arrays and everything `JSON.parse` can produce
still validate, and a canonical checkpoint still restores (both pinned).

## assumptions (this round)

1. **A revoked capability must throw, not return.** Forced by the frozen §7.6
   signatures; documented as the package's one exception. See H1.2.
2. **No new reserved `RUNTIME.*` reason code.** A reserved code attributes a
   persisted decision record; the two landing sites are already modelled
   correctly (`CALLBACK_THREW` inside a later callback, propagation outside any
   evaluation). See H1.2.
3. **Uniform revocation of all ten capabilities**, though only `rng` is a
   determinism hazard: stale reads become loud, and future capabilities inherit
   the guard. See H1.3.
4. **Accessor properties are refused rather than snapshotted.** Calling the
   getter once and persisting the result would make the bytes depend on when
   validation ran; refusing is the fail-closed reading of "a value that changes
   identity when persisted is refused, not tolerated".
5. **Arrays may carry no own property other than in-range indices and
   `length`.** JSON serializes arrays positionally, so anything else is
   dropped; the rule is the array-shaped mirror of the object rule.
6. **The reviewer's constants belong to run seed `"1"`**, located by searching
   the sfc32 stream rather than assumed (H1.1). If the reviewer's scenario
   differed in some other way, the *values* still pin the same behavior: the
   pair is adjacent in the stream, which is exactly what a one-draw shift moves
   between.

## known_risks (this round)

1. **Revocation cannot un-share data already handed out.** A strategy may keep
   a frozen view object from an earlier callback and reason over stale market
   data. Determinism is unaffected (the objects are immutable and the RNG is
   unreachable through them), but the read is not prevented. Stated in
   `context.ts`.
2. **The throw lands wherever the out-of-band call was made.** Outside a
   callback there is no evaluation to contain it, so a composition root that
   calls a stale context in a background task sees an exception. That is the
   intended, loud behavior, but it is a behavior WP-230 must not swallow.
3. **The grammar is stricter than before, and `checkpointableJsonProblem` is
   exported.** Any existing direct caller passing an object with a
   non-enumerable or accessor property now gets a refusal where it previously
   got `null`. No such caller exists in the repository today (the only callers
   are `runtime.ts` and `checkpoint.ts`), and the refusal is the point, but it
   is a behavior change to an exported utility.
4. **`canonicalJsonStringify` still trusts its precondition.** It was left as a
   documented-precondition function rather than made self-validating, so a
   caller that skips validation can still produce lossy bytes. Making it
   re-walk would double the cost on the §8.1 hot path for a guarantee the
   runtime already enforces at the one place it matters.
