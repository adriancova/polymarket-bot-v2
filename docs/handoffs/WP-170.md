## summary

`packages/strategy-sdk` and `packages/strategy-runtime` replace their `WP-010`
placeholders with the handoff §9.6 strategy runtime and the §7.6 strategy
surface. Both are layer-1 application modules under
`docs/contracts/dependency-direction.md` §2: pure logic over the frozen layer-0
contracts, owning **no connection**.

1. **The strategy interface is the handoff's, verbatim.** `Strategy<TParams,
   TState>` declares the nine §9.6 callbacks with the exact signatures §9.6
   prints, and `StrategyContext` / `SeededRandom` are exactly §7.6. Nothing was
   added to either shape. The SDK also owns the read-only view types ADR-005 §6
   assigns to WP-170 rather than to the frozen domain package (`MarketView`,
   `OrderBookView`, `FeatureSnapshot`, `VirtualPositionView`,
   `StrategyOrderView`, `StrategyFill`, `ResolutionView`, `RiskBudgetView`,
   `SourceEventRef`), each deliberately narrow: every field is a contract the
   composition root must populate, so every widening is a reviewable SDK change
   rather than an accident.
2. **Versioning is explicit in three independent places**, because §9.6
   requires "a new run for every code, config, model, feature, or state-schema
   change" and those are different things: `strategy.name`/`version` (code),
   `strategy.stateSchemaVersion` (state shape),
   `STRATEGY_SDK_CONTRACT_VERSION` (the interface itself), and
   `STRATEGY_STATE_CHECKPOINT_SCHEMA_VERSION` (the checkpoint envelope).
3. **Exactly one persisted `DecisionResult` per invoked callback** (§6
   invariant 3), on every path: a valid decision, a no-op decision, a throwing
   callback, an over-budget callback, a returned value that is not a §7.5
   `DecisionResult`, a decision naming a feature snapshot this evaluation did
   not see, a decision claiming a reserved `RUNTIME.*` reason code, and a
   `statePatch` that is not checkpointable JSON. The first case persists a
   **strategy**-attributed record; the rest are CONTAINED as exactly one
   **runtime**-attributed `skip` with a reserved reason code and no intents
   (ADR-005 §3), the strategy's returned value is discarded, the RNG is rolled
   back to its pre-invocation state, and the instance is paused.
4. **A no-op decision is persisted like any other.** §9.6 says "persist exactly
   one `DecisionResult` per evaluation" without exception, and ADR-005 §2
   spells out the consequence: `intents` may be empty, and "no action is a
   recorded fact, not an absence". A `hold` with zero intents therefore takes
   the ordinary DECIDED path — one record, one checkpoint — and this is pinned
   by a named test rather than left to inference.
5. **Refusal is separated from containment, and both are separated from
   halting**, because they are different facts about an evaluation:
   - `REFUSED` — the callback was **never invoked** (paused/stopped instance,
     re-entrant call, invalid input), so §6 invariant 3 does not bind and **no**
     record exists. Nothing was evaluated, so nothing decided.
   - `CONTAINED` — the callback ran and misbehaved: exactly one
     runtime-attributed record, instance paused, incident reported.
   - `HALTED` — a persistence port threw. The write was attempted **exactly
     once** and is deliberately **not retried** (a write of unknown fate must
     not be blindly repeated — the §6 invariant 6 reasoning); the instance
     pauses and the outcome names which port failed, so a `SAVE_CHECKPOINT`
     halt tells the operator the decision *is* durable and only the checkpoint
     is not.
   Nothing recoverable throws out of `evaluate()`; the caller branches on
   `kind`.
6. **The watchdog is honest about what it can and cannot do.** §9.6 callbacks
   are synchronous, so a callback that never returns cannot be preempted in
   process. What this runtime guarantees is that an **over-budget return** is
   discarded, recorded as a runtime skip, and pauses the instance. A genuinely
   wedged process is the composition root's process-level concern (WP-230
   health state). This is stated in the source, not only here.
7. **Determinism has no ambient inputs.** Time enters only as the injected
   logical `evaluatedAt` (which is what `ctx.now()` returns and what the record
   carries); randomness only through a per-run seeded generator (sfc32 over a
   cyrb128 fold of the run seed) whose state is carried in every checkpoint;
   and the watchdog's monotonic clock is an injected port whose readings live
   in `DecisionTelemetry`, never in `DecisionRecord`. That split is what lets
   the §12.4 byte-comparison be meaningful while still measuring evaluation
   latency (§10.3 `decisions.evaluation_duration_us` is nullable for exactly
   this reason).
8. **Checkpoints are versioned, and restore refuses rather than repairs.** A
   checkpoint pins the full run identity; restore returns a typed refusal on an
   unknown `checkpointSchemaVersion` and on every mismatch of run, instance,
   strategy name/version, state-schema version, config, or seed — and on
   non-canonical state bytes, because the store hashes those exact bytes (§10.3
   `state_checkpoints.state_hash`). State is also **rebuildable** without
   checkpoints: `rebuildStateFromPatches` is the fold of the persisted
   `statePatch` values, and a test asserts the fold reproduces the checkpointed
   bytes (§6 invariant 8 applied to strategy state).
9. **Persistence is a port, not a dependency** — see
   [`assumptions`](#assumptions) 1 for the §9.6/F12 justification of that
   boundary decision.

## assumptions

Every open semantic decision, with the justification it rests on. Each is a
place a reviewer can disagree.

1. **Persistence is a port the composition root binds — the boundary decision
   WP-170 was asked to record.** §9.6 requires the runtime to "persist exactly
   one `DecisionResult` per evaluation" and to "checkpoint strategy state after
   defined transitions", but the storage that satisfies those writes is
   `packages/storage-postgres`, which is **layer 2**
   (`dependency-direction.md` §2), and `packages/strategy-runtime` is **layer
   1**. A layer-1 → layer-2 edge is **F12**, forbidden always. The resolution
   §4 of that contract prescribes for exactly this shape ("if a layer-1
   application module ever needs the transport interface directly, the answer
   is to extract the interface … not to permit an upward edge") is applied
   here: the runtime declares `DecisionSink` and `CheckpointStore` as pure
   synchronous interfaces over plain data, and the trader app (WP-230, layer 3
   — the only layer where an adapter may meet an application module) implements
   them over the storage package and injects them. The runtime guarantees the
   exactly-once **call** discipline; the implementation guarantees durability;
   and the database's `unique (run_id, evaluation_seq)` key
   (`db/migrations/0004_strategy.up.sql`) backstops both. **Consequence to
   review:** WP-170 alone cannot prove a decision reached disk — only that
   `persist` was called exactly once. The database constraint and WP-230's
   binding complete the invariant.
2. **Both ports are synchronous.** §8.1: "The core loop must never wait on
   external I/O… The loop may synchronously append to a local journal/outbox
   only if benchmarked within the latency budget." An implementation needing
   slow I/O appends to a bounded local journal and drains it outside the loop.
   An `async` port would have forced `evaluate()` to be async, which would make
   the re-entrancy guard and the "exactly one" ordering far weaker claims.
3. **"Checkpoint after defined transitions" is read as: after every persisted
   decision record**, strategy- or runtime-attributed. This is a superset of
   any narrower "only when state actually changed" rule, and it keeps
   `checkpointSeq` aligned with `evaluationSeq` so a restore never re-uses an
   evaluation sequence number that already has a persisted decision. §9.6 does
   not enumerate the transitions; a narrower rule would have to invent them.
4. **`statePatch` is a shallow merge over a flat JSON object.** §7.5 types it
   `Record<string, unknown>` and calls it opaque to the domain; ADR-005 leaves
   the interpretation to the runtime. Shallow merge is chosen because it is the
   only rule under which `rebuildStateFromPatches` is a plain fold, which is
   what makes state rebuildable from the decision log. **Two consequences a
   strategy author must know:** a nested value must be rewritten whole, and
   **a key cannot be deleted** (the checkpointable grammar refuses `undefined`,
   so there is no tombstone). See [`known_risks`](#known_risks) 4.
5. **A decision must name the feature snapshot the evaluation actually saw.**
   `decision.featureSnapshotRef !== input.features.snapshotRef` is CONTAINED as
   an invalid decision. ADR-005 §2 makes `featureSnapshotRef` what "makes §6
   invariant 4's traceability chain complete"; a decision naming a different
   snapshot breaks the chain silently, which is worse than a loud skip.
6. **The `RUNTIME.` reason-code prefix is reserved in both directions.** A
   strategy-returned decision using it is CONTAINED. ADR-005 §3 forbids
   attributing a runtime action to the strategy; the mirror (a strategy
   impersonating the runtime) would corrupt decision analytics (§14.3) the same
   way. The four reserved codes satisfy the frozen `CodeString` grammar.
7. **`DecisionRecord.attribution` is a WP-170 field with no column in
   `strategy.decisions` today.** WP-040's table has no `attribution` column.
   The value is nonetheless recoverable from what *is* stored, because a
   runtime-attributed record always carries a reserved `RUNTIME.*` code in
   `reason_codes`. The composition root either maps it to reason codes or
   WP-040 adds a column. Recorded as [`follow_up`](#follow_up) 1 rather than
   assumed away.
8. **Run identifiers are bounded non-empty strings, not UUIDs.** §7.2 leaves
   `StrategyRunId` unformatted and ADR-005 §7 ratifies "bounded non-empty
   strings" for it, so inventing a format here would be a silent contract. But
   `strategy.runs.run_id` is `internal.uuid_v7`, so the *composition root* will
   supply UUIDs; the runtime therefore applies the ADR-016 rule to whatever it
   is given — a **UUID-shaped** value that is not canonical lowercase is
   refused with `RUN_IDENTITY_INVALID`, never case-folded. `run.runSeed` is
   validated strictly (`UnsignedBigIntStringSchema`), because §10.3 does pin
   `runs.run_seed` as `internal.uint_string`.
9. **`paramsSchema` is accepted structurally.** §9.6 says "JSON Schema/Zod" and
   types the field `unknown`. The runtime accepts anything exposing
   `safeParse(value) → { success, data?, error? }`, uses `data` when present and
   the raw params otherwise, and refuses anything else with
   `PARAMS_SCHEMA_UNSUPPORTED` rather than guessing. A JSON-Schema strategy
   wraps its validator in a two-line adapter.
10. **A contained failure PAUSES the instance permanently, from the runtime's
    point of view.** There is no `resume()`. §9.6 requires a new run for a code,
    config, model, feature, or state-schema change, and ADR-005 §3 requires the
    incident; resuming a paused instance is an operator decision, and expressing
    it as a runtime affordance would let a crash-looping strategy silently
    continue.
11. **A restored checkpoint restores its `status`.** Restoring a `PAUSED`
    checkpoint yields a paused instance that refuses to evaluate. The
    alternative — reviving it as `ACTIVE` — would erase the incident that paused
    it across a restart.
12. **Input validation is shallow and typed, not a re-validation of every view.**
    Identifiers, timestamps, the terminal-resolution vocabulary, and the
    per-callback payload are checked; book prices and position sizes are not
    re-parsed. Views are produced in-process by components that validated their
    own inputs against the frozen contracts, and §8.1 gives the core loop a
    latency budget; boundary re-validation belongs where untrusted bytes enter.
13. **Passing an `EvaluationInput` transfers ownership of the view objects.**
    The runtime deep-freezes them **in place** before the strategy can see them,
    which is how §7.6's "read-only" is made real rather than advisory. See
    [`known_risks`](#known_risks) 1 — this is the integration constraint most
    likely to surprise WP-230.
14. **A whitespace-only `onStop` reason is accepted.** Emptiness and the
    identifier length bound are enforced; blankness is not. Refusing the *input*
    would refuse the whole `onStop` evaluation and leave the instance unable to
    record its own stop, which is a worse outcome than a useless reason string.
    Pinned by a named test so it is a reviewed decision rather than a discovered
    one.
15. **An exactly-at-budget evaluation is not a timeout** (`durationUs >
    budget`, strictly). A budget is a limit, not an exclusive bound; pinned by a
    named test.
16. **The unit tests live in `test/unit/strategy-runtime/` and import each
    package through its own `exports` entry module by relative path.** This is
    the WP-150 precedent: the root test tree declares no dependency on workspace
    packages, and the root `package.json` is outside WP-170's `allowed_paths`.
    It is the entry point, not a deep import (F16). A consequence worth noting:
    the two packages take no `vitest` devDependency, which is why the lockfile
    delta contains workspace links only.
17. **`evaluationDurationUs` is truncated integer microseconds** from the
    injected nanosecond clock, and a non-monotonic clock reading yields `0`
    rather than a negative duration. It is telemetry, never part of the
    deterministic record.

## known_risks

1. **In-place deep-freezing of caller-supplied views is an integration
   constraint, not a local detail.** `buildStrategyContext` freezes the objects
   handed to it. If WP-230 (or the book/feature components) hands the runtime a
   view object it intends to keep mutating — an order-book instance updated in
   place, a reused snapshot buffer — the first evaluation will freeze the
   producer's own object and its next in-place write will throw in strict mode.
   The contract is stated in `input.ts` and in `assumptions` 13, but it is
   stated *here* too because it is the failure this package is most likely to
   cause somewhere else. *Mitigation for the composition root:* pass a fresh
   view per evaluation (what the tests do), or pass an explicit copy.
2. **The watchdog cannot preempt a non-returning callback.** Callbacks are
   synchronous by §9.6, so an infinite loop inside a strategy wedges the calling
   thread and no in-process budget can fire. Over-budget *returns* are contained
   and the instance is paused; a wedged process needs WP-230's process-level
   watchdog and health state. This is a real residual, stated in the source and
   not papered over.
3. **"Exactly one" is guaranteed at the call boundary, not at the disk.** A
   sink that silently retries internally, or a non-idempotent implementation,
   can still write twice; a sink that swallows its own error can write zero
   times and report success. The database's `unique (run_id, evaluation_seq)`
   is the backstop, and WP-230's binding is where it becomes end-to-end. WP-170
   pins the call discipline and the no-retry-on-throw rule.
4. **Strategy state cannot delete a key.** The shallow-merge fold plus the
   refusal of `undefined` (which does not survive a JSON round trip) means a key
   once written persists for the run unless overwritten with an explicit value —
   `null`, `false`, `""`. Strategies with a large or open-ended key space will
   accumulate state. A future tombstone convention is a checkpoint-schema
   version bump, which is exactly why the version exists.
5. **The purity pins are textual scans, not proofs.** The clock/randomness and
   dynamic-import pins in `package-boundaries.test.ts` are regexes over source
   with comments stripped; they catch the direct spellings, not an obfuscated
   acquisition. This is the same limitation the dependency contract states for
   its own check (§3, F14 consequence 2: "noisy, never silent"), and the
   authoritative mechanism for `packages/strategies/**` remains `check:deps`.
6. **The view contracts are a first cut and their producers do not exist yet.**
   `RiskBudgetView` (WP-180), `VirtualPositionView` (WP-200), `OrderBookView`
   (WP-150, merged), and `FeatureSnapshot` (WP-160) are consumed here as
   declarations. WP-160/180/200/220 will likely need fields that are not there.
   Each addition is an SDK change reviewed on its own merits; that is the
   intended cost of keeping the surface minimal, but it does mean WP-220 may
   land an SDK edit.
7. **`STRATEGY_SDK_CONTRACT_VERSION` is declared but nothing consumes it yet.**
   It is the hook for "a new run for every code change" at the interface level;
   until WP-230 records it in the run manifest, it documents rather than
   enforces.
8. **No golden replay artifact is produced by this package.** §12.4's CI golden
   replay is a cross-package concern (`pnpm test:replay` is still a
   `NOT IMPLEMENTED` placeholder). Determinism is pinned here by an in-process
   double run plus a seed-variation probe, which is strictly weaker than a
   committed golden artifact replayed across commits.

### H1.2 Fix

`buildStrategyContext` now returns a `ScopedStrategyContext`
(`{ context, revoke }`) and `runtime.ts` revokes in a `finally` immediately
around the callback, so revocation happens on the returning path **and** the
throwing path:

```ts
try {
  returned = this.invokeCallback(input, scoped.context);
} catch (cause) {
  threw = true;
  thrown = cause;
} finally {
  scoped.revoke();
}
```

Every capability calls a shared guard **before** doing anything, including the
three RNG draw methods — so a refused draw cannot advance the generator. The
typed refusal is `StrategyContextRevokedError` in `outcomes.ts`, carrying
`code: "STRATEGY_CONTEXT_REVOKED"` and the `StrategyContextCapability` that was
reached for; both are exported from the package entry point.

**Why a throw, and why this code (the judgment call the reviewer asked for).**
This package's convention is that everything recoverable is a *returned* value.
That is impossible here: §7.6 freezes `SeededRandom.nextUint32(): number` and
every other context method as data-returning, so there is no return channel for
a refusal, and returning a fabricated number would *be* the defect. Throwing is
therefore the only fail-closed option, and it is now documented as the single
exception in the `outcomes.ts` header rather than left as a surprise. No new
reserved `RUNTIME.*` reason code was added, deliberately: a reserved code is for
attributing a *persisted decision record*, and the two places this throw can
land are already correctly modelled — inside a later callback the runtime's own
containment persists exactly one `RUNTIME.CALLBACK_THREW` skip whose detail
names the revoked capability (pinned by a test), and outside any callback there
is no evaluation in progress and therefore no record to attribute it to, so it
propagates to the out-of-band caller. Inventing a reason code for a situation
with no decision record would have made ADR-005 §3's vocabulary less honest,
not more.

### H1.3 Capability audit (the reviewer asked which others have the hazard)

Every capability on the context was audited for what it closes over:

| capability | closes over | hazard found | revoked |
| --- | --- | --- | --- |
| `rng`, `rng.nextUint32/nextFloat53/nextIntBelow` | the runtime's **mutable** `DeterministicRng` | **the determinism defect** — a post-return draw shifts the shared stream | yes |
| `state` | the state object as of context construction; the runtime *replaces* `this.state` on commit | silently **stale read** (a retained ctx answers with superseded state) | yes |
| `market`, `book`, `features`, `position`, `orders`, `riskBudget` | that evaluation's deep-frozen views | silently **stale read** of market data across evaluations | yes |
| `now` | that evaluation's logical `evaluatedAt` (immutable string) | silently **stale read** of logical time | yes |
| `params` | the instance's frozen params, identical for the run's whole life | **none found** | yes (uniformity) |

Only `rng` can perturb runtime state; the rest are read hazards. All ten are
revoked on the same discipline anyway, for two stated reasons: a stale read
should be loud rather than silent, and a capability added to this object later
inherits the guard instead of re-opening the hole. There is no checkpoint
capability on the context — `snapshot`/`restore` were never reachable from a
strategy, which the pre-existing `context.test.ts` already pins.

**Honest limit, recorded rather than glossed:** revocation withdraws the
*capability*, not copies of the immutable data already read through it. A
strategy may keep a frozen view object it obtained during its callback. That
object is deep-frozen plain data and cannot affect runtime state or the RNG
stream, so the determinism invariant holds; what it cannot prevent is a
strategy reasoning over data it knows to be old. Stated in `context.ts`.

End to end through the runtime, which the finding did not claim and which turns


So a *top-level* symbol key was already caught by the domain's
`z.record(z.string(), z.unknown())` (`invalid_key`), but a **nested** symbol key
passed the whole runtime: the evaluation was DECIDED, the symbol-keyed entry
rode the spread into live in-memory instance state, and the checkpoint bytes
dropped it. The live instance and any instance restored from that checkpoint
then disagree — a §12.4 replay divergence with no loud failure anywhere. M1 is
therefore a live runtime defect, not only a direct-caller hazard.

### M1.2 Rulings, one per form (all fail-closed)

| own-property form | ruling | reason |
| --- | --- | --- |
| symbol key (object or array, any depth) | **REFUSE** | invisible to `Object.keys`; dropped silently |
| non-enumerable property | **REFUSE** | same |
| accessor (getter and/or setter) | **REFUSE** | `JSON.stringify` persists a *computed* value that returns as a plain data property; a getter over mutable state can serialize differently on two passes over the same object — the exact §12.4 divergence these functions exist to prevent |
| non-index own property on an array | **REFUSE** | arrays serialize positionally; dropped silently |
| array hole | already refused (kept) | reading the index yields `undefined`, already rejected — and it must stay rejected: the canonical serializer emits the invalid text `[1,,3]`, which is now pinned by a test that `JSON.parse` throws on it |
| `length` on an array | allowed | the intrinsic, never a serialized key |

Implementation: the object walk enumerates with `Reflect.ownKeys` (not
`Object.keys`) and checks each own property's descriptor **before reading its
value**, so validating strategy state never invokes a getter; arrays get an
equivalent own-key check. `canonicalJsonStringify` is unchanged — its
documented precondition ("the caller must have validated first") is what makes
`Object.keys` sufficient there, and the header now says so explicitly instead
of leaving it implicit.

Over-refusal was checked, not assumed: ordinary state, `deepFreeze`d state,
`Object.create(null)`, frozen arrays and everything `JSON.parse` can produce
still validate, and a canonical checkpoint still restores (both pinned).

## H2.2 The fix: materialize, do not detect

Detection is the wrong shape of answer, and this is the judgment the reviewer
asked to see argued. A Proxy is not a value with a property one can test; it is
a *program* that answers questions. Whatever a trap answered during validation,
it may answer differently during freezing, serialization, or persistence — so
even a perfect "is this exotic?" predicate would only move the problem to the
first exotic value the predicate does not know about (a `Proxy` over a `Proxy`,
a host object, a future exotic). The reviewer's second option is the one that
closes the class:

**`materializeCheckpointableJson(value, path)`** validates and copies in one
walk. It reads every own key, descriptor and value **exactly once** and inside a
guard, and returns `{ ok: true, value }` where `value` is fresh plain data, or
`{ ok: false, problem }` naming the path. Consequences, each deliberate:

1. **The copy is what the runtime keeps** — state, checkpoint bytes, and the
   persisted `DecisionRecord`'s `statePatch`. The last one matters: the decision
   log is what `rebuildStateFromPatches` folds, so a record holding the
   strategy's live object while the checkpoint holds a copy of one reading of it
   would be exactly the divergence §6 invariant 8 forbids for strategy state. A
   copy that is validated and then discarded in favour of the original fixes
   nothing; this one is pinned by a test that asserts the persisted patch is not
   the strategy's object.
2. **A hostile trap can no longer throw out of the boundary.** Every
   caller-supplied operation — `Reflect.ownKeys`, `Object.getOwnPropertyDescriptor`,
   `Object.getPrototypeOf`, each value read, `length` — goes through one
   `attempt()` wrapper, so a throwing trap becomes a refusal with a stated path.
   `checkpointableJsonProblem` is now that same walk with the copy discarded,
   which is what stops the validator and the materializer from ever drifting
   apart, and it is total for the same reason.
3. **A lying trap can only lie into inert data.** Reading once means a
   two-faced proxy's *second* answer never exists as far as the runtime is
   concerned; the copy cannot change under the state, the bytes, or the sink.
4. **Over-refusal was checked, not assumed.** Ordinary JSON-shaped state, nested
   plain objects, arrays with ordinary indices, empty objects and arrays,
   `length` as an object key, `Object.create(null)`, `JSON.parse` output,
   deep-frozen values and every scalar all still pass, and the copy serializes
   **byte-identically** to the source under both `canonicalJsonStringify` (key
   order sorted) and `JSON.stringify` (insertion order) — the determinism
   property round 1 pinned survives the copying, and a test asserts it directly.
5. One implementation detail worth naming: the copy is built with
   `Object.defineProperty`, not assignment, so an own `__proto__` **data**
   property — which `JSON.parse` can produce and which JSON serialization does
   emit — lands as data in the copy instead of hitting the inherited setter.

## H2.4 The ordering audit (the half that is at least as important)

Every step between "the callback returned" and "the state is committed" was

| Step (round-1 site) | Can it throw on strategy-supplied data? | Round 1 | → Round 2 |
| --- | --- | --- | --- |

Two structural consequences, stated because they are the whole point:

- The commit block after `DecisionSink.persist` consists of assignments of
  values computed before it. **A persisted decision always gets its sequence
  number and its checkpoint.**
- `prepareDecision()` mutates nothing. A failure anywhere in it leaves the
  instance exactly as it was, which is what makes containment honest: exactly
  one RUNTIME-attributed skip, RNG rolled back, instance paused.

The `catch` around `prepareDecision` is belt to the materializer's braces: every
enumerated step returns its failure rather than throwing, and if some path not
yet enumerated throws anyway, it is still contained and attributed to the
strategy rather than escaping. Mutation M4 below shows the two layers failing
independently, which is the evidence that neither is decorative.

**The sequence invariant, stated exactly.** No two persisted records may share
an `evaluationSeq`. Every path that invokes a callback now either persists one
record and advances the sequence (`DECIDED`, `CONTAINED`) or fails in a
persistence port and leaves the instance `PAUSED` (`HALTED`), and a paused
instance refuses every further evaluation without a record. The one asymmetry is

## assumptions (this round)

1. **Materialization, not detection.** Argued in [H2.2](#h22-the-fix-materialize-do-not-detect):
   an exotic value's answers are not a property one can test for, so the
   boundary copies instead of interrogating. The reviewer's remediation text
   permits either; this is the one that closes the class rather than the
   instance.
2. **The persisted record carries the materialized copy, not the strategy's
   object.** Required for the durable log and the checkpoint to agree, since
   `rebuildStateFromPatches` folds the record's `statePatch`. The observable
   consequence: `record.decision.statePatch` is a frozen copy, so a caller
   comparing it by identity to the object its strategy returned will find them
   different (they are `toEqual`, never `toBe`).
3. **A validated-but-kept original is not a crossed boundary.** Hence
   `checkpointableJsonProblem`'s documented meaning and the extension to round
   1's `known_risks` 3, rather than a silent behavior change.
4. **An unfreezable input view is an INPUT refusal, not containment.** The
   callback was never invoked, so §6 invariant 3 does not bind and no record may
   be persisted; `REFUSED`/`INPUT_INVALID` is the existing vocabulary for
   exactly that situation, so no new code was invented.
5. **A `HALTED` at `PERSIST_DECISION` still does not consume the sequence.**
   Pre-existing, deliberate, and now pinned: the write's fate is unknown and is
   not retried, and the no-duplicate guarantee there comes from the instance
   being unusable afterwards, not from the counter.

## R3.3 The HIGH: acquire one snapshot, then use it everywhere

`acquireEvaluationInput(input)` (in `input.ts`) does three things in one order
that matters:

1. **materialize** the whole input under the evaluation-view grammar — every own
   property read exactly once, inside a guard, into fresh plain data;
2. **deep-freeze** that copy (it is the runtime's own data by then, so freezing
   it can neither run caller code nor fail);
3. **validate** the copy with the same shallow, typed checks as before.

`evaluate()` then passes the snapshot — and only the snapshot — to
`buildStrategyContext`, `invokeCallback`, `buildRecord` and `buildCheckpoint`.
The reviewer's NOTE was followed exactly: materialization, not refusal, is the
right shape, so a view that merely refuses to be frozen is now DECIDED rather
than REFUSED (its target is never touched), and only a view the runtime cannot
READ is refused.

**The evaluation-view grammar, and why it differs from the checkpointable one.**
The two walks share one implementation and differ on four documented axes:
`undefined` (views use it for an absent optional; checkpoint bytes cannot
represent it), non-finite numbers (a view may carry one; `NaN` in state is a
replay divergence), ACCESSORS (accepted for views — the getter is invoked
exactly once inside a guard and the result is copied, which closes the
divergence hazard without refusing a producer that exposes a computed view;
still refused for checkpointable state, where the round-1 M1 ruling stands
untouched), and per-key descriptor reads (see the benchmark below). Symbol keys
and non-enumerable properties are refused by BOTH: a view the runtime cannot
represent is refused loudly rather than silently truncated.

**What this replaces.** The runtime no longer freezes the caller's view objects
in place. That was round 1's `assumptions` 13 / `known_risks` 1 and the source
of the BINDING OBLIGATION on WP-230 to pass fresh-or-copied views with an
integration test proving it. That obligation is now **discharged by
construction** — copying is the mechanism, and `frozen=false` in the re-probe
below is the evidence. The obligation text is preserved in `input.ts` as
SUPERSEDED TEXT rather than deleted.

## R3.4 MEDIUM 1: total means total

Three independent fixes, plus the attribution:

1. **`Array.isArray` is inside the guard.** Round 2's comment ("pierces a Proxy
   to its target and cannot be trapped, so it is safe to branch on") was true
   about traps and false about revoked proxies. Corrected in place, dated.
2. **`describeCause` moved to `describe.ts` and made total.** `instanceof`, the
   `message` accessor and `String()` can each run caller code; the last resort
   is `typeof`, the only operation that cannot. Every "never throws" path in the
   package now formats through this one function, so the property cannot drift
   between modules.
3. **Depth: an iterative walk AND a documented bound, deliberately both.** The
   dispatch asked for one and for the choice to be justified. The walk (and
   `canonicalJsonStringify`, and `deepFreeze`) is now iterative over an explicit
   heap stack, because a function that promises never to throw must not depend
   on how much stack the host happens to have. The bound
   (`MAX_MATERIALIZED_DEPTH = 64`, exported) exists for a different reason: it is
   a CONTRACT this boundary owes the consumers it does not control — V8's
   `JSON.stringify`/`JSON.parse`, PostgreSQL's `jsonb` under `max_stack_depth`,
   any future recursive reader — and an accepted-but-unbounded value would only
   move the `RangeError` somewhere the runtime cannot contain it. 64 is far
   beyond any legitimate strategy state (a `statePatch` is a shallow record of
   scalars) and beyond the deepest structure any view contract describes (four
   containers: input → books → yes → bids → level), and the refusal names the
   path, which is a bug report rather than a crash.
4. **Attribution is per REGION.** `prepareDecision` now guards the
   decision-reading region (`RUNTIME.DECISION_INVALID`) and the
   statePatch-materialization region (`RUNTIME.STATE_PATCH_INVALID`)
   separately. The outer `catch` in `runEvaluation` survives as a belt and is
   documented as such.

## Performance: measured, not asserted

Materialization is a new per-evaluation cost, so it was measured rather than
argued about (the precedent WP-200's round-2 remediation set). Method: the same
`/dev/shm` mirror technique, two trees — `base` at `15e032f` and `tip` at this
round's sources — running an identical benchmark file that evaluates 5,000
pre-built inputs through a real runtime with no-op ports, median of five timed
runs inside the process, and the whole thing repeated three times per tree to
see the machine's noise (which is real: individual runs varied by up to 50%).

| Input shape | base `15e032f` | this round | delta |
| --- | --- | --- | --- |
| 2 book levels/side, no orders, 10 features (≈ 15 objects) | 8.24 µs/evaluation | 18.12 µs/evaluation | +9.9 µs |
| 20 book levels/side, 5 orders, 10 features (≈ 55 objects, ~150 properties) | 26.26 / 26.07 / 31.34 µs (medians of three repetitions) | 63.42 / 66.01 / 63.78 µs | ≈ +37.5 µs |

So the copy costs roughly **0.25 µs per property**, and the total scales with
view size rather than with anything the runtime controls. Two things were done
about it, both measured:

- the evaluation-view grammar checks enumerability with one `Object.keys` +
  `Reflect.ownKeys` comparison per object instead of one descriptor read per
  key, and copies with assignment (except for an own `__proto__`, which still
  needs `defineProperty`). Measured effect on the large input: **118.0 →
  65.2 µs/evaluation**;
- the walk holds its pending child in two locals instead of an object.

The checkpointable grammar keeps the per-key descriptor read: refusing an
accessor WITHOUT invoking its getter is a round-1 property with its own test,
and `statePatch` values are small.

Honest reading of the number: a strategy evaluation now costs ~38 µs more on a
40-level book than it did, in a loop whose own budget is the injected watchdog
(1 ms in these tests). That is the price of the callback and the durable record
agreeing about what they saw. It is `known_risks` 3 below, and the actionable
form for WP-230 is: **the cost is proportional to the size of the views you
pass**, so pass the levels a strategy actually needs.

## R4.2 HIGH 1 — the guard route, chosen deliberately over the exact-type route

**The invariant, stated once:** every value the evaluation counter holds is an
exact integer, and every increment of it is exact. `MAX_EVALUATION_SEQ =
Number.MAX_SAFE_INTEGER - 1` (exported from `checkpoint.ts`) is the last
sequence a record may carry, because its successor — the instance's next
sequence — is exactly `Number.MAX_SAFE_INTEGER`, the largest value for which
the counter's arithmetic is still injective.

Two enforced bounds, pinned at exactly the pair the dispatch named:

1. `restoreCheckpoint` refuses `checkpointSeq > MAX_EVALUATION_SEQ` with
   `CHECKPOINT_SEQ_INVALID`. `MAX_SAFE_INTEGER - 1` is accepted (successor
   `MAX_SAFE_INTEGER`, exact); `MAX_SAFE_INTEGER` is refused (successor not
   representable). The older "non-negative safe integer" rule still catches
   `2^53` and above, with its own message.
2. `evaluate()` refuses `EVALUATION_SEQ_EXHAUSTED` when
   `this.evaluationSeq > MAX_EVALUATION_SEQ`. The check runs **before** the
   input is acquired and before any callback, so nothing is evaluated, §6
   invariant 3 does not bind, and no record is owed.

**Why `number` and not an exact type.** The dispatch asked for a deliberate
choice. `checkpointSeq` travels inside a checkpoint DOCUMENT and
`DecisionRecord.evaluationSeq` inside a record, both of which the composition
root serializes as JSON — and this package's own checkpointable grammar refuses
`bigint` with the words "bigint is not representable in JSON". Making the
counter a `bigint` would put the runtime in contradiction with the boundary it
enforces on everyone else; a canonical decimal STRING would change a §10.3
column mapping and every consumer's comparison, to buy range no run can reach
(at one evaluation per millisecond, `2^53 - 1` sequences is ~285,000 years).

**What happens at exhaustion, and the proof it cannot silently continue.** The
instance stays `ACTIVE` — nothing failed — and every further `evaluate()`
returns `REFUSED / EVALUATION_SEQ_EXHAUSTED` with no record, no checkpoint and
no callback. The condition is monotone in a counter that only grows, so it
cannot un-trip; the only way past it is a new run, which is what §9.6 says a
finished run needs. Pinned by a test that calls `evaluate()` five more times
after exhaustion and asserts zero persists, and by a test that restores one
sequence below the bound, consumes it exactly once, and is refused thereafter.
A restored instance sitting exactly at `nextEvaluationSeq =
Number.MAX_SAFE_INTEGER` is legal and immediately exhausted; that is not an
inconsistency but the same rule read twice, and it has its own test.

## R4.3 HIGH 2 — the params ownership grammar

**Round 3's two "deliberate non-applications" are withdrawn.** They are quoted
and answered in `Corrections` below. What replaces them:

`json.ts` gains a THIRD grammar, `IMMUTABLE_PARAMS`, and `createStrategyInstance
Runtime` materializes the parsed params through it before freezing them. The
grammar differs from the other two on exactly the axes that matter:

| Axis | checkpointable state | evaluation view | **immutable params** |
| --- | --- | --- | --- |
| `undefined` | refused (no JSON form) | accepted (absent optional) | **accepted** — a schema may leave an optional field unset, and params never become bytes |
| non-finite numbers | refused (replay divergence) | accepted | **accepted** — same reason |
| accessors | refused | accepted (read once) | **refused** — `ctx.params()` is read inside callbacks; a getter is a value recomputed per read, which is the reviewer's `reads=5` |
| `Map`/`Set`/`Date`/class instance | refused (prototype rule) | refused | **refused** — internally mutable, and freezing the wrapper does nothing |
| `Proxy` over a plain object | copied | copied | **copied** — materialization, not detection |

A params value that cannot be read into a copy is the new typed creation refusal
`PARAMS_NOT_MATERIALIZABLE`, whose detail names the path and the offending form.

**No implicit escape hatch, and why none is needed.** The dispatch allowed an
explicit typed one. None was added, because every escape hatch reopens exactly
the determinism hole the reviewer proved, and because the refusal is not
over-refusal on this repository's own terms: §9.6 params ARE the immutable
configuration record, §10.3 stores them as `strategy.configs` — JSON — and a
config that cannot round-trip through JSON is not a config record. A strategy
that wants a derived structure (a compiled matcher, a `Map` index) builds it in
`onStart` from the materialized params and keeps it **on its own object**: the
runtime applies every callback with `Reflect.apply(fn, strategy, args)`, so
`this` is the strategy and its fields are its own business. That alternative is
written in `outcomes.ts` next to the refusal code, so an author who hits the
refusal is told what to do instead. It is disclosed as `deviations` 3 and
`known_risks` 2.

**What the context now hands out.** `ctx.params()` returns the runtime's own
deep-frozen copy. Round 3's claim that the context "returns data the runtime
already owns" is true as of this round and was not true when it was written.

## R4.5 MEDIUM 2 — the patch is isolated in the DATA, not only in the control flow

Round 3 put the decision region and the patch region in different `try` blocks.
That is not enough when the schema traversal in the FIRST region walks the
value the SECOND region owns: `statePatch: z.record(z.string(), z.unknown())`
enumerates the patch's own keys.

`isolateStatePatch(returned, callback)` (new, in `runtime.ts`) runs first and
does three things:

- reads the returned value's own enumerable string keys ONCE (`Object.keys`,
  guarded) and each value ONCE, into a fresh plain object;
- holds `statePatch` aside instead of copying it in, so the schema never sees
  it;
- attributes its own failures by key: a throw while reading `statePatch` is
  `STATE_PATCH_INVALID`; a throw while enumerating, or while reading any other
  field, is `DECISION_INVALID`.

`Object.keys` rather than `Reflect.ownKeys` is deliberate: it is exactly what
the strict object schema itself can see, so the copy neither hides an
unrecognized key nor invents one. An own `__proto__` is placed with
`defineProperty` rather than assignment, or the copy would be silently
re-parented and the schema would then find required fields on a prototype the
strategy supplied — that consequence has its own test and its own mutation
(M12).

The shape rule the domain schema used to apply (`statePatch` must be a record)
now applies to the **materialized copy**, under the patch attribution, where the
answer cannot change afterwards. Consequence, disclosed: a non-record
`statePatch` is now `RUNTIME.STATE_PATCH_INVALID` rather than
`RUNTIME.DECISION_INVALID`. That is the finding's own rule — a bad patch is a
patch problem — and no existing test asserted the old code.

Side effect worth naming: the patch is now traversed exactly once instead of
twice (Zod's record walk, then the boundary's). That is measured, not assumed —
a trap-counting test asserts `ownKeys` = 1 and `get` = 2 for a two-property
top-level patch proxy.

- `{ success: true, data: X }` — `data` is present, so `X` is the parsed params,

## Performance: measured, not asserted

Same method as round 3 (`/dev/shm` mirrors, `base` at `bed2f1c` extracted with
`git archive`, `tip` at this round's sources, an identical benchmark file in
both, 5,000 pre-built inputs through a real runtime with no-op ports, median of

**Evaluation path — no measurable regression.** Medians of five, per repetition:

| --- | --- | --- |
| 2 levels/side, 0 orders, 10 features | 20.84 / 20.59 / 21.75 µs | 23.18 / 20.80 / 21.33 µs |

Honest reading: the differences are inside the machine's own noise band — the

medians is 20.84 → 21.33 µs (small) and 76.72 → 75.48 µs (large). That is what

statePatch isolation REPLACES Zod's traversal of the patch with one guarded read
(the boundary walk happened before and still happens), so it removes work rather

busier, which is why base and tip were measured interleaved on the same machine

| Params shape | base `bed2f1c` | this round | delta |
| --- | --- | --- | --- |
| ~15 properties (10 flags + scalars + a 5-element array) | 3.94 µs/creation | 8.40 µs/creation | **+4.5 µs** |

the number is better than saying it is negligible.

## assumptions (this round)

1. **Params are configuration, and configuration is JSON.** §9.6 calls them
   immutable configuration and §10.3 stores them as a `strategy.configs` record,
   so a params value that cannot be materialized into plain data is refused
   rather than exempted. The derived-structure case is answered by the strategy
   object's own fields, not by an escape hatch.
2. **A params value may hold `undefined` and non-finite numbers.** They never
   become bytes, so the two rules that protect bytes do not apply, and applying
   them would refuse a schema that legitimately leaves an optional field unset.

   the instance is not paused and no record is owed; the run is simply over.

## R5.2 M5-1 — the enumeration is RESOLVED now, and fails closed

`test/unit/strategy-runtime/boundary-derivation.ts` (new) builds one
`ts.Program` over both packages' sources with the repository's own compiler
options and asks the type checker for each module's exports
(`getExportsOfModule`), resolving alias chains with `getAliasedSymbol`. That
single change closes the `export *`, alias, export-clause-only and barrel rows:
those are not four cases to recognize, they are one question — *what does this
module export?* — answered by the compiler.

What it enumerates, and the four reachability rules:

1. **module export** — every value a module exports: functions, callable
   constants, classes;
2. **class member** — every non-private member of an enumerated class:
   constructor, statics, methods, **property functions** (`run = (v) => …`),
   **getters and setters**;
3. **object property** — every callable property of an enumerated object value,
   recursively (`export const api = { method(v) {…} }`), depth-bounded;
4. **handed out** — the members of a type in the RETURN position of an
   already-enumerated callable, when that type is declared in these packages.

Rule 4 is the one that pays for itself: `StrategyContext.book(outcome)` and the
draw-only `SeededRandom` facade are closures built inside `buildStrategyContext`
and reachable from no exported name, yet they are the capabilities a STRATEGY
calls with its own data. Parameter types are deliberately not followed —
`DecisionSink`, `CheckpointStore`, `MonotonicClock` and `Strategy` are
implemented by the composition root and by strategy authors, so classifying
their totality would be a claim about code that does not live here. The fixture
pins both directions: an interface this package returns is enumerated, an
interface it only ever takes as a parameter is not.

**Visibility is derived, and PUBLIC wins.** A callable is PUBLIC when its symbol
is exported as a VALUE from an entry point, or when it belongs to a class or
interface whose TYPE an entry point exports, or when a PUBLIC callable returns
it. A class exported only as a type has PUBLIC instance members (an instance can
escape through a factory) and a PACKAGE constructor and statics (`new` and
`C.f()` need the value). When two paths disagree the entry is PUBLIC:
over-classifying costs a fuzz obligation, under-classifying costs a defect.

**Fail closed.** Anything the walk cannot classify — a call signature with no
declaration, an unrecognized callable declaration kind, a non-class value with
construct signatures, a callable still below `MAX_SURFACE_DEPTH = 8` — becomes
an `unresolved` entry, and a test asserts that list is empty. The fixture's
`unclassifiable/` package exercises it: `export const C: { new (v): … } = class
{ … }` is refused by name, and produces no silent "internal" entry.

Two guards on the resolution itself, because a resolution is only as good as its
program: `diagnostics` (type errors in our files, asserted empty) and
`foreignWorkspaceResolutions` (a `@polymarket-bot/*` import that lands outside
the tree — a second copy of a workspace package, which would make half the
surface look like somebody else's code). The second is not theoretical: running
this suite inside a `/dev/shm` mirror whose `node_modules` symlink back to the
worktree produces exactly that, and the guard names it —
`packages/strategy-runtime/src/context.ts: @polymarket-bot/strategy-sdk resolved
OUTSIDE the tree, to …/packages/strategy-sdk/src/index.ts` — instead of the
bare `expected 31 to be greater than 40` it would otherwise have printed. It is
also why this round's mutations ran in the worktree rather than in a mirror
(`deviations` 3).

## R6.2 M6-1 — the return-position walk is total now, and refuses by name

`visitHandedOut` used to be four lines of intent: split unions, require the
returned type's own SYMBOL to be ours, call `visitProperties`. It is now total
over the type, and every branch ends in an entry or a refusal:

1. **Call signatures on the handed-out type are recorded**, as
   `X (returned)`, with a new `CallableShape` of `returned callable`. That is
   what puts `makeHandler(): (value) => string` on the list, and the getter of
   shape 2, and the callable interface a callable `Proxy` is handed out under —
   the reviewer's note that "a callable Proxy would inherit the same omission".
   Named by the SITE, because `makeHandler()` is the expression a probe
   evaluates to reach it. Recursion is depth-bounded, so two hops give
   `X (returned) (returned)`.
2. **Conditional types are expanded**, through `ConditionalRoot.node` (public
   API), into both branch types — `Left.left` and `Right.right` are now
   enumerated under their own declaring interfaces. A conditional that cannot be
   expanded is a named refusal, not a skip.
3. **Type parameters become their base constraint.** An unconstrained `T`
   (`params<T>(): Readonly<T>`) carries no callable of ours — it is the caller's
   type — so it contributes nothing, and that is an answer rather than a
   silence.
4. **Index signatures whose value type carries a callable are REFUSED by
   name**: `CallableIndex[string]`. This follows the reviewer's instruction
   literally — "emit `unresolved` where no concrete callable name can be
   driven". There is no key, so there is no expression the battery could call,
   and a synthetic id would put an entry in the registry that no probe can
   drive. That would be a worse lie than the silence it replaced.
5. **A foreign container's type arguments are refused the same way**:
   `readonly Fn[]`, `Promise<Facade>`, `ReadonlyMap<string, Facade>`. An element
   has an index, not a name. Our OWN generics are exempt, because
   `visitProperties` already walks their instantiated members, so refusing there
   would be a false alarm.
6. **A handed-out constructible** is walked as a class when it is one of ours
   and refused otherwise — the same rule `visitValue` has applied since round 5,
   now applied on the return path too.
7. **`MAX_SURFACE_DEPTH` refuses instead of returning.** It used to `return`
   silently on the handed-out path, which truncated a chain of returned facades
   with no trace at all.
8. **The returned type's own symbol no longer has to be ours.** It did, and that
   is the finding with a live analogue — see `R6.3`.

The cost of this shape is **over-refusal, never under-enumeration**: a container
of a NAMED facade is refused even though its members could have been named. That
is the same trade the visibility rule has always made — over-classifying costs a
fuzz obligation, under-classifying costs a defect — and a refusal is a loud,
reviewable stop.

## R7.2 M7-3 — the handed-out class, and the four distinctions

`visitClass` takes a third argument now: how the class VALUE reached the caller.
`visitReturnedConstructible` passes the visibility the handed-out walk has
already derived, so `abstractClassFactory(): typeof AbstractHandedOut` makes the
class value public in exactly the way `new C(x)` and `C.f(x)` need. The four
cases the finding named, and the answer each gets:

| on a class value the caller holds | answer | why |
| --- | --- | --- |
| a **concrete constructor** | PUBLIC `constructor` | `new C(x)` is the caller's to make, with the caller's argument, running our body |
| an **abstract constructor** | PUBLIC `abstract constructor` | `new C(x)` will not compile — but `class S extends factory() {…}; new S(x)` reaches this body through `super(...)`, still with the caller's argument. Over-classifying costs a fuzz obligation; under-classifying costs a defect. The distinct SHAPE tells whoever wires the probe that the call has to go through a subclass |
| a **concrete prototype implementation** | PUBLIC | the body is ours, the argument is theirs; an instance escapes through `new`, through a subclass, or through a static factory |
| an **abstract declaration** | PACKAGE `abstract declaration` | there is no body here. Calling it runs the CALLER's subclass, which is the ruling review round 6 confirmed for `DecisionSink`, `CheckpointStore`, `MonotonicClock` and `Strategy`. It is enumerated BY NAME anyway — absence from both lists is the outcome this mechanism may not have — and PACKAGE is what keeps it out of the battery without hiding it |

Three further details the fix needed, each of which is its own mutation below:

- **The visited-class guard is keyed by the derived visibilities**, not by the
  symbol. A class exported from a package module and handed out by a public
  factory is met TWICE, package-internally first if the file order runs that
  way, and round 6's guard made the first reading final. The fixture's
  `TwiceReachedClass` is declared in `classes.ts` and handed out from
  `twice-reached.ts` precisely so the walk meets it in that order.
- **An abstract member is recognized by its modifier**, wherever it is met —
  method, accessor pair, or callable property — so no later path can re-record
  it as a concrete implementation of ours. An abstract property that is not
  callable (`abstract readonly tag: string`) is not a callable and contributes
  nothing, the same as every other data property.
- **`prototype` is skipped** on the synthesized-property path added for M7-1.
  A class's instance side is `visitClass`'s business, and that is the only place
  which can make the abstract/concrete distinction above.

## R7.4 M7-2 — a predicate that cannot say "I do not know"

The cheap, decisive fix the finding asked for. `carriesCallables` returned a
boolean, and a boolean has no room for *I ran out of depth before I could tell*,
so `depth > MAX_SURFACE_DEPTH → false` and every caller read that as *there is
nothing there*. `CallableVerdict` is `"none" | "callable" | "indeterminate"`
now; `indeterminate` propagates out of any branch that truncates, and all four
call sites refuse by name for it, with a message that says the BOUND is the
reason rather than the type:

```
DeepIndex[string]
  an index signature whose value type could not be shown callable-free within
  MAX_SURFACE_DEPTH (8): a callable may sit below the bound, and an index has no
  name to drive it with either way…
deepContainerFactory (returned) (type argument 1 of Promise<Deep0>)
  a container declared outside these packages whose type argument could not be
  shown callable-free within MAX_SURFACE_DEPTH (8)…
Deep7.next
  the surface walk reached MAX_SURFACE_DEPTH (8) and the predicate that looks
  below it ran out of depth too, so this branch cannot be shown callable-free…
```

Two things worth stating about the shape of the fix:

- **The distinction is preserved, not merged.** A refusal that hedges everything
  is as useless as one that hedges nothing, so "I found a callable" and "I could
  not tell" keep separate wordings, and the new test asserts both.
- **`seen` memoizes the DEPTH** at which a type was explored rather than merely
  that it was. Without that, a type first met near the bound (and truncated
  there) would hand its truncation to a later, shallower path that had the
  budget to look properly. This is a precision refinement, not a silence fix:
  both readings refuse. It is disclosed as an unkilled mutation (`P6`) rather
  than claimed as more.

`Deep7.next` deserves one more sentence: the `visitMember` depth bound had NO
fixture before this round, in either variant, because the only fixture that ever
reached a depth bound went through the handed-out path (`Hop3.hop (returned)`).

## R7.5 M7-1 — the remapped name is a real name

`Readonly<T>` keeps each property's original declaration, which is why round 6's
`MappedFacade.mapped` worked. A remapping clause does not: the compiler
synthesizes a fresh symbol with a NEW NAME and no declaration anywhere, and
`visitProperties` gated on `isOurs`, which needs one. Measured directly with the
compiler API before choosing the fix:

```
returned: Remapped<RemapSource>
  prop renamed_handler: declarations=0  type=(value: unknown) => string
                        callSignatures=1  sigDecl=MethodSignature@index.ts   ← ours
  prop renamed_tag:     declarations=0  type=string  callSignatures=0
```

That is what settled enumeration versus refusal. The name is accessible and a
caller can drive it — `remappedFactory().renamed_handler(value)` — and the
compiler still knows the type, whose call signature is declared right here. So
the walk follows synthesized properties through `getTypeOfSymbol` and enumerates
them under their actual remapped name, reusing `visitValue` so that the
parameters and the shape come from the ORIGINAL declaration (`(value)`,
`declared method`) rather than from anything invented here. The refusal is kept
for the one case where enumeration would be a lie: a synthesized property whose
OWN call signature is declared outside these packages, with one of ours
underneath it — the walk neither claims somebody else's implementation nor
passes over ours.

The same `declarations.length === 0` branch is mirrored inside
`carriesCallables`, so the predicate and the enumeration agree about what is
down there — the property round 6 claimed for the depth bound, and which this
round makes true for synthesized properties too.

## assumptions (this round)

1. **A class VALUE in a caller's hands is a public boundary in all four of its
   parts.** Holding `typeof C` gives a caller `new C(x)`, `C.f(x)`, every

   the shape read from the declaration the compiler mapped it from.

5. **Everything rounds 1–6 assumed still holds**, in particular the

   exported TYPE makes instance members public, that `TOTAL` is a claim about
