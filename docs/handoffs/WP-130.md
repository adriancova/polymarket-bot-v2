## summary

`WP-130` delivers the second half of the first production deliverable (§0.1):
the WAL records without silent gaps, and this package turns those recordings
into **replayable, checksummed datasets**.

Four artifacts:

1. **`packages/storage-parquet`** — the compactor. It reads *verified* WAL
   segments through its own reader of the published on-disk format, transforms
   them into a columnar layout that preserves every byte, writes checksummed
   Parquet objects, reads each object back out of the store to verify it, emits
   an immutable dataset manifest, and only then permits retention to delete a
   WAL segment.
2. **`apps/research-worker`** — the runnable process. Config, scheduling loop,
   typed metrics including §14.3's compaction lag and object upload status, and
   a graceful shutdown that finishes the cycle in flight.
3. **`python/research/compaction`** — the DuckDB validation job. It re-opens a
   written dataset with an independent Parquet implementation and reconciles it
   against its manifest: counts, checksums, layout, ordinals, deduplication,
   incident exclusions, and payload digests.
4. **`test/integration/parquet`** — the end-to-end suite, whose segments are
   written by the **real `WP-050` writer**.

Three design decisions carry most of the weight, and each is answered below in
its own section: the **physical Parquet encoding**, the **same-layer-edge
question**, and **who deletes a WAL segment**.

## The Parquet encoding choice for decimal strings and bigint-as-string fields

**Every string-shaped field is written as `BYTE_ARRAY` with the `UTF8`
logical/converted type. No Parquet `DECIMAL`, no `INT64` for a
bigint-as-string, no floating point, anywhere.**

Two independent reasons, either of which alone is decisive:

- **`DECIMAL` is a scaled integer and therefore lossy for our purposes.** It
  carries a fixed `precision`/`scale`, so `"0.10"` and `"0.1"` become the same
  physical value. Handoff §7.3 makes every economic value an exact decimal
  *string* on every boundary precisely so that no such normalization happens,
  and §12.4 requires byte-identical replay outputs. A representation that
  cannot distinguish two strings the domain treats as distinct bytes is not a
  candidate, however natural it looks in a warehouse schema.
- **`INT64` cannot hold what the WAL admits.** `docs/contracts/wal-format.md`
  §5 permits `ingestSeq` and `receivedMonotonicNs` up to **40 digits**; `INT64`
  holds 19. Storing them as integers would either overflow or silently narrow
  the range the WAL never agreed to narrow.

Exactly three columns are physically integral, and all three are values this
package or the WAL format defines as JSON safe integers, which `INT64`
represents exactly and reversibly: `subscriptionGeneration` (from the record),
and `datasetRowOrdinal` / `segmentIndex` / `segmentRecordIndex` /
`frameLineByteOffset` / `frameLineByteLength` (computed here). One column is
`BOOLEAN` (`replayEligible`) and exactly one is nullable (`exclusionReason`).

**The claim is checkable, not asserted.** Every row carries
`frameLineSha256`: the SHA-256 of the exact WAL segment line it came from,
including its terminating `LF`. `encodeFrameLine` is the inverse of parsing, so
any consumer — including the Python job, which shares no code with the writer —
can rebuild the original bytes from a row and compare. The compactor itself
runs that check twice: once before the bytes leave the process, and once on the
rows it reads back out of the object store.

Codec: **`UNCOMPRESSED` by default**, configurable to `SNAPPY`. Compression is
lossless either way, so this is a reproducibility choice rather than a
correctness one: with no compressor in the path the object bytes are a pure
function of the rows and the pinned writer version, so a third party can re-run
compaction over the same segments and obtain the same digest. The manifest
records which codec produced the objects.

### The library, and its maintenance risk

**`hyparquet-writer@0.16.6`** (writer) and **`hyparquet@1.28.1`** (reader), both
MIT, both pure JavaScript, both **pinned to exact versions**.

Rejected alternatives, with reasons rather than taste:

| Candidate | Why not |
| --- | --- |
| `@dsnp/parquetjs` | Declares **`@aws-sdk/client-s3` as a runtime dependency**. Handoff §2.1 requires every dependency to have a concrete purpose, and the task packet is explicit that no cloud SDK is mandated. Pulling the AWS SDK in to get an encoder is exactly the creep that rule exists to stop. |
| `parquetjs`, `parquetjs-lite` | Unmaintained. |
| `parquet-wasm` | Correct, but a multi-megabyte WebAssembly artifact and a second toolchain. |
| A self-written encoder | The task packet permits it as a fallback. Not needed, and it would mean owning Thrift-compact metadata, page headers, and RLE definition levels whose only validation would be "DuckDB still reads it". |

The versions are pinned **exactly** rather than with a caret because this
library decides the bytes of an archived artifact whose checksum a dataset
manifest pins. A patch release that moved a page boundary would change every
object's digest for identical input; pinning makes that a reviewable upgrade
instead of a surprise.

**Maintenance risk, stated plainly.** `hyparquet-writer` is a `0.x` package
first published 2025-03, from a small maintainer (Hyperparam). It is actively
maintained — the release used here is from 2026-08-11 and the project shipped
again during this work package — but a `0.x` version number is a statement about
API stability, and a single-maintainer dependency in the path of an archive
format is a real risk. Three things reduce it:

1. **It is replaceable.** It is used behind one module
   (`parquet-object.ts`, ~250 lines) and the layout it writes is ordinary
   Parquet with no exotic types. Swapping the encoder would not change the
   layout, the manifest, or any consumer.
2. **Its output is checked by an independent implementation.** The committed
   fixture under `python/research/compaction/testdata/` is produced by this
   writer and read by DuckDB in `test_committed_fixture.py`. A regression in the
   library fails `uv run pytest`, not a production replay six months later.
3. **A change in its bytes fails a test.** The integration suite recompacts the
   fixture and compares byte for byte, with a message naming the regeneration
   command. A change to the bytes of an archive format is exactly the kind of
   change `wal-format.md` §12 says must be deliberate.

Recommended follow-up: a periodic dependency review, and an ADR before any
upgrade that changes object bytes. Recorded in `follow_up`.

## The same-layer-edge question, and how it was resolved

**Resolution: no edge was added, and no §2.1 row is needed.**
`packages/storage-parquet` declares **no workspace dependency at all**.

`docs/contracts/dependency-direction.md` §2 places both
`packages/storage-parquet` and `packages/storage-wal` in **layer 2**, so an edge
between them is a *same-layer* edge; §2.1 is exhaustive, fails closed, and lists
no such row (F13). Adding one is a contract-owner edit with a citation, not
something a consumer does because the edge is convenient.

The compactor therefore consumes the WAL's **published byte format** —
`docs/contracts/wal-format.md`, a document whose own header names `WP-130` as
its reader — through its own implementation in
`packages/storage-parquet/src/wal-format.ts`. That module enforces all six
validity conditions of §7 and the full field-by-field cross-check of §6.3.

The obvious objection is that two implementations of one document can drift, or
can share a misunderstanding. That is answered structurally rather than by
assertion:

- The **integration suite writes its segments with the real `WP-050` writer**
  and then reads them back through this package's reader
  (`test/integration/parquet/end-to-end.test.ts`). A divergence fails a test
  instead of silently producing a wrong dataset. The suite asserts that the two
  implementations agree on segment digests, record counts, byte offsets, and
  every field of every record.
- The suite is owned and run by **`apps/research-worker`**, a **layer-3
  composition root**, which §2 permits to depend on anything below it. Its
  `@polymarket-bot/storage-wal` devDependency is a downward 3 → 2 edge, and
  `pnpm check:deps` passes with it (the graph grew from 11 to 13 declared edges,
  both new edges downward).
- The unit suite keeps a **second, deliberately independent** segment builder
  (`src/testing/wal-fixture.ts`) for speed and for constructing byte-level
  corruption the real writer refuses to produce. Its docstring states that it is
  *not* evidence of format correctness, and points at the integration suite for
  that.

No conflict needed escalation.

## Who deletes a WAL segment

**`WP-130` deletes, and nothing else can.**

`docs/contracts/wal-format.md` §2 is explicit: "This package never deletes a
file. The filesystem port it depends on has no delete operation at all…
Deletion belongs to `WP-130`, and only after a verified upload (ADR-004 §5)."
ADR-004 §5 and handoff §9.1 state the rule identically: "Compaction never
deletes a WAL segment until Parquet upload **and** checksum verification both
succeed."

How that is implemented, in the order it happens:

1. Segments are enumerated **by sidecar manifest**, so an unmanifested segment
   is never read at all (`wal-format.md` §2: no manifest, no exposure).
2. Each candidate is verified against its own bytes — checksum, record count,
   byte size, and every claim the sidecar makes about the header, the footer,
   and the records.
3. Objects are written, then **read back out of the store**, and the digest that
   goes into the manifest is computed from the bytes the store returned. The
   read-back is decoded and every row re-checked against `frameLineSha256`; a
   digest alone would prove the store kept bytes, not that those bytes decode to
   the records the manifest is about to claim.
4. The dataset manifest is written and its own digest verified.
5. **Only then** is `WalSegmentRetention.deleteSegment` called, once per
   segment, with the verified object key and the digest read from the store — so
   the implementation re-checks its own precondition rather than trusting its
   caller (`deleteAfterVerifiedUploadRetention` in `node-file-system.ts` does
   exactly that, and refuses with `RetentionGuardError` if the object is absent
   or its digest moved).

Two further properties:

- **Retention is off by default.** `retainAllWalSegments()` is the default and
  deletes nothing; `RESEARCH_WORKER_RETENTION` defaults to `retain`. ADR-004's
  Consequences section says filling the disk is the *intended* failure
  direction, so reclaiming space is an explicit operational decision.
- **A refused segment is never deleted**, under any policy. It is evidence of an
  incident, and it is named in the dataset manifest's exclusion list with its
  issue codes.

## Two decisions worth stating, because they are not obvious

### Exclusion marks; it never drops

A record inside an excluded incident window, and every later copy of a
duplicated `(gatewayEpoch, ingestSeq)`, is **written to the dataset** with
`replayEligible = false` and an `exclusionReason` — not omitted.

This is forced by the retention rule above. Once an object is verified, the WAL
segment it came from may be deleted, and from that moment the Parquet dataset is
the **only copy** of those bytes. A compactor that dropped incident-window
records would destroy the evidence of the incident — the exact thing §16.6's
fault scenarios and §10.2's incident table exist to preserve. Marking keeps the
archive complete and still gives replay one cheap predicate: `WHERE
replayEligible`. The manifest carries both numbers (`recordCounts.written` and
`recordCounts.replayEligible`) so a reader never has to infer which happened,
and the DuckDB job asserts `segmentRead === written` precisely to catch a future
change that starts dropping.

### Deduplication refuses rather than guesses

Deduplicating on `(gatewayEpoch, ingestSeq)` is a binding obligation on every
consumer of this WAL (`wal-format.md` §12; the `WP-050` completion record). It
is safe **because** a duplicate is a re-recording of the same frame. Two records
under one key whose bytes differ mean the gateway's sequence assignment is
broken, and picking a winner would be arbitrary — so the compactor raises
`DuplicateDivergenceError` and produces no dataset.

## assumptions

1. **The manifest sits at `<root>/<prefix>/manifest.json`.** The Python job
   infers the object-store root by stripping the object keys' prefix from the
   manifest's own directory, which is exact for any prefix depth. `--object-root`
   overrides it.
2. **Dispatch order across segments is `(gatewayEpoch, segmentIndex,
   segmentId)`.** Epoch first because a restart begins a new epoch whose
   ordinals restart from zero (`wal-format.md` §2), so ordinal alone is not a
   total order. `wal-format.md` does not state a cross-segment ordering rule;
   this is the only one consistent with §2 and §8.4, and it is documented at the
   comparator.
3. **Incident windows are inclusive `(gatewayEpoch, ingestSeq)` ranges.** §10.2
   names the table but no schema exists yet, so the shape is defined here and
   the worker reads it from an operator-supplied JSON file. When a component
   owns `data.data_quality_incidents`, this becomes a query rather than a file;
   the compactor's interface does not change.
4. **A `subscriptionGeneration` fits a JS safe integer.** `wal-format.md` §5
   defines it as a non-negative safe integer, so `INT64` is exact and reversible.
5. **One Parquet object per WAL segment.** Not required by any document; chosen
   so an object can be re-verified against exactly one segment and so a
   `raw_segments` row maps to one object. The manifest models the relation
   many-to-one, so a future batching change needs no format change.
6. **`node:crypto`'s SHA-256 is the digest everywhere**, matching `WP-050`.

## deviations

1. **`python/pyproject.toml` `testpaths` extended** from `["tests"]` to
   `["tests", "research/compaction/tests"]`. The ratification for that file
   covers "the mechanical dependency declarations the compaction module
   requires", and this is not a dependency declaration — so it is disclosed
   here. The reason: the module's tests live next to the module (the pattern
   every TypeScript package here follows), and `python/tests/**` is **not** in
   this work package's allowed paths, so the alternative would have been an
   unreachable test suite or an out-of-scope edit. The change is additive and
   alters nothing about the existing `tests/` collection.
2. **`apps/research-worker`'s `start` bundles with esbuild** rather than using
   `tsc` + `node dist/main.js`. This is disclosed because it is a small
   architectural choice a composition root should not make silently.
   The reason it is necessary: **the repository has no runtime build story
   yet.** Every package's `main` points at TypeScript source, no package emits a
   `dist`, and the relative imports inside package sources use `.js` specifiers
   that no runtime resolves to `.ts`. `apps/ops-cli`'s `tsc && node dist/...`
   works only because its executable path imports no workspace package; the
   research worker imports one, and the `tsc` form was **verified to crash**
   with `ERR_MODULE_NOT_FOUND` on
   `packages/storage-parquet/src/constants.js`. Shipping that would have been a
   false claim of a runnable process. esbuild is already in the dependency tree
   (via vitest) and already allowed to build in `pnpm-workspace.yaml`, so the
   choice adds no new supply-chain surface; it is declared as a devDependency of
   this app alone and imposes nothing on any other package. **A repository-wide
   runtime-build convention is a decision for the orchestrator**, not for this
   work package — recorded in `follow_up`.
3. **`hyparquet-writer` and `hyparquet` are pinned to exact versions** rather
   than carets, contrary to the surrounding convention. Reason in the encoding
   section: this dependency decides the bytes of a checksummed archive.
   `hyparquet-writer@0.16.6` was chosen over the latest `0.16.8` because the
   newer release was under pnpm's minimum-release-age gate, and taking it would
   have required editing `pnpm-workspace.yaml` — a file this work package does
   not own. Pinning an older, already-aged release was the correct answer rather
   than a workaround.
4. **A binary fixture is committed** (`python/research/compaction/testdata`, 32
   KB: two Parquet objects, a manifest, a digest sidecar). It is the only way to
   demonstrate that DuckDB reads what this writer produces. It is regenerated by
   `pnpm --filter @polymarket-bot/research-worker fixture:python` and an
   integration test fails if it drifts.

No other deviation. No shared contract, migration, protected config, or
adjacent package was modified.

## known_risks

1. **`hyparquet-writer` is a `0.x` dependency in the path of an archive
   format.** Discussed in full above. Mitigated by exact pinning, a single
   ~250-line seam, cross-implementation validation by DuckDB, and a byte-level
   drift test. **Not** mitigated against the library being abandoned; that would
   be an encoder swap, which the layout survives unchanged.
2. **The compactor holds one segment's records in memory** while encoding it, so
   its resident set is bounded by `maxSegmentBytes` (WAL default 64 MiB) rather
   than by a streaming budget. A segment past `DEFAULT_MAX_SEGMENT_BYTES` (256
   MiB) is **refused with a stated reason**, never truncated. Reasoned, not
   profiled — profile it in the `WP-140` soak.
3. **Compaction lag is computed only from refused segments' `closedAt`.** A
   segment that is simply not compacted yet — because nobody ran a cycle — does
   not contribute, since this package sees only what a cycle looked at.
   `WP-140`'s dashboard should combine this with the recorder's own segment-age
   metric to get the whole picture.
4. **Incident windows come from a file, not from PostgreSQL.** Until a component
   owns `data.data_quality_incidents` (§10.2), the exclusion list is only as
   good as the operator's file. The failure direction is safe — a configured but
   unreadable file is a hard error rather than a silent "no incidents" — but a
   window nobody wrote down is a window nobody excluded.
5. **`data.raw_segments` and `data.dataset_manifests` are not written.** §10.2
   places this metadata in PostgreSQL; this package produces it and returns it,
   and the wiring to `packages/storage-postgres` belongs to whichever package
   owns that write path. Nothing here depends on it, and the object-store
   manifest is self-sufficient for replay.
6. **Run-scoped §12.5 pins are `null`.** `runSeed`, the fill/latency model
   versions, fee/reward snapshot versions and settlement-spec versions are
   chosen by the replay run, not by a compactor. They are present and explicitly
   `null`, with a note saying so, rather than omitted or invented. A replay run
   must fill them; a dataset manifest alone does not satisfy §12.5.
7. **Single-writer assumption inherited from the WAL.** If a second writer is
   appending to a segment while compaction reads it, the read may see a
   partially written record and refuse the segment. That is the correct
   behaviour, and `wal-format.md` §12 already records single-writer-per-directory
   as an unenforced invariant.
