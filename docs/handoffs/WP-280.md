## summary

1. **The subscription manager** (`manager.ts`).
   - `createUserStreamManager` runs WP-260's `assertSignerGate` before it reads anything else. In PAPER, BACKTEST, SHADOW, REPLAY, or with an unreadable context, it throws `SignerBoundaryRefusal`. A test shows the transport is never touched, and the network tripwire records nothing.
   - It subscribes by market through an injected `AuthenticatedUserSocketPort`. The port builds the auth frame.
   - Its states are an explicit table: IDLE, CONNECTING, SUBSCRIBED, STALE, DISCONNECTED, RECONNECTING, CLOSED.
   - It sends PING every 10 s, a documented fact. It goes STALE after 30 s without a PONG; the server side is undocumented (U-2), so this copies the SDK's own default.
2. **Normalized events** (`normalize.ts`, `oms-projection.ts`).
   - Order lifecycle events (PLACEMENT, UPDATE, CANCELLATION) and trades (MATCHED, MINED, CONFIRMED, RETRYING, FAILED, in both spellings per ADR-002).
   - Identifiers and decimals are exact. Anything unrecognized is UNRECOGNIZED, never coerced.
   - C-3's `MATCHED_NOT_BROADCASTED` is UNRECOGNIZED, with its own reason: four sources against one.
   - Owner fields hold API keys and are never carried.
   - The projections into WP-270's observation, fill and settlement inputs refuse anything ambiguous. A fill is produced only when the event fixes its economics and an exact fee; maker fees are no longer assumed to be 0 (round 1, F-01).
3. **Reconnects and gaps.**
   - Every loss requests reconciliation with its own cause. So do every resubscription, added market, unrecognized message, unapplied event, stop and fault.
   - Each request covers every market the connection subscribed to or attempted during its lifetime (rounds 2 and 3).
   - Requests stay in a bounded backlog until acknowledged.
   - There is no cursor, resume or backfill API, and nothing is re-emitted.
4. **Redaction.** `redactUserStreamPayload` hides owner fields and the auth frame, on top of WP-260's redactor. 200 generated frames with planted secrets leak nothing.
