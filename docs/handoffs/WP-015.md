## summary

`docs/contracts/dependency-direction.md` §6 specified a check that did not
exist; F1–F13 were unenforced prose (§5 of that document says so explicitly).
This package implements the check and puts it in the same pipeline as the type
gate.

`tools/check-dependency-direction.mjs` (Node built-ins plus the repository's
existing root `typescript` devDependency, which rule 3 uses as its parser; no
dependency added, no manifest or lockfile change, no network, no credentials):

- **Contract as data.** The §2 layer table and the §2.1 permitted-same-layer
  edge list are parsed from the Markdown at run time. No copy of either lives in
  the checker or in the tests, because §6's last bullet requires exactly that
  ("A test's private copy of either table is exactly how coverage drifts").
  The parser reads §2 layer subsections from Markdown table rows, fenced blocks,
  and the prose form that states the class entry ("`packages/strategies/**` is a
  … member of this layer"), and reads §2.1 rows as `` `from` → `to` `` in the
  second table cell. The parse result is then **validated eagerly**: every §2.1
  data row must parse into an edge, carry a numeric layer, and name
  packages/classes that §2 classifies at that same layer, and no §2 pattern may
  appear twice. Each failure is a `CHK` error, not a skipped row.
- **Graph.** Nodes are the workspace members discovered from
  `pnpm-workspace.yaml` globs that carry a `package.json`; the workspace root
  manifest is deliberately not a node (§6, "Graph construction"). Edges are
  declared `dependencies`/`devDependencies`/`peerDependencies`/
  `optionalDependencies` entries naming a workspace member, directed
  dependent → dependency.
- **Rule 1 (F9).** Cycle detection with the named cycle in the output,
  including the one-node cycle of a package that declares itself.
- **Rule 2 (F12, F13).** Downward edges pass; upward edges fail naming both
  packages and both layers; same-layer edges pass only when a §2.1 row matches
  (glob-aware, so the S2 class row will permit a concrete strategy's
  `strategy-sdk` edge when `WP-220` adds it) and fail otherwise with a message
  pointing at §2.1 as the place to add a *cited* row.
- **Fail-closed (both directions).** A workspace package absent from §2 is an
  error; a *named* §2 entry with no `package.json` is an error; a class entry
  matching zero packages is not. `packages/strategies/*` matches are classified
  layer 1, not exempted — the 2026-08-26 M6 correction is what the code
  implements.
- **Rule 3 (F1–F8, F11) — parsed, not lexed (round 2).** Source scan of every
  package's `.ts/.tsx/.mts/.cts/.js/.jsx/.mjs/.cjs` files, using the
  **TypeScript compiler API** (`ts.createSourceFile` + one full AST walk,
  script kind chosen by extension). There is no regular expression over source
  text anywhere in rule 3. `typescript` is already a root devDependency and the
  tool runs after `pnpm install` in dev and CI, so this adds no dependency and
  does not touch the lockfile; it is resolved from the checker's own location
  first and from the scanned root second, and a failure to resolve it is a
  `CHK` error and a non-zero exit rather than a run that scans nothing.
  Comments and string data are structurally inert in an AST, so text that
  merely mentions `node:fs` or `Math.random()` cannot produce a finding, and a
  specifier is recognised wherever the grammar puts one — arbitrary intervening
  trivia included. Collected exactly:
  `ImportDeclaration`/`ExportDeclaration` module specifiers (so `export * from`
  and `export { x } from` count), `import x = require("…")` external module
  references, `import("…")` type nodes, dynamic `import(…)`, and any call whose
  callee resolves to the CommonJS `require` **capability** — bare or wrapped
  (`(require)("…")`, `(require as F)!("…")`), aliased (`const r = require`,
  `= module.require`, `= createRequire(…)`, `const { require: r } = module`),
  `module.require(…)`, reflected (`require.call(thisArg, "…")`, specifier at
  index 1), or a directly-invoked `createRequire(…)("…")` (round 3) — plus, since
  round 5, any call that resolves to `process.getBuiltinModule`, which loads a
  Node built-in by name and whose specifier is classified exactly like an
  import's; plus, since round 7, `process.mainModule.require(…)` and
  `require.main.require(…)` — the live CommonJS `Module` under a CJS entry point,
  bound to the same `module`-global capability so `.require` on it is the loader;
  plus, since round 8, NAMED/renamed `node:module` imports —
  `import { createRequire as cr, Module as M, register } from "node:module"` binds
  `cr` to the createRequire factory, `M` to the `Module` class (its `_load` is a
  loader call, its `.prototype.require` and instances' `.require` are loaders), and
  `register` to a dynamic import of its arg-0 specifier — closing the last
  ordinary-code loader gap the default/namespace forms already handled.
  The ambient
  `require`, even when only named through `declare const require`, is the
  capability; a *genuine* local `require`/`module` still shadows. A string
  literal or no-substitution template literal is an exact specifier. Relative
  specifiers that escape the package are
  resolved to the owning workspace package so a deep relative import is judged
  like a bare one. Reports carry `package (file:line)` — the line from
  `ts.getLineAndCharacterOfPosition` — the rule id, the message, the
  contract/handoff/ADR citation, and a fix. A file the parser cannot read is a
  `CHK` error: scanning a recovered partial tree and reporting nothing would be
  a silent coverage hole.
- **Rule 3, unevaluable constructs (`F-OPAQUE`).** A dynamic `import()` or a
  `require`-capability call whose specifier is an interpolated template or any
  non-literal expression (including the array a `require.apply(thisArg, […])`
  passes), and a reference to `eval`/`Function`, all defeat static checking
  outright. Inside the four purity-restricted packages
  (`packages/domain`, `packages/strategies/**`, `packages/ledger`,
  `packages/simulation`) each is itself a finding rather than a silent pass;
  elsewhere they are allowed, because a composition root may legitimately load a
  module by computed name. Round 1 deliberately excluded `require(` because it
  is not a reserved word and `packages/domain`'s schema registry has an
  unrelated `require(eventType, schemaVersion)` method — which round 2 showed
  was a bypass (`require(target)` in a `.cjs` file was silently accepted), and
  round 3 showed that recognising *only* the bare-identifier callee was itself a
  family of bypasses (aliases, `module.require`, reflection, an ambient
  `declare`d require, and `createRequire`). The AST now models `require` as a
  capability and distinguishes the legitimate cases exactly: a *method* call on
  a non-module object (`registry.require(…)`) is a property access on something
  that is not the module global, and a *genuine* local `require`/`module` still
  shadows the ambient one — while an ambient `declare const require`, being a
  type assertion over the global rather than a real implementation, does not.
  Round 4 showed that even that was an *enumeration* of the positions the check
  reads, and enumerating positions is not a rule about all positions: seven legal
  spellings moved the capability into a value and loaded through it silently. So
  the rule is inverted and `F-OPAQUE` now also covers a **capability escape** —
  any reference to a require capability, inside a purity-restricted package, that
  is not in one of the analysed positions (callee of an analysed call,
  `.call`/`.apply` reflection callee, initializer of a tracked declaration alias,
  base of a larger capability expression, `typeof` operand, or a type position).
  See "Review round 4". Round 5 added the sixth analysed position — the base of a
  computed member read, which the next bullet reports at the access itself — and
  widened the capability set to every *loader*.
- **Rule 3, computed member access on a capability (`F-OPAQUE`, round 5).** When
  the object of an element access resolves to a capability and the member is not
  a literal (`getBuiltinModule("node:module")["create" + "Require"]`,
  `process[key]`, `require[k]`), the member cannot be classified, so the access
  itself is a finding in a purity-restricted package instead of resolving to
  "no capability". A computed member on a **non**-capability object
  (`table[key]`) is out of scope and adds no noise. Composed with the unrecognised
  `process.getBuiltinModule` loader, the previous `null` result is exactly what
  let `packages/simulation` acquire a working `require` and load `ethers` in
  silence. See "Review round 5".
- **Rule 3, the evaluator surface (`F-OPAQUE`, round 6).** Since round 1 a
  reference to `eval` or `Function` inside a purity-restricted package has been a
  finding, but that was an **identifier list**, and round 6 showed the same
  capability is reachable without naming either: for every function `f`,
  `f.constructor === Function`, so
  `(function () {}).constructor('return process.getBuiltinModule("node:fs")')()`
  and `queueMicrotask.constructor('…createRequire…')()` are arbitrary code
  evaluation and a reconstituted `require` — and both exited 0 in all four
  restricted packages. A member read whose property resolves to `constructor` is
  now itself an evaluator-acquisition finding there. It fails **closed** on the
  object's type, because "is this expression function-valued" is not statically
  decidable: `[].constructor` is `Array` and is flagged anyway. *Declaring* a
  `constructor` member (`class C { constructor() {} }`, an object-literal key) is
  not a read and stays clean, which is what keeps the shipping
  `packages/domain/src/errors.ts` passing. See "Review round 6".
- **Rule 3, impure globals — by reference, not by call spelling (round 2).**
  `packages/domain` (F1) and `packages/strategies/**` (F3, F11) are scanned for
  ADR-005 §1's full list: clock (`Date`, `performance`, `process.hrtime`,
  `setTimeout`/`setInterval`/`setImmediate`), unseeded randomness (`Math.random`,
  `crypto`), environment (`process`, `globalThis`/`window`/`self`/`global`,
  `navigator`, `import.meta`), and network reachable without an import (`fetch`,
  `WebSocket`, `XMLHttpRequest`, `EventSource`, `navigator.sendBeacon`). **Any**
  reference to one of those identifiers is a finding, including a bare one used
  as a value (`const D = Date`), because ADR-005 §1's prohibition is absolute
  and an alias defeats any call-shape check. `globalThis.X`, `window.X`,
  `self.X` and `global.X` resolve to a reference to global `X`. `Math` is the one
  root with a pure majority, so `Math.max(a, b)` passes while `Math.random` and a
  bare `Math` value reference do not. Two things are deliberately *not*
  findings: `new Date(argument, …)` with at least one argument (constructing a
  date from a value the caller already holds is deterministic), and a name bound
  by a declaration in the file (`function f(Date: string) { return Date; }` is
  clean). Type positions are not walked at all, so `const d: Date` and
  `typeof process` are not findings.

## assumptions

1. **§6's "the check parses them or is generated from them" is binding**, so the
   layer table and the allowlist are parsed from
   `docs/contracts/dependency-direction.md` rather than embedded. This is a
   deliberate departure from the task packet's suggested "embed the table as
   data mirroring §2 exactly, with a comment requiring the two stay in sync" —
   see `deviations` 1.
2. `packages/strategies/**` (§2 prose, §3 F3) and `packages/strategies/*` (§6,
   §2.1 S2) name the **same class**; both are treated as globs matching the
   concrete strategy packages.
3. "Live signer" (F5) is not enumerated in the contract. Implemented as: the
   signing libraries `ethers`, `@ethersproject/*`, `viem`, `web3`, `eth-crypto`,
   `@safe-global/*`, the unified SDK, the archived clients, and the workspace
   package `packages/polymarket-secure` (ADR-010 §4 makes it the signer
   boundary).
4. "Redis client" (F8) is implemented as `redis`, `ioredis`, `@redis/*`,
   `redis-om`, `node-redis` — with the "for market-event transport" qualifier
   dropped because purpose is not mechanically decidable (see `deviations` 3).
5. "Filesystem/venue/database" (F3) is implemented as the four named classes
   **plus** ADR-005 §1's wider list (network, environment, clock, unseeded
   randomness), because ADR-005 is cited as F3's own source. Pure built-ins
   (`path`, `url`, `util`, `assert`, `events`, `buffer`, `stream`) stay allowed.
   Round 1 found that this was implemented for *imports* only: the strategy scan
   applied neither the process/environment globals nor any network-global check,
   so `process.env` and a global `fetch()` inside a strategy passed. Both are now
   applied, so ADR-005 §1's four categories are each enforced by both routes
   (import and global) — subject to `known_risks` 4.
6. Rule 3 scans every source file in a package, **including `*.test.ts`**. §6
   says "inside the offending package's source" and does not carve out tests.
7. `pnpm-workspace.yaml` currently uses only positive globs; the workspace
   parser throws on a `!` exclusion rather than silently mis-modelling it.
8. **A construct that makes the rules unevaluable is a finding in a
   purity-restricted package** (`F-OPAQUE`, added in round 1, widened in round
   2). The contract does not name this case. The ruling is that
   `import(<not a static literal>)`, `require(<not a static literal>)`, and a
   reference to `eval`/`Function` inside `packages/domain`,
   `packages/strategies/**`, `packages/ledger` or `packages/simulation` make
   F1–F8/F11 unevaluable, and an unevaluable rule must fail rather than pass.
   Outside those four scopes they are permitted, because a composition root
   loading a module by computed name is normal and the contract constrains apps
   only by layer. Round 1 excluded `require(` on the grounds that it is not a
   reserved word and `packages/domain`'s schema registry has an unrelated
   `require(eventType, schemaVersion)` method; round 2 showed that exclusion was
   a bypass, and the AST distinguishes the two cases exactly — a method call is
   a property access, and a `require` declared in the file is shadowed — so the
   exclusion is no longer needed. Round 3 widened `F-OPAQUE` again: a computed
   specifier reached through *any* `require`-capability shape (an alias, a
   `module.require`, a `require.apply(thisArg, […])`) is `F-OPAQUE`, not just the
   literal `require(target)`. **The phrase "a reference to `eval`/`Function`" in
   this assumption was a description of an identifier list, not of the evaluator
   surface**; round 6 found `.constructor` outside it and 8d restates the rule.
8a. **`require` is a capability, tracked like `Date`/`process` (round 3).** A
    call is a require-load when its callee resolves to the ambient/global
    `require`, an alias bound to it, `module.require`, or `createRequire(...)`.
    Two rulings make that precise. First, **an ambient `declare const require` is
    not a shadow**: it is a type assertion over the global, binds no runtime
    value, and so a call to it in a restricted package is a require-load. The
    scanner keeps two shadow frames per scope — all locally *named* bindings
    (used by the impure-global rules, unchanged) and the *genuine*, non-`declare`
    subset — and only a genuine local `require`/`module` shadows the capability.
    Second, a call whose callee identifier is `createRequire` yields a capability
    regardless of where `createRequire` came from; importing `node:module`/
    `createRequire` is independently the F-row finding (`node:module` is now in
    the impure-builtin set), so this is belt-and-suspenders. A local function
    literally named `createRequire` that is *not* Node's would therefore be
    flagged — a deliberately noisy, never-silent limit for an exotic shape.
8b. **An unconsumed reference to a loader capability is itself a finding
    (round 4, binding orchestrator direction; corrected in round 5).**
    Assumption 8a still enumerates
    the positions in which the check can *read* what a capability loads, and
    round 4 proved that an enumeration of positions is not a rule about all
    positions: seven legal spellings (`({ r: require }).r(…)`, `[require][0](…)`,
    `exports.load = require`, `Reflect.apply(require, …)`,
    `const { r } = { r: require }`, `require.bind(null)(…)`, and a plain
    `r = require` assignment) each loaded a module while naming none of the
    handled positions, and each passed silently. The ruling is therefore
    inverted: inside the four purity-restricted packages, **any** reference to
    the ambient `require`, the CommonJS `module` global, `createRequire`, the
    result of calling it, `process.getBuiltinModule`, the `node:module`
    namespace, or a tracked alias to one of those is `F-OPAQUE` unless
    it sits in one of the analysed positions listed under "Review round 4". The
    trade is explicit — an escape finding does not prove a forbidden module was
    loaded, only that the check can no longer prove one was not — and it is
    affordable because a purity-restricted package has no legitimate use of a
    module loader at all under ADR-005 §1 and contract §3.

    **Correction of round 4's totality claim (round 5).** Round 4 said the rule
    was "total by construction" and that a restricted package "cannot hold the
    capability at all without failing the gate". That was overstated in a way
    round 5 disproved with a working silent load. The rule is total over
    *references the walk resolves to a member of the capability set* — it is not
    total over "every way to obtain a module loader", because the capability set
    is itself a recognised list. `process.getBuiltinModule` was not on that list,
    so no reference to it was a reference the rule could be total over, and
    `getBuiltinModule("node:module")["create" + "Require"](__filename)` produced a
    working `require` while the scanner reported nothing. The accurate statement
    is: **the rule is total over statically visible references to the loaders
    this check recognises, and adding a loader to that set is what extends it.**
    Round 5 adds `process.getBuiltinModule` and the `node:module` namespace, and
    makes a computed member read on *any* capability fail closed (8c), which
    closes the builtin-loader route and the "reach a member without naming it"
    route together. The two limits that remain are stated, not claimed away: an
    unrecognised loader spelling, and the cross-file/reachability limits in
    `known_risks` 2.
8c. **`process.getBuiltinModule` is a module loader, and a computed member read
    on a capability fails closed (round 5, binding orchestrator direction).**
    `process.getBuiltinModule("node:fs")` returns Node's `fs` namespace without
    an import statement and without `require`, and
    `getBuiltinModule("node:module").createRequire(…)` reconstitutes `require`
    itself. It is therefore treated as a loader in the specifier machinery
    everywhere F1–F8/F11 apply: a string or no-substitution-template argument is
    that call's **specifier**, classified exactly like an import's, and a
    computed argument is `F-OPAQUE` in a restricted package. It is recognised
    through `process.getBuiltinModule`, `globalThis.process.getBuiltinModule`, a
    tracked `process` alias, a `const { getBuiltinModule } = process`
    destructure, and `.call`/`.apply` reflection. Two rulings make the shape
    precise. First, `process` is a **carrier, not a loader**: the check resolves
    it so the loader can be found through it, but a bare `process` reference is
    *not* an escape, because the contract puts `packages/ledger` and
    `packages/simulation` under F4/F5 (what they load) rather than under
    ADR-005 §1's impure-global list — only `packages/domain` and
    `packages/strategies/**` are, and their existing globals rule already reports
    `process`. Second, a **computed** member read on any capability-bearing
    expression is itself `F-OPAQUE`, because the member cannot be classified and
    returning "no capability" is precisely what made the review's probe silent.
    A computed member on a non-capability object is out of scope, so ordinary
    `table[key]` code produces no new noise.
8d. **Reading the `constructor` property is acquiring an evaluator, and fails
    closed (round 6, binding orchestrator direction).** The `F-OPAQUE` evaluator
    rule had been an *identifier* list — `eval`, `Function` — since round 1.
    Round 6 showed the identical capability is obtained without naming either,
    because for every function `f`, `f.constructor === Function`:
    `(function () {}).constructor('return process.getBuiltinModule("node:fs")')()`
    loads `node:fs`, and `queueMicrotask.constructor('…createRequire…')()` hands
    back a working `require`. Both were runtime-verified on Node 24 (v24.13.0)
    and both scanned clean in all four purity-restricted packages. The ruling is
    therefore: **inside a purity-restricted package, a member read whose property
    resolves to `constructor` is itself an `F-OPAQUE` evaluator-acquisition
    finding.** Four points make the boundary explicit, because it is a judgement
    call and a reviewer should be able to disagree with it deliberately:

    1. **No non-function exemption.** Whether an arbitrary expression is
       function-valued is not statically decidable (and would not become
       decidable with a type checker, across `any`/`unknown`/`never`). The
       direction permitted an optional exemption for objects the check can prove
       are not functions; it is **refused**. `[].constructor` is `Array`, not
       `Function`, and is flagged anyway — the exemption that would clear it is
       exactly the recognised-shape list that rounds 3, 4, 5 and 6 each found a
       hole in, and `[].constructor.constructor` is `Function` regardless.
    2. **"Resolves to" folds the obvious computed spellings**: `f["constructor"]`,
       `f["constr" + "uctor"]`, ``f[`constr${"uctor"}`]``, and
       `const k = "constructor"; f[k]` (a file-wide, scope-insensitive map of
       string constants — deliberately over-eager, never silent). The
       destructures `const { constructor } = f`, `const { constructor: F } = f`
       and `const { ["constructor"]: F } = f` are the same acquisition and are
       covered too.
    3. **Declaring is not reading.** `class C { constructor() {} }` and
       `{ constructor: f }` as an object-literal key bind a member; they do not
       read one, and they stay clean. This is what keeps the shipping
       `packages/domain/src/errors.ts` (seven class constructors) passing, and it
       is the only "ordinary `constructor` usage" the boundary allows.
    4. **Restricted packages only.** The rule does not run in `apps/**`; the
       evaluator rule has always covered all four restricted packages (unlike the
       impure-globals rule, which covers two), and that scope is unchanged.

    The acquisition site is always the finding, so no additional machinery is
    needed for what happens next: `X.constructor(...)()`, or binding
    `const F = X.constructor` and calling `F` later, is reported at the read.
    What this rule does **not** cover is stated in `known_risks` 10.
8e. **`process.mainModule` and `require.main` are `Module`-object loaders
    (round 7, closing follow_up 10).** Under a CommonJS entry point
    (runtime-verified on Node v24.13.0) `process.mainModule` is a live `Module`
    and `require.main === process.mainModule`, so `.require(...)` on either loads
    a module. The ruling is that both are the same MODULE-object capability
    (`CAP_MODULE`) the CommonJS `module` global already is: a string/
    no-substitution-template argument to `.require` is that specifier fed through
    F1–F8/F11, and a computed argument is `F-OPAQUE`. Recognised through
    `process.mainModule`, `globalThis.process.mainModule`, a tracked `process`
    alias `.mainModule`, a `const { mainModule } = process` destructure,
    `require.main`, and aliases of any of those; the computed-member (8c) and
    escape (8b) rules then follow because the base is `CAP_MODULE`. Two facts make
    this necessary rather than cosmetic. First, `process` is a **carrier** no
    escape rule catches (8c), so `process.mainModule` HAD to be recognised or the
    load stayed silent — and it did on `900b299`, in `packages/simulation` and
    `packages/ledger`, the two restricted packages that run no impure-global rule.
    Second, `require` is itself a loader capability, so an *unresolved*
    `require.main` was already an escape finding; resolving it only makes the
    finding the precise F-row rather than a generic escape. The neighbouring
    module-graph reads `module.parent` and `module.children[i]` are deliberately
    **not** resolved into capabilities: `module` is itself a loader capability, so
    `module.parent.require(...)` is already an escape finding today (the bare
    `module` escapes into a `.parent`/`.children` read), and resolving them would
    grow the recognised set — the exact anti-pattern follow_up 8 warns of — for no
    safety gain. `import.meta` (ESM) offers no synchronous require;
    `import.meta.resolve` resolves-not-loads and `import.meta` is already an
    environment-global finding in domain/strategies; `process.binding`/
    `process._linkedBinding` are live but internal/deprecated Node APIs, out of
    scope as internal APIs (`known_risks` 11).
8f. **NAMED (and renamed) `node:module` imports bind their local names to the
    export's capability (round 8, closing the last ordinary-code loader gap).**
    `import { createRequire as cr, Module as M, register } from "node:module"`
    binds `cr`→`CAP_FACTORY`, `M`→`CAP_MODULE_CLASS`, `register`→`CAP_REGISTER`
    in the import-collection layer (`collectAliasDecls`'s `ts.isNamedImports`
    branch, via `NODE_MODULE_NAMED_CAPABILITIES`); the same map backs the CJS
    mirror `const { Module } = require("node:module")` and the namespace member
    reads `mod.Module`/`mod.register`. The `Module` class is an
    evaluator-or-loader capability — the same class `module.constructor` yields
    (8d) — whose members are loaders: `Module._load(spec, parent, isMain)` is a
    loader *call* (`CAP_MODULE_LOAD`, arg 0 classified like `require(...)`; a
    computed arg is `F-OPAQUE`), `Module.prototype` and `new Module(...)` are
    `Module`-object capabilities (`CAP_MODULE`) whose `.require` resolves through
    8a, and a bare `Module` reference is an 8b escape. `register`'s arg-0 specifier
    is a dynamic import classified like `require(...)`. The DEFAULT and NAMESPACE
    import forms already resolved (round 5); this closes the named-import gap
    without regressing them (`mod.Module._load(…)` and `mod.createRequire(…)(…)`
    still flag). `createRequire`/`getBuiltinModule` are still additionally matched
    by bare name (the wider match 8c documents); `Module`/`register` are matched
    only through a `node:module` binding, because both are common identifiers
    elsewhere. Inert exports (`builtinModules`, `isBuiltin`, `SourceMap`,
    `syncBuiltinESMExports`, `_resolveFilename`, the compile-cache helpers) load
    nothing and are deliberately left clean — see the export-by-export audit in
    "Review round 8".
9. **`new Date(<argument>)` is deterministic and is not a finding.** Every other
   reference to `Date` is, including the no-argument `new Date()`, a bare
   `Date(…)` call (which returns the current time whatever arguments it is
   given), `Date.now`, `window.Date`, and a bare `Date` used as a value. Round 2
   established the last of these: `const D = Date; D()` passed the round-1
   call-shape patterns, and ADR-005 §1's prohibition is absolute, so the alias
   itself is the finding.
10. **"Global" means "not declared in this file."** There is no type checker and
    no cross-file resolution: the walk maintains a scope stack and treats a name
    bound by an enclosing declaration as shadowed. The direction that could
    hide a violation (over-broad shadowing) is deliberately narrowed — type
    parameters, interfaces, type aliases and method names do not shadow a value
    — and the direction that could produce a spurious finding (a `var` declared
    in a nested block and used in an outer scope) is accepted, because it names
    an exact `file:line` rather than passing silently. For the `require`/`module`
    capability specifically (assumption 8a), the shadow must also be *genuine*:
    an ambient `declare const require` names the binding but does not shadow the
    global, so it does not suppress the finding.
11. **`setTimeout`/`setInterval`/`setImmediate` are clock reads.** The contract
    names `Date.now` and `Math.random` as examples, not as an exhaustive list;
    ADR-005 §1 forbids the "global clock", and handoff §7.5 gives a strategy
    `nextWakeupAt` precisely so it never schedules its own timer. Flagging them
    is a strengthening beyond round 1, and beyond the round-2 direction's
    literal list, recorded here so `WP-220` is not surprised.

## deviations

1. **Contract parsed, not embedded** (assumption 1). The packet asked for an
   embedded mirror of §2 with a sync comment; §6's final bullet asks for the
   opposite, and the packet states the contract is the spec. Consequence: a
   cosmetic reformat of §2/§2.1 can break the parse. The parse is validated
   eagerly, so every case tested to date fails **closed** — unclassified
   packages, an empty allowlist, or an explicit `CHK` error naming the offending
   line. The round-1 review found five contract mutations that had exited 0
   (an unparseable §2.1 edge cell, a row whose layer contradicted §2, a row
   naming a nonexistent package, a non-numeric layer cell, and a duplicate §2
   assignment inside one layer); all five are now `CHK` errors with regression
   tests. The honest statement of the residual risk is in `known_risks` 1: the
   parser recognises the shapes §2/§2.1 use today, and a shape it does not
   recognise yields *no* assignment or *no* row rather than a wrong one — which
   is caught by the fail-closed rules — but this is an enumerated set of shapes,
   not a proof.
2. **Edge set is a superset of §6's literal wording.** §6 says
   "`dependencies`/`devDependencies` … (`workspace:` specifiers)". The checker
   also reads `peerDependencies` and `optionalDependencies`, and treats *any*
   dependency entry naming a workspace member as an edge even if its specifier
   is a version range rather than `workspace:`. All three widen coverage in the
   fail-closed direction; none changes today's verdict (the repository has
   exactly the three `workspace:*` declarations §6 describes, one of which is
   the excluded root's). `optionalDependencies` was added in remediation round 1
   — pnpm links it exactly like `dependencies`, so omitting it let a real
   layer-0 → layer-2 edge through.
3. **F8's "for market-event transport" qualifier is not implemented as a
   qualifier**: any Redis client import outside `packages/event-bus` fails. A
   future package with a non-transport Redis need would have to change the
   contract, which is the intended review path but is stricter than F8's literal
   text.
4. **No standalone cross-package deep-import rule.** The packet's example list
   mentioned "cross-package deep imports"; §6 does not specify one, and the
   packet directs "implement what §6 actually specifies". Relative imports that
   escape a package *are* resolved so that F1–F8/F11 apply to them (the F5 test
   proves it), but an otherwise-legal deep import (e.g. an app reaching into a
   layer-1 package's internal file) is not reported today. See `follow_up` 3.
5. **`check:deps` is a standalone script, not chained into `lint`.** `pnpm lint`
   is `eslint .`; folding a second tool into it would change an existing WP-010
   gate's meaning and hide which tool failed. CI gets its own named step instead,
   so the failure is legible in the job log. No existing script or step was
   modified.
6. **`.d.ts` files are scanned, contrary to the round-2 direction's "skip
   `.d.ts` … as before".** They were never skipped: `path.extname("x.d.ts")` is
   `.ts`, so they have always been in `SOURCE_EXTENSIONS`. Skipping them now
   would *remove* coverage — a declaration file can name `@polymarket/client` or
   `node:fs` in a real import — so the pre-existing behaviour is kept. `dist/`
   is skipped, as directed. This is the only place where the round-2 direction
   was not followed literally, and it is followed in the stricter direction.
7. **Three fail-closed additions beyond the round-2 direction**, each recorded
   because they were not requested: a source file the parser cannot read is a
   `CHK` error rather than a silently partial scan; a reference to
   `eval`/`Function` in a purity-restricted package is `F-OPAQUE` (widened in
   round 6 to a read of the `constructor` property — `deviations` 11); and
   `setTimeout`/`setInterval`/`setImmediate` are clock reads (`assumptions` 11).
   All three only ever turn a pass into a failure.
8. **Unclassified packages are reported once per package, not once per edge.**
   §6 rule 2 lists "either package unclassified in §2 → fail" as a per-edge
   verdict; reporting it per edge would duplicate the same finding. The package
   is reported once and its edges are skipped, so the run still fails and names
   the package.
9. **Three round-4 additions beyond the binding direction**, recorded so they are
   not silent. The direction named the capability set as "the ambient `require`,
   `module`, and the result of `createRequire(…)`"; the implementation also
   (a) resolves an environment root's `.require` member (`globalThis.require`,
   `window["require"]`) to the same capability, because the impure-global scan
   that would otherwise report the root runs only in `packages/domain` and
   `packages/strategies/**` — the identical construct was silent in
   `packages/ledger` and `packages/simulation`; (b) gives tracked aliases a
   *kind*, so `const m = module` and `const f = createRequire` are followed as
   well as `const r = require`; and (c) makes a nearer genuine binding shadow an
   outer alias, so `const r = require; function f(r) { r("contract"); }` no
   longer misreports the parameter. (a) and (b) only turn passes into failures;
   (c) only removes a false positive and cannot hide a real reference, because
   the shadowing binding is a genuine local by construction.
10. **Five round-5 additions beyond the binding direction**, recorded so they are
    not silent. The direction named `process.getBuiltinModule` and computed
    member access; the implementation also
    (a) matches `getBuiltinModule` **by name** as a bare identifier and as a
    member, without the genuine-shadow test, exactly as round 3 already matched
    `createRequire` — otherwise `import proc from "node:process"` or
    `const { getBuiltinModule } = process` (both genuine declarations) would hide
    the loader, and both were confirmed silent by probe;
    (b) treats the `node:module` **namespace** as capability-bearing however it
    is obtained — `require("node:module")`, `getBuiltinModule("node:module")`,
    `import * as m from "node:module"`, `import m = require("node:module")`, or
    `await import("node:module")` — because the direction's "same as an import of
    node:module" is only true if the import is also covered, and three of those
    five spellings were confirmed silent with a computed `["create"+"Require"]`;
    (c) includes the `process` **carrier** in the computed-member rule, so
    `process["getBuiltin" + "Module"]` fails closed (confirmed silent before);
    (d) reads `.call`/`.apply` reflection over the builtin loader, for symmetry
    with `require.call`; and
    (e) treats the base of a computed member read as *consumed*, so the construct
    yields exactly one finding at the access rather than two. (a)–(d) only turn
    passes into failures; (e) only removes duplicate output and cannot hide a
    reference, because the access itself is always reported.
11. **Four round-6 additions beyond the binding direction**, recorded so they are
    not silent. The direction named "a member access whose property is
    `constructor` (dot `.constructor` or computed `["constructor"]`)"; the
    implementation also
    (a) **folds** a computed key that is a literal concatenation, a fully
    constant template literal, or an identifier bound to a string constant in the
    file, so `f["constr" + "uctor"]` and `const k = "constructor"; f[k]` are the
    same finding — all three were confirmed silent by probe on `a187ccf`, and the
    fold is file-wide rather than scope-aware, which can only over-flag;
    (b) covers the **destructures** `const { constructor } = f`,
    `const { constructor: F } = f` and `const { ["constructor"]: F } = f`, which
    are the same acquisition in binding-pattern form and were also confirmed
    silent;
    (c) **refuses** the direction's optional non-function exemption
    (`assumptions` 8d.1), so `[].constructor` is a finding — this is the only
    place round 6 is *stricter* than the direction allowed, and it is pinned by a
    test so it can be argued with;
    (d) makes the round-5 computed-capability rule **stand down** when the key
    folds to `constructor`, so `const k = "constructor"; require[k]` yields one
    finding (the more specific one) rather than two. (a)–(c) only turn passes
    into failures; (d) only removes duplicate output and cannot hide anything,
    because the round-6 finding is always emitted in its place.

    Also recorded here as a **refactor**, not a rule change: the six-way nested
    ternary that built the `F-OPAQUE` message and fix became two module-level
    lookups (`OPAQUE_MESSAGES`, `OPAQUE_FIXES`). Every pre-existing message
    string is byte-identical, and the round-5 tests that assert those strings
    pass unmodified.
12. **Three round-7 additions beyond the binding direction**, recorded so they
    are not silent. The direction named the carrier chain `process.mainModule`,
    `globalThis.process.mainModule`, a tracked `process` alias `.mainModule`,
    `require.main`, and aliases; the implementation also
    (a) adds `mainModule` to the `process`-carrier **destructure** map so
    `const { mainModule } = process; mainModule.require(…)` resolves — without it
    the destructure binds a *genuine* local `mainModule` that shadows the carrier
    and the load is silent (confirmed silent on `900b299`);
    (b) **broadens the `CAP_MODULE` escape label** from "the CommonJS `module`
    global" to "a CommonJS `Module` object (`module`, `process.mainModule`, or
    `require.main` …)", because that capability now denotes three spellings — no
    test asserted the old string, so nothing regressed; and
    (c) **declines** to resolve `module.parent`/`module.children[i]` into
    capabilities (they are already escape findings, and resolving them would grow
    the recognised set) — recorded as a deliberate non-change so the asymmetry
    with `require.main` is a documented choice, not an oversight. (a) only turns a
    pass into a failure; (b) and (c) change no verdict.

    One **consequence** stated plainly so a reviewer can weigh it: because
    `require.main` now resolves to the precise specifier, `require.main.require(X)`
    where `X` is a specifier the package *permits* (e.g. `ethers` in
    `packages/ledger`, whose only forbidden-specifier rule is F4) is now clean,
    where on `900b299` it was a generic `F-OPAQUE` escape. This is a precision
    improvement, not a new bypass: it is identical to `require(X)` and
    `module.require(X)`, which are already clean for a permitted `X` in the same
    package, and every *forbidden* `X` (an F4 strategy in the ledger; a signer/
    built-in in a strategy, simulation, or domain), every computed `X`, and every
    bare capability escape still fails.

## known_risks

1. **Parser brittleness against contract edits.** The layer-1 *class* entry
   exists only in a prose sentence ("`packages/strategies/**` is a
   **restricted** member of this layer"). If a future contract edit rewords that
   sentence, `packages/strategies/static-bracket` becomes unclassified and CI
   fails closed with an actionable message — correct behaviour, but the failure
   will look unrelated to the edit that caused it. `follow_up` 1 proposes the
   durable fix, which requires editing `docs/contracts/**` (forbidden to this
   package).
2. **A parser, not a lexer — and what the parser still cannot know.** Round 1's
   `lexSource` claimed both of its residual limits "fail in the noisy direction,
   not the silent one". Round 2 proved that claim false in both halves: the
   regex-versus-division heuristic *blanked executable code* (`value! /
   Math.random() / 2` was read as a regex literal and produced no finding), and
   the 96-character specifier lookbehind *lost real imports* separated from
   their keyword by a longer comment. Both were silent passes. The lexer is
   gone; rule 3 is now `ts.createSourceFile` plus one AST walk, and comments,
   strings and regex literals are inert by construction rather than by
   heuristic. The residual limits are now these, and each is stated as what it
   is rather than as a claim about noise:
   - **No type checker and no cross-file resolution.** "Global" means "not bound
     by a declaration in this file". A `var` declared in a nested block and used
     in an outer scope is not recognised as a shadow, so it yields a spurious
     finding naming an exact `file:line` — noisy, not silent. The mirror case is
     the one to watch: a name *declared* in the file is trusted to shadow, so a
     declaration that appears textually after the use it "shadows" (illegal at
     run time under TDZ, but syntactically parseable) would suppress a finding.
     Nothing in the repository does this and no probe has produced it, but it is
     a real hole rather than a proof of its absence.
   - **`.js`/`.cjs`/`.mjs` are parsed as JavaScript, `.ts`/`.tsx` as
     TypeScript.** A file whose extension misdeclares its dialect may parse with
     errors — which is now a `CHK` error, not a skipped file.
   - **`typescript` must be resolvable.** It is a root devDependency, and if it
     cannot be loaded the check emits `CHK` and exits non-zero. It is not
     vendored, so an environment that runs the checker without installing first
     gets a hard failure rather than a scan of nothing.
   - **Reachability is still not modelled.** The check reports what the source
     *names*; it cannot tell whether a flagged reference is on a live path, and
     it cannot follow a capability handed in from another package.
3. **F11 applies to strategy test files too** (assumption 6). When `WP-220`
   writes tests for `packages/strategies/static-bracket`, a test that calls
   `Math.random()` or `Date.now()` will fail this gate. That is arguably right
   (a strategy's tests should be deterministic too) but it is a decision the
   contract does not state; `follow_up` 2.
4. **The library catalogues are enumerations, not classifications — this is a
   floor, not a ceiling.** `REDIS_CLIENTS`, `DATABASE_CLIENTS`,
   `SIGNER_LIBRARIES`, `NETWORK_LIBRARIES`, `VENUE_SDKS` and
   `FILESYSTEM_LIBRARIES` name the packages known today. **A filesystem,
   database, network or signing library that is not on a list is not caught by
   rule 3.** There is no mechanical way to decide "is this npm package a
   filesystem wrapper" from its name, so no list here can be complete, and the
   check must not be read as proving the absence of I/O in a strategy — only the
   absence of *enumerated* I/O.
   Round 1 found this concretely: `fs-extra` reached the filesystem without ever
   naming `node:fs` and passed. `fs-extra`, `graceful-fs`, `chokidar` and a
   dozen other common wrappers are now listed, and `DATABASE_CLIENTS` was
   widened past PostgreSQL to match ADR-005 §1's word "database" — but the next
   unlisted wrapper will pass in exactly the same way.
   The compensating controls are that adding a dependency to an owned package is
   a reviewed, lockfile-touching event (§7 of the contract), that a *workspace*
   edge to an owning adapter package is still caught by rule 2, and that the
   built-in and global routes into a restricted package are now genuinely
   caught: the impure-global scan (F1/F3/F11) covers the clock/randomness/
   environment/network globals regardless of library name, and — since round 3 —
   the `require` **family** (bare, wrapped, aliased, `module.require`, reflected,
   ambient-`declare`d, and `createRequire`) routes every statically readable
   specifier through the same F1–F8/F11 classification and fails closed
   (`F-OPAQUE`) on a computed one.
   Round 3 stated this as "a restricted package can no longer reach an
   *enumerated* library or a built-in through a `require` shape". **That claim
   was false as written, and round 4 disproved it with seven working silent
   loads** — the round-3 rule enumerated the require *positions* it could read,
   and an enumeration of positions is not a rule about all positions. Round 4
   then claimed the replacement was true "by construction", and **round 5
   disproved that too**, with one working silent load through
   `process.getBuiltinModule`, a built-in loader that had never entered the
   require-family machinery. The honest statement is the one in risk 9: the
   escape rule is total over the loaders the check *recognises*, and the
   recognised set (like the library catalogues) is a list. Two residual gaps
   therefore stand together and should be read as the same kind of limit — an
   *unlisted* library wrapper imported by a statically readable name still passes
   F1–F8/F11, and an *unrecognised* loader spelling is not a reference the escape
   rule can fire on. The lists live
   in one clearly-marked block at the top of the script with a `KNOWN LIMIT`
   note; extend them when a new library enters the repository.
5. **The check does not evaluate §4's interface-versus-implementation
   discipline.** §4 says so itself ("If Redis concepts … surface in a consumer's
   types, the boundary has been broken in substance even though the layer check
   passes"). That remains a review obligation.
6. **`node_modules` is not consulted.** Transitive/vendored code is out of
   scope; the check reads manifests and first-party source only. Dependency
   vulnerability scanning is a separate existing CI step.
7. **Reference-level global detection is deliberately noisy in two places.**
   `const { max } = Math;` and `const c = crypto;` are findings even though the
   destructured member is pure, because a bare reference to either root reaches
   `Math.random`/`crypto.getRandomValues` through an alias and no static check
   survives that. `Math.min`/`Math.max`/`Math.abs` used directly are not
   findings. If `WP-220` hits this, the fix is to use the members directly, not
   to relax the rule.
8. **The scan still applies to strategy *test* files** (`assumptions` 6,
   risk 3), and the round-2 semantics make that stricter: a strategy test that
   calls `new Date()`, `setTimeout`, or `Math.random()` now fails the gate.
9. **The capability-escape rule (round 4, widened in round 5) is intentionally
   noisy, and its noise lands on future package owners.** Inside
   `packages/domain`,
   `packages/strategies/**`, `packages/ledger` and `packages/simulation`, *any*
   reference to `require`/`module`/`createRequire`/`process.getBuiltinModule`/the
   `node:module` namespace outside the analysed positions
   fails the gate — including references that load nothing, such as
   `const has = Boolean(require)` or a local helper named `createRequire` or
   `getBuiltinModule`. A **computed** member read on one of those
   (`require[k]`, `process[key]`) fails the gate for the same reason. There
   is no allowlist and no suppression comment, deliberately: a suppression
   mechanism is how a "never silent" rule becomes silent. If `WP-220` or a later
   package hits this, the fix is to delete the reference, not to relax the rule —
   a package under F1/F2/F3 loads no module at run time and receives every
   capability it needs as a constructor or `StrategyContext` argument.

   **What the rule's totality does and does not mean (corrected in round 5).**
   Round 4 recorded here that "the rule is total over *references the walk
   sees*". Read as a claim about coverage that was too strong, and round 5
   disproved it with a working silent load: the rule is total over references the
   walk resolves to a **recognised** loader, and `process.getBuiltinModule` was
   not recognised, so `getBuiltinModule("node:module")["create" + "Require"]`
   moved a live `require` into `packages/simulation` with the scanner reporting
   nothing. The corrected statement, matching `assumptions` 8b/8c: the rule is
   total over statically visible references to the loaders in the recognised set
   (ambient `require`, the CommonJS `module` global, `createRequire` and its
   result, `process.getBuiltinModule`, the `node:module` namespace, and tracked
   aliases of those), and a computed member read on any of them fails closed
   rather than resolving to nothing. Three consequences stated plainly: a finding
   proves only that the capability left the positions the check reads, **not**
   that a forbidden module was loaded; **a loader spelling that is not in the
   recognised set is not covered** — this is the same class of limit as the
   library catalogues in risk 4, and it is the class of defect rounds 3, 4, 5, 6,
   7, 8 and 9 each closed once (round 7: `process.mainModule`/`require.main`;
   round 8: NAMED/renamed `node:module` imports; round 9: a `new`-result escape).
   Round 8 claimed the **ordinary-code** surface — non-reflective, single-file,
   statically named — was exhausted; round 9 disproved that (the `new`-result
   escape was exactly such a route). After round 9 the value-producing forms
   (identifier, property/element access, CALL result, and `new` result) are all
   covered by the escape rule; the set that remains non-empty is the
   reflective / runtime-computed-member / cross-file residual (risk 2's limits
   below, and reflective getters in risk 10), which the negative list cannot
   close and only the positive rule in `follow_up` 8 subsumes. The rule still
   inherits risk 2's limits (no cross-file resolution, no reachability, and a
   capability handed in from another package is invisible).
10. **The evaluator surface was a list too, and what round 6 leaves open.** Until
    round 6 the evaluator rule matched exactly two identifiers, `eval` and
    `Function`, and `assumptions` 8 had called that "a reference to
    `eval`/`Function`" as though it were the whole surface. It was not:
    `.constructor` hands out the same `Function` constructor without naming it,
    which is **arbitrary code evaluation — the broadest possible escape**, and it
    was silent in all four restricted packages. It is one of *seven* consecutive
    rounds in which the defect was the same shape: *a recognised-name list, or a
    node-filter, that was assumed complete and was not.* Rounds 3 (the `require`
    family), 4 (unconsumed capability references), 5 (`process.getBuiltinModule`),
    6 (`.constructor`), 7 (`process.mainModule`/`require.main`), 8 (NAMED/renamed
    `node:module` imports) and 9 (a `new`-result escape) each closed exactly one
    missing member or form. Round 8 called the ordinary-code surface exhausted;
    round 9 falsified that by finding a silent `new`-result escape, so the honest
    reading is: after round 9 every value-producing form is covered, and what
    remains is the reflective / runtime-computed-member / cross-file residual,
    which is inherent to a name-enumeration scanner rather than one more spelling
    to add. The honest reading is still **not** "the list is now complete" for
    reflective/cross-file access; it is that only the positive rule can be total
    over it. `follow_up` 8 records that durable form for the WP-030 contract owner
    and remains the real fix.

    **The noise this lands on future package owners.** Because there is no
    non-function exemption, ordinary reflective idioms fail the gate inside the
    four restricted packages, and they are worth naming so `WP-220` and later
    owners are not surprised: `this.constructor.name` (a common `toString`/logging
    idiom — verified flagged in `packages/ledger`), `value.constructor === Foo`
    and `x.constructor === Object` type tests, `Object.getPrototypeOf(v).constructor`,
    `v?.constructor`, and a `{ constructor: F }` parameter destructure. Each was
    probed and each flags. There is no allowlist and no suppression comment, for
    the same reason round 4 gave: a suppression mechanism is how a "never silent"
    rule becomes silent. The fix when one of these is hit is to use a different
    idiom — `Object.prototype.toString.call(v)`, an explicit discriminant field,
    or `v instanceof Foo` (which is *not* a finding) — not to relax the rule. If
    that proves untenable in practice, the decision belongs to the contract owner
    via `follow_up` 6, not to a local exemption.

    Two things round 6 deliberately does **not** close, stated so they are not
    discovered later:
    - **A property name computed at run time is not folded.** The rule folds
      literals, `+` concatenations, constant template literals and file-level
      string constants; `f[parts.join("")]` reaches `constructor` and this check
      cannot see it. Closing it would mean flagging *every* dynamic-key read in a
      restricted package, which contradicts the accepted round-5 ruling that
      `table[key]` on a non-capability object adds no noise. That trade is a
      contract-owner decision, not a tooling one, and it is filed as
      `follow_up` 9.
    - **Reflective property getters are not modelled.** `Reflect.get(f,
      "constructor")` and
      `Object.getOwnPropertyDescriptor(f, "constructor").value` are not member
      accesses and are not caught. `Object.getPrototypeOf(f).constructor` *is*
      caught, because it still ends in a `.constructor` read.
11. **Two ambient routes examined in round 6; the first CLOSED in round 7, the
    second an accepted exclusion.** The round-6 review raised both as NOTEs. Round
    7 re-audited both together with the full ambient-loader surface (see "Review
    round 7"): `process.mainModule`/`require.main` is now a finding, and
    `process.binding`/`process._linkedBinding` remains a documented,
    runtime-justified exclusion.
    - **`process.mainModule` — CLOSED in round 7 (was follow_up 10).** The
      round-6 review's NOTE said it is absent on Node 24 and therefore not viable;
      that was corrected here against runtime evidence: measured on Node v24.13.0,
      `process.mainModule` is `undefined` under an **ESM** entry point (this
      repository's shape) but a live `Module` under a **CommonJS** one, and
      `process.mainModule.require("ethers")` in `packages/simulation` scanned
      clean on `900b299`. Round 6's scope was `.constructor` only, so it was
      surfaced as `follow_up` 10 rather than fixed. **Round 7 closes it**:
      `process.mainModule` and `require.main` now resolve to the `CAP_MODULE`
      capability (`assumptions` 8e), so `.require(...)` is a require-load
      classified like an import, a computed member fails closed, and a bare escape
      is `F-OPAQUE`. This entry is retained (rather than deleted) as the record of
      a runtime fact and its closure.
    - **`process.binding`/`process._linkedBinding` remain out of scope as
      internal APIs.** They are covered by the disclosed unrecognised-loader
      limitation (risk 9). Both are still live on Node v24.13.0 (`process.binding("fs")`
      returns an object under both ESM and CJS entry points), so "deprecated" is
      not "unreachable"; they are out of scope because they are internal Node APIs
      no first-party code has any reason to name, not because they do not work.
      Round 7 re-audited this and leaves the round-6 ruling unchanged: `process`
      is a carrier, `.binding` is not a resolved loader member, and the route is
      an accepted, runtime-justified exclusion rather than a closed finding.

### The fix: the rule is inverted, and is now total by construction

> In a purity-restricted package (`packages/domain`, `packages/strategies/**`,
> `packages/ledger`, `packages/simulation`), **any** reference to a require

> finding, reported as `F-OPAQUE` with the escape shape named.

A "require capability" is the ambient `require`, the CommonJS `module` global,
`createRequire` (which manufactures one), the result of calling it, and any alias
the check tracks to one of those. The closed list of positions that do *not*
additionally flag, because the value is followed through them:

| Position | Why it is consumed |
| --- | --- |
| Callee of an analysed call | Produces the specifier (F1–F8/F11) or `F-OPAQUE` |
| `.call`/`.apply` reflection callee | Same, with the specifier at index 1 |

### The fix (binding orchestrator direction)

1. **`process.getBuiltinModule` is a loader capability** in the specifier

   `.createRequire` member is the factory.
2. **A computed member read on a capability-bearing expression fails closed.**

   `node:module` namespace, the `createRequire` factory or its result,

### The terminal position, stated plainly and finally (corrected at round 9)

**The round-8 phrasing here — "no ordinary-code silent route is known" — was
premature.** The round-9 review found one more ordinary-code, single-file,
statically-named route the negative list had missed: a capability-bearing `new`
result whose value ESCAPES. `capabilityOf` recognised `new Module(...)` as a

value-producing form the negative list had not yet enumerated.

Round 9 generalises the round-4/5 escape rule to the one value-producing arm it
had skipped. After this fix the escape rule is total over **every** value form
the walk sees:

> In a purity-restricted package, a capability-bearing VALUE — an identifier
> read, a property/element access, a CALL result, or a `new` result — that
> reaches any position this check does not follow is ITSELF a finding.

A `new M(...)` result is CONSUMED (no finding) only where the module-call
visitor already reads it: the direct base of `.require(...)` (absorbed), or an
argument of an analysed loader call / `.call`/`.apply` reflection
(`M._load("x", new M(u), false)`, `M.prototype.require.call(new M(u), "x")`).
Everywhere else it is an F-OPAQUE escape naming the shape. The symmetric
`require`-capability CALL result escaping directly (`pass(createRequire(url))`,
no intervening binding) was already covered by the round-4 `CallExpression`
arm — verified by probe, pinned by test — so `new` was the single omitted
value-producing arm, and it is now closed.

The residuals that remain are **not** one-more-spelling-to-add; they are inherent
to a name-enumeration scanner, and are now exactly three:

1. **Reflective property acquisition** of a loader or evaluator, which names no
   member the walk can read — `Reflect.get(process, "mainModule").require(...)`,
   `Reflect.get(fn, "constructor")(...)`. Accepted as a documented limitation.
2. **Runtime-computed member names** — a member read whose key is only known at
   run time on a base the walk does not recognise as a capability (a recognised
   capability base already fails closed via the round-5 computed-access rule);
   the walk cannot fold the name statically.
3. **Cross-file capability injection** — a loader handed in from another package
   is invisible to a single-file, no-type-checker, no-reachability walk
   (`known_risks` 9, 11).

All three are subsumed by the DURABLE FIX: the POSITIVE rule in `follow_up` 8 —
"a call whose callee does not statically resolve to a declared import binding or a
known-pure local is a finding." That rule is total over what the walk sees
*regardless* of which loader/evaluator the callee names, so it ends the
add-one-member pattern (of which round 9 is the latest instance). It is
explicitly the **WP-030 contract owner's** to authorize, not this package's: it
needs a numbered `docs/contracts/**` §3 rule and carries a real noise trade-off
(it flags every dynamically-dispatched call in a restricted package) that
requires contract-level buy-in. This is the accurate closing position — the
negative-list approach is provably incomplete (round 9 is the proof), and the
positive rule is the only form a checker can be total over.

### The gap: a `new`-result that escapes into a same-file helper

`capabilityOf` had recognised `new Module(...)` as a `Module` instance whose

### The fix: generalise the escape rule to the `new`-result value

The escape visitor's node filter now includes `ts.isNewExpression(node)`, so a
`new <node:module Module>(...)` result is a capability-bearing value subject to
the SAME round-4/5 escape rule as an identifier / property / call result. It is
CONSUMED (no finding) only where the module-call visitor already reads it:

- the direct base of `.require(...)` — `new M(url).require("ethers")` — absorbed
  by the existing `isAbsorbedCapability` rule (the enclosing `.require` member is
  itself a capability), so the direct chain stays the precise **single F5**, not
  double-reported;
- an argument of an analysed loader call / `.call`/`.apply` reflection — the
  `thisArg` of `M.prototype.require.call(new M(url), "ethers")` and the parent of
  `M._load("ethers", new M(url), false)` — consumed by a new
  `capabilityIsConsumed` branch (an argument to a callee that resolves to a
  loader-call label or a loader reflection), so those stay a **single F5** too.

Everywhere else — `load(new M(url))` (non-loader callee), `[new M(url)]`,
`return new M(url)`, an assignment RHS — the `new M(...)` result is an F-OPAQUE
capability escape reported at the NewExpression, naming the shape. A `new M(...)`

package), and a genuine local `class Module {}` instance stays clean (its
