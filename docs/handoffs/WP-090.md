## summary

`packages/coinbase-adapter` now normalizes the **public, unauthenticated Coinbase
Advanced Trade market-data WebSocket** into the frozen domain reference
contracts, replacing the WP-010 placeholder scaffold.

- **Surface chosen:** `wss://advanced-trade-ws.coinbase.com`, channels
  `market_trades` (→ `ReferenceTradeObserved`), `ticker` (→
  `ReferenceTopOfBookChanged`), and `heartbeats` (liveness and a second,
  independent gap signal). The rationale and the rejected alternative (Coinbase
  Exchange market data) are in `packages/coinbase-adapter/VENUE.md` §1.
- **Connection and reconnect manager** (`connection.ts`) owns the socket and the
  two timers and nothing else; every judgement is delegated to a pure
  `CoinbaseStreamProcessor` (`stream-processor.ts`) that holds no socket, no
  timer, and no network. That split is why the whole contract suite runs offline.
- **Reconnect is never a silent resumption.** A replaced connection emits, in
  order: `FeedDisconnected` → `FeedConnected` on a new `subscriptionGeneration` →
  `FeedGapDetected` (`requiresAuthoritativeSnapshot: true`) →
  `DataQualityIncidentOpened` recording that missed trades are unrecoverable →
  and only once the venue's own `snapshot` events have arrived on every declared
  channel **and been applied in full**, `FeedResynchronized`. A snapshot with an
  entry the adapter had to refuse is not an authoritative statement of current
  state: it reports `COINBASE_SNAPSHOT_NOT_APPLIED` and leaves the gap open
  (remediation round 1, finding H1).
- **Venue and receipt timestamps stay distinct.** `venueTimestamp` is the trade's
  own `time` (or, for a ticker, the message `timestamp` — the only venue time
  that channel supplies); `receivedAt` and `receivedMonotonicNs` come from
  injected clocks and are never derived from a venue field; the message-level
  `timestamp` is preserved as a third fact in `venueDetail.venueMessageTime`.
- **Staleness is typed data**, not a log line: `CoinbaseFeedMetrics` (global and
  per channel), a `COINBASE_FEED_STALE` anomaly, and a `FeedStale` domain event
  carrying the same number. No `packages/observability` dependency and no
  Prometheus.
- **Nothing is ever dropped in silence.** *Every frame is accounted for* — it is
  counted, and unless it was refused before any state could be touched it also
  advances the sequence and per-channel state the metrics expose — and *every
  non-conforming or suppressed market-data path yields a typed `CoinbaseAnomaly`
  with the raw frame preserved*. Some conforming frames legitimately yield
  neither a normalized event nor an anomaly: a heartbeat and a `subscriptions`
  acknowledgement carry no market data, and `test/contract/coinbase/malformed.test.ts`
  names exactly those. Nineteen anomaly codes, each already a valid `CodeString`
  so it can be a `DataQualityIncidentOpened.reasonCode` without a translation
  table. *(Corrected in remediation round 1, finding L1: the original wording —
  "every frame yields normalized events, anomalies, or both" — was false.)*
- **Two open repository items settled** — see *Venue facts* below: the ADR-004 §1
  "Coinbase framing to verify" item, and a genuine contradiction between two
  official Coinbase pages about the scope of `sequence_num` (C-CB-1).

### Envelope draft, not an envelope

The adapter emits `source`, `sourceChannel`, `venueTimestamp`, `receivedAt`,
`receivedMonotonicNs`, `connectionId`, and `subscriptionGeneration`, and stops.
`eventId`, `gatewayEpoch`, and `ingestSeq` belong to WP-120 (ADR-002 §2.1,
handoff §9.1); a test asserts the adapter does not mint them.

## Venue facts: what was verified, and what was not

Full detail with URLs in `packages/coinbase-adapter/VENUE.md`; the same content
is machine-readable in `src/venue-facts.ts` and asserted by its colocated test.

### Product chosen, and why

**Coinbase Advanced Trade Market Data WebSocket**,
`wss://advanced-trade-ws.coinbase.com`. Both this and Coinbase Exchange
(`wss://ws-feed.exchange.coinbase.com`) are documented as available without
authentication, so both satisfy the hard rule. Advanced Trade won on three
grounds: the unauthenticated guarantee is stated **per channel** in a table
("Requires Authentication: No") rather than as one sentence about the endpoint; a
published **AsyncAPI 3.0.0** document pins the exact frame shapes the parser
transcribes; and its `ticker` carries **best bid/ask sizes** as well as prices,
which the frozen `ReferenceTopOfBookChanged` contract has fields for. The
authenticated `advanced-trade-ws-user` endpoint and the `user` /
`futures_balance_summary` channels are out of scope by rule.

### VERIFIED (all fetched and read 2026-08-27)

1. Public URL `wss://advanced-trade-ws.coinbase.com`; "A JWT is not required" —
   [endpoints](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-endpoints)
2. Per-channel table marking `heartbeats`, `ticker`, `ticker_batch`, `level2`,
   `market_trades`, `candles`, `status` as needing no authentication —
   [channels](https://docs.cdp.coinbase.com/coinbase-business/advanced-trade-apis/websocket/websocket-channels)
3. The documented public subscribe form, with no `jwt` key —
   [overview](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-overview)
4. Subscribe mandatory within 5 s; one channel per subscription message —
   [overview](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-overview)
5. All messages are JSON objects; new message types may appear at any time —
   [overview](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-overview)
6. Envelope `{channel, timestamp (RFC 3339), sequence_num}`; `sequence_num`
   described as "Per-connection message sequence number" —
   [AsyncAPI](https://docs.cdp.coinbase.com/api-reference/advanced-trade-api/advanced-trade-asyncapi.json)
7. Gap semantics: a forward jump means a dropped message; a lower value may be
   ignored or is out of order; consumers must handle both —
   [overview](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-overview)
8. `market_trades` shape: `events[].type` ∈ {`snapshot`,`update`}, trades of
   `{trade_id, product_id, price, size, side, time}`, `price`/`size` strings,
   `time` RFC 3339, `side` enumerated `BUY`/`SELL` —
   [market-trades](https://docs.cdp.coinbase.com/api-reference/advanced-trade-api/websocket/market-trades)
9. `side` "refers to the makers side" / "The maker's side of the trade";
   updates batch 250 ms —
   [channels](https://docs.cdp.coinbase.com/coinbase-business/advanced-trade-apis/websocket/websocket-channels)
10. `ticker` shape including `best_bid`, `best_ask`, `best_bid_quantity`,
    `best_ask_quantity`, all strings; emits on every match —
    [ticker](https://docs.cdp.coinbase.com/api-reference/advanced-trade-api/websocket/ticker)
11. `ticker_batch` "currently doesn't provide best bid or best ask fields" —
    [channels](https://docs.cdp.coinbase.com/coinbase-business/advanced-trade-apis/websocket/websocket-channels)
12. `heartbeats` once a second with `heartbeat_counter`, no products, no auth —
    [heartbeats](https://docs.cdp.coinbase.com/api-reference/advanced-trade-api/websocket/heartbeats)
13. Most channels close within 60-90 s without updates —
    [endpoints](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-endpoints)
14. A `subscriptions` message answers a subscribe/unsubscribe —
    [overview](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-overview)
15. 8 connections and 8 unauthenticated messages per second per IP —
    [rate limits](https://docs.cdp.coinbase.com/coinbase-app/advanced-trade-apis/websocket/websocket-rate-limits)

### CONFLICT C-CB-1 (resolved, recorded)

Two current official pages disagree about `sequence_num`: the overview says "for
each **product**", the AsyncAPI says "**Per-connection**". Resolved in favour of
per-connection, on the AsyncAPI's authority as the machine-readable spec of these
frames, corroborated by observation O-CB-2. Documented in `src/sequence.ts` at
the point of use. If the venue ever moves to per-product numbering this adapter
reports a storm of gaps rather than mis-detecting quietly.

### Live observation (evidence, NOT documentation)

One read-only, unauthenticated, 25-second subscription to the public endpoint on
2026-08-27, used only where the documentation was silent or self-contradictory.
**No credential was sent, no order was placed, no observed bytes became a
fixture, and no test touches a network.**

- **O-CB-1 — framing (settles an ADR-004 open item).** All 338 frames were UTF-8
  text carrying JSON objects; no binary frame and no bare non-JSON text frame.
  ADR-004 §1 recorded Coinbase framing as "to verify" and warned that
  `payloadUtf8` cannot hold binary. On this evidence **no ADR-004 amendment is
  needed for the Coinbase side**. The adapter still reports a binary frame as a
  `PAGE`-severity anomaly rather than assuming it cannot happen.
- **O-CB-2 — `sequence_num` is per-connection** (0, 1, 2, … across all channels
  and products on one socket). See C-CB-1.
- **O-CB-3 — envelope key set** was exactly `{channel, timestamp, sequence_num,
  events}`, `timestamp` RFC 3339 with nanosecond precision, which
  `IsoTimestampSchema` accepts unchanged.

## assumptions

1. **The gateway (WP-120) completes the envelope.** The adapter emits a draft and
   never mints `eventId`, `gatewayEpoch`, or `ingestSeq` (ADR-002 §2.1).
2. **The caller supplies `feedId`, product ids, thresholds, and the ports.** The
   adapter reads no configuration and no environment; it validates `feedId`
   against the domain `CodeStringSchema` at construction so an invalid value
   cannot surface mid-stream.
3. **A `snapshot`-typed event that the adapter applied in full is the venue's
   authoritative statement of current state**, and is therefore what closes a
   gap. Grounded in the documented `snapshot`/`update` vocabulary, and
   deliberately narrow on three counts, each tested: an *undocumented* event
   type cannot close a gap; a snapshot with an entry the adapter refused cannot
   close a gap; and a snapshot delivered by a superseded connection cannot close
   a gap. An entry that was knowingly *suppressed* — a trade already emitted, a
   top of book identical to the last — does count as applied, because the state
   the snapshot describes is state the consumer already holds. (The last two
   are remediation round 1, findings H1 and H2.)
4. **The first connection opens no gap.** Nothing preceded it, so claiming lost
   data would be a false report. Every subsequent connection does.
5. **A gap forces a new connection, not a re-subscribe on the live socket.** What
   a second `subscribe` for an already-subscribed channel does is undocumented;
   a fresh subscription is documented to begin with a snapshot.
   `CoinbaseStreamProcessor.resubscribed()` is exposed for a caller with its own
   evidence.
6. **`ticker` is the top-of-book source, not `level2`.** The work plan scopes this
   package to trades and top of book; a `level2` frame is reported as
   `COINBASE_UNKNOWN_CHANNEL` rather than parsed.
7. **Suppressing a duplicate or an unchanged top of book is not a §8.3 silent
   drop**, because each suppression emits an anomaly and increments a counter.
   Emitting the same trade twice would corrupt any downstream volume feature.
8. **Node 24's global `WebSocket` is sufficient**, so no `ws` dependency was
   declared and the lockfile grew by nothing on that account.

## deviations

1. **Added `packages/coinbase-adapter/VENUE.md`** (inside the allowed package
   tree). The packet required cited contract documentation for the package;
   `docs/contracts/**` is protected, so it lives in the package.
2. **`test/contract/coinbase/fixtures/*.json` carry a `classification` field**
   beyond the packet's wording. It exists because "this is a malformed fixture"
   and "this frame fails to parse" turned out to be different claims —
   `malformed-nonpositive-size` parses perfectly as `market_trades` and fails at
   the decimal boundary. Declaring the arm keeps that visible.
3. **A read-only live observation was performed** (see above). The packet
   contemplated documentation as the authority; the observation is recorded as
   *evidence*, clearly separated from citations, used only where the docs were
   silent or self-contradictory, and never as a fixture source. It was necessary
   to settle C-CB-1 honestly rather than guess, and it closes the ADR-004
   Coinbase-framing item this package was assigned.
4. **`COINBASE_TIMESTAMP_INVALID` was added to the anomaly set** after the first
   test pass showed that an undocumented time spelling would otherwise be
   passed through and fail envelope validation at the gateway, where the
   offending field is much harder to attribute.
5. **Root wiring untouched.** `test/vitest.config.ts` does not include
   `test/contract/**`, so the contract suite runs only through the package's
   `test:contract` script. Root wiring is orchestrator-owned at merge — see
   `follow_up` 1.

## known_risks

1. **HIGH — the maker-side reading (U-CB-3).** `takerSide` is the *inverse* of
   the documented `side`, on two official statements that it is the maker's side.
   If the documentation is wrong, every `takerSide` this adapter emits is
   inverted, and trade-flow or aggressor-imbalance features built on it would be
   backwards. Mitigations: the derivation is one named function
   (`takerSideFromDocumentedMakerSide`), the raw venue value is preserved on
   every normalized trade as `venueDetail.venueSide` with
   `venueSideMeaning: "MAKER"`, and no recorded event loses the venue's own word.
   Correcting it is a one-function change plus a `schemaVersion` decision for
   already-recorded data (ADR-002 §3).
2. **MEDIUM — `sequence_num` scope (C-CB-1).** Resolved in favour of
   per-connection on strong evidence, but the disagreement is between two current
   official pages and the venue could change either. A move to per-product
   numbering would produce continuous spurious `FeedGapDetected` events and
   continuous forced reconnects. Loud, but disruptive.
3. **MEDIUM — empty or null decimals (U-CB-1).** If Coinbase does send `""` where
   the Polymarket CLOB does, this adapter currently rejects the frame and opens
   an incident rather than mapping to absent. That is the deliberate conservative
   choice, but under real traffic it would be a stream of rejections until the
   handling is settled with evidence.
4. **MEDIUM — the reconnect gap is unbounded and unquantified.** With no replay
   (U-CB-2), the adapter cannot say *how much* was missed, only that something
   was. Downstream volume or VWAP features computed across a reconnect will be
   short by an unknown amount; the incident records the fact but not the size.
5. **LOW — the bounded dedupe window fails toward emission.** A trade that
   reappears after eviction (default 4096 identities) is emitted again. Chosen
   deliberately: a visible duplicate beats an invisible suppression. A very
   large product set with a long outage could see this.
6. **LOW — one live observation is weak evidence.** O-CB-1/2/3 rest on a single
   25-second window. Nothing depends on an observation alone, but they are not
   documentation and are labelled as such.
7. **LOW — staleness polling depends on the caller's timer.** A caller that never
   drives `pollStaleness` (or supplies a starved timer) gets metrics but no
   `FeedStale` events. The bundled manager schedules it; a direct user of the
   processor must.
8. **LOW — `subscriptions` payload is opaque (U-CB-5).** If the venue ever
   reports a *failed* subscription inside that message, this adapter would not
   notice: it counts the frame and reads nothing. It would surface indirectly, as
   staleness on the channel that never arrived.

## Finding-by-finding resolution matrix

### H1 — a malformed snapshot could falsely emit `FeedResynchronized` — RESOLVED

**Probe reproduction (against `44eb525`, verbatim output).**

```text
{"probe":"malformed-only-channel-snapshot","anomalies":["COINBASE_ECONOMIC_FIELD_INVALID"],"feedEvents":["FeedResynchronized"],"gapOpen":false,"normalized":0}
{"probe":"partial-invalid-snapshot-sequence","firstAnomalies":["COINBASE_ECONOMIC_FIELD_INVALID"],"secondFeedEvents":["FeedResynchronized"],"gapOpen":false,"normalizedTotal":1}
```

Confirmed exactly as reported: a `market_trades` snapshot whose only trade the
decimal boundary refused still satisfied its channel, and the resulting
`FeedResynchronized` carried `authoritativeSnapshotApplied: true` with nothing
applied.

**Fix.** Receipt of a `snapshot`-typed event no longer satisfies a channel;
*application* of it does. `#ingestTrades` and `#ingestTicker` now return a
`CoinbaseSnapshotApplication` (`seen`, `fullyApplied`) accumulated from a
per-entry verdict, and `#noteSnapshot` adds the channel to `#snapshotSeen` only
when `fullyApplied`. An entry counts as **applied** when it was normalized and
emitted, *or* when it was knowingly suppressed as state the consumer already
holds — a duplicate trade, or a top of book identical to the last one emitted.
An entry the adapter refused is not applied, and one refused entry disqualifies
the snapshot. The disqualification is reported, not inferred: a new
`COINBASE_SNAPSHOT_NOT_APPLIED` anomaly (severity `NOTIFY`) names the channel and
says the gap stays open, and a `snapshotsNotApplied` counter is exposed.

Why suppression counts as applied: on a reconnect the venue replays trades that
are already in the dedupe window, so every entry of that snapshot is suppressed.
Had suppression counted as "not applied", the gap could never close, the
processor would demand a resubscription for ever, and the manager would reconnect
in a loop. That direction is pinned by its own test.

**Tests (probe → test), `test/contract/coinbase/reconnect.test.ts`.**

- *"does not accept a snapshot it could not apply as an authoritative snapshot"*
  — the malformed-only case, plus the recovery half: the next snapshot that
  *does* apply closes the gap, so a refusal delays resynchronization rather than
  blocking it.
- *"does not let one channel's valid snapshot close a gap the other channel has
  not closed"* — the invalid-trade-plus-valid-ticker case.
- *"counts a snapshot of trades it has already emitted as applied"* — the
  livelock guard above.

New fixture `test/contract/coinbase/fixtures/malformed-snapshot-empty-price.json`
(`SYNTHETIC_COMPLETION`, based on `market-trades-snapshot`, every change listed):
a `snapshot` whose one trade carries `price: ""`, the U-CB-1 case.

**Mutation check.** `#noteSnapshot` reverted to add the channel unconditionally
→ **2 tests fail** (`does not accept a snapshot it could not apply…`, `does not
let one channel's valid snapshot…`); the rest of the suite passes, so the two
new tests are what hold the property.

### H2 — old-connection frames were relabelled as current-generation data — RESOLVED

**Probe reproduction (against `44eb525`, verbatim output).**

```text
{"probe":"old-generation-frame","processorGeneration":1,"emittedGeneration":1,"emittedConnection":"coinbase.reference-c2","anomalies":[],"normalized":2}
{"probe":"old-socket-late-close","feedEvents":["FeedDisconnected"],"socketsOpened":2,"generation":1}
```

Confirmed: a frame delivered by the *first* socket after the second was already
open was published under `connectionId` `…-c2` and generation 1, with no anomaly;
and a late `onClose` from the superseded socket produced a `FeedDisconnected` for
the connection that was still open.

**Fix, in two places, both required.**

1. **Processor.** `ingestFrame(raw, from?: CoinbaseFrameOrigin)`. When `from` is
   supplied and its `connectionId` is not the current one, the frame is refused:
   a `COINBASE_STALE_CONNECTION_ACTIVITY` anomaly carrying the raw bytes, the
   channel and the sequence number, and **no** state change — no sequence
   observation, no dedupe entry, no snapshot mark, and deliberately **no
   staleness reset**, because a frame from a dead socket is not evidence that the
   live one is alive. `framesFromStaleConnection` counts it. `from` is optional
   so a caller with one connection in view (a replay, a hand-driven test) can
   omit it; the processor then says it cannot check by not checking, rather than
   guessing.
2. **Connection manager.** Each listener closes over its own connection ordinal
   and id, and asks `isCurrent()` first. `onFrame` passes `{ connectionId }` down
   so exactly one place decides; `onOpen`, `onClose` and `onError` from a
   superseded socket call the new
   `CoinbaseStreamProcessor.staleConnectionActivity(...)`, which emits the same
   anomaly and changes nothing — no `FeedDisconnected`, no reconnect scheduled,
   no error folded into the live connection's next close. The identity is the
   **ordinal, not the socket object**: `socketFactory.connect` may invoke
   `onOpen` before it returns, when `this.#socket` is not yet assigned, and
   comparing against it would misjudge the current connection as stale.

**Tests (probe → test).**

- `reconnect.test.ts`, processor: *"refuses a frame delivered by a connection it
  has already replaced"* — the frame used is a `snapshot`, so it also pins the
  H1/H2 interaction the reviewer named ("could also satisfy H1's
  resynchronization gate"); *"accepts the same frame when it comes from the
  current connection"* (the fix must not refuse live data); *"does not let a
  stale frame stand in for liveness on the current connection"*.
- `reconnect.test.ts`, manager: *"refuses a frame delivered late by a socket it
  has already replaced"*; *"does not report a superseded socket's late close as
  the live connection's disconnect"* (also asserts no second reconnect was
  scheduled, over 60 simulated seconds); *"ignores a late error from a superseded
  socket instead of folding it into the next close"*.
- `packages/coinbase-adapter/src/stream-processor.test.ts`: *"records a
  superseded connection's callback without changing any state"*.

**Mutation check**, three independent reversions:

| Reverted | Failing tests |
| --- | --- |
| processor origin check disabled | 3 (`refuses a frame delivered by a connection…`, `does not let a stale frame stand in for liveness…`, `refuses a frame delivered late by a socket…`) |
| manager `isCurrent()` forced to `true` | 3 (all three manager tests) |
| manager stops passing `{ connectionId }` | 1 (`refuses a frame delivered late by a socket…`) |

### M1 — a rejected trade poisoned the duplicate window — RESOLVED

**Probe reproduction (against `44eb525`, verbatim output).**

```text
{"probe":"rejected-trade-poisons-dedupe","firstAnomalies":["COINBASE_ECONOMIC_FIELD_INVALID"],"secondAnomalies":["COINBASE_DUPLICATE_TRADE"],"secondNormalized":0,"tradesNormalized":0}
```

Confirmed: the corrected copy of a trade that had never been emitted was
suppressed as "already normalized" — a silent drop of a real trade wearing a
duplicate's label.

**Fix.** `CoinbaseTradeDeduplicator.observe` (ask-and-reserve in one call) is
replaced by `isKnown` (pure question) and `remember` (record). The processor
calls `remember` only after `normalizeTrade` succeeded and the event was pushed.
`remember` is idempotent and does not move a known identity in the eviction
order, so the window keeps its first-seen FIFO semantics under a replayed
snapshot. The key helper is extracted and its `U+0000` separator is now written
as an escape rather than as a literal control byte in the source.

**Tests (probe → test), `test/contract/coinbase/duplicates.test.ts`.**

- *"does not let a REFUSED trade reserve its identity"* — malformed copy, then
  the venue's corrected copy, which must be emitted.
- *"reports a refused trade again rather than calling the second copy a
  duplicate"*.
- *"still suppresses the second copy of a trade that WAS normalized"* — the
  guard that the fix did not simply turn duplicate suppression off.
- `packages/coinbase-adapter/src/dedupe.test.ts`: *"does not reserve an identity
  merely by asking about it"* and *"does not move a known identity in the
  eviction order when remembered again"*.

New fixture `test/contract/coinbase/fixtures/market-trades-corrected-price.json`
(`SYNTHETIC_COMPLETION`, based on the H1 fixture): the same
`(product_id, trade_id)` with a usable price.

**Mutation check.** Identity recorded before normalization again → **2 tests
fail** (`does not let a REFUSED trade reserve its identity`, `reports a refused
trade again…`).

### M2 — silent non-conforming paths in the anomaly taxonomy — RESOLVED

**Probe reproduction (against `44eb525`, verbatim output).**

```text
{"probe":"invalid-message-time-market-trades","classification":"MARKET_TRADES","normalized":1,"anomalies":[],"preserved":"not-rfc3339","metricVenueTime":"not-rfc3339"}
{"probe":"invalid-message-time-heartbeats-and-control","heartbeatAnomalies":[],"controlAnomalies":[],"perChannel":[["heartbeats","yesterday"],["subscriptions","soon"]]}
{"probe":"heartbeat-counter-nonadvance","repeatAnomalies":[],"regressAnomalies":[],"heartbeatGaps":0}
```

Confirmed on all three channels for (1), and on both the repeat and the backward
step for (2).

**Fix (1) — every envelope timestamp is validated before it is recorded as venue
time.** `ingestFrame` runs `IsoTimestampSchema` on `classified.frame.timestamp`
for **every** classified arm — market trades, ticker, heartbeats, and the
`subscriptions` control frame — before `#recordChannel`. A value that fails
emits `COINBASE_TIMESTAMP_INVALID` with the raw frame, and
`perChannel[].lastVenueTimestamp` is cleared rather than set: the field is typed
as the venue's own time, and an unvalidated string there is a claim the adapter
cannot support. Three deliberate non-changes: the wire schema stays permissive
(`z.string().min(1)`), because rejecting the whole frame would discard real
trades over a misspelled publication time; the trade is still normalized, with
its own RFC 3339 `time` as `venueTimestamp`; and the raw value is still preserved
verbatim in `venueDetail.venueMessageTime`, which is a record of what arrived,
not a claim that it is a timestamp. `lastMessageAt` and `framesReceived` still
advance, so the frame remains accounted for.

**Fix (2) — the heartbeat counter is classified explicitly.** The
`if (observation.kind !== "GAP") continue;` — the exact shape that let a repeat
or a regression pass without a report — is replaced by an exhaustive `switch`
over `FIRST | IN_ORDER | REGRESSED | GAP`. `REGRESSED` emits a new
`COINBASE_HEARTBEAT_REGRESSED` (severity `NOTIFY`) and increments
`heartbeatRegressions`. It is deliberately **not** a gap and forces no
resubscription: nothing is provably missing. It is a distinct code from
`COINBASE_SEQUENCE_REGRESSED` because the two counters are independent facts and
one code could not say which stopped advancing.

**Tests (probe → test), `test/contract/coinbase/malformed.test.ts`** — two new
describes, seven tests: the market-trades case (anomaly, trade kept, raw value
preserved, `lastVenueTimestamp` refused, `lastMessageAt` still recorded), the
heartbeat case, the `subscriptions` control-frame case, a valid timestamp still
recorded unchanged, the repeated counter, the backward counter, and a forward
jump still reported as a gap.

New fixture
`test/contract/coinbase/fixtures/malformed-envelope-timestamp.json`, plus a
`frameTextWithTimestamp(id, timestamp)` helper alongside the existing
`frameTextWithSequence`, so the heartbeat and control cases are one documented
frame with one envelope field visibly replaced rather than a forked fixture.

**Mutation check.** Timestamp validation removed → **3 tests fail** (the three
envelope-timestamp reports). The `continue`-for-everything-but-`GAP` restored →
**2 tests fail** (both heartbeat non-advance tests).

## assumptions

1. **"Applied" is the right bar for closing a gap**, and a knowingly suppressed
   entry meets it. A duplicate trade and an unchanged top of book are state the
   consumer already holds, so a snapshot restating them does establish the state
   it describes. The alternative reading — only newly emitted entries count —
   makes the ordinary reconnect replay unable to close its own gap.
2. **A misspelled envelope timestamp does not disqualify a `market_trades`
   snapshot.** The snapshot's authority is its entries; the envelope time is the
   batch's publication time and carries no state. (For `ticker` the question does
   not arise: the message timestamp *is* that channel's venue time, so the entry
   fails normalization and the snapshot is disqualified through the entry rule.)
3. **`connectionId` alone identifies a socket for the origin check.** It is
   minted once per connection attempt and never reused, whereas a generation can
   advance on a live socket via `resubscribed()`, so keying on the generation
   would refuse legitimate post-resubscription frames.
4. **Refusing a stale frame is better than relabelling it.** Its data is already
   covered by the reconnect gap and its permanent incident, and the raw bytes are
   preserved on the anomaly, so nothing is lost in silence.

## deviations

1. **Three anomaly codes were added** (16 → 19). The packet's remediation for H1,
   H2 and M2(2) each requires the condition to be *reported* rather than merely
   handled, and reusing `COINBASE_SEQUENCE_REGRESSED` for a heartbeat, or leaving
   a non-applied snapshot to be inferred from the absence of an event, would have
   been a quieter kind of the defect under repair.
2. **`CoinbaseTradeDeduplicator.observe` was removed rather than kept alongside
   the new pair.** Leaving an ask-and-reserve method in the class would leave the
   exact call the finding is about available to the next caller.
3. **The dedupe key's separator changed from a literal `U+0000` byte in the
   source to the escape `\u0000`.** Same string value, same behaviour; the
   literal control character was invisible when reading the file (it is what made
   the first attempt to edit that function fail to match).
4. **The `stream-processor.ts` module header was corrected as part of L1**, which
   the finding cited only against the handoff. The same false sentence was in the
   code.

## known_risks

1. **MEDIUM — a snapshot that never fully applies keeps a gap open.** If a venue
   product persistently sends one entry this adapter refuses, that channel never
   resynchronizes and the manager reconnects on each attempt. That is the
   conservative direction — the alternative is a false claim of recovery — and it
   is loud (`COINBASE_SNAPSHOT_NOT_APPLIED` on every attempt, plus `gapOpen` in
   the metrics), but it is a reconnect loop. A future package may want a bounded
   "degraded resynchronization" state; that is a design decision beyond this
   round's scope.
2. **LOW — a caller that omits `from` gets no origin protection.** The parameter
   is optional so hand-driven callers and replays are unaffected. The bundled
   manager always supplies it; a future direct user of the processor that owns
   its own socket must too. Recorded in the `CoinbaseFrameOrigin` doc comment.
3. **LOW — a refused trade can be reported twice.** With the identity no longer
   reserved on refusal, two malformed copies of the same trade produce two
   refusals. That is the honest count (nothing was emitted either time) and it is
   asserted by a test, but it does mean a persistently malformed trade produces
   an anomaly per redelivery.
4. **LOW — `lastVenueTimestamp` is now clearable.** A channel whose most recent
   frame had an invalid timestamp reports no venue time at all rather than the
   previous frame's. That is deliberate — the field describes the last frame —
   but a consumer that assumed the field was monotone once set will now see it
   disappear.
5. Round-0 risks 1-8 are unchanged and still stand.
