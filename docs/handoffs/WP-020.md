## summary

WP-020 freezes the versioned contracts every later package consumes, plus the
exact-decimal foundation underneath them.

`@polymarket-bot/decimal` (dependency: `decimal.js`; `node:crypto` for pure
SHA-256) implements handoff §7.3 literally. A canonical decimal string is
`-?(0|[1-9][0-9]*)(\.[0-9]*[1-9])?` with canonical zero `"0"`: scientific
notation, a leading `+`, `"-0"`, redundant leading zeros, trailing fractional
zeros, and a trailing decimal point are all rejected. Three grammars are kept
deliberately distinct (`docs/contracts/domain.md` §3.1.1): the canonical
boundary form; the **hash-input** form, which adds only the one relaxation §7.3
sanctions before hashing (redundant leading/trailing zeros and signed zero) and
still rejects `"+1.5"`, `"1."`, `".5"`, `"1e5"`, and non-strings; and the
lenient `normalizeDecimalString`, the one sanctioned way to accept a venue
spelling, scoped to adapters. The strict boundary never coerces. Arithmetic is
string in / string out over `decimal.js` with explicitly configured precision
and rounding: add/sub/mul cannot round (a breach raises a typed error rather
than returning a rounded value), `divDecimal` rounds at 34 significant digits
with ROUND_HALF_EVEN (both overridable), and `divDecimalExact` refuses to round.
Passing a JavaScript `number` throws. Canonical hashing normalizes under the
hash-input grammar and then takes SHA-256 over a domain-separated preimage, so
every *permitted* spelling of one value shares a digest and every forbidden
spelling raises a typed error. Tick conformance scales both operands to exact
integers and takes an integer modulo, so `"0.07"` on a `"0.01"` grid is
conformant where `0.07 % 0.01` in IEEE-754 is not.

`@polymarket-bot/domain` (dependencies: `zod`, `@polymarket-bot/decimal`, and
nothing else — no Node built-in, no adapter, no process global) freezes the
§7.1 event envelope (with `gatewayEpoch` and `ingestSeq` REQUIRED, bigint-like
fields as canonical unsigned integer strings, ISO-8601 timestamps, strict
objects), the §7.2 identifiers, the §7.3 decimal boundary types wired to the
decimal package, all 22 §7.4 normalized event contracts, the §7.5
`DecisionResult` whose `intents` array may be empty, the five §7.7 intent types
with their exact fields and enum values, the six §11 run modes with an
escalation ordering and a pure process-maximum assertion, and a schema-version
registry keyed by `(eventType, schemaVersion)` that keeps older versions
available for replay and validates the version at both contract construction and
registry insertion against exactly the range envelope routing accepts (positive
**safe** integers). Where the handoff states an invariant unconditionally the
contracts make the violating document unrepresentable: the feed gap/resync
snapshot flags are `z.literal(true)`, `MarketResolved` accepts only terminal
outcomes, and reference payload `venue` is drawn from the §7.1 `source`
vocabulary and is checked against the envelope `source` **by the envelope schema
itself**, so no envelope whose two provenance fields contradict each other can
be parsed by any registered contract or by the registry (the pure
`assertEnvelopePayloadProvenance` / `checkEnvelopePayloadProvenance` helpers
remain exported for boundaries that hold the two halves separately).
`StrategyContext` and the §7.6 views are deliberately absent (WP-170).

`docs/contracts/domain.md` documents package purposes, the §5.2 dependency
direction, the three decimal grammars and the strict-boundary decision,
precision/rounding, canonical hashing, the versioning policy and registry
usage, the invariants the contracts encode, the boundary hygiene bounds, every
refinement and inferred shape, and the contract-freeze rule (changes after
acceptance require an ADR).

   `z.iso.datetime`, `z.int`, `z.strictObject`, and `.readonly()` are used.
3. **`marketId` in §7.7 intents is an `InternalMarketId`.** §7.7 types it as
   `string`; §7.2 makes `InternalMarketId` the canonical internal market

   informed by §9.1–§9.4, and avoid encoding volatile venue facts (§1.2). No
   venue behavior was invented: `docs/venue/` does not exist on this base

5. **Canonical zero is unsigned and drops the sign on normalization**
   (`"-0.000"` → `"0"`), which is what §7.3's "canonical zero is `\"0\"`"
   requires for hashing to be representation-independent.
6. **Lowercase UUIDs.** All UUIDs in these contracts are generated in-process,
   so requiring the canonical lowercase form costs nothing and gives each
   identifier exactly one representation.

## known_risks

1. **Zod 4 API surface.** The contracts rely on `z.iso.datetime({ offset: true })`,
   `z.int()`, `z.strictObject`, `z.discriminatedUnion`, and `.readonly()`. A
   future major upgrade of `zod` would need a contract-level review, not a
   mechanical bump.
2. **Strict envelopes and strict payloads reject unknown keys.** This is
   deliberate (silently stripping data on the recording path would violate §8.3)
   but it means a gateway that starts emitting an extra field fails validation
   until a new schema version is registered. Since the round-1 remediation the
   versioning policy makes this explicit — **every** emitted field-set change,
   including an added optional field, increments `schemaVersion`. The registry
   supports keeping both versions and an evolution test pins the behavior; the
   operational runbook for that transition (dual-publish or upgrade ordering) is
   still not written and is a real deployment concern for WP-040+.
3. **Inferred `QuoteLevel` / `BasketLeg` shapes** may need fields once the
   execution planner and the market-making path are implemented. Extending them
   after acceptance requires an ADR.
4. **`divDecimalExact` uses a bounded 200-significant-digit probe.** A quotient
   that is exact but needs more digits raises `DecimalInexactError` rather than
   returning a value. This is conservative by design (it never silently rounds),
   but it is a bound, not a proof of exactness for arbitrary inputs.
5. **`MAX_DECIMAL_STRING_LENGTH = 1024` is a policy choice.** A multiplication
   whose exact result exceeds it raises a typed error instead of returning a
   value. No realistic economic value comes close, but the bound is visible in
   behavior.
6. **The canonical-hash preimage format is now load-bearing.** Any change to
   `CANONICAL_DECIMAL_HASH_DOMAIN`, to the preimage layout, **or to the
   hash-input grammar** invalidates or changes the meaning of persisted digests
   and requires an ADR plus a bump of the `v1` segment.
7. **The hash-input grammar is narrower than the venue-input grammar.** An
   adapter that passes a raw venue spelling such as `"+1.5"` or `"1."` straight
   to `canonicalDecimalHash` now gets a typed error instead of a digest. That is
   the intended behavior (§7.3 forbids those forms), but it is a real behavior
   change for any future caller that expected the lenient path, and it must be
   handled by calling `normalizeDecimalString` first, explicitly.
8. **`DISPUTED` has no dedicated event.** Excluding it from `MarketResolved`
   (§6.2 of `docs/contracts/domain.md`) is the right call, but it means a
   venue transition into dispute is currently expressible only as
   `MarketClarificationObserved` plus a data-quality incident. If WP-000 shows
   the venue publishes an explicit dispute transition, a `MarketDisputed` event
   type should be added under an ADR rather than by loosening `MarketResolved`.
9. **`parameterVersionRef` is deliberately opaque.** The catalog layer
   (WP-050+) owns its addressing scheme; until that exists, no consumer can
   actually resolve a ref. This is intentional (the alternative would freeze a
   fee-schedule shape before WP-000 evidence) but it is an unresolved seam.
10. **Round-1 and round-2 review findings were remediated, not re-reviewed by
    the remediating agents.** The next independent review is the real gate — see
    [Review round 1](#review-round-1) and [Review round 2](#review-round-2).
11. **Provenance is now enforced inside the envelope contract.** This is the
    right place for it, but it is a behavior change with an operational edge: a
    gateway that mislabels either half of the pair now fails validation instead
    of recording an inconsistent event. That is intended (§8.3 forbids silent
    drops, so the failure must be surfaced and routed to
    `DataQualityIncidentOpened`), but the routing itself belongs to the gateway
    work package — see `follow_up` 9.
12. **The schema-version range is now `1..Number.MAX_SAFE_INTEGER`.** That is
    the only range the envelope routing schema can express, so it is a real
    ceiling rather than a stylistic bound. It is nowhere near reachable by a
    hand-incremented contract version, but it is now a behavior, not an
    accident.

A third grammar now exists between the strict canonical form and the lenient
venue-input form. `normalizeHashableDecimalString` (`packages/decimal/src/canonical.ts`)

previously-accepted forbidden spelling now throws instead of producing that same

### MEDIUM-1 — provenance was not contract-enforced

Reproduced first: on `9790e0a`, `DOMAIN_EVENT_REGISTRY.parseEnvelope` returned a
parsed envelope for `source: "coinbase"` + `payload.venue: "binance"`. The
round-1 remediation had made the rule *available* (`provenance.ts`) but not
*enforced*; the only test exercising it invoked the helper by hand.

The fix puts the rule where the other unconditional invariants of this package
live — in the contract, so the violating document is unrepresentable:

- `envelopeProvenanceRefinement` (`packages/domain/src/envelope.ts`) is attached
  by **both** `eventEnvelopeSchema` and `pinnedEventEnvelopeSchema` via
  `.superRefine`, so every registered contract's `envelopeSchema` rejects a
  contradicting pair with an issue on `payload.venue`. Zod 4 keeps refinements
  inside the schema, so the schema type and the `EventEnvelope` inference are
  unchanged. The refinement is silent when `source` is not a string or the
  payload is not an object: those failures belong to the field schemas.
- `parseEnvelope` (`registry.ts`) additionally calls
  `assertEnvelopePayloadProvenance` on the parsed envelope. This is redundant for
  any contract built by `defineEventContract`, and deliberately so: it is the
  same defense-in-depth as `assertSchemaVersion`, because `EventContractLike` is
  structural and a hand-assembled contract can carry an envelope schema that
  never applied the refinement. `EnvelopeParseResult` therefore gained
  `EventProvenanceMismatchError` (exported as `EnvelopeParseFailure`) so
  `safeParseEnvelope` stays total.
- `checkEnvelopePayloadProvenance` now treats any non-object payload as "does
  not restate its origin" instead of relying on the caller. `"venue" in payload`
  throws on a primitive, which the transport-level envelope schema
  (`z.unknown()` payload) can now reach.

Tests: 12 parameterized cases — each of the three reference events × each of the
four §7.1 sources that is not its own venue — assert that the pinned envelope
schema rejects with an issue at `payload.venue`, that
`DOMAIN_EVENT_REGISTRY.parseEnvelope` throws `EventValidationError`, and that
`safeParseEnvelope` returns a typed failure. A guard test pins the matrix size at
12 so a shrunk vocabulary cannot silently shrink the coverage. Matching pairs are
asserted to still parse for all three events, and `MarketOpened` (a payload that
does not restate provenance) is asserted to remain routable from every source, so
the refinement cannot over-reject. `registry.test.ts` covers the structural

still rejected by `parseEnvelope` with `EventProvenanceMismatchError`.
**Verified by mutation:** removing the refinement fails all 12 cases.

### MEDIUM-2 — unsafe integers passed construction but were unroutable
