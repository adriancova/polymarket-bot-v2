## summary

WP-020 freezes the versioned contracts every later package consumes, plus the
exact-decimal foundation underneath them.

`@polymarket-bot/decimal` (dependency: `decimal.js`; `node:crypto` for pure
SHA-256) implements handoff §7.3 literally. A canonical decimal string is
`-?(0|[1-9][0-9]*)(\.[0-9]*[1-9])?` with canonical zero `"0"`: scientific
notation, a leading `+`, `"-0"`, redundant leading zeros, trailing fractional
zeros, and a trailing decimal point are all rejected. Three grammars are kept
deliberately distinct (`docs/contracts/domain.md` §3.1.1): the canonical
boundary form; the **hash-input** form, which adds only the one relaxation §7.3
sanctions before hashing (redundant leading/trailing zeros and signed zero) and
still rejects `"+1.5"`, `"1."`, `".5"`, `"1e5"`, and non-strings; and the
lenient `normalizeDecimalString`, the one sanctioned way to accept a venue
spelling, scoped to adapters. The strict boundary never coerces. Arithmetic is
string in / string out over `decimal.js` with explicitly configured precision
and rounding: add/sub/mul cannot round (a breach raises a typed error rather
than returning a rounded value), `divDecimal` rounds at 34 significant digits
with ROUND_HALF_EVEN (both overridable), and `divDecimalExact` refuses to round.
Passing a JavaScript `number` throws. Canonical hashing normalizes under the
hash-input grammar and then takes SHA-256 over a domain-separated preimage, so
every *permitted* spelling of one value shares a digest and every forbidden
spelling raises a typed error. Tick conformance scales both operands to exact
integers and takes an integer modulo, so `"0.07"` on a `"0.01"` grid is
conformant where `0.07 % 0.01` in IEEE-754 is not.

`@polymarket-bot/domain` (dependencies: `zod`, `@polymarket-bot/decimal`, and
nothing else — no Node built-in, no adapter, no process global) freezes the
§7.1 event envelope (with `gatewayEpoch` and `ingestSeq` REQUIRED, bigint-like
fields as canonical unsigned integer strings, ISO-8601 timestamps, strict
objects), the §7.2 identifiers, the §7.3 decimal boundary types wired to the
decimal package, all 22 §7.4 normalized event contracts, the §7.5
`DecisionResult` whose `intents` array may be empty, the five §7.7 intent types
with their exact fields and enum values, the six §11 run modes with an
escalation ordering and a pure process-maximum assertion, and a schema-version
registry keyed by `(eventType, schemaVersion)` that keeps older versions
available for replay and validates the version at both contract construction and
registry insertion. Where the handoff states an invariant unconditionally the
contracts make the violating document unrepresentable: the feed gap/resync
snapshot flags are `z.literal(true)`, `MarketResolved` accepts only terminal
outcomes, and reference payload `venue` is drawn from the §7.1 `source`
vocabulary with a pure `assertEnvelopePayloadProvenance` helper for the
envelope/payload pairing. `StrategyContext` and the §7.6 views are deliberately
absent (WP-170).

`docs/contracts/domain.md` documents package purposes, the §5.2 dependency
direction, the three decimal grammars and the strict-boundary decision,
precision/rounding, canonical hashing, the versioning policy and registry
usage, the invariants the contracts encode, the boundary hygiene bounds, every
refinement and inferred shape, and the contract-freeze rule (changes after
acceptance require an ADR).

## known_risks

1. **Zod 4 API surface.** The contracts rely on `z.iso.datetime({ offset: true })`,
   `z.int()`, `z.strictObject`, `z.discriminatedUnion`, and `.readonly()`. A
   future major upgrade of `zod` would need a contract-level review, not a
   mechanical bump.
2. **Strict envelopes and strict payloads reject unknown keys.** This is
   deliberate (silently stripping data on the recording path would violate §8.3)
   but it means a gateway that starts emitting an extra field fails validation
   until a new schema version is registered. Since the round-1 remediation the
   versioning policy makes this explicit — **every** emitted field-set change,
   including an added optional field, increments `schemaVersion`. The registry
   supports keeping both versions and an evolution test pins the behavior; the
   operational runbook for that transition (dual-publish or upgrade ordering) is
   still not written and is a real deployment concern for WP-040+.
3. **Inferred `QuoteLevel` / `BasketLeg` shapes** may need fields once the
   execution planner and the market-making path are implemented. Extending them
   after acceptance requires an ADR.
4. **`divDecimalExact` uses a bounded 200-significant-digit probe.** A quotient
   that is exact but needs more digits raises `DecimalInexactError` rather than
   returning a value. This is conservative by design (it never silently rounds),
   but it is a bound, not a proof of exactness for arbitrary inputs.
5. **`MAX_DECIMAL_STRING_LENGTH = 1024` is a policy choice.** A multiplication
   whose exact result exceeds it raises a typed error instead of returning a
   value. No realistic economic value comes close, but the bound is visible in
   behavior.
6. **The canonical-hash preimage format is now load-bearing.** Any change to
   `CANONICAL_DECIMAL_HASH_DOMAIN`, to the preimage layout, **or to the
   hash-input grammar** invalidates or changes the meaning of persisted digests
   and requires an ADR plus a bump of the `v1` segment.
7. **The hash-input grammar is narrower than the venue-input grammar.** An
   adapter that passes a raw venue spelling such as `"+1.5"` or `"1."` straight
   to `canonicalDecimalHash` now gets a typed error instead of a digest. That is
   the intended behavior (§7.3 forbids those forms), but it is a real behavior
   change for any future caller that expected the lenient path, and it must be
   handled by calling `normalizeDecimalString` first, explicitly.
8. **`DISPUTED` has no dedicated event.** Excluding it from `MarketResolved`
   (§6.2 of `docs/contracts/domain.md`) is the right call, but it means a
   venue transition into dispute is currently expressible only as
   `MarketClarificationObserved` plus a data-quality incident. If WP-000 shows
   the venue publishes an explicit dispute transition, a `MarketDisputed` event
   type should be added under an ADR rather than by loosening `MarketResolved`.
9. **`parameterVersionRef` is deliberately opaque.** The catalog layer
   (WP-050+) owns its addressing scheme; until that exists, no consumer can
   actually resolve a ref. This is intentional (the alternative would freeze a
   fee-schedule shape before WP-000 evidence) but it is an unresolved seam.
10. **Round-1 review findings were remediated, not re-reviewed by this agent.**
    The round-2 independent review is the real gate — see
    [Review round 1](#review-round-1).

### HIGH-1 — hash canonicalization accepted §7.3-forbidden forms

A third grammar now exists between the strict canonical form and the lenient
venue-input form. `normalizeHashableDecimalString` (`packages/decimal/src/canonical.ts`)
accepts only what §7.3 sanctions normalizing *before hashing* — redundant
leading zeros, trailing fractional zeros, and signed/padded zero — and rejects a
leading `+` (`DECIMAL_LEADING_PLUS`), a trailing decimal point
(`DECIMAL_TRAILING_POINT`, new code), an omitted integer part
(`DECIMAL_MISSING_INTEGER_PART`, new code), scientific notation, empty strings,
and non-strings. `hash.ts` routes through it instead of `normalizeDecimalString`.

**Golden digests are unchanged, and that is deliberate.** The preimage rule did
not change: it is still `"polymarket-bot/decimal/v1:" + canonicalForm`, and both
pinned vectors (`"1.50"` → `…:1.5`, `"-0.000"` → `…:0`) are still legal hash
inputs that normalize to the same canonical strings. Only the *accepted input
set* narrowed. No persisted digest changes meaning; what changes is that a
previously-accepted forbidden spelling now throws instead of producing that same
digest. Had the preimage rule changed, the `v1` segment would have had to be
bumped — see `known_risks` 6.

`normalizeDecimalString` is untouched and remains the venue-input normalizer.

### HIGH-2 — version policy incompatible with strict schemas

The additive-optional exemption is removed. **Every change to the emitted field
set increments `schemaVersion`**, because every contract rejects unknown keys:
an old v1 consumer would reject a new v1 document carrying the added field, and
`(eventType, schemaVersion)` would stop identifying one historical schema.
Rewritten in `packages/domain/src/schema-version.ts` (module doc) and
`docs/contracts/domain.md` §5.2, with §5.3 restating that the pair is a total,
injective key into the historical schemas.

New evolution suite in `registry.test.ts`: registers v1 and v2 of `EvolvedEvent`
where v2 adds an *optional* field, then asserts a v2 document fails v1 payload
and envelope parsing, v1 documents still parse and route under v1, a v1-shaped
document parses under v2, both versions resolve from the registry with the right
payload schema, and an unregistered v3 raises `UnknownEventContractError`.

### HIGH-3 — gap-recovery contracts could violate the snapshot invariant

`FeedGapDetected.requiresAuthoritativeSnapshot` and
`FeedResynchronized.authoritativeSnapshotApplied` are now `z.literal(true)`.
Rationale recorded in the field comments and `docs/contracts/domain.md` §6.1: the
§7.1/§9.1 requirement is unconditional, the fields are kept (not dropped) so the
obligation appears in every recorded frame, and a feed that reconnected without
applying a snapshot is still in the gap state — that is a `FeedConnected`
alongside the still-open gap/incident, not a `FeedResynchronized`. Negative tests
cover `false`, `"true"`, `1`, `null`, `undefined`, and omission on both fields.

### MEDIUM-1 — reference-event provenance could contradict the envelope

Envelope `source` is documented as the authoritative provenance (§7.1);
the payload `venue` is a restatement for consumers holding a payload without its
envelope. `REFERENCE_VENUES` is now `satisfies readonly EventSource[]`, so the
payload vocabulary is a compile-time-checked subset of the §7.1 `source` enum and
cannot drift — no mapping beyond the source enum was invented. New pure module
`packages/domain/src/provenance.ts` exports
`assertEnvelopePayloadProvenance` / `checkEnvelopePayloadProvenance` and the new
`EventProvenanceMismatchError`; it performs no I/O, consistent with §5.2.

Test samples fixed: `EventSample` gained `envelopeOverrides`, `sampleEnvelope`
gained an overrides parameter, `envelopeForSample` pairs each sample with a
consistent envelope, and the three reference samples now carry
`source: "binance" | "coinbase" | "rtds"` with matching channels. `events.test.ts`
and `registry.test.ts` use `envelopeForSample`. New tests cover the vocabulary
subset at runtime, sample consistency, an explicit mismatch rejection, payloads
that do not restate provenance, and a non-string `venue`.

### MEDIUM-2 — `MarketResolved` accepted non-terminal outcomes

`TerminalMarketOutcomeStateSchema` (`YES_WIN`, `NO_WIN`, `SPLIT_50_50`,
`CANCELLED`) now types `MarketResolved.outcome`. The full §9.3
`MarketOutcomeStateSchema` is retained unchanged for market *state* (catalog,
settlement, payoff models), with `NON_TERMINAL_MARKET_OUTCOME_STATES` and
`isTerminalMarketOutcomeState` exported so consumers branch explicitly, and a
test asserting the two sets partition the §9.3 vocabulary.

**Ruling on `DISPUTED`: excluded.** A dispute is an in-flight process, not an
outcome; a disputed market has no determined payoff, so `MarketResolved` with
`DISPUTED` would assert a resolution that has not happened and invite a
settlement consumer to compute a payoff from it. The dispute stays observable as
market state and through `MarketClarificationObserved` /
`DataQualityIncidentOpened`. `CANCELLED` is included: terminal, payoff (refund)
determined. Rationale in `docs/contracts/domain.md` §6.2; the missing dedicated
dispute event is logged as `known_risks` 8.

### MEDIUM-3 — no runtime schema-version validation

`assertSchemaVersion` / `isSchemaVersion` added to `schema-version.ts`, throwing
the new `InvalidSchemaVersionError`. Called by `defineEventContract` and again by
`createEventSchemaRegistry` — `EventContractLike` is structural, so a
hand-assembled contract can bypass the constructor. Twenty parameterized negative
tests (`0`, `-1`, `1.5`, `NaN`, `±Infinity`, `"1"`, `1n`, `null`, `undefined`,
via both entry points) plus a positive-integer acceptance test. The static type
is unchanged (branding `SchemaVersion` would have rippled through the envelope
and registry signatures — recorded as a deliberate non-change).

### MEDIUM-4 — `TradingParametersChanged` could not express all parameters

Per orchestrator direction the payload now carries `parameterVersionRef` (opaque
handle to the catalog's versioned snapshot, required) and `changedParameters` (a
non-empty array over `tick_size`, `minimum_order_size`, `fee_schedule`,
`trading_delay`, `neg_risk`, `status`). `tickSize` and `minimumOrderSize` became
**optional** detail fields. `parametersVersion` / `previousParametersVersion` are
kept as the monotonic ordinal (§6 invariant 9) — the ref is a lookup handle, not
an ordering key, and this mirrors the existing `metadataVersion` /
`rulesVersionId` split in the same module. **No venue-specific fee or `negRisk`
shape was invented**: those are volatile venue facts (§1.2) and the detailed
snapshot belongs to the catalog layer pending WP-000 evidence. Documented in
`docs/contracts/domain.md` §6.4; sample and `optionalFields` updated; six new
tests including empty/unknown change lists and a missing ref.

Because WP-020 is not yet accepted, the contract is not frozen and this field-set
change stays at `schemaVersion` 1.
