## summary

`@polymarket-bot/storage-wal` records exact raw frames so that a crash costs at
most one partial record and a completed segment can be verified by anyone
holding the bytes.

**Ingestion (§8.3).** The queue is bounded by frame count *and* by encoded
bytes. `enqueue` never blocks and never discards: it returns
`{ accepted: false, reason }` for `queue-overflow`, `capacity-exceeded`,
`writer-closed`, or `writer-faulted`, reports the refusal through
`observer.onOverflow`, and leaves the frame with the caller, who owns the §8.3
decision to halt trading and open an incident. The §8.3 metric names are exposed
literally; `messagesDropped` moves **only** through
`recordCallerDrop(count, reason)`, so a silent drop has no code path at all. A
malformed record raises `WalRecordValidationError` synchronously — a caller bug
surfaced, not a frame recorded badly. `producerBlockedTimeMs` is always `0`
because the design refuses rather than blocks; that is a stated fact, not a
missing metric.

**Format (ADR-004 §1–2, §9.1).** Append-only JSON Lines, UTF-8, LF-terminated,
one record per line. The first line is a header carrying the WAL schema version
and the gateway epoch. Frame lines carry **exactly** the ten §9.1
`RawFrameRecord` keys in their declared order and nothing else — the recording
layer adds no field to the record the handoff specifies, and header/footer lines
are distinguished by a `record` key that a `RawFrameRecord` never has.
`payloadUtf8` is stored verbatim: `PING`/`PONG` heartbeats, non-JSON text,
embedded newlines, control characters, lone surrogates, and payloads that
impersonate a footer line all round-trip byte for byte. `payloadSha256` is
SHA-256 over exactly those payload bytes and is verified on enqueue by default.
`RawFrameRecord` is declared in this package, not in the frozen
`packages/domain` (ADR-004 §1); `packages/domain` is untouched.

**Completion and verification (§9.1).** A cleanly closed segment gets both forms
ADR-004 §2 allows: an in-file footer and a sidecar manifest, each carrying the
record count and the SHA-256 over the header-plus-frames prefix
(`checksummedByteLength`), and they must agree — **field by field**, across every
value the manifest shares with the header, the footer, or the records themselves,
plus the manifest's own internal consistency (`wal-format.md` §6.3, corrected in
review round 1). A checksum protects the bytes; only a cross-check protects the
claims made about them, and those claims are what `WP-130` carries into dataset
manifests. The manifest is also the
per-segment metadata `WP-130` consumes: id, epoch, segment index, record count,
`ingestSeq` and `receivedAt` ranges, byte size, checksum, created/closed
timestamps, close reason, whether a footer exists, and how many bytes recovery
truncated. A segment **without** a manifest is unverified and therefore invisible
to a compactor — which is the mechanism that excludes a corrupt range from
dataset manifests (§12.5) without any extra bookkeeping.

**Rotation and durability (§9.1, ADR-004 §3).** Rotation by size and by time,
both configured, both observable; a record is never split across segments and an
empty segment never rotates. `fsync` is periodic — by interval and by byte
threshold, whichever trips first — never one per frame, and the interval is
surfaced as `dataLossBoundMs` because ADR-004 makes it a published bound rather
than a tuning knob. The byte threshold is a **high-water mark, not a hard cap**:
a drain stops its batch at the crossing record, so unsynced bytes are bounded by
the threshold plus one record rather than by the queue depth (stated in
`wal-format.md` §9, tightened in review round 1). The fault suite makes that bound concrete: a simulated power
loss must lose exactly the frames appended since the last successful `fsync`. All
interval decisions use a monotonic clock, so a wall-clock step cannot rotate or
flush spuriously.

**Recovery (§9.1, ADR-004 §3).** On open, and on demand from an ops tool,
recovery truncates **only** an incomplete final record — trailing bytes after the
last LF — and then writes the sidecar manifest for the verified prefix. A record
that is newline-terminated but malformed is *corrupt*, not incomplete, even when
it is the last one: the bytes are left exactly as found, no manifest is written,
the issue is reported with its line index and byte offset, and the recorder keeps
running on a fresh segment (§4.2 forbids letting a storage problem stop
recording). Recovery is idempotent — a second pass finds a manifest and touches
nothing. A crash between the footer and the manifest preserves the footer's own
close reason and timestamp.

**Write faults.** *(Corrected in review rounds 1, 2, and 3 — see the history
section. The original claim was true only for a failed append; the round-1 claim
was still wrong about what a post-failure `fsync` proves and about frames left in
the queue; the round-2 claim was still wrong about frames an earlier `fsync` had
proven.)* The accepted-frame invariant is total: a frame `enqueue` accepted
leaves the writer's accountability only by appearing in a segment manifest, or by
being handed back through `pendingFrames()` — never by both, never by neither.
That holds for every failing write path, not just an append: creating the segment
(the header write), rotating it (the footer write), finalizing it, `fsync`, and
the sidecar write, and for a fault raised by `tick()` as much as by `drain()`.
On a fault the writer refuses further frames and takes back all three groups it
is holding: **every** record it appended to the active segment that no written
manifest names, the frames `drain()` had taken from the queue, and **the frames
still in the queue** — which a faulted writer will never write, so leaving them
there would hide them from the caller.

**Accountability is not durability** (`wal-format.md` §10.2, new in round 3).
The two questions are kept apart and answered separately. *Durable-for-manifest*
is the watermark below: it governs what a manifest may claim, and a successful
`fsync` advances it. *Retained-for-accountability* is every record appended to
the active segment that no **written** manifest names, and only a manifest write
releases it — an `fsync` releases nothing. Releasing on `fsync`, as rounds 1 and
2 did, was wrong precisely *because* of the watermark rule: a later failure
freezes the watermark short of the file, the segment then gets no manifest at
all, and the records an earlier `fsync` had proven were left named by nothing and
absent from `pendingFrames()`. The two numbers are both exposed —
`unprovenFrameCount` for durability, `retainedRecordCount` for accountability —
and the second is never smaller. Its price is memory: the active segment's
records are held until it is manifested, so the resident set is bounded by
`maxSegmentBytes` rather than by the fsync interval (`known_risks` 17).

**Durability is a watermark.** Each segment records the bytes and records covered
by the last `fsync` that succeeded with no earlier `fsync` or write failure on
its handle; any such failure **freezes** it, and no later `fsync` success moves
it again. That is stricter than "the last `fsync` returned 0" because on Linux a
writeback error is reported once and then cleared, so a subsequent `fsync` can
return success while the failed writeback never landed. A fault close still
attempts one last `fsync` — on a handle with no failure history it genuinely
proves what a torn append left behind — but its success extends no claim once the
watermark is frozen.

Closing a faulted writer therefore truncates an incomplete final record, and then
either writes a manifest for the verified prefix, when the watermark covers all
of it, or writes **none at all**. There is no partial manifest: the format cannot
express one, and a manifest naming an unproven record is exactly the claim a
power loss falsifies. Accountability transfers **at the manifest write and
nowhere else** — the records a manifest names leave `pendingFrames()` in the same
step it lands — so a failed sidecar write leaves every frame with the caller and a
later successful retry moves them exactly once. The rules underneath are that **a
manifest never names a record whose durability is unproven** and therefore **a
manifest never overcounts**, including after a power loss. The price is paid in
duplicates rather than in data: an unmanifested segment keeps its bytes, its
records are also pending, and recovery finalizing it later produces duplicates
detectable by `(gatewayEpoch, ingestSeq)`. If the manifest cannot be written at
all — a genuinely full disk — `close()` fails, stays retryable, and recovery is
the backstop if the process dies first.

**Determinism and boundaries (§12.4, §5.2).** No module reads a clock, a
filesystem, an id source, or randomness directly; all four are injected. The Node
filesystem adapter and the system clock are the only modules that touch the real
world, and the filesystem port deliberately has **no delete operation** —
`WP-050` never deletes, because deletion is `WP-130`'s and only after a verified
upload. Dependencies: Node built-ins only, plus `vitest`/`@types/node`/
`typescript` as devDependencies. The package is layer 2
(`dependency-direction.md` §2) and imports no workspace package.

`docs/contracts/wal-format.md` specifies the bytes: framing, every record's field
grammar, checksum coverage with a shell verification recipe, the rotation and
durability rules with their guarantees, the recovery decision table, the
validation predicate, the ingestion contract, the versioning policy, an explicit
open-limits table, and a byte-exact worked example whose digest reproduces under
`sha256sum`.

1. **"Crash recovery truncates only an incomplete final record."**
   `recovery.test.ts` asserts the partial tail is removed to the byte, that the
   preceding records survive, and that `truncations` stays at **zero** for a
   segment ending on a record boundary and for both corrupt-record cases (final
   and non-final), with the file bytes asserted byte-identical before and after.
   `torn-write-recovery.test.ts` reproduces the same through an injected torn
   append, and `node-file-system.test.ts` reproduces it on a real disk.
2. **"Full segments validate by record count and SHA-256."**
   `checksum-validation.test.ts` validates at four sizes, proves the digest
   covers exactly the header-plus-frames prefix, and requires detection of every
   mutation listed above. `docs/contracts/wal-format.md` §13's worked example was
   independently re-hashed outside the code and matches.
3. **"Queue overflow is observable and never silently drops frames."**
   `queue-overflow.test.ts` asserts offered = accepted + refused, that every
   accepted frame is on disk, that `overflowSignals` counts every refusal while
   `messagesDropped` stays `0`, and that the observer receives the exact refused
   frames. `queue.test.ts` adds the unit-level matrix, including that
   `messagesDropped` moves only through `recordCallerDrop`.

   **Round 1 found this criterion only half-evidenced.** Refusal was covered;
   the frame the writer *accepted* and then failed to write was not, and three
   failure paths lost such frames silently. `accepted-frame-invariant.test.ts`
   now covers the other half: on every failing write path, the frames in a
   manifest and the frames in `pendingFrames()` form an exact ordered partition
   of the accepted frames, and `messagesDropped` stays `0` throughout.

   **Round 2 found the partition still breakable in two ways**: a frame left in
   the queue by a fault raised by `tick()` appeared in neither half, and a
   retried sidecar write could put the same records in *both*. Both are now
   regression-tested at fault level and at unit level, and the partition is
   asserted immediately after the fault as well as after `close()`.

   **Round 3 found the remaining hole, and it was in the "never by neither"
   half again**: a frame an earlier `fsync` had proven durable was dropped from
   the writer's accountability at that `fsync`, on the assumption that a durable
   frame ends up in a manifest. Under the round-2 watermark rule it usually does
   not — a later failure freezes the watermark and the segment gets no manifest
   at all — so those frames were named by nothing and absent from
   `pendingFrames()`. Durability and accountability are now separate accountings
   (`wal-format.md` §10.2), and an unmanifested segment returns **every** record
   it might hold. Five fault-level and five unit-level tests cover both
   directions: nothing lost, and nothing returned that a manifest names.

## assumptions

1. **`RawFrameRecord` belongs to this package.** ADR-004 §1 quotes the type but
   the packet and `packages/domain/**` (forbidden, import-only) require it not be
   added to the frozen domain. It is declared in
   `packages/storage-wal/src/raw-frame.ts` and its evolution follows the WAL
   versioning policy, not the domain contract freeze.
2. **Field grammars beyond the handoff's literal types are mine.** §9.1 types
   most fields as `string`. I validate `ingestSeq` and `receivedMonotonicNs` as
   canonical unsigned integer strings (§7.1 "bigint serialized as string"),
   `receivedAt` as an ISO-8601 instant with an explicit offset,
   `subscriptionGeneration` as a non-negative safe integer, and `payloadSha256`
   as 64 lowercase hex. `gatewayEpoch`, `source`, `endpoint`, and `connectionId`
   are deliberately left as bounded non-empty strings: the archive should not
   reject a frame because the gateway used a vocabulary the archive did not
   anticipate. The §7.1 `source` enum is enforced in `packages/domain`, where
   normalized events live.
3. **Length bounds are policy choices**, stated in the format document:
   8 MiB per payload, 2048 for `endpoint`, 256 for the short identifiers, 40
   digits for bigint strings, 16 MiB for the longest line a reader will buffer.
   They exist so a corrupt file cannot become an OOM, not because a venue
   requires them.
4. **The writer owns one gateway epoch.** §7.1 assigns the epoch at gateway
   startup, so a frame carrying a different epoch is a caller bug and raises a
   typed error rather than opening a second segment lineage.
5. **A non-monotonic `ingestSeq` is observed, not rejected.** §7.1 says the
   sequence is monotonic within an epoch, but refusing to *record* a frame
   because of a gateway bug would destroy evidence. The writer records it,
   increments `nonMonotonicIngestSeqCount`, and calls
   `observer.onIngestSeqAnomaly`.
6. **A corrupt segment found during recovery does not stop the writer**
   (default `report`, not `throw`). §4.2 is explicit that a storage-side problem
   must not stop recording; the failure is surfaced in `writer.recovery`,
   `hasIntegrityFailures`, and the observer, and the caller opens the
   data-quality incident.
7. **The writer schedules nothing.** No timer exists; the owning process
   (`WP-120`) calls `drain`, `tick`, `flush`, `rotate`, and `close`. This is what
   makes the fsync interval and time-based rotation testable and replayable
   (§12.4). It also means an idle recorder that never calls `tick()` will hold
   unsynced bytes past the published bound — stated in the format document and in
   `follow_up`.
8. **Segments open lazily**, on the first frame that needs one, so a writer that
   accepts nothing creates no file.

## known_risks

1. **Single-writer-per-directory is an invariant, not an enforced one.** No lock
   file exists. A second writer refuses to reopen an existing segment file, but
   two writers with different gateway epochs can interleave segments in one
   directory and both believe they are alone. `WP-120` should either take a lock
   or own the directory exclusively.
2. **Directory-entry durability is not guaranteed.** The Node adapter fsyncs
   files but not the containing directory, so on some filesystems a power loss
   immediately after a segment is created can leave no directory entry. The
   segment's *contents* are then irrelevant because the file is gone; this is a
   real (if narrow) hole in the published bound, and it is stated in
   `wal-format.md` §9.
3. **At-least-once at a fault boundary, and now the common case.** A caller that
   re-enqueues `pendingFrames()` without letting `close()` reconcile can
   duplicate the frames of the failed batch. Round 2 made this the *usual*
   outcome rather than an edge: the durability watermark freezes on any write or
   `fsync` failure on a segment's handle, so a torn append, an `ENOSPC`, or a
   failed periodic `fsync` normally leaves the whole segment unmanifested with
   its records both on disk and in `pendingFrames()`. Recovery finalizing that
   segment later then produces duplicates. They are detectable by
   `(gatewayEpoch, ingestSeq)`; a lost frame would not be. `WP-120`/`WP-130` must
   deduplicate on that key rather than assume a fault boundary is clean.
4. **`segmentIndex` is a per-directory ordinal derived from what recovery
   found**, not a durable counter. With a custom `segmentIdFactory` that ignores
   the epoch, a restart could theoretically produce a colliding id; the writer
   then refuses to reopen the existing file rather than appending to it, which
   turns a silent corruption into a loud failure but still stops the recorder.
   Round 3 added a width contract for such a factory (`wal-format.md` §11.2) but
   deliberately no *uniqueness* contract: uniqueness cannot be checked before the
   file exists, and refusing to reopen is the check that matters.
5. **The reader does not verify per-record payload digests by default.** The
   segment checksum covers the same bytes, so this is a cost decision, not a gap
   — but a consumer that reads a single record out of a segment gets no integrity
   check unless it calls `assertPayloadDigest` itself.
6. **`payloadUtf8` cannot hold a binary frame.** Binance and Coinbase framing is
   unverified (`WP-080`, `WP-090`). If either turns out to be binary, ADR-004 must
   be amended and `walSchemaVersion` bumped; nothing here should be quietly
   reinterpreted.
7. **The fsync interval is only a bound if someone drives the clock.** An idle
   writer that never gets a `tick()` holds unsynced bytes indefinitely. The
   contract is documented, but it is a real operational dependency on `WP-120`.
8. **The format is now load-bearing.** Changing key order, escaping, or checksum
   coverage changes `segmentSha256` for identical logical content and invalidates
   comparisons against already-recorded data. The versioning policy
   (`wal-format.md` §12) exists for exactly this and requires an ADR.
9. **`maxTotalBytes` counts segment bytes the writer knows about**, seeded from
   recovery plus what it has written. It is not a `statvfs` reading, so it
   bounds the WAL, not the disk; a disk shared with other data can still fill.
10. **A time-driven rotation while frames are queued is not pre-accounted**
    against `maxTotalBytes`. The reservation covers size-driven rotation exactly,
    including for a queued burst; a time rotation can transiently exceed the
    threshold by at most one segment's framing overhead, after which the next
    admission decision sees the real bytes (`wal-format.md` §11.1).
11. **An unmanifested faulted segment is a duplicate source**, and round 2 made
    it the normal fault outcome (`known_risks` 3). The segment keeps its bytes
    but gets no manifest, and its frames also go back to the caller.
12. **Durability is deliberately under-claimed.** The watermark freezes on *any*
    failure on a segment's handle, including a synchronous append error that on
    Linux would not by itself poison the writeback error cursor. Records that did
    reach the disk can therefore be reported as unproven. This is the direction
    the orchestrator mandated and the one that cannot lose data, but it is a
    conservative reading: a future ADR could narrow the freeze to `fsync`
    failures and recover the round-1 behaviour of manifesting a torn append's
    verified prefix. It is a durability-semantics change, not a patch
    (`wal-format.md` §12).
13. **The capacity projection assumes `drain()`'s packing.** The reservation
    replays the rotation rule over the queued frame sizes. If the drain path's
    batching or rotation rule ever changes without the projection changing with
    it, the bound silently weakens; the queued-burst tests are what would catch
    that.
14. **A partially written header is not counted** toward `totalSegmentBytes`,
    because the byte accounting advances only after a successful open. The writer
    is faulted at that point and the file is recovered as empty on the next open,
    so the undercount does not survive a restart.
15. **The remediation was validated against injected faults, not real hardware.**
    No EIO, ENOSPC, or power loss on a real disk was reproduced; the fault
    filesystem models a torn append as a prefix, a power loss as truncation to
    the last successful `fsync`, and the Linux `fsync` error cursor as "a later
    success makes nothing durable". Those are models of documented kernel and
    POSIX behaviour, not measurements of it.
16. **Rounds 1, 2, and 3 have been performed and remediated; round 4 has not.**
    Rounds 2 and 3 each caught overclaimed guarantees in this record, so the
    claims here are written to be literally true of the code as committed and
    nothing more. The claims are still the implementer's plus three adversarial
    rounds.
17. **Accountability retention costs memory bounded by `maxSegmentBytes`, not by
    the fsync interval.** The round-3 fix requires the writer to hold the active
    segment's raw records until that segment is manifested, because a segment
    that ends unmanifested must return all of them. With the 64 MiB default
    segment size a busy recorder's resident set therefore grows to roughly one
    segment's worth of records between rotations, where before it was bounded by
    the 1 MiB fsync byte threshold. Only the records are held, not their encoded
    copies. A deployment that needs a smaller resident set buys it with smaller
    segments or more frequent rotation; the alternative — releasing on `fsync` —
    is what left frames unaccountable. **No memory measurement was taken**: this
    is reasoned from the retention rule, not profiled.
18. **The `SegmentIdFactory` width contract is new and is enforced by refusing.**
    A deployment whose factory returns an id past
    `MAX_SEGMENT_ID_ENCODED_BYTES` now fails at `openWalWriter`, and one whose
    factory crosses the bound later faults at the next segment open with every
    accepted frame in `pendingFrames()`. That is the intended direction — a cap
    nobody can enforce is not a cap — but it is a configuration that used to
    "work" while quietly overrunning `maxTotalBytes`. An injected factory is also
    charged the full bound in the reservation, so it reaches `capacity-exceeded`
    roughly 1 KB per segment sooner than the default factory does.
19. **`segmentIdKind` is additive, and its absence is treated as unknown.** The
    ordinal cross-check is skipped for a manifest that does not carry it. Nothing
    in this repository has written such a manifest, so the branch is defensive
    rather than exercised in production — but it is exercised by a unit test, and
    the check it guards is redundant with `MANIFEST_HEADER_DISAGREE` anyway.

## review history

### Review round 1 — independent adversarial review of `3c2228a`

Reviewed by a non-implementing agent (`AGENTS.md`: the implementer may not review
its own work). Four findings, all reproduced by the reviewer with probes and
**re-reproduced before being fixed** in the remediation branch
`wp-050-remediation-round1`. Resolutions:

#### HIGH — accepted frames could disappear on non-append write failures

*Finding.* `drain()` removed every frame from the queue before opening,
rotating, or syncing anything, but only the `#appendBatch` catch fed `#pending`,
and `#finalizeFaultedSegment()` reconciled only `#failedBatchSize` — zero on
every other path. Reproduced: (a) a header-write failure left 3 accepted, 0
written, `pendingFrames=[]`, the writer still `open`, `close()` returning `null`;
(b) a rotation-footer failure left 3 accepted, 1 recorded, two frames simply
gone, and a one-record manifest standing for the batch; (c) an `fsync` failure
had the frames appended but treated as durable — `close()` wrote a 3-record
manifest, and a simulated power loss then left zero records behind it.

*Resolution.* The invariant is now total and stated as such
(`wal-format.md` §10.1): an accepted frame leaves accountability only by
appearing in a manifest or by coming back through `pendingFrames()`.

- `drain()` wraps the in-flight window and, on **any** error, hands
  `items.slice(cursor)` — the frames it took from the queue and did not write —
  to a single `#enterFault()` that is now the only place the writer becomes
  `faulted`. `tick()`, `flush()`, `rotate()`, and `close()` do the same.
- A new `#unproven` list holds frames appended to the active segment since its
  last successful `fsync`. A successful `fsync` — the only proof of durability
  there is — clears it; a fault moves it to `pendingFrames()` ahead of the
  never-written frames, preserving accept order. *(Superseded in round 3: an
  `fsync` proves durability but does not end accountability, and clearing the
  list there is exactly what left an earlier-fsynced record answerable to
  nobody. `#unproven` is now `#segmentRecords`, released only by a manifest
  write.)*
- `#finalizeFaultedSegment()` now issues one last `fsync` before writing
  anything, and **writes no manifest at all** when that fails: the segment stays
  unverified and invisible to a compactor, and every frame stays with the caller.
  The governing rule, new in `wal-format.md` §9.1, is that a manifest never
  describes bytes no `fsync` covered — hence **a manifest never overcounts**.
- `ActiveSegment.finalize()` no longer releases the handle when the footer append
  or its `fsync` fails, so the fault path can still prove the file durable; a
  released handle now implies durability. `syncForFaultClose()` always issues the
  `fsync` even when the counters believe nothing is unsynced, because after a
  torn append they describe only the last known-good prefix.
- `close()` reconciles and then re-throws a fault it raised itself, rather than
  returning as though the shutdown were clean.

*Tests.* `test/fault-injection/wal/accepted-frame-invariant.test.ts`, 10 tests
covering all three reviewer scenarios, a torn header, a footer whose `fsync`
fails, a rotation that cannot write its sidecar, power-loss-after-failed-`fsync`,
and a six-scenario matrix. Each asserts `manifested + pending === accepted` as an
**ordered partition** (a partition that loses frame 3 and duplicates frame 4 has
the right size) and that no manifest overcounts after a simulated power loss.
Verified to fail 9/10 against `3c2228a` and pass against the remediation.

#### MEDIUM — manifest/footer agreement accepted doctored metadata

*Finding.* `validateSegment()` compared only count, hash, checksummed length, and
byte size. Doctored `gatewayEpoch`, `segmentIndex`, `firstIngestSeq`,
`lastReceivedAt`, `closeReason`, `footerPresent`, and `truncatedTailBytes` all
returned `valid: true`.

*Resolution.* `validateSegment()` cross-checks every field the manifest shares
with the segment header (`MANIFEST_HEADER_DISAGREE`), with the footer
(`FOOTER_MANIFEST_DISAGREE`, extended from two fields to nine), and with the
records themselves (`MANIFEST_CONTENT_DISAGREE`), plus six internal-consistency
rules (`MANIFEST_INCONSISTENT`) including the `segmentIndex`-versus-encoded-
ordinal check, which is applied only when the id actually encodes one. Content
comparisons are skipped when the scan stopped on corruption, so one defect does
not produce a cascade. Documented as `wal-format.md` §6.3 and folded into the §7
validity predicate, keeping "when both exist they must agree" true.

*Tests.* `test/fault-injection/wal/manifest-agreement.test.ts`, 7 tests: one per
doctored field across all three cross-check families, the internal-consistency

#### MEDIUM — `maxTotalBytes` was not a hard threshold

*Finding.* The enqueue projection charged only frame bytes, excluding the header
and footer lines a segment also costs, so a 427-byte cap admitted 1,049 bytes on
disk and `capacityRemainingBytes` went negative. Reviewer note, same area: the
byte-triggered `fsync` fired after an arbitrary batch.

*Resolution.* The projection now reserves worst-case framing overhead **B** — the
open segment's footer plus one header-and-footer per further segment the
unwritten bytes require, with numeric fields at `Number.MAX_SAFE_INTEGER`,
timestamps at 24 characters, the longest `closeReason`, and 64 bytes of slack per
segment. B is deliberately an over-estimate, because over-reserving only refuses
sooner. `capacityRemainingBytes` is redefined to match and clamped at zero, and
`capacityReservedBytes` is exposed so an operator can see the reservation. The
bound, its formula, and the one case it does not pre-account — a *time*-driven
rotation while frames are queued, bounded by one segment's overhead per rotation
— are stated in `wal-format.md` §11.1.

A consequence recorded rather than hidden: a threshold too small to hold one
segment's framing now refuses every frame. Two existing tests encoded the old
projection (`maxTotalBytes: 800`, and `capacityRemainingBytes === cap − onDisk`);
both were corrected to the new definition **and strengthened** — the first now
also asserts on-disk bytes stay under the cap, and a new test asserts refusal is
total and costs nothing.

For the `fsync` note: a drain now stops its batch at the byte threshold, so
unsynced bytes are bounded by the threshold plus one record rather than by queue
depth. It remains a high-water mark, not a hard cap, and `wal-format.md` §9 says
so.

*Tests.* `wal-capacity.test.ts` gains cap-exact admission/refusal vectors across
six thresholds, a never-negative `capacityRemainingBytes` sweep, and an on-disk
bound check across five thresholds with rotation; `fsync-policy.test.ts` gains
two tests for the high-water bound, including a 200-frame burst drained at once.
Verified to fail 3/3 against `3c2228a`.

### Review round 2 — independent adversarial review of `a972e96`

Reviewed by a non-implementing agent. Four findings, every one of them a
durability-accounting defect the round-1 remediation introduced or left behind.
All four were **re-reproduced on `a972e96` before being fixed**, in the
remediation branch `wp-050-remediation-round2`; the reproduction output is quoted
under each finding. Fourteen tests fail against `a972e96` and pass against the
remediation (10 in the fault tree, 4 in the root-gated unit tree).

#### HIGH-1a — a fault raised by `tick()` stranded the frames still queued

*Finding.* `tick()` faults through `#enterFault()`, which took `#unproven` and
whatever `drain()` had in flight — but `tick()` has nothing in flight, and it
takes nothing from the queue. A frame sitting in the queue when `tick()`'s
rotation failed was therefore handed to nobody, and the faulted `close()` that
followed reconciled only the active segment. Reproduced with a two-frame writer,
one written and one queued, a time rotation whose footer append fails:

| Fault-close `fsync` | manifested | pending | queue depth |
| --- | --- | --- | --- |
| succeeds | `["1"]` | `[]` | 1 |
| fails | `[]` | `["1"]` | 1 |

Frame 2 is in neither column: neither manifested nor in `pendingFrames()`, which
is the "never by neither" half of the invariant.

*Resolution.* `#enterFault()` now empties the queue into `pendingFrames()` as a
third group, after `#unproven` and after the in-flight frames, which is exactly
accept order because a faulted writer accepts nothing more. `close()`'s fault
path absorbs the queue again before reconciling, so the sweep is total rather
than dependent on which method faulted. The queue depth is `0` immediately after
any fault, and `wal-format.md` §10.1 now lists all three groups.

*Tests.* Three in `accepted-frame-invariant.test.ts` — fault-close `fsync`
succeeds, fails, and the sharpest variant where the rotation *is* manifestable so
the exact partition has both halves non-empty (`["1"]` manifested, `["2"]`
pending) — plus one in `writer.test.ts` for the root gate.

#### HIGH-1b — a retried sidecar accounted for the same records twice

*Finding.* `ActiveSegment.finalize()` advanced `durableRecordCount` on its footer
`fsync` and only then wrote the sidecar, while those same frames were still in
`#unproven`. `#enterFault()` captured that already-advanced counter as its
reconciliation pivot, so the pivot said "all durable" while the pending list said
"all yours". Two sidecar failures in one `close()` therefore returned the frames
to the caller **and** left a later retry free to write a manifest declaring them.
Reproduced with three frames and two failing whole-file writes:
`manifested = ["1","2","3"]` and `pending = ["1","2","3"]` — "never by both",
violated.

*Resolution.* Accountability now transfers **at the manifest write and nowhere
else**. The fault path builds the manifest, writes it, and only in the same step
removes from `pendingFrames()` exactly the records that manifest names; a failed
write changes nothing, so a retry is idempotent and can only move each record
once. The pivot no longer reads `durableRecordCount` — it is computed as
`activeSegment.recordCount − #unproven.length` at the moment of the fault, which
is by construction "the records that are *not* in the pending list". The
`#faultReconciled` latch that used to guard double-removal is gone, since there
is nothing left to double.

*Tests.* Four: double-failure-then-retry-success and never-lands in
`accepted-frame-invariant.test.ts`, the triple-failure-then-success path in
`wal-capacity.test.ts`, and one in `writer.test.ts`.

#### HIGH-2 — a post-failure `fsync` success was treated as durability proof

*Finding.* `syncForFaultClose()` read a successful `fsync` as proof even when an
earlier one on the same handle had failed. On Linux a writeback error is reported
once and then cleared from the file description's error cursor, so that second
call can return success while the failed writeback never reached the disk; POSIX
leaves the file's state after a failed `fsync` unspecified. The reviewer's
power-loss probe — header `fsync` OK, frame `fsync` `EIO`, fault-close `fsync`
"success", power loss — produced a manifest claiming **1** record over a file
holding **0**, with the frame in neither the file nor `pendingFrames()`.

*Resolution.* The orchestrator-mandated fix: a per-segment **durability
watermark**, being the bytes and records covered by the last `fsync` that
succeeded with no earlier `fsync` or write failure on that handle. Any failure
freezes it permanently. The fault close still attempts a last `fsync` — on a
handle with no failure history it genuinely proves what a torn append left — but
its success extends no claim once frozen. A manifest may name only
watermark-covered records, and since this format cannot describe a segment
partially, a watermark that falls short of the verified prefix means **no
manifest at all**. `finalize()` refuses outright to write a manifest on a frozen
watermark. `wal-format.md` §9.1 is rewritten around this, with both of its costs
stated: it under-claims on purpose, and it makes duplicates the normal fault
outcome.

*Tests.* The fault filesystem now models the error cursor by default, which is
what makes the probe possible at all. The round-1 test that asserted the opposite
("keeps the manifest honest when a later fsync does prove the bytes") is
**replaced** by the reviewer's fsyncgate probe, carried through a power loss.
`torn-write-recovery.test.ts`, `fsync-policy.test.ts` and `wal-capacity.test.ts`
are corrected to the honest outcome — no manifest, every frame pending — and the
at-least-once consequence is asserted rather than glossed: after re-recording,
the directory holds `["1","2","1","2","3","4","5"]`, duplicates and no loss.

#### MEDIUM — the capacity reservation under-counted segments for a queued burst

*Finding.* `#overheadReserve()` computed the segments a backlog needs as
`ceil(unwrittenBytes / maxSegmentBytes)`, which ignores the header each segment
spends out of that same budget **and** assumes records subdivide. With 900-byte
segments and 415-byte frames only one frame fits per segment, so ten frames need
ten segments where the division predicted five. Measured overshoot of
`maxTotalBytes` for queued bursts: 306 bytes at 3 frames, 2,340 at 10, 4,695 at
20. Only a queued burst exposes it — draining between offers leaves one frame
unwritten, and one frame never needs more than one segment.

*Resolution.* The reservation now *packs*: it places the queued frames one at a
time against the real rotation rule, starting from the open segment's remaining
room and subtracting each new segment's worst-case header from its budget, and
charges a header plus a footer per segment it lands on. The projection is
maintained incrementally per `enqueue` and invalidated whenever the active
segment or the queue moves under it, so a burst costs O(1) per frame. §11.1 is
rewritten with the packing rule, the two ways the division under-reserved, and
the new "a `maxSegmentBytes` below one header's width refuses everything"
consequence.

*Tests.* `wal-capacity.test.ts` gains a cap-exact sweep — for bursts of
1/2/3/10/20 it binary-searches the smallest threshold that admits the whole
burst, asserts on-disk bytes stay at or under it, and asserts that one byte below
it exactly one frame is refused, so the reservation is provably neither too small
nor arbitrarily large — plus a matrix over three segment sizes × three bursts ×
six thresholds, and one root-gated test in `writer.test.ts`.

### Review round 3 — independent adversarial review of `3f35a0c`

Reviewed by a non-implementing agent. The review **endorsed the round-2
durability design** — freezing the watermark on any failure on a segment's
handle, and accepting under-claiming plus at-least-once plus `WP-130`
deduplication as the right trade — and found that the *other* side of that trade

#### HIGH — an earlier-fsynced record was accountable to nobody

*Finding.* A successful `fsync` cleared `#unproven` and **discarded those frame
objects**. On a later fault, `#enterFault()` returned only the current
`#unproven`, the in-flight batch, and the queue; and when the frozen watermark
could not cover the whole verified prefix, `#finalizeFaultedSegment()` wrote **no
manifest**. A record fsynced before the failure was then in neither the manifest
nor `pendingFrames()` — the silent accountability gap `wal-format.md` §10.1
case 4 forbids in as many words ("*every* frame it might hold stays with the
caller"). Three probes, each with frame 1 flushed, frame 2 unproven, frame 3
queued:

| Probe | `pendingFrames()` | Required |
| --- | --- | --- |
| `tick()` rotation, footer append fails | `["2","3"]` | `["1","2","3"]` |
| `tick()` rotation, footer `fsync` fails | `["2","3"]` | `["1","2","3"]` |
| mid-batch torn append after a flush | `["2","3","4","5"]` | `["1","2","3","4","5"]` |

In every case no manifest was written, so frame 1 was simply gone from the
writer's books while its bytes sat on disk unverified.

*Resolution.* The two accountings are separated and both are stated in a new
`wal-format.md` §10.2. **Durable-for-manifest** is the watermark, advanced by a
clean `fsync`, and governs what a manifest may name — unchanged. **Retained-for-
accountability** is `#segmentRecords`: every record appended to the active
segment that no *written* manifest names, released **only** by a manifest write.
`#sync()` no longer touches it; `#appendBatch()` fills it; `#finalizeActive()`
and the fault path's manifest write empty it, in the same step the claim lands.
`#enterFault()` hands the whole list back, ahead of the in-flight frames and the
queue, so accept order is preserved. `unprovenFrameCount` is now derived from the
watermark and a new `retainedRecordCount` exposes the accountability number,
which is never smaller. The reconciliation pivot is computed from the real counts
rather than assumed to be zero, so a drift would fail safe.

The cost is stated rather than hidden (`known_risks` 17): retention is bounded by
`maxSegmentBytes` instead of by the fsync byte threshold. Only the records are
held, not their encoded copies. Paying bounded memory beats an unaccountable
frame, which is the entire reason this package exists.

*Tests.* `at-least-once-accountability.test.ts` — the three probes, plus the
opposite direction in two forms: a clean close must manifest all four records and
leave `pendingFrames()` empty, and a segment manifested by an earlier rotation
must stay out of the pending list when a later segment faults. Two root-gated
tests in `writer.test.ts` cover both directions.

#### MEDIUM — a variable-length `segmentIdFactory` defeated `maxTotalBytes`

*Finding.* The §11.1 projection measured the factory's id once, cached it per
ordinal, and added 64 bytes of slack. But `SegmentIdContext` carries
`createdAtMs` and the factory is called **again** at `#openSegment` — so a
time-dependent factory answered the reservation and the open with different
widths. The reviewer measured a short projected id, a 5,000-byte actual id, and
`maxTotalBytes` exceeded by 7,964 bytes. Re-reproduced here with a milder factory
(ids growing from 27 to 546 encoded bytes): 12 frames admitted against a
6,000-byte threshold, 6,756 bytes on disk, **756 bytes over a threshold this
document calls hard**.

*Resolution.* Option (c) of the packet, plus option (a) as the backstop, written
up as `wal-format.md` §11.2. A `SegmentIdFactory` must return a non-empty string
whose JSON encoding is at most `MAX_SEGMENT_ID_ENCODED_BYTES` (1024 bytes), and
the bound is **enforced** — at `openWalWriter`, against the factory's first id,
and at every segment open **before the file is created**, so a violation costs a
loud refusal and never bytes nothing reserved for. The reservation then charges a
bounded width instead of a measurement that goes stale: the default factory, a
pure function of the epoch and the ordinal, is still measured exactly, so every
number in §11.1 is unchanged; **any injected factory is charged the full bound**,
because a factory is entitled to use `createdAtMs` and no measurement can bound a
function of the clock. Removing the factory call from the admission path also
removed a clock read from it (§12.4).

*Tests.* Three in `wal-capacity.test.ts` — the bound holds for a clock-dependent
factory inside the contract, an over-long factory is rejected at
`openWalWriter` with nothing created, and a factory that leaves the bound only
later faults at open with every accepted frame pending and no segment on disk —
plus two root-gated tests in `writer.test.ts`.

#### LOW-1 — the ordinal cross-check false-positived on an opaque id

*Finding.* `validateSegment` read *any* `<gatewayEpoch>-<digits>` id as a
default-factory ordinal, so an injected factory producing `<epoch>-999999` at
`segmentIndex` 0 yielded `valid: false` with `MANIFEST_INCONSISTENT` on a
perfectly good segment. That contradicts §2, which says the id is opaque and
identity is what the header says.

*Resolution.* Provenance is recorded rather than inferred. The manifest carries
an optional `segmentIdKind`, derived identically by the segment writer, the
writer's fault path, and recovery through one shared `segmentIdKindFor()`:
`"default"` exactly when the id is what the default factory would produce for
that epoch and ordinal, `"opaque"` otherwise. The cross-check runs only on
recorded `"default"` provenance and compares against the default factory's actual
output; absent provenance is skipped rather than guessed at. The check that
matters survives — editing `segmentIndex` in a default-provenance manifest still
fires — and it was always redundant with `MANIFEST_HEADER_DISAGREE`, which
compares the same field against the checksummed header. The field is additive
under the §12 rule that manifest metadata may grow, so `manifestVersion` is
unchanged and a manifest without it still parses.

*Tests.* Three in `manifest-agreement.test.ts` (the opaque id validates, the
doctored index still fires, a recovery-written opaque manifest invents nothing),
three in `manifest.test.ts` (the derivation, the optional round-trip, the
unknown-value rejection), and one in `writer.test.ts`.
