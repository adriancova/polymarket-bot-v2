## summary

`packages/inventory` is a layer-1 package. Its only dependencies are `@polymarket-bot/decimal` and `@polymarket-bot/domain`.

- **`InventoryBook`:** keeps a line per (account, asset) with actual, reserved, pendingOut, pendingIn and available amounts.
  - available = actual − reserved − pendingOut.
  - All amounts are exact decimal strings.
  - pendingIn is never available.
  - The book seeds its actual balances from `packages/ledger`'s `ACTUAL_ACCOUNT` balance lines. The ledger stays the monetary source of truth.
  - `available` is the uncommitted collateral that `packages/capital-allocator` expects. The allocator keeps the per-strategy budgets.
- **`ReservationService`:** makes double reservation impossible.
  - Reservation ids are single-use.
  - A holder has at most one ACTIVE reservation per asset.
  - Each check and its apply happen inside one synchronous call.
  - A journal failure faults the service, fail-closed.
  - A partial fill releases only the unused part.
  - A BUY holds pUSD. A SELL holds the outcome token and is refused when none is available.
- **`WalletOperationManager`:** a state machine over the §9.14 states.
  - States: PLANNED, SUBMITTED, MINED, CONFIRMED, FAILED, UNKNOWN, RECONCILING.
  - Operations: ERC20 and ERC1155 approvals, SPLIT, MERGE, REDEEM, and pUSD wrap and unwrap.
  - An UNKNOWN or unrecognised outcome triggers reconciliation. Reservations stay held until authoritative evidence resolves the operation.
- **Evidence across identifiers (from round 6):** `OperationIdentity` holds every transaction hash and relayer id an operation has named.
  - Every observation and answer is weighed against the whole set, contradictions first.
  - A FAILED or contradicting fact under any member sets aside every CONFIRMED standing.
  - Nothing is released, and no approval is ready, until an authoritative answer covers the members.
  - No verified report documents how relayer ids pair with hashes, so the code assumes no pairing.
- **`ApprovalTracker`:** applies S-D48's order: the approval is confirmed, then the CLOB allowance sync is recorded, then readiness.
- **Venue facts:** each lives in `venue-facts.ts` with its citation. A contract suite checks each one against `docs/venue/verified-2026-09-30.md` or `verified-2026-09-16.md`.
- **No bridge or withdrawal:**
  - no such operation type exists;
  - a plan has a strict key set, with no recipient or destination field;
  - a source scan, shown to fire on planted lines, pins this.

## assumptions

- One process holds one book. Injected ports may answer synchronously or asynchronously.
- No relayer-id-to-hash pairing is documented (verified-2026-09-16 §10.2, re-confirmed in verified-2026-09-30 §10.2), so the code assumes none.
- In flight (SUBMITTED or MINED), lifecycle observations are trusted. The first value of an empty identity field is learned as the operation's own.
- The first entry into reconciliation marks nothing by itself. Every claim that accompanies it is weighed.

## known_risks

- **Liveness depends on the reconciler.** An operation stays RECONCILING, with its holds, until every member is answered terminally by name. There is no timeout.
- **State is in memory only.** Identity sets, kept observations, quarantines and the request map are not journaled. A restart loses them, and the package has no rebuild from the journal.
- **The in-flight trust boundary.** A current non-authoritative answer in flight is applied like an observation.
- **WP300-R10-01 (LOW): closed by `WP-300b` (`05535ae`).** A terminal reconciliation answer bound to a request never issued for the operation can arrive while the executor call is pending (PLANNED). It is buffered and then applied after SUBMITTED. The observe() control behaves the same way, which is the disclosed in-flight trust boundary. The package header still says such an answer is refused with `WALLET_OP_EVIDENCE_REQUIRED`.
- **Other limits.** Order fills have no recognition boundary yet. The no-bridge scan is textual. Proxy inputs are not detected.
