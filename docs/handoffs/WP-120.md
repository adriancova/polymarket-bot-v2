## summary

`apps/data-gateway` is the always-on Market Data Gateway and Recorder — the
handoff's **first useful production deployment** (§0.1). It assembles the four
public venue adapters, the WAL recorder, the event-bus transport, and the
universe catalogue into one layer-3 composition root, and it does so under one
governing rule: **evidence is recorded before it is interpreted, and nothing is
ever dropped in silence.**

**One epoch, one sequence, one funnel.** `IngestSequencer` is the only place
`gatewayEpoch` and `ingestSeq` are assigned (ADR-002 §2). Raw frames and
normalized events draw from the SAME counter, so a published event's
`causationId` names the exact WAL record that precedes it and §6 invariant 4's
chain terminates in bytes on disk. `GatewayDispatcher` is the only path from an
adapter to the transport: assignment and submission happen in one synchronous
turn, so submission order *is* assignment order and the transport's
strictly-increasing-per-epoch publish rule is satisfiable by construction
rather than by luck. *(Round 1 wrote "assigns and submits in one step", which
read as if a sequence could never be assigned without being published.
Envelope validation sits between the two, so a rejected draft consumes its
sequence and leaves a gap — see `known_risks` 2 for exactly what is and is not
guaranteed.)*

**Raw before normalized, enforced rather than hoped for** (acceptance 1). Each
driver records the exact wire frame in the adapter's own pre-parse callback,
then dispatches that frame's normalized events with the recorded record's
identity as their causation. Where a WAL refusal makes the evidence
unavailable, the derived market data does **not** enter the stream — publishing
data whose raw frame was refused is precisely what this criterion forbids — and
a PAGE incident opens instead. Feed-health events keep flowing, so the outage
is visible in the recorded stream rather than only in a log.

**The Coinbase seam.** The Coinbase manager owns its own socket, so the gateway
cannot interpose between socket and processor — except at the one seam the
manager itself injects. `RecordingCoinbaseSocketFactory` wraps the factory: it
records each frame under the identity of the socket that produced it, captured
by closure, and only then forwards it. That is what makes acceptance 1 true on
a feed whose transport the gateway does not own, and it is why a late frame
from a superseded Coinbase socket is recorded under `-c1` while `-c2` is live.

**Connection identity is not reinvented at the assembly layer.** The
relabelling defect appeared independently in all three Wave-1B adapters; the
adapters now guard it, and the gateway's job is to not undo that. Every attempt
gets an id from a per-feed ordinal — uniqueness *proved*, not merely made
unlikely — the Binance driver registers it with `feed.connecting(id)` before
asking the transport for the socket and stamps the same value on the request,
and a refusal is counted rather than absorbed. Three refusal shapes carry
driver obligations and all three are implemented: a rejected `PENDING` close is
counted as a failed attempt and retried (the feed emits no `FeedDisconnected`
for it); `NONE` after a `FeedDisconnected` means "wait for the attempt you
already started", and the driver waits — but if it holds no unresolved attempt,
that is a transport bug and it says so loudly instead of stalling; an
unauthorized-identity rate past a threshold escalates to PAGE.

**Recovery is keyed off the gap, never off "a reconnect happened."** The
Polymarket driver fetches authoritative REST snapshots for the gap's own
generation, publishes them, and only then acknowledges that exact generation —
so `FeedResynchronized`, whose `authoritativeSnapshotApplied` is pinned `true`,
is never published without a snapshot having been fetched and applied. The
`GENERATION_MISMATCH` rejection branch re-runs recovery for the gap that is
actually open; a failed fetch leaves the gap open with an incident and retries.
On RTDS, where no authoritative snapshot can ever exist, the gateway does the
opposite of waiting: it halts with a PAGE incident and clears the adapter's gap
state — and **the acknowledgement is never an authoritative resync**, which is
why no `FeedResynchronized` is synthesized on that feed and none exists to
synthesize.

**A transport outage costs decisions, not data** (§4.2, acceptance 4).
`EventBusUnavailableError` — including its `EVENT_BUS_PUBLISH_QUEUE_FULL`
subclass, which WP-060 makes a *halt* signal and not a drop signal — halts
publication terminally for the epoch, and recording continues untouched because
the WAL path does not run through the publisher. Publication deliberately does
**not** resume mid-epoch when the server returns: the events assigned during
the outage were never in the stream, and a mid-epoch resume would hand
consumers a gap the transport cannot detect, since its resync arithmetic
watches its own publication ordinals rather than `ingestSeq`. A restart mints a
new epoch and a fresh snapshot obligation, which is the §7.1 path.

**Epoch handling matches the format contract.** The journal opens the WAL on a
per-epoch subdirectory `<walRoot>/<gatewayEpoch>`, so a restart starts a new
directory rather than interleaving epochs in one. The WP-130 compactor refuses
a mixed-epoch directory; this layout means it never meets one from this
gateway, and it also gives the journal exclusive ownership of a directory whose
name only one writer could know (WP-050 `known_risks` 1). Deletion is not
implemented and not reachable — it is WP-130's, and only after a verified
upload.

**Bounded, and loud at every bound** (§8.3). The WAL ingestion queue refuses
rather than discards (`messagesDropped` stays `0` by construction); a write
fault becomes a PAGE incident rather than a silent stop; the publisher refuses
a repeated ordering identity with a counter; and the incident registry itself
is bounded, deduping repeats per `(scope, reasonCode)` with a counter and
evicting closed keys before open ones, so a pathological feed can flood neither
the stream nor memory.

**No credential surface, by construction.** Every configuration schema is a
strict Zod object at every level, so a key resembling an API key, signer,
wallet, or password is a *validation error* rather than an ignored field. There
is no code path in this app that reads, holds, or transmits authentication
material, and the run-mode defaults are untouched.

## assumptions

1. **A restart mints a new epoch and a new WAL directory.** §7.1 assigns the
   epoch "at gateway startup" and the WP-050 writer owns exactly one epoch, so
   `<walRoot>/<gatewayEpoch>` follows. It is also what keeps the WP-130
   compactor's mixed-epoch refusal from ever firing on this gateway's own
   layout. The alternative — one directory for all epochs — is expressly
   refused by the compactor.
2. **Publication does not resume mid-epoch after an outage.** The transport
   detects loss through its own contiguous publication ordinals, not through
   `ingestSeq`; resuming after a halt would produce a stream whose ordinals are
   contiguous while the gateway's sequence has a hole, which no consumer could
   detect. Halting for the epoch makes the loss visible as a restart plus a
   snapshot obligation. This is a **design decision, not a venue fact**, and it
   is the most consequential one in this package (`known_risks` 1).
3. **Feed-health events publish even while raw recording is refused.** They are
   not frame-derived, and suppressing them would hide the outage from the very
   stream an operator reads to diagnose it.
4. **The Coinbase recording wrapper's connection id tracks the manager's.** The
   manager mints `<feedId>-c<ordinal>` once per attempt and calls the factory
   once per attempt; the wrapper counts the same calls. The correspondence is
   asserted by a test rather than assumed, because the whole raw-frame
   provenance chain on that feed rests on it (`known_risks` 4).
5. **A market announced on the wire is observed, not adopted.** §9.2 makes
   series binding configuration; the venue documents no pairing rule between
   `assets_ids` and `outcomes`, so nothing here can decide which token is YES.
   `registerDiscoveredMarket` therefore always declines, the observation is
   retained (bounded) and counted, and the adapter's `UNREGISTERED_MARKET`
   problem is routed at LOG severity.
6. **The gateway consumes no settlement verdict, so the WP-110 narrowing
   obligation does not arise here.** This process records data and activates
   nothing: `SettlementActivationVerdict` never reaches it, and
   `SettlementActivationView` is not constructed anywhere in this package. The
   obligation to narrow the verdict at the composition root **remains open and
   belongs to `WP-160`/`WP-170`**, which is stated here so it is handed on
   rather than dropped.
7. **`FeedStale` is escalated to an incident by the gateway.** The Polymarket,
   RTDS, and Binance adapters report staleness and deliberately leave the
   operational judgement to their caller; §8.3/§9.9 make a stale feed an
   operational condition. Coinbase reports its own `COINBASE_FEED_STALE`
   anomaly, which routes through the same funnel, so it is not double-counted.
8. **The gateway tick drives the WAL's published data-loss bound.** WP-050's
   writer schedules nothing; `tickIntervalMs` (default 1 s) must stay at or
   below the configured `fsyncIntervalMs` for `dataLossBoundMs` to be a real
   bound (`known_risks` 6).

## deviations

1. **The runtime bundle is CommonJS, not ESM.** The `apps/research-worker`
   precedent (`--format=esm`) does not survive contact with `ioredis`, which is
   CommonJS and uses dynamic `require`: the ESM bundle built cleanly and then
   died at startup with `Dynamic require of "events" is not supported`.
   Externalising `ioredis` instead failed differently (`ERR_MODULE_NOT_FOUND` —
   it is a dependency of `packages/event-bus`, not of this app, so pnpm's
   strict layout does not expose it here), and declaring it as a dependency of
   this app to fix that would put a Redis client in the manifest of a package
   that never imports one, which is the shape F8 exists to prevent. `--format=cjs`
   bundles it correctly and needs no dependency-graph fiction. **Both failures
   were observed, not predicted.**
2. **Unit tests are colocated in `apps/data-gateway/src/**`**, per the
   `WP-020`/`WP-050` precedent; the root vitest config already includes
   `apps/**/src/**/*.test.ts`.
3. **The integration tree is registered by its own config plus a package-level
   script**, not by editing the protected root config. Root-script and CI
   wiring is orchestrator-owned at merge (`follow_up` 1).
4. **A `./testing` subtree ships an in-memory transport and manual
   clock/timers**, unexported from the package barrel. The WP-060 package
   provides Testcontainers helpers but no in-memory transport implementation,
   and acceptance 4 must be exercised against the interface's failure
   injection rather than a real server.
5. **The example configuration carries no `_comment` key.** The first draft did;
   the strict schema rejected it at startup, which is the schema working as
   designed. The explanation moved to the README, and `main.ts` now prints the
   validation issues so the next operator sees *which* field failed.
6. **`GatewayDispatcher.openIncident` takes an optional payload builder.** The
   first implementation let the three adapter-payload routes open incidents on
   the registry directly, which meant those incidents never reached the
   observer — the one delivery that still works during a transport outage. The
   defect was found by acceptance test 2 and fixed by making the dispatcher the
   single funnel; a regression test pins it.
7. **`ManualGatewayTimers`/`deterministicIdSource` take a seed.** A test that
   models a restart needs a genuinely different epoch, which a fresh
   deterministic source would not produce. This was a test-double defect
   surfaced by the obligation-7 test, not a product change.

## known_risks

1. **The terminal publication halt is a deliberate availability trade.** A
   transient Redis blip costs the rest of the epoch's publication until the
   process is restarted, even though recording is unaffected. The alternative —
   resuming mid-epoch — hands consumers an undetectable gap (`assumptions` 2).
   A future refinement could publish an explicit in-stream discontinuity marker
   and resume, but that is a transport-contract change (ADR-003), not a patch.
2. **Publication order rests on synchronous assignment-and-submission — and
   round 1 overstated what that buys.** *(Corrected in round 1 remediation;
   review L1 rejected the original wording as incomplete.)* What the shape
   guarantees is that no `await` separates `sequencer.next()` from
   `publisher.enqueue()`, so submission order IS assignment order and the
   transport's strictly-increasing-per-epoch rule holds. What it does NOT
   guarantee — and the round-1 sentence "assigns and enqueues in one step"
   read as if it did — is that every assigned sequence reaches the transport:
   envelope validation runs between the two, so a draft that fails its frozen
   contract consumes its `ingestSeq` and publishes nothing. That hole is
   correct behaviour (raw WAL frames draw from the same counter, so the
   published stream is non-contiguous by design) and it is loud (counted,

## H1 — WAL `tick()` raced newly scheduled drains

**Probe.** Three scenarios on an instrumented WAL filesystem
(`apps/data-gateway/src/testing/observing-file-system.ts`, new) that counts
concurrent filesystem calls and can hold an `fsync` open. Against round-1
`journal.ts`: a frame arriving during a tick-driven fsync →
`maxConcurrentOperations = 2`; a frame arriving during a tick-driven time
rotation → `maxConcurrentOperations = 2` **and the writer FAULTED**; a
`close()` issued during an in-flight tick → `maxConcurrentOperations = 2`. The
WP-050 writer guards `drain()` against `drain()` and nothing else, so two
overlapping operations corrupt its accountability state — the reviewer saw
`framesDurable > framesAccepted` and a frame that was BOTH manifested and in
`pendingFrames()`, which `wal-format.md` forbids absolutely.

**Fix.** `GatewayJournal` now runs **every asynchronous writer call on one
serial chain** (`#run`): drains, ticks, flushes, and the close. Nothing awaits
a partial chain and then calls the writer — which is exactly what round-1
`tick()` did (`await this.#draining` and then `writer.tick()` outside it).
`settle()` loops until the chain stops growing, so work queued during settling
is not missed. `close()` runs on the chain too, and deliberately runs even when
faulted, because WP-050's faulted `close()` is what reconciles `pendingFrames()`.
Two writer calls stay off the chain and are documented as such: `enqueue()`
(synchronous, queue-only, required to be synchronous by acceptance 1) and
`metrics()`/`pendingFrames()` (synchronous reads).

**Re-probe.** `maxConcurrentOperations = 1` in all three; writer not faulted;
after `close()`, every accepted frame is in **exactly one** of manifest or
pending.

**Permanent tests** (`apps/data-gateway/src/journal.test.ts`, 3 new):
"does not run a drain concurrently with a DELAYED FSYNC driven by tick()",
"does not run a drain concurrently with a DELAYED TIME ROTATION" (this one
asserts the exact-one manifest-or-pending invariant frame by frame), and
"serializes close() behind an in-flight tick rather than racing it".

**Mutation.** Reverting `journal.ts` to `4f71f9e` fails all three new tests
(2 on concurrency, 1 additionally on `journal.faulted === true`).

## H2 — the publisher's Promise chain was an unbounded hidden queue

**Probe.** Against the round-1 publisher, with a transport whose first
`publish()` never settles: `transportPublishCalls: 1`, `highWaterMark: '1000'`,
`halted: false`, `queuedButUnreported: 999` — the reviewer's numbers,
reproduced exactly.

**Fix.** The chain is replaced by an explicit FIFO admission queue with a head
cursor, and admission is decided **synchronously** against two bounds:

| Bound | Config key | Default | Constant |
| --- | --- | --- | --- |
| depth | `publisher.maxQueueDepth` | `1024` | `DEFAULT_PUBLISH_QUEUE_MAX_DEPTH` |
| bytes | `publisher.maxQueueBytes` | `8388608` (8 MiB) | `DEFAULT_PUBLISH_QUEUE_MAX_BYTES` |

Both are **safety parameters, not tuning knobs**, and the README says so.
Crossing either is a loud refusal (`admission-queue-full`, counted in
`admissionRefusals`) **and a terminal halt through the same machinery a
confirmed outage uses** — cause `GATEWAY_PUBLISH_ADMISSION_OVERFLOW`, one PAGE
incident, one operator story. Byte accounting is exact UTF-8 length of the
serialized envelope, computed by a small total function rather than a runtime
global; it costs one serialization pass per admitted envelope, which is the
price of a real byte bound and is disclosed as such in `publisher.ts`.

Real metrics now exist, and round 1's claim that they did was false:
`queueDepth`, `queueMaxDepthObserved`, `queueMaxDepth`, `queueBytes`,
`queueMaxBytesObserved`, `queueMaxBytes`, `oldestQueuedAgeMs` (off the injected
clock), `admissionRefusals`.

One subtlety found while fixing, and fixed: `#pumping` is cleared
**synchronously** inside the pump's `finally`, not in a `.then` on its promise.
A caller awaiting the last outcome resumes on a microtask scheduled before any
`.then` would run, so a `.then` would leave `#pumping` true exactly when that
caller enqueues again — and its envelope would sit in the queue with no pump.
That bug was caught by two pre-existing tests timing out.

**Re-probe.** With `maxQueueDepth: 4` behind a stalled publish: one submission
in flight, exactly four admitted, the fifth refused and the epoch halted;
`oldestQueuedAgeMs` reports 250 after advancing the clock 250 ms.

**Permanent tests** (`publisher.test.ts`, 3 new): "refuses admission and halts
once the depth bound is reached behind a stalled publish", "refuses admission
on the BYTE bound even when the depth bound is far away", "reports queue depth,
bytes, and configured bounds while draining normally". Plus `config.test.ts`
"defaults the publisher admission bounds and accepts explicit ones".

**Mutation.** Disabling the admission predicate fails the first two by timeout
(the unbounded queue never refuses).

## H3 — a non-outage rejection silently lost an event

**Probe.** Against the round-1 publisher: seq 1 refused by the transport's
schema validation, seq 2 published. `accepted: ['2']`, `halted: false` — the
reviewer's exact result, and an undetectable mid-epoch hole.

**Fix.** **Every** unsuccessful submission now halts the epoch. There is no
safe third option: retrying a permanently-invalid envelope in place would loop
forever, and stepping over it loses an event. A non-outage refusal increments

callback (round 1 wired nothing) and the PAGE incident
`GATEWAY_PUBLISH_REJECTED`. A halt is **total**: entries already admitted but
not yet submitted resolve as suppressed rather than publishing behind the
boundary. The one submission already handed to the transport cannot be unsent
and completes; the stream therefore ends at exactly one identity and nothing
follows it, which the test asserts.

**The round-1 unit test that pinned the unsafe continuation ("counts a
non-outage transport rejection without halting") is DELETED, not preserved.**

**Permanent tests** (`publisher.test.ts`, 2 new): "halts on a non-outage

already-admitted entry rather than publishing it after a halt".

**Mutation.** Removing the `GATEWAY_PUBLISH_REJECTED` halt fails both.

## assumptions (remediation round 1)

1. **A terminal publication halt is the right answer to every unsuccessful
   submission**, including a gateway-side envelope defect. The alternative the
   review allowed — retry in place with the same identity, preserving ordering
   — cannot terminate on a permanently-invalid envelope, so it would trade a
   silent hole for a silent stall. This is a design decision, not a venue fact.
2. **A halt is total, not a trickle.** Entries admitted before the halt are
   suppressed rather than published, so the stream has exactly one boundary.
   The single submission already in flight when the halt fires cannot be
   unsent and completes.
3. **The RTDS halt suppresses normalized publication but not quality
   diagnostics.** The review required "raw WAL recording and diagnostics"
   preserved; coverage-break, freshness, and first-observation signals are read
   as diagnostics and keep firing while halted.
4. **`counters.connectionsOpened` advancing by exactly one across a forwarded
   `onOpen` means the manager adopted THAT socket.** It is the only observable
   that distinguishes adoption from the manager's stale-activity refusal, and
   the manager increments it in exactly one place.
5. **The publisher's default bounds (1024 envelopes / 8 MiB) are a starting
   point, not a measured figure.** No soak has sized them. They are
   configurable and their meaning is documented; `queueMaxDepthObserved` and
   `queueMaxBytesObserved` are what a real deployment should be sized against.

The seven round-1 deviations stand unchanged, including deviation 1 (the CJS
bundle), which the review ACCEPTED and which was not revisited. Additional this

1. **`GatewayPublisher` now requires an injected `GatewayClock`.** The
   oldest-queued-age gauge the review demanded is a real measurement, and this
   package takes no clock from a global. Every construction site was updated.
2. **`GatewayConfigSchema` gained a `publisher` object** (`maxQueueDepth`,
   `maxQueueBytes`, both defaulted). The review left the bound's value to this
   agent but required it configurable and documented; a strict schema means it
   had to be a declared field.
3. **`DataGateway.haltPublication(cause, detail)` is new public API**, used by

   lets the composition root put publication into the same terminal state a
   mid-run outage produces.
4. **The integration harness gained `startupTransportFailure`.** It models the

   set, `published()` reads an untouched memory transport and is empty by
   construction, which the option's doc comment says.
5. **`MemoryEventTransport` gained stall injection and `publishCalls` /
   `subscribeCalls` counters.** A never-settling publish is the only way to

## known_risks (remediation round 1, additional)

1. **The publisher's byte accounting serializes every admitted envelope.** One
   `JSON.stringify` pass per event, in addition to the transport's own. It is
   the price of a real byte bound; at recorder rates it is not expected to
   matter, and **it has not been measured** (no benchmark exists — round-1
   `known_risks` 7 still stands).
2. **RTDS now halts for the epoch on the FIRST unrecoverable gap, which on that
   feed means the first reconnect.** That is what the review required and what
   ADR-009 §6 implies, but it is a large availability trade: a single dropped
   socket costs the rest of the epoch's normalized TWAP publication until the
   process restarts. Recording is unaffected. If this proves too aggressive in
   operation, the fix is a documented in-stream discontinuity marker plus
   resume — a transport-contract change (ADR-003), not a patch.
3. **The admission bounds are unmeasured** (see `assumptions` 5). A deployment
   that sets them too low turns a slow transport into an avoidable halt; too
   high, and the halt arrives later and costs more memory.
4. **`UnavailableEventTransport` is only installed at startup.** A transport
   that connects and then dies is handled by the ordinary halt path, which is
   correct — but there is no code path that swaps a live transport for this one
   mid-run, and none should be added without deciding what `close()` then means.
5. **No sustained-recording evidence exists** — unchanged from round 1. Every
   suite here runs in milliseconds against fixtures. The new admission queue,
   the RTDS halt state, and the per-socket provenance objects are bounded by
   construction and **not measured** under a real multi-hour feed. That remains
   `WP-140`'s soak, and it has not happened.

**Design decision: startup is TRANSACTIONAL, with single-owner disposal.**
The sequence `main.ts` runs is extracted verbatim into
`apps/data-gateway/src/run.ts` (`runGatewaySequence`; identical log lines;
`main.ts` now parses env/config, supplies the real ports and a
`connectTransport` thunk, and keeps its outer fatal handler). The invariant,
stated and enforced: **on ANY fatal startup error, every resource acquired so
far is released, `close` is called exactly once per resource, and the process
exits 1 promptly.** Ownership is explicit, which is what makes exactly-once
checkable rather than hoped:

- the TRANSPORT belongs to the sequence from `connectTransport` resolving
  until `DataGateway.create()` returns; a failure in that window closes it in
  the sequence's catch (and nothing else can — no signal handler exists yet).
- once `create()` returns, the GATEWAY owns everything: a failure at or after
  `start()` runs `gateway.stop()`, the single disposal for the WAL journal,
  the transport, and the lifetime anchor. No double-close: `stop()` is
  state-guarded (round 2), the Redis transport's own `close()` is idempotent
  (`#closed` guard) and non-hanging (`closeRedisClient`: `quit` caught,
  `disconnect` always), and `start()`'s release-on-throw (round 2) clears the
  lifetime handle before `stop()`'s `finally` can see it, so the counting
  test observes `{acquired: 1, released: 1}` — never 2.
- the fatal path cannot race the signal path: `SIGINT`/`SIGTERM` handlers are
  registered only AFTER `start()` succeeds, at which point the fatal cleanup
  is unreachable — mutual exclusion by construction, not locking.
- one level down, **`create()` is transactional over what IT acquires**
  (the startup-sequence sweep the finding demanded): it opens the WAL journal
  FIRST, and a throw from anything after (a configured feed with a missing
  port, a refused subscription plan) previously dropped the open writer.
  `create()` now closes the journal before the error escapes; ownership
  transfers to the gateway exactly at construction, so the close cannot
  double with `stop()`'s. Verified while sweeping: a SUCCESSFUL `create()`
  holds no OS handle beyond the journal (the WAL writer opens its segment
  file lazily on first drain; recovery's reads are transient), and a FAILED
  `RedisStreamsEventTransport.connect()` disconnects its own client before
  throwing (WP-060 `createRedisClient`), so the transport-connect boundary
  itself leaks nothing.

## assumptions (remediation round 3)

1. **The referenced in-memory transport is a faithful stand-in for the
   connected Redis transport with respect to R3-H1.** The property under test
   is "one referenced handle that only `close()` releases"; the reviewer's
   own probe used the same substitution. The real client's close is
   idempotent and non-hanging by WP-060's design (`close()` `#closed` guard;
   `closeRedisClient` catches `quit` and always `disconnect`s), which is an
   upstream contract this round relies on, not re-proves.
2. **`GatewayJournal.close()` never rejects** (its serial chain converts
   writer failures into the fault state), so `create()`'s cleanup cannot mask
   the original error. Should that contract ever break, the sequence-level
   transport cleanup still runs (the caller's `gateway === undefined`
   branch), so the process still exits — with the close error surfaced
   instead of the original.
3. **Every feed component's `stop()` is safe from any state, including
   partially started** — verified by reading each one (`PublicMarketFeed`,
   `RtdsTwapFeed`: status-guarded with all-optional teardown;
   `CoinbaseConnectionManager`: unconditional teardown of optionals; the two
   app drivers: idempotent flags) and exercised end-to-end by subprocess
   test 2, where `stop()` runs against a gateway whose `start()` threw
   mid-way with the real Coinbase manager in the partially started set.

## known_risks (remediation round 3, additional)

1. **The connected-Redis variant is modelled, not measured.** If the real
   `RedisStreamsEventTransport.close()` ever hung or left a referenced handle
   AFTER resolving, the fatal path would still not exit; that contract
   belongs to WP-060 (`closeRedisClient` exists precisely to prevent it) and
   is not re-verified by a live measurement here.
2. **A hypothetical socket factory that opens an OS socket and then throws
   from `connect()`** (rather than returning the handle or throwing before
   dialling) would leak that one socket past the fatal cleanup — no factory
   in this repository behaves that way (the Coinbase `ws://` refusal throws
   before any dial; the others return the handle they open). Stated so the
   invariant's edge is visible rather than implied away.
3. **Fatal-path stderr can carry extra lines with a live transport**: feeds
   that started before a later feed's `start()` threw are stopped by the
   cleanup, and their disconnect events may attempt publication during
   teardown (rejections land in the publisher's halt accounting). Harmless
   for the exit invariant — after `transport.close()` nothing referenced
   remains — but an operator reading a fatal log may see halt lines after
   the fatal line.
4. **The probe entry is a second bundled entry point** (dev-only, gitignored
   output, built by the test itself). It shares the round-2 subprocess
   suite's tooling dependency (`pnpm` + the package's own esbuild) and its
   loud-failure discipline.
