## summary

WP-040 implements the entire §10 database model — the six semantic schemas, the
§10.7 constraints, forward and rollback migrations, a SQL-first runner, Kysely
typed table definitions for all 55 tables, and typed repositories for the shared
records — with an integration suite that exercises every acceptance criterion
against a real PostgreSQL 16.6 container.

**Migrations** (`db/migrations/**`, 8 forward + 8 rollback files). The mechanism
is plain SQL plus a small runner in this package, because every §10.7 constraint
is DDL (domains, partial unique indexes, constraint triggers, deferred
constraint triggers) that a migration DSL would either not express or would
carry as embedded SQL anyway; and because Kysely's own migrator uses TypeScript
modules that must be compiled first, which would make `db:migrate` depend on a
build of the package that owns the schema. The runner takes a session advisory
lock, runs each migration and its bookkeeping row in one transaction, records
the SHA-256 of the SQL as applied and re-checks it (editing an applied migration
is an error, not something to reconcile), and rolls back newest-first. A full
rollback leaves only `migrations.schema_migrations` — verified, not asserted.

**Schemas.** `catalog` (10 tables), `data` (8), `strategy` (9), `execution`
(10), `accounting` (11), `ops` (8), plus two infrastructure schemas holding no
business records: `internal` (domains, enums, trigger functions) and
`migrations` (runner bookkeeping). The §10.1–§10.6 table lists are implemented
verbatim; three additions are documented in [assumptions](#assumptions).

**Economic values are canonical decimal TEXT, never `numeric`, never a JS
`number`.** `numeric` was rejected for storage because it accepts `1.50` and
`1.5` as two spellings of one value and hands back whichever scale it stored,
breaking the one-representation property that equality, unique constraints, and
canonical hashes depend on (`docs/contracts/domain.md` §3.2). Domains
(`internal.decimal_string`, `…non_negative…`, `…positive…`, `internal.price_string`)
enforce the §7.3 grammar in the database; constraint triggers aggregate in
`numeric`, which is exact arbitrary-precision decimal. Timestamps cross the
boundary as ISO-8601 strings, never `Date`: connections run `TimeZone=UTC` and
`DateStyle=ISO` and the conversion is total, throwing rather than guessing.

**§10.7, constraint by constraint.** Sortable ids: an `internal.uuid_v7` domain
on every internal primary key (a plain-`uuid` primary key anywhere in the six
schemas fails a test), with a server-side generator and a client-side `uuidV7()`.
`orders(venue_order_id)` unique where not null, scoped by `(environment,
account_ref)`. Fills unique on the §10.7 triple, additionally environment/account
scoped (§10.8). `submission_attempts(expected_order_hash)` unique where not null.
Immutable configs and rule versions, and append-only event/ledger tables, by
`BEFORE UPDATE OR DELETE OR TRUNCATE` triggers — **not** by privileges, because a
grant does not bind the table owner that migrations run as (a complementary
least-privilege grant script is in the package README). Live orders and live
submission attempts require a valid fencing token through three layers: a CHECK
(unrepresentable without one), a composite foreign key to `(lease, token)`, and a
trigger that additionally requires the lease to have been ACTIVE, unexpired, and
for that account and environment. Fill allocations are checked twice: immediately
(never exceed the fill) and deferred to COMMIT (equal the fill exactly). Ledger
transactions balance to zero per asset via a deferred constraint trigger on both
the header and the entries. Available balance is a `GENERATED ALWAYS` column with
a CHECK, and `reserved_amount` is maintained by a trigger on
`inventory_reservations`, so the invariant holds for any writer. One active live
owner per market is a partial unique index keyed by
`(market_id, internal.execution_realm(environment))`.

**Environment separation (§10.8).** One semantic model with an `environment`
discriminator over the six §11 run modes. `internal.execution_realm()` groups
`EXECUTION_PROBE`/`LIVE_MICRO`/`LIVE` into one `REAL` realm and gives each
simulated mode its own — so a `SHADOW` or `PAPER` owner never blocks the live
owner (§6 invariant 11 explicitly permits shadow), while a `LIVE` and a
`LIVE_MICRO` owner of one market still collide. Both directions are tested.

**Typed repositories** (`src/repositories/**`): catalog, strategy, ownership,
fencing, orders, fills, ledger, balances. Every economic parameter and result is
a `DecimalString` imported from the frozen `@polymarket-bot/domain` contracts. No
repository computes an economic value in JavaScript; sums and comparisons happen
in PostgreSQL. Multi-row writes go through one transaction so the deferred
§10.7 checks fire inside the awaited call rather than somewhere later.

**Typed errors** (§21). Every database-enforced invariant raises a stable
SQLSTATE (`PMB01`…`PMB09`) and each maps to exactly one error class, so callers
branch on a type rather than on a message substring.

**Contracts respected.** `packages/domain` and `packages/decimal` are imported
and never edited. `src/schema/enums.ts` pins each mirrored vocabulary to the
frozen domain type with `satisfies`, and a unit test parses the SQL enums out of
`0001_foundation.up.sql` and requires an exact, ordered match in both directions
— so SQL/TypeScript drift fails `pnpm test` rather than production. (That test
found one real drift while being written.)

## assumptions

1. **Three tables beyond the §10.1–§10.6 lists**, each a normalization of a
   listed table's stated purpose rather than a new concept:
   - `strategy.market_ownership`. §10.3 gives `instances` the purpose "Named
     deployments and ownership rules", but an instance is bound to a *series*
     while §10.7's constraint is per *market*, and a rolling series produces a
     new ephemeral market every cadence. Materializing ownership is what lets
     "one active live owner per market" be a database constraint (ADR-011 §1
     enforcement layer 1) instead of prose.
   - `data.dataset_manifest_segments` and `data.dataset_manifest_exclusions`.
     §10.2 defines `dataset_manifests` as "Exact input segments and exclusions
     for replay"; the two lists are normalized so a manifest cannot cite a
     segment that does not exist (§12.5 pins segment ids *and* checksums).
2. **`account_ref` is an opaque bounded identifier, not a foreign key.** §10.7
   requires `orders(venue_order_id)` to be "scoped by environment/account", but
   §10 lists no accounts table. Inventing one would have been a larger
   invention than carrying an opaque reference, so accounts are referenced, not
   catalogued. A future accounts table can add the foreign key additively.
3. **`environment` is the §10.8 environment discriminator**, typed as the six
   §11 run modes, with `internal.execution_realm()` grouping the real-order
   modes. §10.8 requires one semantic schema and forbids baking live/backtest
   mixing into the model; this keeps the model single while making "live" a
   property of a row rather than of a deployment.
4. **A fill and its allocations are written in one transaction.** §10.7 states
   the sum *equals* the fill quantity; the deferred check enforces exactly that,
   and §6 invariant 7 makes it always satisfiable (allocate to `UNATTRIBUTED`).
   Consequently there is no API that records a fill without attributing it.
5. **`fill_allocations.allocated_shares` is positive and the table is
   append-only**, so a reattribution mechanism is deliberately absent (see
   `follow_up` F3).
6. **The `internal.code` grammar is for metric-label-safe codes only.** Version
   strings (`code_version`, `model_version`, `simulator_version`,
   `normalizer_version`, the model versions on a manifest) use
   `internal.identifier`, because `0.1.0` is a legitimate version and is not a
   Prometheus label value. This was found by a failing test, not assumed.
7. **`payload`/`parameters` `jsonb` documents are validated by their owning
   contract, not re-validated here.** A stored intent or signed order already
   satisfies the frozen domain contracts, which reject a `number` for an
   economic field.

## deviations

**D1 — BLOCKER: `pnpm install --frozen-lockfile` needs a three-line decision in
`pnpm-workspace.yaml`, which is outside this package's `allowed_paths`.**

`@testcontainers/postgresql` (required by the task packet and by handoff §16.4,
"Use Testcontainers for PostgreSQL and Redis") brings three transitive packages
with install scripts: `cpu-features@0.0.10`, `protobufjs@7.6.5`, `ssh2@1.17.0`.
This repository's pnpm runs with strict dependency-build policy, so:

- on a pristine checkout, `pnpm install --frozen-lockfile` **exits 1** with
  `[ERR_PNPM_IGNORED_BUILDS]`, and every `pnpm <script>` fails with it too
  because pnpm runs a dependency-status install first;
- pnpm **rewrites `pnpm-workspace.yaml` itself**, adding placeholder
  `allowBuilds` entries (`cpu-features: set this to true or false`, …), so
  merely running any pnpm command dirties that file. This is the same mechanism
  that produced the already-committed `allowBuilds: esbuild: true`.

The required change, verified to make `pnpm install --frozen-lockfile` exit 0:

```yaml
allowBuilds:
  cpu-features: false
  esbuild: true
  protobufjs: false
  ssh2: false
```

`false` is the correct answer on the merits, not merely the convenient one:
these are native build scripts we do not want executed, and Testcontainers talks
to the Docker socket over HTTP without `ssh2`'s optional native binding.

**Verification method, disclosed.** To produce the gate evidence above, the
three lines were applied locally, every gate was run, and the file was then
restored with `git checkout -- pnpm-workspace.yaml`. **The commit contains no
change to `pnpm-workspace.yaml`.** A reviewer re-running the gates without the
decision will see `pnpm install --frozen-lockfile` exit 1 with
`ERR_PNPM_IGNORED_BUILDS` and pnpm re-adding the placeholders.

Alternative, if the orchestrator prefers not to touch the workspace file:
replace the Testcontainers dependency with a ~80-line Docker-CLI driver in
`src/testing/container.ts` (`docker run` / `docker port` / `docker rm -f`),
which removes all three packages and needs no root change — at the cost of
deviating from §16.4's named library. **Not** done unilaterally: §16.4 names
Testcontainers, and swapping mandated test infrastructure is a bigger decision
than a three-line build policy.

**D2 — root script wiring deferred, per the task packet.** `db:migrate` and
`test:integration` exist as package-level scripts:

```bash
pnpm --filter @polymarket-bot/storage-postgres db:migrate            # --status, --down --steps=N, --down --all
pnpm --filter @polymarket-bot/storage-postgres test:integration
```

Root `package.json` currently has `db:migrate` as a "NOT IMPLEMENTED" stub
exiting 1 and `test:integration` as an exit-0 skip placeholder that names
WP-040. Both should now delegate to the package scripts, and `.github/workflows/ci.yml`
should run the integration job on a Docker-enabled runner. Neither path is in
this package's `allowed_paths`.

**D3 — `internal.trade_settlement_state` carries six values, not §9.11's five.**
§9.11 lists `MATCHED`, `MINED`, `CONFIRMED`, `RETRYING`, `FAILED`. The SDK
enumerates six and ADR-006 §5 names `MATCHED_NOT_BROADCASTED` explicitly (venue
report §4). A venue state the table cannot record would be unrecordable venue
truth, so it is included. Recorded here as a deliberate, cited superset.

**D4 — two schemas beyond the six.** `internal` (domains, enums, trigger
functions) and `migrations` (runner bookkeeping). Neither holds a business
record; they exist so that "the semantic model" remains exactly the six schemas
§10 names, and so that a full rollback can be shown to leave nothing behind.

**D5 — `fills` and `orders` uniqueness is additionally scoped by
environment/account.** §10.7 scopes `orders(venue_order_id)` that way
explicitly, and states the fills key without a scope. Fills are scoped the same
way for the §10.8 reason: a replayed or simulated fill must never collide with a
live one in a database that holds both. Documented rather than silently applied.

**D6 — controlled-vocabulary array columns are `text[]`, validated by trigger.**
`market_parameter_history.changed_parameters` and `decisions.reason_codes` would
naturally be `<enum>[]` / `<domain>[]`, but the PostgreSQL wire protocol returns
an array of a custom type as an unparsed literal (`{tick_size}`), which would
leak into every repository result. They are `text[]` with
`internal.assert_text_array_elements()` checking each element against the enum
or domain, so the vocabulary is still defined exactly once.

**D7 — `internal.assert_valid_fencing_reference` fires before the composite
foreign key**, so a fabricated lease reference surfaces as `PMB06` rather than
`23503`. Both constraints exist; `fencing.test.ts` proves the foreign key is not
decorative by disabling the trigger for one assertion and re-enabling it.

## known_risks

1. **R1 — D1 leaves CI red until the workspace decision is merged.** Every
   `pnpm` script in the repository fails until then, not only this package's.
2. **R2 — the deferred fill-allocation equality is strict.** A component that
   learns of a fill before it can attribute it must still allocate the whole
   quantity in the same transaction, to `UNATTRIBUTED` if necessary. That is
   §6 invariant 7 working as designed, but it constrains `WP-200`'s write path
   and should be confirmed there rather than discovered.
3. **R3 — aggregate constraint triggers serialize per aggregate.** The
   fill-allocation and ledger-balance triggers take a row lock on the fill or
   the transaction header (`FOR UPDATE`) so concurrent writers cannot both read
   a stale total. Correct, but it means allocations for one fill and entries for
   one ledger transaction are serialized. No throughput measurement was taken;
   these are per-fill and per-transaction locks, not table-wide.
4. **R4 — the append-only guard is a trigger, so a role that can
   `ALTER TABLE … DISABLE TRIGGER` can bypass it.** That is a privileged,
   auditable act, and the integration suite itself uses it once (re-enabling in
   a `finally`). Production hardening is the least-privilege grant script in the
   package README; it is documented, not implemented, because roles are
   cluster-global and do not belong in a per-database migration.
5. **R5 — `available_amount` is a stored generated column.** A future migration
   that changes `internal.decimal_text` would need to rewrite the table.
6. **R6 — no load or size testing.** Index selection is reasoned, not measured.
   The high-cardinality tables (`order_events`, `ledger_entries`,
   `book_checkpoints`) will need partitioning or retention before they are
   large; §10.2 already keeps raw frames out of PostgreSQL.
7. **R7 — the USDC/pUSD denomination question (venue conflict C-2) remains
   open.** The schema is deliberately neutral: every ledger entry and every fee
   or reward snapshot names its own asset explicitly, and nothing in the model
   treats the two as interchangeable. `WP-200` must still resolve it
   (ADR-006 §7 rule 4).
8. **R8 — `market_ownership` scoping by execution realm is an interpretation.**
   §10.7 says "Only one active live owner per market" without naming a scope.
   Global scoping would make a `BACKTEST` replay of a real market collide with
   the live owner, which §10.8 forbids assuming; the realm split is the reading
   that satisfies both §6 invariant 11 and §10.8. Flagged for review.
