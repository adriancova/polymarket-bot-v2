## summary

WP-040 implements the entire §10 database model — the six semantic schemas, the
§10.7 constraints, forward and rollback migrations, a SQL-first runner, Kysely
typed table definitions for all 57 tables (53 from the §10.1–§10.6 lists plus the
four additions in [assumptions](#assumptions)), and typed repositories for the
shared records — with an integration suite that exercises every acceptance
criterion against a real PostgreSQL 16.6 container.

**Migrations** (`db/migrations/**`, 8 forward + 8 rollback files). The mechanism
is plain SQL plus a small runner in this package, because every §10.7 constraint
is DDL (domains, partial unique indexes, constraint triggers, deferred
constraint triggers) that a migration DSL would either not express or would
carry as embedded SQL anyway; and because Kysely's own migrator uses TypeScript
modules that must be compiled first, which would make `db:migrate` depend on a
build of the package that owns the schema. The runner takes a session advisory
lock, runs each migration and its bookkeeping row in one transaction, records
the SHA-256 of the SQL as applied and re-checks it (editing an applied migration
is an error, not something to reconcile), and rolls back newest-first. A full
rollback leaves only `migrations.schema_migrations` — verified, not asserted.

**Schemas.** `catalog` (10 tables), `data` (8), `strategy` (9), `execution`
(10), `accounting` (11), `ops` (9), plus two infrastructure schemas holding no
business records: `internal` (domains, enums, trigger functions) and
`migrations` (runner bookkeeping). The §10.1–§10.6 table lists are implemented
verbatim; four additions are documented in [assumptions](#assumptions).

**Economic values are canonical decimal TEXT, never `numeric`, never a JS
`number`.** `numeric` was rejected for storage because it accepts `1.50` and
`1.5` as two spellings of one value and hands back whichever scale it stored,
breaking the one-representation property that equality, unique constraints, and
canonical hashes depend on (`docs/contracts/domain.md` §3.2). Domains
(`internal.decimal_string`, `…non_negative…`, `…positive…`, `internal.price_string`)
enforce the §7.3 grammar in the database; constraint triggers aggregate in
`numeric`, which is exact arbitrary-precision decimal. Timestamps cross the
boundary as ISO-8601 strings, never `Date`: connections run `TimeZone=UTC` and
`DateStyle=ISO` and the conversion is total, throwing rather than guessing.

**§10.7, constraint by constraint.** Sortable ids: an `internal.uuid_v7` domain
on every internal primary key, checking both the version and the variant nibble
so that nothing the client calls invalid is storable (a plain-`uuid` primary key
anywhere in the six schemas fails a test), with a server-side generator and a
client-side `uuidV7()`. `orders(venue_order_id)` unique where not null, scoped by
`(environment, account_ref)` and `NULLS NOT DISTINCT` so an unknown account does
not disable deduplication. Fills unique on the §10.7 triple, additionally
environment/account scoped (§10.8) and likewise `NULLS NOT DISTINCT`.
`submission_attempts(expected_order_hash)` unique where not null. Immutable
configs and rule versions, and append-only event/ledger tables, by
`BEFORE UPDATE OR DELETE OR TRUNCATE` triggers — **not** by privileges, because a
grant does not bind the table owner that migrations run as (a complementary
least-privilege grant script is in the package README). Live orders and live
submission attempts require a valid fencing token through four layers: a CHECK
(unrepresentable without one), a composite foreign key to `(lease, token)`, a
trigger that requires the lease to be ACTIVE, unexpired **by the database's own
clock**, and for that account and environment, read **under a row lock** so a
concurrent release serializes against it — and composite foreign keys binding the
order's `environment`/`account_ref` to its plan, so the discriminator the CHECK
reads cannot disagree with the chain that authorized the write. Fill allocations
are checked twice: immediately (never exceed the fill) and deferred to COMMIT
(equal the fill exactly). Ledger transactions balance to zero per asset via a
deferred constraint trigger on both the header and the entries. Available balance
is a `GENERATED ALWAYS` column with a CHECK, and `reserved_amount` is recomputed
from `inventory_reservations` by trigger *and* validated against those rows on
every write to `balance_projection` (`PMB08`), so the reservation facts are
authoritative for any writer rather than for one that goes through this package.
One active live owner per market is a partial unique index keyed by
`(market_id, internal.execution_realm(environment))`, with the ownership row's
`environment` bound to the owning instance by composite foreign key. Exactly one
fenced live writer per account is a partial unique index keyed by
`(account_ref, internal.execution_realm(environment))`, and a CHECK rejects a
fencing lease in any simulated run mode outright (ADR-008 §2, ADR-010).

**Environment separation (§10.8).** One semantic model with an `environment`
discriminator over the six §11 run modes. `internal.execution_realm()` groups
`EXECUTION_PROBE`/`LIVE_MICRO`/`LIVE` into one `REAL` realm and gives each
simulated mode its own — so a `SHADOW` or `PAPER` owner never blocks the live
owner (§6 invariant 11 explicitly permits shadow), while a `LIVE` and a
`LIVE_MICRO` owner of one market still collide. Both directions are tested.

**Typed repositories** (`src/repositories/**`): catalog, strategy, ownership,
fencing, orders, fills, ledger, balances. Every economic parameter and result is
a `DecimalString` imported from the frozen `@polymarket-bot/domain` contracts. No
repository computes an economic value in JavaScript; sums and comparisons happen
in PostgreSQL. Multi-row writes go through one transaction so the deferred
§10.7 checks fire inside the awaited call rather than somewhere later.

Three values are deliberately **not** repository parameters, because a caller
that can state them can state them wrongly: an ownership claim's `environment`
(read from the instance), and an order's, submission attempt's, and fill's
`environment` and `account_ref` (read from the plan or the order). Each is read
in the same statement that writes the row, and a composite foreign key enforces
the same agreement for every other writer.

**Economic values inside `jsonb`.** The document types for signed payloads,
intents, approved intents, order-event payloads, and strategy parameters exclude
`number` at every depth (`DecimalSafeJsonInput`), and
`assertDecimalSafeJson()` deep-checks them at the repository boundary, including
pre-serialized text. Four payloads are exempt with a documented reason
(`src/json.ts`): a JSON Schema, two verbatim venue records, and model outputs.

**Typed errors** (§21). Every database-enforced invariant raises a stable
SQLSTATE (`PMB01`…`PMB09`) and each maps to exactly one error class, so callers
branch on a type rather than on a message substring.

**Contracts respected.** `packages/domain` and `packages/decimal` are imported
and never edited. `src/schema/enums.ts` pins each mirrored vocabulary to the
frozen domain type with `satisfies`, and a unit test parses the SQL enums out of
`0001_foundation.up.sql` and requires an exact, ordered match in both directions
— so SQL/TypeScript drift fails `pnpm test` rather than production. (That test
found one real drift while being written.)

## assumptions

1. **Three tables beyond the §10.1–§10.6 lists**, each a normalization of a
   listed table's stated purpose rather than a new concept:
   - `strategy.market_ownership`. §10.3 gives `instances` the purpose "Named
     deployments and ownership rules", but an instance is bound to a *series*
     while §10.7's constraint is per *market*, and a rolling series produces a
     new ephemeral market every cadence. Materializing ownership is what lets
     "one active live owner per market" be a database constraint (ADR-011 §1
     enforcement layer 1) instead of prose.
   - `data.dataset_manifest_segments` and `data.dataset_manifest_exclusions`.
     §10.2 defines `dataset_manifests` as "Exact input segments and exclusions
     for replay"; the two lists are normalized so a manifest cannot cite a
     segment that does not exist (§12.5 pins segment ids *and* checksums).
2. **`account_ref` is an opaque bounded identifier, not a foreign key.** §10.7
   requires `orders(venue_order_id)` to be "scoped by environment/account", but
   §10 lists no accounts table. Inventing one would have been a larger
   invention than carrying an opaque reference, so accounts are referenced, not
   catalogued. A future accounts table can add the foreign key additively.
3. **`environment` is the §10.8 environment discriminator**, typed as the six
   §11 run modes, with `internal.execution_realm()` grouping the real-order
   modes. §10.8 requires one semantic schema and forbids baking live/backtest
   mixing into the model; this keeps the model single while making "live" a
   property of a row rather than of a deployment.
4. **A fill and its allocations are written in one transaction.** §10.7 states
   the sum *equals* the fill quantity; the deferred check enforces exactly that,
   and §6 invariant 7 makes it always satisfiable (allocate to `UNATTRIBUTED`).
   Consequently there is no API that records a fill without attributing it.
5. **`fill_allocations.allocated_shares` is positive and the table is
   append-only**, so a reattribution mechanism is deliberately absent (see
   `follow_up` F3).
6. **The `internal.code` grammar is for metric-label-safe codes only.** Version
   strings (`code_version`, `model_version`, `simulator_version`,
   `normalizer_version`, the model versions on a manifest) use
   `internal.identifier`, because `0.1.0` is a legitimate version and is not a
   Prometheus label value. This was found by a failing test, not assumed.
7. **`payload`/`parameters` `jsonb` documents are validated by their owning
   contract, not re-validated here.** A stored intent or signed order already
   satisfies the frozen domain contracts, which reject a `number` for an
   economic field. Round 2 narrowed this: where the vocabulary is narrow enough
   to state in SQL, the rule is *also* a database constraint — `model_outputs`
   is checked by `internal.jsonb_contains_number()` for every writer, not only
   for one that goes through this package.
8. **(Round 2) A fourth table beyond the §10.1–§10.6 lists:
   `ops.fencing_token_high_water`.** ADR-008 §1 says a fencing token is never
   reused. Deriving the next token from `max(fencing_token)` over
   `ops.fencing_leases` made that claim only as durable as the lease rows: delete
   the released history and the maximum drops, so the next acquisition re-issues
   a token a previous holder already used. The high-water mark is the token
   *sequence* as its own fact — one row per `(account_ref, execution_realm)`,
   monotonic, non-deletable, non-truncatable. It lives in `ops` because it is
   fencing state that belongs beside the leases it constrains, and it takes the
   §10 table count to 57.
9. **(Round 2) `accounting.ledger_entries` keeps its own `account_ref`,
   deliberately unbound to the transaction header.** The header's discriminators
   are now bound to the order, fill, and wallet operation it books; the *entries*
   are the double-entry legs, and a transfer between two accounts is exactly one
   transaction with legs in two accounts. Binding the legs to the header would
   make that unrepresentable. The header is a label about what happened, the
   entries are what moved, and the ledger's own balance check is per asset, not
   per account.
10. **(Round 2) A ledger transaction that references an order or a fill
    references an account-bearing one.** `ledger_transactions.account_ref` is
    NOT NULL and the binding is an equality, so an order with no account can
    have no ledger transaction. That is not a new restriction in substance:
    `balance_projection` and `pnl_snapshots` are keyed by a non-null
    `account_ref` too, so an accountless order was already outside the
    accounting model. A simulated deployment that wants a ledger names an
    account for it.
11. **(Round 2, corrected in round 3) The §9.11 lineage boundary is "has this
    order been signed", not "is this order terminal".**
    `orders_submission_requires_attempt` exempts `PLANNED`, `CANCELED`,
    `REJECTED`, and `EXPIRED` — but only while the row carries no venue order id,
    no venue order hash, no `submitted_at`, and no fills. `PLANNED` is the state
    before §9.11 step 1, and the three terminal states are reachable by
    abandoning an order before transmission; any evidence of venue contact
    removes the exemption regardless of the state label.

    **Round 2 also exempted `SIGNED`, and that was wrong.** The round-2 text
    said `SIGNED` "precedes the attempt legitimately"; §9.11's step order says
    the reverse — the attempt id is created at step 1, the order is signed at
    step 2, the signed payload is persisted at step 3, and `SIGNED` is committed
    at step 4. The durable signed payload lives in `execution.submission_attempts`,
    so an attemptless `SIGNED` order asserts a signature with no signature on
    record — exactly the artifact §6 invariant 6 reconciles a lost response
    against. `SIGNED` is no longer exempt.

that names neither may omit it. Structurally this only *removes* previously-valid
calls that were exactly the bypass, and there is no downstream consumer yet
(`WP-200` is unwritten), so nothing had to be migrated; every existing call site
in the suite was already either standalone or market-bearing. The alternative —
leaving `marketId` optional and relying on the CHECK alone — would have kept a
compile-clean way to write a row the database then rejects at runtime, which is a
worse API for the same enforcement. Both layers are kept: the type stops it here,
the CHECK stops it for every other writer, and a test casts through the type to
prove the runtime layer is not decorative.

**D18 (round 3) — three round-2 bypass rows were made *more* truthful.** The
three F10 raw-SQL bypasses now name the correct market, because without it the
new CHECK rejects them first and they stop being tests of the discriminator
binding they were written for. Each still fails, on the same constraint as
before. This is the same situation round 2 recorded for itself: a bypass row now
has two things wrong with it, and the test is about the other one. **No
constraint was weakened.**

## known_risks

1. ~~**R1 — D1 leaves CI red until the workspace decision is merged.**~~
   **Closed**: the decision is committed in `49d065c`, and
   `pnpm install --frozen-lockfile` exits 0 on this branch.
2. **R2 — the deferred fill-allocation equality is strict.** A component that
   learns of a fill before it can attribute it must still allocate the whole
   quantity in the same transaction, to `UNATTRIBUTED` if necessary. That is
   §6 invariant 7 working as designed, but it constrains `WP-200`'s write path
   and should be confirmed there rather than discovered.
3. **R3 — aggregate constraint triggers serialize per aggregate.** The
   fill-allocation and ledger-balance triggers take a row lock on the fill or
   the transaction header (`FOR UPDATE`) so concurrent writers cannot both read
   a stale total. Correct, but it means allocations for one fill and entries for
   one ledger transaction are serialized. No throughput measurement was taken;
   these are per-fill and per-transaction locks, not table-wide.
4. **R4 — the append-only guard is a trigger, so a role that can
   `ALTER TABLE … DISABLE TRIGGER` can bypass it.** That is a privileged,
   auditable act, and the integration suite itself uses it once (re-enabling in
   a `finally`). Production hardening is the least-privilege grant script in the
   package README; it is documented, not implemented, because roles are
   cluster-global and do not belong in a per-database migration.
5. **R5 — `available_amount` is a stored generated column.** A future migration
   that changes `internal.decimal_text` would need to rewrite the table.
6. **R6 — no load or size testing.** Index selection is reasoned, not measured.
   The high-cardinality tables (`order_events`, `ledger_entries`,
   `book_checkpoints`) will need partitioning or retention before they are
   large; §10.2 already keeps raw frames out of PostgreSQL.
7. **R7 — the USDC/pUSD denomination question (venue conflict C-2) remains
   open.** The schema is deliberately neutral: every ledger entry and every fee
   or reward snapshot names its own asset explicitly, and nothing in the model
   treats the two as interchangeable. `WP-200` must still resolve it
   (ADR-006 §7 rule 4).
8. **R8 — `market_ownership` scoping by execution realm is an interpretation.**
   §10.7 says "Only one active live owner per market" without naming a scope.
   Global scoping would make a `BACKTEST` replay of a real market collide with
   the live owner, which §10.8 forbids assuming; the realm split is the reading
   that satisfies both §6 invariant 11 and §10.8. Flagged for review. Round 1
   accepted the reading and closed the way around it: the realm is now derived
   from the owning instance, so the scope cannot be chosen per row.
9. **R9 (round 1) — the reservation guard serializes writers per balance row.**
   Maintaining `reserved_amount` takes `FOR UPDATE` on the balance row before
   summing, so reservations against one account/asset are serialized. That is
   what makes the concurrent-oversubscription test deterministic, and it is a
   per-row lock, not table-wide; no throughput measurement was taken. Two
   sessions reserving the same two assets in opposite orders can deadlock, which
   PostgreSQL detects and reports — `WP-200` should reserve in a stable asset
   order.
10. **R10 (round 1, updated round 2) — the guard makes `balance_projection`
    unwritable while the reservations disagree.** If a future path deletes
    reservation rows outside the trigger's reach (it would have to bypass both
    the row trigger and the TRUNCATE guard), every later write to that balance
    row raises `PMB08` until the two agree again. That is loud rather than
    silent, which is the intent, but it is a lockout rather than a correction.
    **Round 2 closed the other half of this risk**: the row's key
    (`account_ref`, `environment`, `asset_id`) is now immutable
    (`balance_projection_immutable_key`, `PMB02`), so the lockout can no longer
    be escaped by *moving* the balance to a key whose reservations happen to
    agree — which was the HIGH-1 continuation. The remaining risk is the lockout
    itself, and the way out of it is to restore or release the reservation rows,
    not to rewrite the projection.
11. **R11 (round 1) — the composite discriminator keys add foreign keys to hot
    write paths.** An order insert now checks four composite keys against the
    plan, and a fill checks three against the order. Each is an index lookup on a
    primary-key-prefixed unique index, so the cost is small and bounded, but it
    is not zero and has not been measured under load.
12. **R12 (round 1) — `clock_timestamp()` makes lease validity non-repeatable
    inside one transaction.** A transaction that inserts two live orders around
    the expiry instant can have the first accepted and the second rejected. That
    is the correct answer (authority really did lapse between them) and it means
    a batch is not atomic with respect to expiry; `WP-320` should refresh the
    lease before a batch rather than rely on the batch being fast.
13. **R13 (round 1) — the lease `FOR SHARE` lock puts heartbeats behind
    in-flight order inserts.** A heartbeat is an UPDATE of the lease row, which
    conflicts with the share lock an order insert holds for the duration of its
    transaction. Order inserts are short, and the alternative (no lock) is the
    HIGH-3c bypass, but a transaction that inserts a live order and then does
    something slow before committing will delay that account's heartbeat — and a
    late heartbeat is venue-side cancellation (ADR-008 §4). `WP-320` should keep
    the live-order transaction to the insert.
14. **R14 (round 2) — the token high-water mark is a second row to lock on the
    acquisition path.** Every lease insert upserts
    `ops.fencing_token_high_water` for its `(account_ref, execution_realm)`, so
    two acquisitions for one account serialize on that row as well as on the
    advisory lock the repository takes. That is what makes the race safe (the
    `on conflict … where` re-evaluates against the committed value), and it is a
    per-account row, not a table-wide lock. Acquisition is rare by design —
    ADR-008: "failover is not instant and must not be" — so the cost is not on a
    hot path.
15. **R15 (round 2) — a terminal lease is frozen, so nothing can be *annotated*
    afterwards either.** `fencing_leases_forward_only` rejects every UPDATE to a
    lease that is no longer ACTIVE, including one that only fills in
    `revoked_reason`. An operator who wants to record why a lease ended must do
    it in the statement that ends it (`releaseLease` and
    `expire_stale_fencing_leases` both do), or in `ops.incidents`. This is
    deliberate — a mutable "reason" on a terminal grant is a mutable grant — but
    it is a real constraint on the fencing owner's API in `WP-320`.
16. **R16 (round 2, corrected and tightened in round 3) —
    `orders_submission_requires_attempt` constrains the OMS write order, and the
    boundary is `SIGNED`, not "submitted".** Round 2 stated this as "an order
    that goes straight to a *submitted* state must have its attempt row first",
    which understated it, because round 2 exempted `SIGNED`. It does not any
    more, and the accurate statement is:

    > An order may exist at `PLANNED` with no attempt. Everything from `SIGNED`
    > onward requires `submission_attempt_id`. So the write order is: create the
    > `submission_attempt` row **first**, then either create the order already
    > naming it, or create the order at `PLANNED` and update it to name the
    > attempt in the same statement that moves it to `SIGNED`.

    `WP-200`/`WP-320` cannot create the order row and sign afterwards. That is
    §9.11's own step order — attempt id at step 1, sign at step 2, persist the
    signed payload at step 3, commit `SIGNED` at step 4 (and §6 invariant 6
    depends on the payload being persisted before transmission) — so it is the
    intended direction. It remains a sequencing requirement discovered here
    rather than in integration; F13 tracks confirming it in the OMS write path.
17. **R17 (round 2) — the never-NULL `account_key` is a generated column, so a
    future change to how "no account" is spelled is a table rewrite.** Both
    `execution.orders` and `execution.fills` store
    `coalesce(account_ref, '')`, and the empty string is unavailable to
    `internal.identifier` (length ≥ 1), which is what makes the sentinel
    unambiguous. If an `accounts` table ever makes `account_ref` a foreign key
    (F8), the sentinel has to be reconsidered at the same time.
18. **R18 (round 3) — an order- or fill-linked ledger transaction must name its
    market, which is a new required argument on that write path.**
    `ledger_transactions_execution_link_has_market` and the repository input type
    both require it. The value is never unknown — `execution.orders.market_id`
    and `execution.fills.market_id` are NOT NULL, so a caller holding either row
    holds its market — but a `WP-200` posting path that previously passed only
    `orderId`/`fillId` now has to carry the market through. Deliberately *not*
    solved by having the repository look the market up from the order: that would
    make the ledger's market a value this package derives rather than one the
    caller asserts and the database verifies, and the whole point of the round-2
    binding is that the two must agree.
19. **R19 (round 3) — `MATCH SIMPLE` composite keys are only as strong as the
    nullability of their own columns, and this is the second time that has
    mattered.** Round 2 fixed it for `account_ref` with a never-NULL generated
    `account_key`; round 3 fixed it for `market_id` with a CHECK. Every remaining
    MATCH SIMPLE binding in the schema whose *parent-side* column is nullable
    should be read with that in mind. The audited residue on
    `ledger_transactions` is deliberate and documented rather than outstanding:
    `wallet_operations.market_id` is nullable because a deposit or withdrawal
    genuinely has no market, and `ledger_entries.account_ref` is deliberately
    unbound (assumption 9). Both are stated positions, not oversights — but a
    future column added to one of these bindings needs the same question asked
    of it.
