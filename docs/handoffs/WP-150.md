## summary

`packages/order-book` replaces its `WP-010` placeholder with the handoff
§9.4 local order book: a pure layer-1 state-machine library fed by the
frozen domain book events.

1. **Independent books per outcome token.** `OutcomeTokenBook` pins one
   `(internalMarketId, tokenId)`; `MarketOutcomeBooks` holds the two books of
   a binary market and routes by the payload's own `tokenId`. A payload for
   any other identity is a typed refusal; neither book is ever derived from
   the other (the golden fixture asserts the NO book is NOT the YES
   complement).
2. **ADR-013 applied exactly.** A `BookLevelChanged.size` REPLACES the
   level's size — never adds, never subtracts — and `"0"` removes the level.
   The ADR's own §2 template (a level at `5000` receiving `5` results in
   `5`, never `5005`, never `4995`) is a named test and a golden-fixture
   step. A zero-size snapshot level is dropped as an empty level (the same
   reading as the `WP-140` recorder job).
3. **Exact decimals everywhere.** Prices and sizes are canonical decimal
   strings validated by the frozen domain contracts; `"0.10"` is refused at
   the boundary (`ORDER_BOOK_INPUT_INVALID`), never normalized —
   normalization belongs to adapters (ADR-001 §3). Sums are exact
   (`addDecimal`); the one division (VWAP) uses `divDecimal`'s documented
   policy, overridable per call.
4. **Tracked (§9.4):** best bid, best ask, exact spread, depth (level counts
   plus exact per-side share sums), the venue-provided book hash last carried
   by an applied event, last update provenance, and staleness computed
   against a caller-supplied `now` (the book reads no clock).
5. **Stale-generation rejection, aligned with what WP-070 actually emits.**
   The freshness identity is `(gatewayEpoch, subscriptionGeneration)`,
   adopted from the last applied authoritative snapshot. Verified against
   `packages/polymarket-public`: generations are strictly increasing from
   `1`, `0` is never carried by an event, a generation advances exactly when
   a gap opens, WS events are always stamped with the session's generation,
   and REST snapshots taken to close a gap are stamped via the fetcher
   context. Hence: older generation → `ORDER_BOOK_STALE_SUBSCRIPTION_GENERATION`
   carrying **both** generations; newer generation on a delta →
   `ORDER_BOOK_GENERATION_AHEAD_REQUIRES_SNAPSHOT` (§7.1: a gap requires an
   authoritative snapshot before the market resumes); missing generation →
   fail-closed refusal; different epoch on a delta →
   `ORDER_BOOK_EPOCH_MISMATCH` (epochs are identity, not chronology —
   `wal-format.md` §12.1); non-increasing `ingestSeq` within an epoch →
   `ORDER_BOOK_OUT_OF_ORDER_INGEST`. **No venue sequence number is invented
   anywhere** — ordering material is exactly `gatewayEpoch + ingestSeq`,
   venue timestamps, and venue-provided hashes (§9.4 closing rule).
6. **Executable price.** `executablePrice` walks asks (BUY) or bids (SELL)
   best-first with exact cost accumulation; a book too shallow returns a
   typed `ORDER_BOOK_INSUFFICIENT_DEPTH` carrying requested and available
   shares — never a partial silent answer.
7. **REST-snapshot validation, pure and order-robust.**
   `compareAgainstRestSnapshot` is a pure function (no HTTP in the package);
   it canonicalizes both snapshot sides into price-keyed sets before
   comparing — robust to `verified-2026-09-02.md` §6's Contradiction 1, where
   the venue's two first-party sources publish OPPOSITE orders for both
   sides — and compares canonical forms byte-exactly, returning named
   divergences (`LEVEL_MISSING_FROM_BOOK`, `LEVEL_NOT_IN_SNAPSHOT`,
   `LEVEL_SIZE_MISMATCH`, `SNAPSHOT_DUPLICATE_LEVEL`,
   `SNAPSHOT_LEVEL_NOT_CANONICAL`, `SNAPSHOT_IDENTITY_MISMATCH`). The WS and
   REST hashes are reported side by side and never judged across surfaces
   (no source documents a shared algorithm; `WP-070` `known_risks` 3).
8. **Tick changes invalidate price helpers.** `priceGrid` issues a helper
   pinned to the book's tick size and tick epoch; an applied tick-size VALUE
   change advances the epoch and every previously issued helper's operation
   returns `ORDER_BOOK_PRICE_HELPER_INVALIDATED` carrying both tick sizes —
   typed, visible, never silently wrong. An identical restatement does not
   invalidate. Grid arithmetic (conformance, snap up/down) is exact integer
   arithmetic, no floats.

Refusals are data (the `universe`/`settlement` pattern): stable codes,
bounded detail, evidence attached. Throws are reserved for structurally
impossible construction (`OrderBookConfigurationError`).

## assumptions

1. **Generation semantics are read from WP-070, not invented.** Verified in
   `packages/polymarket-public/src/feed/subscriptions.ts` (generations
   strictly increasing from 1; `0` never carried by an event; a removal
   retains the generation; "the generation advances exactly when a gap is
   opened for it"), `src/feed/connection.ts` (sessions stamp every published
   event), and `src/snapshot/fetcher.ts` / `src/normalize/snapshot.ts` (a
   gap-closing REST snapshot is stamped with the gap's generation via the
   caller-supplied context). The fail-closed consequences (missing
   generation refused; newer-generation delta refused pending snapshot) are
   this package's design on top of those verified facts plus §7.1's
   unconditional gap-⇒-snapshot rule.
2. **A generation-less snapshot is refused rather than adopted** (README
   decision 3). If a future gateway path legitimately emits book snapshots
   without a generation, that path must either stamp one or this rule needs
   an explicit revisit — recorded here so the integration failure mode is a
   typed refusal, not silent staleness.
3. **Cross-epoch handling:** a *snapshot* from a different epoch re-baselines
   (it is the §7.1 "new authoritative snapshot" a restart requires); a
   *delta* from a different epoch is refused. The book deliberately does not
   attempt to decide which of two epochs is newer — `wal-format.md` §12.1
   defines no such order — so cross-epoch dispatch order is the caller's
   responsibility, and the book follows internal ingest order (§9.4).
4. **`venueTimestamp`/`receivedAt` are ISO-8601 at this layer** (the §7.1
   envelope grammar). The venue's epoch-milliseconds form is the adapter's
   input, not this package's. `Date.parse` on an already-validated ISO string
   is used for the staleness epoch-ms derivation — deterministic, not a clock
   read.
5. **`BestBidAskChanged` is intentionally not consumed** (README decision 4):
   top-of-book derives from reconstructed levels only, avoiding a second,
   rivalrous top-of-book history. `WP-070` `follow_up` 6 (whether
   `price_change.best_bid/best_ask` should be carried) remains open and
   unblocked by this package: nothing here needs it.
6. **Hash usage is tracking, not verification.** §9.4 lists "hash" among
   tracked values and permits using venue-provided hashes; no official
   source documents the hash algorithm or a WS↔REST correspondence, so the
   book tracks the venue value and the REST comparison reports both without
   judging (fail-closed against inventing a venue fact).
7. **The serialization format is package-owned, versioned by its first
   line** (`polymarket-bot/order-book/v1`), and is a test/diagnostic oracle
   — not a domain contract and not persisted by any other component.

## known_risks

1. **The generation-gating lattice is stricter than any recorded producer
   behavior requires.** If a real gateway path emits, e.g., generation-less
   WS book snapshots, integration will surface typed refusals
   (`ORDER_BOOK_MISSING_SUBSCRIPTION_GENERATION`) rather than data loss.
   That is the intended failure mode, but it means `WP-120`-side wiring must
   propagate the envelope's `subscriptionGeneration` faithfully.
2. **Silent single-frame loss remains undetectable**, exactly as `WP-070`
   `known_risks` 4 warned: with no venue sequence number, a missed message
   on a healthy connection is invisible to any client. This package's
   defense is the §9.4 REST-snapshot comparison (divergences are named, not
   averaged away) and the generation/epoch gating; it does not and cannot
   claim gap-freedom.
3. **`ingestSeq` strict-increase is per book, not per stream.** Two books
   fed from one stream each see a subsequence, so the check catches
   replays/reordering per token but cannot validate global stream
   contiguity (which would require inventing per-book sequence expectations
   the venue does not provide).
4. **Staleness depends on the caller's clock discipline.** `stalenessMs`
   subtracts a stored gateway `receivedAt` from a caller-supplied now; skew
   between those clocks is reported as-is (negative values possible), never
   clamped. Consumers alerting on staleness should source `now` from the
   same clock domain as the gateway's `receivedAt`.
5. **The VWAP division default (34 significant digits, `ROUND_HALF_EVEN`)
   is a policy choice** inherited from `divDecimal`'s documented default.
   Any consumer needing a different rounding contract (e.g. conservative
   rounding for risk) must pass explicit `division` options; the parameter
   exists and is tested.
6. **The serialization oracle is hand-derived.** If a future change alters
   the format, every golden fixture must be re-derived by hand (the fixture
   README forbids regenerating the oracle from implementation output); the
   version line makes such a change loudly visible.
