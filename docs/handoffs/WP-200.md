## summary

`packages/ledger` and `packages/pnl` replace their `WP-010` placeholders with
the handoff §9.15 accounting ledger and the §9.16 PnL engine. Both are pure
layer-1 libraries: they own rules and typed records, never a connection.

1. **The ledger is an append-only VALUE.** `Ledger.append` returns a new
   ledger and never mutates the receiver, so a caller holding an earlier
   snapshot still sees the history it saw, and two branches from one snapshot
   cannot disturb each other. Recorded transactions are deep-frozen: writing
   to an appended entry throws. Consecutive appends share one backing buffer,
   so building an n-transaction ledger stays O(n) — ADR-006's consequence list
   makes rebuild speed a tracked property, because an invariant too slow to
   check quietly stops being checked.

2. **Every transaction balances to zero PER ASSET (the central invariant).**
   `checkPerAssetBalance` nets each asset independently with exact decimal
   arithmetic and emits one refusal per unbalanced asset, each naming the
   asset and its exact imbalance. Two assets that are individually unbalanced
   but happen to cancel numerically are TWO violations, not zero — a global
   sum is not accounting. An imbalance is REFUSED, never repaired: no code
   path adjusts an input to make it appendable.

3. **Attribution is a partition, enforced per transaction.** ADR-006 §2 says
   virtual allocation never creates or destroys value, so every append also
   checks `Δ(ACTUAL_ACCOUNT) = Δ(VIRTUAL_STRATEGY) + Δ(UNATTRIBUTED)` per
   asset. Enforcing it per transaction makes §6 invariant 7 hold inductively
   from the empty ledger rather than being audited after the fact
   (`auditAttributionPartition` exists for externally-loaded state and is
   always empty for a ledger-derived projection).

4. **Fill allocation partitions the actual quantity, never over-covers it.**
   Claims summing past the fill are refused with the exact excess (§10.7,
   §16.2). A shortfall — or no claims at all — becomes an EXPLICIT
   `UNATTRIBUTED` record with `haltRequired: true`. There is no silent
   absorption path: every share of a fill appears in exactly one returned
   record. Fees follow the ownership partition but are never prorated by
   silent division: with more than one owner every owner's fee share is
   explicit and the shares must sum exactly.

5. **Projections rebuild from zero and equal incremental state.** Both paths
   run the SAME `applyTransaction` fold step, and equality is asserted
   byte-for-byte through `serializeProjection` (a canonical sorted form) —
   over the whole projection, not a hand-picked field list. Balances are keyed
   by the ENTRY's `accountRef`, never the transaction header's (WP-040
   obligation F20), so a transfer between two accounts lands in two accounts.

6. **PnL separates realized from unrealized structurally.** The fold
   accumulates only realized facts; unrealized value is computed at snapshot
   time from open lots and caller-supplied marks, so the two cannot mix by
   construction. A missing midpoint mark is a typed refusal — "unrealized PnL
   at midpoint" is a required §9.16 measure and is never guessed. Model and
   liquidation values are `null` unless a mark supplies them for EVERY open
   lot of the denomination: a partially-marked measure is not a measure.

7. **Reward estimates are never booked as realized (§9.16, verbatim).** The
   rule is enforced in three independent places: the `REWARD_ESTIMATE` strict
   schema has no settlement-evidence field, so "an estimate that realizes" is
   unrepresentable; `REWARD_PAYOUT` REQUIRES the ledger transaction id of the
   observed payout; and the estimate handler touches only the estimate
   buckets. `serializeRealizedPnl` gives the tests a whole-state oracle for
   "the money did not move".

8. **Denominations never interchange.** Every monetary figure is per
   denomination asset and no code path sums across them (ADR-006 §7; the C-2
   USDC/pUSD question is unresolved and is NOT resolved here — see
   `deviations`). A record whose denomination contradicts an open lot's is
   refused.

### Persistence boundary (recorded decision)

`docs/contracts/dependency-direction.md` §2 places both packages in **layer
1**, which owns "rules, state machines, and computation; they do not own
connections." §10.5's `accounting.ledger_transactions` /
`accounting.ledger_entries` / `pnl_snapshots` tables (shipped by `WP-040` in
`packages/storage-postgres`, layer 2) are the persistence binding target, and
importing that package from here would be an upward edge (F12).

So these packages ship **pure transaction/projection logic and typed
records**, and the composition root binds them to the tables. The record
fields mirror the WP-040 columns field-for-field in camelCase
(`ledgerTransactionId`, `eventType`, `environment`, `accountRef`, `marketId`,
`orderId`, `fillId`, `walletOperationId`, `reconciliationRunId`,
`settlementState`, `reversesLedgerTransactionId`, `source`, `referenceHash`,
`detail`, `occurredAt`; entries: `scope`, `accountRef`, `instanceId`,
`runId`, `marketId`, `assetId`, `assetKind`, `amount`, `detail`), so a
composition root binds an `AppendedLedgerTransaction` with no mapping layer.
`recorded_at` and the surrogate `ledger_entry_id` are database concerns and
are deliberately absent. The §9.15 scope/event/asset-kind vocabularies are
re-declared here and pinned token-for-token against the migration enums by
`packages/ledger/src/vocabulary.test.ts`; the two can drift, so that test is
the drift detector and the fix is always to correct the divergent side.

## assumptions

Every open semantic decision, with its justification. None of these is a
venue fact; where a venue fact would have been required, the decision was to
refuse or to demand it from the caller.

1. **Persistence is a composition-root binding, not this package's job.**
   Justified by `docs/contracts/dependency-direction.md` §2 (layer 1 "does
   not own connections") and F12. Recorded in full under *Persistence
   boundary* above.

2. **`haltRequired` distinguishes an ARRIVAL from a RE-ATTRIBUTION.** §9.15's
   trigger is precise: "Any actual BALANCE CHANGE lacking attribution is
   allocated to UNATTRIBUTED, and the affected market is halted." A
   transaction moving value between `UNATTRIBUTED` and `VIRTUAL_STRATEGY`
   changes no actual holding — it is the REMEDIATION for an earlier arrival.
   Treating it as a fresh trigger would mean every fix re-raises the alarm it
   is fixing. So `UnattributedActivityRecord` is a discriminated union:
   `ACTUAL_ARRIVAL` carries the literal `haltRequired: true` (a record with
   `false` does not typecheck, so no code path can waive it) and
   `REATTRIBUTION` carries `false` and stays in the audit trail. This was
   found by a test, not assumed up front: the first version flagged the
   remediation as a halt trigger. **Reviewer note:** this is the one place
   where the implementation reads §9.15 more narrowly than "every
   `UNATTRIBUTED` entry halts", and the narrowing is deliberate and
   test-visible.

3. **A reversal must negate the original exactly, leg for leg.** ADR-006 §5.2
   says a failure is "a compensating append-only reversal, never an edit". A
   partial compensation is an adjustment and has its own event types
   (`MANUAL_ADJUSTMENT`, `RECONCILIATION_CORRECTION`), so a non-exact
   "reversal" is refused rather than accepted as an approximation. A second
   reversal of the same transaction is refused (it would double-compensate).

4. **An asset id has exactly one kind, and an outcome token belongs to
   exactly one market.** ADR-006 §7 rule 1 plus §9.2 identity binding. Both
   are enforced within a transaction and against the ledger's recorded
   history.

5. **Identifiers are caller-minted and validated, never generated.** A pure
   layer-1 package reads no clock and no randomness, so it cannot mint
   UUIDv7 values. ADR-016 §2's amendment is applied at the input surface:
   REFUSE, carrying the raw value; never a case-fold. This includes a
   lowercase **v4** in a v7 position — ADR-016 §2 pins the version and
   variant nibbles as part of the canonical form ("a v4 in that position
   would break the ordering property the field is there to provide"), and the
   amendment covers an "otherwise non-canonical" spelling, not only a
   mixed-case one. A value that is not UUID-shaped at all is an ordinary
   schema failure.

6. **A fee is prorated only by an explicit, machine-checked split.** With one
   owner the whole fee is theirs. With more than one, every claim must state
   its `feeAmount` and the shares must sum exactly to the fee; the
   unattributed remainder's share is derived by exact subtraction and refused
   if negative. A silently rounded division would put fractions of a cent
   somewhere nobody chose.

7. **Average cost per token asset, with basis conserved by subtraction.**
   Removing q of Q shares with basis B removes exactly B when the lot closes,
   otherwise `B·q/Q` under `divDecimal`'s documented policy — and the
   REMAINING basis is derived by exact subtraction, so total basis is
   conserved across any split. The handoff names the measures but not the
   cost method; average cost matches `actual_position_projection`'s single
   average-cost column (§10.5) rather than implying a lot table the schema
   does not have.

8. **§9.16 measure formulas** (the handoff lists the measures without
   formulas): `realizedPnl` = realized trading PnL; `grossTradingPnl` =
   realized + unrealized at midpoint; `coreNetPnl` = gross − fees (§6
   invariant 14: excludes rewards, realized or estimated); `allInPnl` =
   coreNet + realized rewards ONLY; `worstCaseResolutionPnl` = realized − Σ
   open cost basis (every open token resolving to zero — a sound lower bound
   because a short position cannot exist here, oversell being refused);
   `capitalCommitted` = Σ open basis + caller-stated reservations
   (reservation lifecycles are WP-190's domain).

9. **Selling more than the position holds is refused, not booked as a
   short.** Venue report §10.2: selling requires outcome-token inventory. A
   negative position would corrupt average-cost accounting silently; the
   caller escalates to reconciliation instead.

10. **A `FAILED` trade is not a fresh recognition.** ADR-006 §5 books a
    failure as a compensating reversal of a previously recognized trade, so
    `applyTrade` refuses a record already marked `FAILED` (`PNL_SETTLEMENT_
    FAILED_TRADE`) rather than folding a trade that did not settle.

11. **A split's cost-basis partition is the caller's explicit statement.** It
    arrives as a `COST_BASIS_INJECTION`; the engine never guesses a 50/50.

12. **`test/integration/ledger/**` was granted but is unused** — see
    `deviations` item 2.

## known_risks

1. **The §9.15 vocabulary is re-declared, so it can drift from the WP-040
   enums.** Layer 1 cannot import layer 2, so duplication is forced. Mitigated
   by `vocabulary.test.ts`, which pins all four lists literally — but that
   test asserts against the handoff, not against the SQL, so a migration that
   changed an enum spelling would not fail it. A future generator or a
   contract test that reads `db/migrations/0001_foundation.up.sql` would
   close this properly.

2. **The ledger↔PnL agreement is structural, not compiled.** No §2.1 row
   permits a `ledger → pnl` edge, so `buildFillPosting` cannot import the PnL
   schemas. `test/unit/ledger/ledger-to-pnl-contract.test.ts` parses every
   record the ledger emits under `PnlRecordSchema` across seven posting
   shapes, and asserts owner-shape assignability at compile time — but a
   record shape neither package's tests exercise could still drift. If the
   coupling tightens, the fix is a §2.1 row with a citation, not a loosened
   assertion.

3. **Rebuild cost is O(n) in transactions and is not benchmarked.** ADR-006
   makes rebuild speed a tracked property. The implementation shares one
   backing buffer across consecutive appends to keep append O(1) amortized,
   and `applyTransaction` copies the balance maps per transaction — fine at
   test scale, and the copy is what makes the projection an immutable value.
   At production ledger sizes the per-transaction map copy is the thing to
   measure first. No benchmark exists; none is claimed.

4. **`serializeProjection` / `serializePnlState` are oracles, not a
   persistence format.** They are stable and versioned with a domain prefix,
   but nothing yet depends on their bytes across process boundaries. Treating
   them as a wire format later needs a compatibility decision.

5. **Average cost is a modeling choice with tax/reporting consequences.** It
   matches the §10.5 schema, but if reporting later needs specific-lot
   identification, the fold changes shape. Flagged now because changing a
   cost method after history accumulates is expensive.

6. **`worstCaseResolutionPnl` assumes a long-only inventory.** It is a sound
   lower bound only because oversell is refused, so no short can exist. If a
   future package admits shorts, this formula silently stops being a bound.

7. **The purity source-scan is textual.** It fails on the SPELLING of a
   capability, so it is a deliberate-act detector, not a proof. `check:deps`
   (F1–F16) is the real structural gate; the scan catches the in-module cases
   that the import graph cannot see.

## follow_up

1. **Resolve ADR-006 §7's C-2 (USDC vs pUSD) at contract-owner level.** This
   is the one item WP-200 was assigned and could not discharge (deviation 3).
   It needs a network-permitted venue-verification round and an ADR-006
   amendment — both outside this package. Until then, fee and reward entries
   carry the denomination of their source and cannot be summed with
   collateral balances without an explicit, recorded conversion transaction.

2. **WP-040 obligations F12, F17, F18, F19 remain open for their owning
   paths** — inventory reservation ordering (`packages/inventory`), the OMS
   `SIGNED` write order (`packages/oms`/WP-320), and the §9.14/§9.17
   wallet-operation market resolution. WP-040 listed them against `WP-200`,
   but none of those write paths is in this package's `allowed_paths` and
   none exists yet. They should be re-assigned rather than assumed closed.

3. **Root wiring at merge time.** If the orchestrator wants
   `test/unit/ledger/**` to import the packages by name rather than by
   relative path, add `@polymarket-bot/ledger` and `@polymarket-bot/pnl` to
   the root `package.json` devDependencies (the same decision WP-150 deferred).

4. **A vocabulary drift test against the SQL migrations** (known risk 1).

5. **Reservation events are declared but not exercised.**
   `ORDER_RESERVATION` / `RESERVATION_RELEASE` are in the vocabulary and post
   like any other balanced transaction, but the reservation LIFECYCLE (no
   double reservation, no negative available balance, release on every
   terminal path — ADR-006 §9) belongs to WP-180/WP-190 and is not modeled
   here. Whoever owns it should confirm the ledger shape suits them before
   building on it.

6. **Wallet operations (split/merge/redeem) are representable but not
   built.** ADR-006 §8 makes each a balanced per-asset transaction, and the
   event types exist; the §9.14 path that constructs them does not. The PnL
   engine's `COST_BASIS_INJECTION` is the split-side hook and is tested, but
   no builder emits it yet.

7. **Rebuild benchmarking** (known risk 3), if ADR-006's "tracked property"
   is to be more than a note.
