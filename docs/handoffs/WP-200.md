## summary

`packages/ledger` and `packages/pnl` replace their `WP-010` placeholders with
the handoff §9.15 accounting ledger and the §9.16 PnL engine. Both are pure
layer-1 libraries: they own rules and typed records, never a connection.

1. **The ledger is an append-only VALUE.** `Ledger.append` returns a new
   ledger and never mutates the receiver, so a caller holding an earlier
   snapshot still sees the history it saw, and two branches from one snapshot
   cannot disturb each other. Recorded transactions are deep-frozen: writing
   to an appended entry throws. Consecutive appends share one backing buffer,
   so building an n-transaction ledger stays O(n) — ADR-006's consequence list
   makes rebuild speed a tracked property, because an invariant too slow to
   check quietly stops being checked.

2. **Every transaction balances to zero PER ASSET (the central invariant).**
   `checkPerAssetBalance` nets each asset independently with exact decimal
   arithmetic and emits one refusal per unbalanced asset, each naming the
   asset and its exact imbalance. Two assets that are individually unbalanced
   but happen to cancel numerically are TWO violations, not zero — a global
   sum is not accounting. An imbalance is REFUSED, never repaired: no code
   path adjusts an input to make it appendable.

3. **Attribution is a partition, enforced per transaction.** ADR-006 §2 says
   virtual allocation never creates or destroys value, so every append also
   checks `Δ(ACTUAL_ACCOUNT) = Δ(VIRTUAL_STRATEGY) + Δ(UNATTRIBUTED)` per
   asset. Enforcing it per transaction makes §6 invariant 7 hold inductively
   from the empty ledger rather than being audited after the fact
   (`auditAttributionPartition` exists for externally-loaded state and is
   always empty for a ledger-derived projection).

4. **Fill allocation partitions the actual quantity, never over-covers it.**
   Claims summing past the fill are refused with the exact excess (§10.7,
   §16.2). A shortfall — or no claims at all — becomes an EXPLICIT
   `UNATTRIBUTED` record with `haltRequired: true`. There is no silent
   absorption path: every share of a fill appears in exactly one returned
   record. Fees follow the ownership partition but are never prorated by
   silent division: with more than one owner every owner's fee share is
   explicit and the shares must sum exactly.

5. **Projections rebuild from zero and equal incremental state.** Both paths
   run the SAME `applyTransaction` fold step, and equality is asserted
   byte-for-byte through `serializeProjection` (a canonical sorted form) —
   over the whole projection, not a hand-picked field list. Balances are keyed
   by the ENTRY's `accountRef`, never the transaction header's (WP-040
   obligation F20), so a transfer between two accounts lands in two accounts.

6. **PnL separates realized from unrealized structurally.** The fold
   accumulates only realized facts; unrealized value is computed at snapshot
   time from open lots and caller-supplied marks, so the two cannot mix by
   construction. A missing midpoint mark is a typed refusal — "unrealized PnL
   at midpoint" is a required §9.16 measure and is never guessed. Model and
   liquidation values are `null` unless a mark supplies them for EVERY open
   lot of the denomination: a partially-marked measure is not a measure.

7. **Reward estimates are never booked as realized (§9.16, verbatim).** The
   rule is enforced in three independent places: the `REWARD_ESTIMATE` strict
   schema has no settlement-evidence field, so "an estimate that realizes" is
   unrepresentable; `REWARD_PAYOUT` REQUIRES the ledger transaction id of the
   observed payout; and the estimate handler touches only the estimate
   buckets. `serializeRealizedPnl` gives the tests a whole-state oracle for
   "the money did not move".

   > **Corrected 2026-09-02 (remediation round 1, review MEDIUM).** The middle
   > clause overstated what the second "independent place" enforced. Requiring
   > the id was a SCHEMA check only: nothing verified that the named
   > transaction existed, booked a reward, booked this amount, or credited this
   > owner, so a caller could mint a canonical UUIDv7 and realize any figure
   > (the reviewer did, for 9999 pUSD). Since this round a payout realizes only
   > against `PnlSettlementEvidence` — the booked transaction itself, checked
   > for event type, environment, settlement state, `REWARD_INCOME` amount,
   > denomination, and owner. The first and third enforcement points were, and
   > remain, exactly as described.
   >
   > **Extended 2026-09-03 (remediation round 2, review HIGH-2 and HIGH-3).**
   > Those six checks all hold and all still run. Two things they could not do
   > on their own: they are STATELESS, so one booked transaction could be
   > realized by any number of distinct payout records (the reviewer booked 10
   > from one 5 pUSD booking), and they ran on a document the caller could
   > rewrite afterwards (the reviewer edited a genuine 5 into 999 and realized

8. **Denominations never interchange.** Every monetary figure is per
   denomination asset and no code path sums across them (ADR-006 §7; the C-2
   USDC/pUSD question is unresolved and is NOT resolved here — see
   `deviations`). A record whose denomination contradicts an open lot's is
   refused.

### Persistence boundary (recorded decision)

`docs/contracts/dependency-direction.md` §2 places both packages in **layer
1**, which owns "rules, state machines, and computation; they do not own
connections." §10.5's `accounting.ledger_transactions` /
`accounting.ledger_entries` / `pnl_snapshots` tables (shipped by `WP-040` in
`packages/storage-postgres`, layer 2) are the persistence binding target, and
importing that package from here would be an upward edge (F12).

So these packages ship **pure transaction/projection logic and typed
records**, and the composition root binds them to the tables. The record
fields mirror the WP-040 columns field-for-field in camelCase
(`ledgerTransactionId`, `eventType`, `environment`, `accountRef`, `marketId`,
`orderId`, `fillId`, `walletOperationId`, `reconciliationRunId`,
`settlementState`, `reversesLedgerTransactionId`, `source`, `referenceHash`,
`detail`, `occurredAt`; entries: `scope`, `accountRef`, `instanceId`,
`runId`, `marketId`, `assetId`, `assetKind`, `amount`, `detail`), so a
composition root binds an `AppendedLedgerTransaction` with no mapping layer.
`recorded_at` and the surrogate `ledger_entry_id` are database concerns and
are deliberately absent.

## assumptions

Every open semantic decision, with its justification. None of these is a
venue fact; where a venue fact would have been required, the decision was to
refuse or to demand it from the caller.

1. **Persistence is a composition-root binding, not this package's job.**
   Justified by `docs/contracts/dependency-direction.md` §2 (layer 1 "does
   not own connections") and F12. Recorded in full under *Persistence
   boundary* above.

2. **`haltRequired` distinguishes an ARRIVAL from a RE-ATTRIBUTION.** §9.15's
   trigger is precise: "Any actual BALANCE CHANGE lacking attribution is
   allocated to UNATTRIBUTED, and the affected market is halted." A
   transaction moving value between `UNATTRIBUTED` and `VIRTUAL_STRATEGY`
   changes no actual holding — it is the REMEDIATION for an earlier arrival.
   Treating it as a fresh trigger would mean every fix re-raises the alarm it
   is fixing. So `UnattributedActivityRecord` is a discriminated union:
   `ACTUAL_ARRIVAL` carries the literal `haltRequired: true` (a record with
   `false` does not typecheck, so no code path can waive it) and
   `REATTRIBUTION` carries `false` and stays in the audit trail. This was
   found by a test, not assumed up front: the first version flagged the
   remediation as a halt trigger. **Reviewer note:** this is the one place
   where the implementation reads §9.15 more narrowly than "every
   `UNATTRIBUTED` entry halts", and the narrowing is deliberate and
   test-visible.

   > **Superseded 2026-09-02 (remediation round 1, review HIGH-1).** The
   > distinction stands; the TEST for it was wrong twice over. It asked "did
   > this transaction's per-ASSET actual movement net to zero?", so two real
   > movements that cancelled — in different accounts, or in one account and
   > asset — were both filed as re-attributions and never halted. The rule now
   > reads: an `UNATTRIBUTED` entry is an `ACTUAL_ARRIVAL` exactly when the
   > transaction carries an `ACTUAL_ACCOUNT` entry in that entry's OWN
   > `(accountRef, assetId)` bucket. Presence, not a net; per account, not per
   > asset. See the remediation-round-1 section for why that is faithful to
   > §9.15 and for the barriers on either side of it.
   >
   > **Superseded again 2026-09-03 (remediation round 2, review HIGH-1).** The
   > round-1 rule was still too LOCAL: asking only about the entry's own bucket
   > makes the answer depend on where the writer PUT the attribution, and a
   > writer that put it in the wrong bucket is the writer the rule exists to
   > catch. The rule now has a whole-transaction precondition — an
   > `UNATTRIBUTED` entry is a `REATTRIBUTION` only when the transaction's
   > ADR-006 §2 partition holds in EVERY bucket AND its own bucket has no
   > actual leg — and every breached bucket additionally produces an
   > `UnexplainedActualMovementRecord` with `haltRequired: true`, whether or
   > not the transaction contains an `UNATTRIBUTED` entry at all. See the
   > remediation-round-2 section.

3. **A reversal must negate the original exactly, leg for leg.** ADR-006 §5.2
   says a failure is "a compensating append-only reversal, never an edit". A
   partial compensation is an adjustment and has its own event types
   (`MANUAL_ADJUSTMENT`, `RECONCILIATION_CORRECTION`), so a non-exact
   "reversal" is refused rather than accepted as an approximation. A second
   reversal of the same transaction is refused (it would double-compensate).

4. **An asset id has exactly one kind, and an outcome token belongs to
   exactly one market.** ADR-006 §7 rule 1 plus §9.2 identity binding. Both
   are enforced within a transaction and against the ledger's recorded
   history.

5. **Identifiers are caller-minted and validated, never generated.** A pure
   layer-1 package reads no clock and no randomness, so it cannot mint
   UUIDv7 values. ADR-016 §2's amendment is applied at the input surface:
   REFUSE, carrying the raw value; never a case-fold. This includes a
   lowercase **v4** in a v7 position — ADR-016 §2 pins the version and
   variant nibbles as part of the canonical form ("a v4 in that position
   would break the ordering property the field is there to provide"), and the
   amendment covers an "otherwise non-canonical" spelling, not only a
   mixed-case one. A value that is not UUID-shaped at all is an ordinary
   schema failure.

6. **A fee is prorated only by an explicit, machine-checked split.** With one
   owner the whole fee is theirs. With more than one, every claim must state
   its `feeAmount` and the shares must sum exactly to the fee; the
   unattributed remainder's share is derived by exact subtraction and refused
   if negative. A silently rounded division would put fractions of a cent
   somewhere nobody chose.

7. **Average cost per token asset, with basis conserved by subtraction.**
   Removing q of Q shares with basis B removes exactly B when the lot closes,
   otherwise `B·q/Q` under `divDecimal`'s documented policy — and the
   REMAINING basis is derived by exact subtraction, so total basis is
   conserved across any split. The handoff names the measures but not the
   cost method; average cost matches `actual_position_projection`'s single
   average-cost column (§10.5) rather than implying a lot table the schema
   does not have.

8. **§9.16 measure formulas** (the handoff lists the measures without
   formulas): `realizedPnl` = realized trading PnL; `grossTradingPnl` =
   realized + unrealized at midpoint; `coreNetPnl` = gross − fees (§6
   invariant 14: excludes rewards, realized or estimated); `allInPnl` =
   coreNet + realized rewards ONLY; `worstCaseResolutionPnl` = realized − Σ
   open cost basis (every open token resolving to zero — a sound lower bound
   because a short position cannot exist here, oversell being refused);
   `capitalCommitted` = Σ open basis + caller-stated reservations
   (reservation lifecycles are WP-190's domain).

9. **Selling more than the position holds is refused, not booked as a
   short.** Venue report §10.2: selling requires outcome-token inventory. A
   negative position would corrupt average-cost accounting silently; the
   caller escalates to reconciliation instead.

10. **A `FAILED` trade is not a fresh recognition.** ADR-006 §5 books a
    failure as a compensating reversal of a previously recognized trade, so
    `applyTrade` refuses a record already marked `FAILED` (`PNL_SETTLEMENT_
    FAILED_TRADE`) rather than folding a trade that did not settle.

11. **A split's cost-basis partition is the caller's explicit statement.** It
    arrives as a `COST_BASIS_INJECTION`; the engine never guesses a 50/50.

12. **`test/integration/ledger/**` was granted but is unused** — see
    `deviations` item 2.

13. **One booked ledger transaction realizes one reward payout, per stream.**
    *(Added by remediation round 2, review HIGH-2.)* ADR-006 §6 makes the
    OBSERVED payout the thing that realizes; the observation is a transaction,
    so realizing one transaction twice books the same money twice. The
    consumed-evidence key is the ledger transaction id ALONE. A transaction
    carries one `eventType`, so one booking supports one program, and the only
    legitimate shape this coarser key refuses is a single booking crediting
    rewards in TWO denominations at once — refused deliberately, because no
    reward-posting builder exists yet, ADR-006 §7 keeps denominations apart
    anyway, and losing that argument loudly is better than double-realizing
    money quietly. Recorded in `follow_up` for whoever builds the first real
    reward posting.

14. **A projection fold must stay TOTAL, so a partition breach in external
    history becomes a recorded halt, not a refusal.** *(Added by remediation
    round 2, review HIGH-1.)* The reviewer offered two routes — refuse external
    history before the fold, or fail closed inside it. The fold is the only
    thing that makes damaged history VISIBLE; a fold that throws leaves an
    operator with no projection and therefore no diagnosis, and §9.15's remedy
    for an unattributed actual movement is to halt the affected market, not to
    stop reporting. So the validation is mandatory and lives INSIDE the fold —
    there is no separate call a caller could skip — and its outcome is an
    unwaivable `haltRequired: true` record. `Ledger.append` still REFUSES the
    same shapes outright, so the refusal route is unchanged for everything this
    package writes.

### HIGH-1 — attribution and halt classification were keyed by asset alone

**The corrected rule, and why it is faithful.** §9.15: "Any actual balance
change lacking attribution is allocated to `UNATTRIBUTED`, and the affected
market is halted." The balance that changes belongs to an ACCOUNT — which is
why `accounting.ledger_entries.account_ref` is NOT NULL for every scope and
why WP-040 obligation F20 makes every position read the ENTRY's account. A
rule keyed by `assetId` alone therefore answers a question §9.15 did not ask:
"did this asset move on net, anywhere?" instead of "did this account's holding
of this asset move?". Two real movements in different accounts cancel in the
first question and not in the second.

Two changes, at two different granularities, because there are two different
failure modes:

1. **Parity is keyed by `(accountRef, assetId)`** (`balance.ts`,
   `attributionBuckets` / `checkAttributionParity`). Every violation is
   reported, one refusal per bucket, naming the account, the asset, and both
   exact deltas. The reviewer's counterexample is refused twice: account A
   moved −5 with no attribution at all, account B moved +5 while attributing
   0 net.
2. **The halt classification asks for PRESENCE, not a net** (`projections.ts`).
   An `UNATTRIBUTED` entry is an `ACTUAL_ARRIVAL` exactly when the transaction
   carries an `ACTUAL_ACCOUNT` entry in that entry's own
   `(accountRef, assetId)` bucket. A re-attribution is recognizable without
   arithmetic — it is a transaction with no actual leg in the bucket — so no
   cancellation at any granularity can hide behind a zero. Where the two
   readings differ the rule errs toward halting: a transaction that both moves
   a real holding and re-attributes it in one bucket is ambiguous, and handoff
   §2's fail-safe says halt rather than guess.

**Why BOTH, and not just the stricter parity.** The stricter parity protects
what this package appends. It does not protect what this package FOLDS: the
WP-040 tables enforce the per-asset zero-sum in a SQL trigger and do NOT
enforce the attribution partition, so a transaction of exactly the reviewer's
shape can be written by another writer and reach `applyTransaction` through
`Ledger.rebuild` or a projection rebuild. The classifier is the barrier that
covers that path, and it is tested on the reviewer's exact transaction.

> **Superseded 2026-09-03 (remediation round 2, review HIGH-1).** The last
> sentence was the false one, and the falsehood is exactly the gap between "is
> tested on the reviewer's exact transaction" and "is general". The classifier
> keyed on the UNATTRIBUTED entry's own bucket, so it covered the shapes where
> the misplaced attribution happened to land in the arriving bucket and NOT the

**A fifth key defect, found by the same sweep and fixed here: COLLISION, not

signature entirely, and `isExactNegation` would then accept a "reversal" that

### HIGH-1 — the external-history barrier was not general

**What was actually wrong.** Round 1 argued correctly that the WP-040 tables
enforce the per-asset zero-sum and NOT the ADR-006 §2 attribution partition, so
history written by another writer can reach `applyTransaction` without ever
passing `Ledger.append`'s refusal. Its barrier for that path was a
CLASSIFICATION rule: an `UNATTRIBUTED` entry is an arrival exactly when the
transaction carries an `ACTUAL_ACCOUNT` entry in that entry's OWN
`(accountRef, assetId)` bucket. That rule asks where the writer PUT the
attribution — and a writer that put it in the wrong bucket is precisely the
writer the rule exists to catch. Five SQL-admissible shapes defeat it, all now
pinned in `packages/ledger/src/external-history-partition.test.ts`:

| shape | why it escaped |
| --- | --- |
| CROSS-ASSET (the reviewer's) — `ACTUAL A pUSD +5`, `CLEARING pUSD −5`, `UNATTRIBUTED A USDC +5`, `VIRTUAL A USDC −5` | the unattributed entry is in the USDC bucket, which has no actual leg |
| CROSS-ACCOUNT — the same with the attribution in account B | the unattributed entry is in B's bucket |
| THREE-WAY SPLIT — attribution split across B and C | two buckets, neither with an actual leg |
| CROSS-ASSET, TOKEN SIDE — real outcome tokens in, collateral "explained" | same defect, different asset kinds |
| BARE ARRIVAL — `ACTUAL A +5`, `CLEARING −5`, nothing else | there is no `UNATTRIBUTED` entry to classify AT ALL — a classification rule structurally cannot see this one |

Each nets to zero per asset, so `accounting.ledger_transactions`' trigger admits
every one; each is refused by `Ledger.append`; and each folded to
`haltRequired: false` everywhere before this round.

**The route chosen, and why.** The reviewer offered two: make partition
validation mandatory before external history reaches the fold, OR make ambiguous
attribution fail closed as a halt. This round does BOTH, in the only arrangement
that makes "mandatory" literally true: the validation lives INSIDE
`applyTransaction`, so there is no separate call a caller could skip, and its
OUTCOME is a recorded halt rather than a thrown refusal.

Refusal was rejected as the outcome for three reasons, and the choice is a
deliberate one rather than a convenience. First, the fold is what makes damaged
history VISIBLE; a fold that throws leaves an operator with no projection and
therefore no diagnosis of history that already exists in the database. Second,
§9.15's remedy for an unattributed actual movement is stated — "the affected
market is halted" — and halting is an act that needs a projection saying so.
Third, `Ledger.append` already refuses every one of these shapes, so the refusal
route is unchanged for everything this package writes; the fold is only ever
reached by history that was written elsewhere, where refusing is a denial of
service against the operator, not a safety property.

**The rule now.** `applyTransaction` recomputes `attributionBuckets` — the SAME
function `checkAttributionParity` refuses with, so the two can never drift — and
for every `(accountRef, assetId)` bucket whose `Δ(ACTUAL_ACCOUNT)` does not equal
`Δ(VIRTUAL_STRATEGY) + Δ(UNATTRIBUTED)` it records an
`UnexplainedActualMovementRecord` carrying the account, the asset, both exact
deltas, the exact unexplained amount, the affected market, and the literal
`haltRequired: true` (a record that waives it does not typecheck). And an
`UNATTRIBUTED` entry is a `REATTRIBUTION` only when the WHOLE transaction's
partition holds AND its own bucket has no actual leg — under exactly those two
conditions its bucket has zero actual movement and its attributed movement nets
to zero, so it PROVABLY moved value between attribution buckets and touched no
holding. Anything else is an `ACTUAL_ARRIVAL`.

The binding property this gives, stated as the reviewer stated it: no history
the SQL layer admits can produce an unattributed actual movement without a halt.
It holds by case analysis, not by enumeration of shapes — an unattributed actual
movement IS a bucket where actual ≠ attributed, every such bucket produces a
halt record regardless of what entries the transaction does or does not contain,
and `unattributedExposure` reports it without being asked.

**Surfacing.** `LedgerProjection` gains `unexplainedMovements` (append-only, in
ledger order, never erased), `UnattributedExposureLine` gains
`unexplainedActualMovement`, and breached buckets appear in the exposure summary
even when they have no unattributed entry at all. `net` deliberately still means
"the sum of recorded `UNATTRIBUTED` entries, equal to the bucket's balance
line": an operator reconciling against the database needs that sentence to stay
literally true, so the unexplained figure is a separate column rather than being
added into it. `LEDGER_PROJECTION_SERIALIZATION_DOMAIN` moves to `v3` because
the oracle now covers the new section — a section left out of the byte oracle is
a section a mutated history can change without the comparison noticing.

**Deliberate over-classification, disclosed.** A transaction whose partition is
broken in one bucket makes EVERY `UNATTRIBUTED` entry in it an arrival, even one
in a bucket that looks like an honest remediation. That is the fail-closed half
of the reviewer's remediation and it is tested as such: a transaction whose
attribution is not a partition is not a transaction whose attribution can be
trusted at entry granularity, and §2's fail-safe says halt rather than guess.
A transaction whose partition HOLDS is unaffected, which is every transaction
this package appends.

**Cost to the honest path: none.** For any projection folded from a `Ledger`,
`unexplainedMovements` is always empty, because append enforces the partition
per transaction — the same relationship `auditAttributionPartition` already had.
That is pinned by a test.

### HIGH-2 — one booking could be realized any number of times

The round-1 evidence check is STATELESS: it answers "does this booking support
this claim?", and for a genuine booking it answers yes every time it is asked.
`state.refs` deduplicated the PnL record's own `ref`, which says nothing about
the money, so two records with different refs naming one booked 5 pUSD
transaction both folded and `realizedRewards` became 10.

`PnlState` now carries `consumedRewardEvidence`: `ledgerTransactionId` → the
record `ref` that realized it. `applyRewardPayout` refuses a repeat with
`PNL_REWARD_EVIDENCE_ALREADY_REALIZED`, naming the earlier record.

The identity is **persisted and derived**, not remembered. It lives in the
folded state and is built from the record stream, so a rebuild reconstructs it
exactly — a consumed set held in a caller's memory would vanish on rebuild and
let the second claim straight through, which is the failure the reviewer named.
It is carried by `serializePnlState` AND by `serializeRealizedPnl` (it is part
of the money, not bookkeeping), so `PNL_STATE_SERIALIZATION_DOMAIN` moves to
`v3`. Rebuild-equals-incremental is re-asserted with the new state, and
acceptance 3 still holds: folding an estimate leaves the realized bytes
identical, consumed evidence included.

The consumption key is the ledger transaction id alone — see `assumptions` item
13 for why the coarser key is the deliberate choice and what it refuses.

### HIGH-3 — validated evidence could be rewritten afterwards

`from()` froze the transaction OBJECT and left its `entries` array and every
entry writable, and `find()` handed the internal transaction out. So evidence
built from a genuine 5 pUSD booking could be edited — by ordinary property
assignment — into a 999 pUSD booking, and the 999 payout realized. Validating a
value and then handing out a mutable reference to it validates nothing: the
check ran on a document that no longer exists.

Three changes, each closing a different half of it:

1. `sealedTransaction` copies every booking leg by leg and freezes the entry
   objects, the entries array, and the transaction. Applied on the way IN, so
   the set does not share an object with the caller that supplied it either —
   tested, because a caller keeping a reference to what it passed to `from()`
   is the same hole from the other side.
2. `find()` returns a fresh sealed COPY. Nothing outside the class ever holds
   the value the verification reads.
3. `verifyRewardPayoutEvidence` reads a module-private `WeakMap` rather than
   calling `evidence.find(...)`. A method call dispatches through
   `PnlSettlementEvidence.prototype`, which is a mutable object in JavaScript;
   the `WeakMap` cannot be reached from outside the module. The `instanceof`
   check from round 1 is unchanged, and a prototype-forged object now fails
   closed with `PNL_REWARD_EVIDENCE_UNKNOWN` (pinned).

### HIGH-4 — returned values were mutable through the map VALUES

Round 1's guard sealed each `Map`/`Set` and stopped there, so the objects INSIDE
stayed writable. No capability bypass was needed for any of it:

- a returned balance line's `balance` went from `5` to `999`; a later `+2` then
  read `1001` incrementally against `7` on rebuild — two different answers about
  one history, in one process;
- a virtual position line the same way;
- an `OpenLot`'s `costBasis` went from `4` to `999`, and the next snapshot
  reported `capitalCommitted = 999` and `unrealizedPnlMidpoint = −994`;
- an `AppliedTradeEffect`'s `shares` went from `10` to `4`, so a reversal of the
  whole buy left 6 shares behind with zero basis.

`frozenMap`/`frozenSet` in BOTH packages now deep-freeze every key and value
they hold, recursively, following arrays and own ENUMERABLE DATA properties
only — an accessor is never invoked, and the non-enumerable mutator guards are
not walked. A module-level `WeakSet` memoises what has been walked: it
terminates a cyclic walk and makes the walk O(1) amortized per object, which
matters because the fold copies its maps on every transaction. A member of that
set is frozen, so its property values cannot have changed since it was walked;
skipping it is sound, not merely cheap.

Also frozen, for the same reason and found by the same sweep: the arrays
`balancesOfScope`, `actualPositions`, `virtualPositions`, and
`auditAttributionPartition` return, and the violation objects inside the last of
them.

**Measured, not asserted (the packet asked).** Deep-freezing costs about 19% of
the projection fold: `projectLedger` over 2000 four-entry transactions ran at a
median of **27.9 ms** with the shallow guard and **33.2 ms** with the deep one
(five runs each after a warm-up, same process, same fixtures) — roughly 2.6 µs
per transaction. That is a real cost and it is disclosed rather than waved away;
it is also inside the same O(n) fold that already copies the whole balance map
per transaction, which known risk 3 already names as the thing to benchmark
first at production sizes. No asymptotic behaviour changed.

**The disclosure stays accurate.** `Map.prototype.set.call(guarded, k, v)` still
reaches the internal slot in both packages, and the reviewer accepted that as a
documented limitation. Both modules now say explicitly that the limitation is
about the CONTAINER only: the values inside are ordinary frozen objects and
ordinary property assignment on them throws.

### known_risks added by this round

1. **The consumption key is the ledger transaction id alone.** A single booking
   that credited rewards in two denominations at once would have its second
   denomination refused. Deliberate (`assumptions` item 13), and cheap to
   revisit because no builder emits reward postings yet — but it is a rule, and
   the first real reward posting should be checked against it.
2. **Fail-closed classification over-halts a mixed transaction.** An honest
   remediation inside a transaction whose partition is broken elsewhere is
   reported as an arrival. That is the intended direction of error, and it means
   an operator repairing damaged external history will see halts on the repair
   transactions until the partition holds.
3. **Deep freezing costs ~19% of the projection fold** (measured above). It is
   inside the O(n) path known risk 3 already flags; if that path is ever
   optimised, the freeze cost should be measured again rather than assumed
   unchanged.
4. **`unexplainedMovements` is a new section of the byte oracle.** Anything that
   compared `serializeProjection` bytes across process boundaries — nothing does
   yet (known risk 4) — sees different bytes at `v3`.

### follow_up added by this round

1. When the reward-posting builder lands (round 1's follow-up 2), decide
   whether a single booking may credit two denominations, and widen the
   consumption key to `(ledgerTransactionId, denominationAsset)` if so. Known
   risk 1.
2. A composition-root convention for reading `unexplainedMovements` alongside
   `unattributedActivity` when it loads history from the WP-040 tables. The
   projection states the obligation; §9.9 says halting is the composition
   root's act, and no composition root exists yet.
3. Re-measure the deep-freeze cost if rebuild benchmarking (round 1 follow-up /
   known risk 3) is ever done properly, so the two numbers come from one
   harness.
