## summary

Two pure layer-1 packages replace the WP-010 placeholder scaffolds.

**`packages/settlement`** owns the §9.3 artifact and the payoff arithmetic:

1. **`SettlementSpec` as a strict Zod contract** carrying every §9.3 field, with
   two DB-cited additions (`specVersion`, `payoffModel`). `verification` is a
   discriminated union, so a spec that claims `VERIFIED` without a reviewer — or
   names a reviewer while claiming to be unverified — is unrepresentable, exactly
   as WP-040's `settlement_specs_verification_complete` constraint requires.
   Required rule text refuses placeholders (`TBD`, `n/a`, `unspecified`, `-`, …)
   per ADR-009 §5.4: "'Halt and escalate' is a legitimate policy; 'unspecified'
   is not."
2. **A total 5 × 4 model-compatibility matrix.** Every observation type × payoff
   model cell has an explicit verdict, and the tests walk all twenty rather than
   sampling. `TWAP × TerminalSpotBinaryModel` carries its own refusal code
   (`SETTLEMENT_TWAP_TERMINAL_SPOT_FORBIDDEN`) citing §9.3. `VWAP`,
   `EVENT_RESULT` and `MANUAL_ORACLE` have an empty row (ADR-009 §2).
3. **Two independent gates for acceptance 1.** The spec schema refuses the
   forbidden combination at construction, AND every observation is tagged with
   the model that consumes it, so a terminal-spot reading cannot reach a
   TWAP-settled spec even if the spec were somehow correct.
4. **Exact payouts**, including the 50/50 case, as canonical decimal strings with
   exact multiplication. Two properties are asserted over generated share counts:
   a 50/50 position is exactly half the shares (proved by doubling it back), and
   a YES/NO pair sums to exactly the share count in every terminal outcome.
5. **The activation gate**: seven statuses, exactly one of which permits
   model-dependent activation. A spec that CLAIMS a review is re-checked against
   the conditions that must have held when it was signed, so a feed that stops
   publishing a window invalidates the specs that depend on it (ADR-009 §6).

**`packages/universe`** owns identity, configuration, versioning and readiness:

6. **Immutable versioned parameters.** Appending returns a new history whose
   earlier entries are the SAME frozen objects; every version, snapshot and
   change list is frozen so an in-place edit throws; a no-op change and an
   out-of-order observation are refused; `parametersAsOf` makes §6 invariant 9
   ("historical runs use historical parameters") operational.
7. **Series binding as configuration.** A suggestion and an approval are
   different TYPES, and no function promotes one to the other. Binding a market
   requires an approver AND an already-approved series. *(Corrected in
   remediation round 1 — the original claim that "the unreviewed decision
   cannot be pushed one level down" was contradicted by review finding H3: the
   registry's shallow freeze left the nested approval object mutable, and an
   in-place forgery of `binding.approved` made `bindMarketToSeries` succeed
   without `approveSeries` ever being called. Stored series and projections are
   now deeply frozen and the registry's exposed collections refuse
   `set`/`delete`/`clear` at runtime, so that forgery now throws — see the
   remediation record below. A determined attacker with prototype-level access
   is out of scope; see remediation residual risks.)* The emitted
   `MarketDiscovered` payload names a series only when the binding is approved.
8. **Lifecycle projection** over the frozen §7.4 events, with explicit handling
   of clarification-after-open, the rule that only `MarketResolved` may set a
   terminal outcome, ordering by `gatewayEpoch + ingestSeq`, and `CLOSED` derived
   (never stored) because no domain event asserts it.
9. **Readiness with two answers**: `observationReady` and
   `modelDependentActivationAllowed`. *(Corrected in remediation round 1 — the
   original claim that activation was "false unless every condition holds" was
   contradicted by review finding H2: identity fields on the settlement verdict
   were optional and each correlation was silently skipped when a field was
   absent, so a verdict naming a DIFFERENT series, or naming no rules version
   at all, still activated. After remediation the permitted arm of the port is
   a discriminated shape requiring series id, settlement-spec id, rules-version
   id, payoff model, and an empty refusal list; readiness re-checks
   completeness at runtime, requires the approved `SeriesDefinition`, and
   correlates the verdict's series against the market's approved binding and
   the supplied definition, the verdict's spec against the series'
   `activeSettlementSpecId`, and the verdict's rules version against the
   market's trading rules version — refusing when any field is missing or
   mismatched, and failing closed when the market's own rules version is
   unknown.)* `asOf` is validated unconditionally at the readiness boundary
   (review finding M2), and `observationReady` follows the EVENT-DRIVEN
   lifecycle state rather than the schedule (review finding M3).

The two packages exchange nothing but a structural verdict shape; neither
imports the other.

## venue facts verified (U-6)

The packet made this the mandatory first step, and ADR-009 §5 / venue report §12
made it a blocker: "`WP-110` must verify against the resolution doc before
settlement-spec implementation."

**Method.** Unauthenticated `curl` reads of the current official documentation
on **2026-08-28**. No credential, no order, no authenticated endpoint. The page
that WP-000 could not capture returned HTTP 200 in both its rendered and its
Markdown (`.md`) form; the Markdown form is quoted below because it is the
source text.

### U-6 (a) — the 50/50 resolution outcome: **CONFIRMED**

Source: `https://docs.polymarket.com/concepts/resolution` (accessed 2026-08-28).
Verbatim, from the "UMA Vote" outcome table:

> | **Unknown/50-50** | Neither outcome applicable (rare) | Market resolves
> 50/50 — each token redeems for \$0.50; disputer gets bond back + half of
> proposer's bond |

and from "After Resolution":

> * **Trading stops** — You can no longer buy or sell tokens for this market
> * **Winning tokens** become redeemable for \$1.00 each
> * **Losing tokens** become worthless (\$0.00)

Supporting, `https://docs.polymarket.com/concepts/positions-tokens` (accessed
2026-08-28):

> Outcome tokens are always fully backed. Every Yes/No pair in existence is
> backed by exactly `$1` of pUSD collateral locked in the CTF contract.

**Consequence.** The 50/50 payout is no longer an inference from the collateral
statement (ADR-009 §5.3's conditional "IF the venue's 50/50 outcome pays both
sides from that same backing"): the venue states \$0.50 per token directly.
`SPLIT_50_50_PAYOUT_PER_SHARE = "0.5"` is venue-verified as of 2026-08-28, and
the UNVERIFIED markers ADR-009 §5.2 required for it may be lifted by the
orchestrator. This is a dated snapshot; handoff §1.2 requires re-verification at
each phase gate.

### U-6 (b) — post-open on-chain clarification: **CONFIRMED**

Same source, section "Clarifications", verbatim:

> In rare cases, unforeseen circumstances require clarification of the rules
> after trading begins. Polymarket may issue an **"Additional context"** update
> that proposers and voters should consider during resolution.
>
> Clarifications:
>
> * Cannot change the fundamental intent of the question
> * Are published onchain via the bulletin board contract
> * Should be considered by UMA voters when resolving disputes

**Consequence.** `MarketClarificationObserved`, the `PENDING_CLARIFICATION`
state, and the required `clarification_policy` spec field are all
venue-justified. The projection records `afterOpen` per clarification and halts
model-dependent activation while one is open.

### What the same pass did NOT confirm — three items for the register

1. **`CANCELLED` has no documented venue mechanic.** The resolution page
   documents exactly three redemption outcomes (win \$1.00, lose \$0.00, 50/50
   \$0.50 each) and NO cancellation, void, or refund path; "Unknown/50-50" is
   what the venue does when "neither outcome [is] applicable". `CANCELLED`
   remains in the §9.3 vocabulary and in the frozen `MarketResolved` terminal
   subset, but `payoutPerShare("CANCELLED")` **refuses** with
   `SETTLEMENT_CANCELLED_PAYOUT_UNVERIFIED` rather than inventing a refund rule.
   *Proposed register row: a new UNVERIFIED item, "cancellation/void resolution
   mechanics and payout".*
2. **No documented dispute EVENT or status vocabulary.** ADR-009 §4 left an open
   item: add a `MarketDisputed` event "if `WP-110` (or `WP-070`) finds that the
   venue publishes an explicit dispute transition". The resolution page documents
   a dispute PROCESS (\$750-bond proposal, 2-hour challenge period, 24–48 h
   debate, ~48 h UMA DVM vote) but no published transition this repository could
   consume. `https://docs.polymarket.com/api-reference/markets/get-market-by-id`
   (accessed 2026-08-28) exposes `umaResolutionStatus` as a **nullable string**
   with no documented value vocabulary, and `umaResolutionStatuses` on the event
   object likewise. That is not an "explicit dispute transition", so **no
   `MarketDisputed` event is proposed**; the register row "No dedicated dispute
   event" stands, and `DISPUTED` enters the projection as an operator
   observation through `recordObservedOutcomeState`, which refuses every terminal
   state.
   *Proposed register annotation: `umaResolutionStatus` exists but its value set
   is undocumented — do not parse it until verified.*
3. **The UMA resolution timeline is now documented** (2 h challenge, 24–48 h
   debate, ~48 h vote, "Disputed resolution: 4-6 days total") and the
   `UmaCtfAdapter` addresses are published. Neither is load-bearing for this
   package; recorded so a later package does not re-fetch it blind.

I did not edit `docs/contracts/protected-contracts.md` or
`docs/venue/verified-2026-08-24.md`: both are outside this package's allowed
paths, and the register is the orchestrator's to update.

## assumptions

1. **`payoffModel` is optional on a spec.** ADR-009 §2 says an observation type
   with no implementing model still yields a spec ("a spec that cannot be
   activated"), and such a spec has no model to name. WP-040's column is
   `NOT NULL`; see `deviations` 1 and `follow_up` 1.
2. **`specVersion` belongs on the spec.** §9.3 does not list it; §6 invariant 9
   and `catalog.settlement_specs.spec_version` do. Carried, cited.
3. **A verified spec must name a `rulesVersionId`.** §9.3 lists the field without
   saying when it is required; a review that does not name the rules it reviewed
   cannot be checked against what a market is trading under (§6 invariant 9), so
   it is optional on a draft and a review blocker when absent.
4. **The published-window list is injected, not hardcoded.** ADR-009 §6 scopes
   its rule to the RTDS TWAP feed; this package applies it to any windowed spec
   and takes the permitted windows from the caller, failing closed when the
   caller states none. `RTDS_TWAP_WINDOW_SECONDS_VERIFIED_2026_08_24` is exported
   as a dated snapshot of venue report §10.3, not as a constant truth.
5. **The compatibility matrix's non-§9.3 cells.** §9.3 states one forbidden cell
   by name. The other refusals are stated with rationale in
   `models/compatibility.ts`: a TWAP model on a terminal-spot spec is the mirror
   of the stated rule; `ReferenceOpenUpDownModel` forbids `strikeSource` because
   the reference open IS the strike and naming both leaves two candidates;
   `ThresholdByDateModel` forbids `windowSeconds` because its period is bounded
   by the deadline, not by an averaging length. `ReferenceOpenUpDownModel` is
   permitted on `TWAP` because an up/down series may legitimately settle on a
   TWAP observation against the open.
6. **`ThresholdByDateModel` semantics.** A met threshold settles `YES_WIN`
   immediately (it cannot be un-met); an unmet one is `PENDING` until the
   deadline passes, then `NO_WIN`. The observation must carry the extreme that
   answers the comparison (`MAX` for `GT`/`GTE`, `MIN` for `LT`/`LTE`) and is
   refused otherwise.
7. **The `MarketDiscovered.seriesId` field is the series KEY.** The frozen
   contract types it as a `CodeString` and documents "such as `btc-15m-updown`",
   while the catalog keys series by UUID. The registry emits the key, and only
   for an approved binding.
8. **An open instant is a fact; a close instant is a schedule.** A conflicting
   `MarketOpened` is refused; a `MarketClosing` reschedule is applied, because
   §9.2 versions `close_time`.
9. **Any clarification halts an unresolved market**, whether or not it arrived
   after the open; `afterOpen` (judged by the observation instant, not delivery
   order) is recorded so the two cases stay distinguishable.

## deviations

1. **`payoffModel` optionality diverges from migration `0002`.** See
   `assumptions` 1 and `follow_up` 1. The migration is outside this packet's
   allowed paths.
2. **This package is stricter than the `catalog.settlement_specs` columns.**
   `timestamp_boundary`, `rounding_rule`, `fallback_source`, `dispute_policy`
   and `clarification_policy` are nullable in SQL and required here (ADR-009
   §5.4). A row with a null policy will not parse — the intended direction, but
   a loader must know it.
3. **`test/unit/universe/**` and `test/unit/settlement/**` were not created.**
   The workplan lists them; the WP-020 precedent (binding, and restated in the
   packet) is that `test/unit/**` cannot resolve workspace packages. All tests
   are colocated under `packages/*/src/**`.
4. **`db/seeds/settlement-specs/**` contains a `series/` subtree** as well as
   `specs/`. A settlement spec references a series, and the series shape is
   validated by a different package; splitting them lets each package validate
   what it owns without an edge to the other.
5. **Two eleven-line time helpers are duplicated** across the packages. Sharing
   them would need either a same-layer edge `dependency-direction.md` §2.1 does
   not list or a new shared package no work package owns. Each copy has its own
   tests. Disclosed rather than resolved.
6. **`Date.parse` is used** (in `time.ts` in both packages) to parse
   caller-supplied ISO strings. `Date.now()` and `new Date()` appear nowhere;
   the precedent is `packages/binance-adapter/src/time.ts`. No clock is read.
7. **Two test files read the filesystem** (`seeds.test.ts` in each package),
   which is the only I/O anywhere in either package and is test-only. Validating
   the seeds — in particular proving that none claims a human review — is not
   possible otherwise.

## known_risks

1. **The venue snapshot is dated.** Everything in `venue facts verified` is true
   as of 2026-08-28 and must be re-verified at the next phase gate (§1.2). In
   particular the 50/50 payout is now a hard-coded `"0.5"` constant with a cited
   comment; if the venue changed it, the constant is wrong and the tests would
   still pass.
2. **The `CANCELLED` refusal will surface as an operational error** the first
   time a market resolves `CANCELLED`, because no payout can be computed. That is
   deliberate — inventing a refund rule is worse — but the consumer of
   `payoutPerShare` must handle the refusal rather than assume a value.
3. **The settlement port is structural, not compiler-verified across packages.**
   Nothing in this repository imports both unions today, so a divergence is
   caught only when a composition root wires them (where it IS a type error) or
   by `settlement-binding.test.ts`. *(Strengthened in remediation round 1: the
   pin now reads the settlement package's `activation.ts` SOURCE TEXT — a
   test-only file read, no import or `package.json` edge — and compares both
   the status list and the permitted status, so a Settlement-only vocabulary
   change fails the Universe pin test. Verified by mutation: adding a status
   token to the settlement source alone failed the pin.)* Until `WP-160`/
   `WP-170` wire them, assignability itself remains review-enforced.
4. **`ReferenceOpenUpDownModel` on a `TWAP` observation is permitted on
   reasoning, not on venue evidence.** Whether any Polymarket up/down series
   settles on a TWAP against the open is unverified; a spec claiming it cannot be
   verified without a reviewer establishing it from the market rules.
5. **The series-suggestion heuristic is deliberately naive** (substring matching
   on slug and title). It can suggest nothing useful, or several candidates. It
   is safe because it can only ever produce a suggestion, but an operator who
   treats a high "score" as evidence would be over-reading it: the score is a
   count of matched signals, not a probability.
6. **`CLOSED` is derived from a schedule, and the schedule can be wrong in BOTH
   directions** *(disclosure corrected in remediation round 1, review finding
   M3 — the original text disclosed only the early-close case)*:
   - **Venue closes EARLY**: if the venue halts trading before the announced
     `closesAt` and no event says so, the projection calls the market `CLOSING`
     past its real close. The market-data adapters see the trading halt first.
   - **Venue trades PAST the schedule**: if the venue keeps trading after the
     announced `closesAt`, the derived `CLOSED` overstates what is known. After
     remediation this no longer misrepresents an observed fact: readiness
     refuses NEW activation under `UNIVERSE_SCHEDULED_CLOSE_ELAPSED` (a
     statement about the schedule, not the venue) while `observationReady`
     stays true for an opened, unresolved market — a market that may be holding
     an open position keeps being observed until `MarketResolved` or
     reconciliation establishes closure.
   A `MarketClosed`-equivalent signal would remove the inference entirely (see
   `follow_up` 3).
7. **`TradingParametersChanged` is folded as a consistency check only.** If a
   different component versions parameters independently, the projection refuses
   the event rather than reconciling. That is loud by design and will need a
   reconciliation path when `WP-120` wires a real producer.

## follow_up

1. **`catalog.settlement_specs.payoff_model` is `NOT NULL`.** A spec whose
   observation type has no implementing model (ADR-009 §2) cannot be persisted
   by migration `0002`. Owner: the `db/migrations/**` owner (`WP-040`'s
   successor), under a new migration — this package must not edit migrations.
2. **Register updates for the orchestrator** (outside this packet's paths):
   close U-6 in `docs/contracts/protected-contracts.md` §8 and annotate venue
   report §11/§12 with the 2026-08-28 confirmation; add the two new UNVERIFIED
   items proposed above (cancellation/void mechanics; the undocumented
   `umaResolutionStatus` vocabulary); and lift the ADR-009 §5.2 "UNVERIFIED
   marker" obligation for the 50/50 payout, which is now verified. ADR-009 §4's
   `MarketDisputed` condition remains unmet — no contract change is proposed.
3. **No domain event asserts "the trading window has ended".** `CLOSED` is
   derived here. If `WP-070`/`WP-120` find a venue signal for it, the correct
   response is a new event type under a new schema version (ADR-002 §3), not a
   looser projection.
4. **Wire the settlement verdict into the universe readiness check** at the
   composition root (`WP-160`/`WP-170`/`WP-120`), which is where the two unions
   meet and where a divergence becomes a type error.
