## A1. The outcome-to-token pairing

Sources: S-D23 (market details), S-D82 (markets and events), S-D65 (CLOB
market info), S-O02 (CLOB OpenAPI), S-D70 (Gamma OpenAPI, list events), SDK
`gamma/market.ts` at `0.12.0` (S-R-gamma_market) and `0.11.0` (S-R11).

- **F-01 (DOCUMENTED, Gamma).** S-D23, "Market Outcomes", API tab:
  - "Each market has YES and NO outcomes. Each outcome includes a label,
    current price, and CLOB token ID." (line 96)
  - "Gamma returns the outcome labels, prices, and CLOB token IDs as
    JSON-encoded arrays" (lines 148-149)
  - "Parse each array and correlate its values by index:" (line 159)
  - "Index `0` describes the YES outcome and index `1` describes the NO
    outcome." (line 173)

  S-D82: "Each market represents a single binary question with Yes/No
  outcomes." (line 19), and token IDs are "one for Yes, one for No" (line 33).
  The Gamma OpenAPI types `outcomes` and `clobTokenIds` as nullable `string`
  with no description (S-D70 lines 569-571, 706-708).

  These sentences were already on the page on 2026-09-30 (VENUE-3's body,
  lines 159 and 173). The repository's standing reading, that "no pairing
  rule" is documented (`packages/polymarket-public/src/ports.ts:150`), concerns
  the WebSocket `new_market` arrays `assets_ids` and `outcomes` (§A2, F-13). It
  does not hold for Gamma.

- **F-02 (SDK).** `normalizeOutcomes` takes `outcomes[0]`, `clobTokenIds[0]`
  and `outcomePrices[0]` as `yes`, and index 1 as `no`. It throws unless there
  are exactly two outcomes (S-R-gamma_market lines 548-577). The file is
  byte-identical at `0.11.0` (`d527956f…`) and `0.12.0` (`71f9723f…`): both
  digests are `b7499fe5…`.

- **F-03 (DOCUMENTED, CLOB, explicit labels).**
  - `GET /clob-markets/{condition_id}` returns `t`, "Tokens for this market"
    (S-D65 lines 97-101). Each item is a `ClobToken`, "A token in a CLOB market
    with its ID and outcome label.", with `t` "The token ID" and `o` "Outcome
    label for the token (e.g. "Yes", "No")" (lines 157-169).
  - The CLOB OpenAPI's `Market` and `SimplifiedMarket` schemas carry `tokens`
    items `{token_id, outcome, price, winner}` (S-O02 lines 5208-5219, 5227,
    5423). The documented paths that return them are `/sampling-markets`,
    `/simplified-markets` and `/sampling-simplified-markets` (lines
    2067-2138).
  - **`GET /markets/{condition_id}` is not a path in the CLOB OpenAPI.** Its
    shape below is OBSERVED only.

- **F-04 (OBSERVED).** Four windows were read: two resolved and two open
  (S-K01 … S-K04).
  - On all four, `clob-markets` `t[]` equals Gamma's
    `zip(outcomes, clobTokenIds)`: `[{"t": clobTokenIds[0], "o": "Up"},
    {"t": clobTokenIds[1], "o": "Down"}]`.
  - The undocumented CLOB `/markets/{condition_id}` returned the same order,
    with `outcome` set to `Up` or `Down` and `winner: true` on the resolved Up
    token.

- **F-05 (CONFLICT C-17).** `GET /markets-by-token/{token_id}` documents
  `primary_token_id` as "The primary (Yes) token ID" and `secondary_token_id`
  as "The secondary (No) token ID" (S-O02 lines 5339-5357).
  - For the two resolved windows, `primary_token_id` was the Up token
    (`clobTokenIds[0]`).
  - For the two open windows it was the **Down** token (`clobTokenIds[1]`).
  - In all four, `primary_token_id` was simply the numerically smaller id.

  So for this series the field does not mark the YES outcome.

**Answer to Q3.1.** `outcomes[i]` ↔ `clobTokenIds[i]` **is documented for
Gamma** (F-01), and the SDK does the same (F-02). The documented explicit
pairing is `GET /clob-markets/{condition_id}` `t[].{t,o}` (F-03). The undocumented
CLOB `/markets/{condition_id}` also returns `tokens: [{token_id, outcome}]`,
but as an observation only. A window's YES token is the one paired with index
0 (`Up`) and its NO token the one paired with index 1 (`Down`).

Consequence for `ROLLOVER-1` (`yesTokenId`/`noTokenId`): take the pair from
Gamma by index, and cross-check it against `clob-markets` `t[].o`. Refuse the
window if the two disagree. Never pair from `markets-by-token` (C-17), and
never from the `new_market` arrays (F-13).

1. `GET /events/keyset?series_id=<id>&closed=false&order=…&limit≤100`,

2. `GET /events` bounded by `end_date_min`/`end_date_max`, filtered client-side
   on the documented Event fields `seriesSlug` or `series[].slug`. This is the
   HOST-BENCH recorder's method.

The series id `10192` and the slug `btc-up-or-down-15m` are observed values,
fit to be reviewed configuration constants, not documented ones. `series_slug`
is undocumented and should not be relied on. `new_market` can be at most a hint
to poll: its delivery scope is undocumented and it carries no schedule.

## A3. The window-schedule fields

Sources: S-D70 and S-D72 (OpenAPI types), S-D23 (market timing), S-D33
(resolution), the 33 windows in S-G02, S-G03, S-G04 and S-G07, and, for the
round's first review, the 100 windows in S-G09 and the four in S-G08.

- **F-14 (DOCUMENTED, types only).**
  - In the Gamma OpenAPI, `Market.eventStartTime` (lines 898-901),
    `Market.startDate` (538-541), `Market.endDate` (522-525) and
    `Event.startTime` (386-389) are each a nullable `string` of format
    `date-time`, with **no description**.
  - S-D23, "Market Timing": "Markets include start and end dates, while sports
    markets may also include the scheduled start time of the game." Its field
    table defines `startDateIso` as "Market start date in ISO 8601 format." and
    `endDateIso` as "Market end date in ISO 8601 format." (lines 874-875).
  - S-D33, "Resolution Rules": "**End date** — When the market is eligible for
    resolution" (line 24).
  - **No document says which field is the window open, or that `endDate` is
    the window close.** `eventStartTime` is described nowhere (U-29).

- **F-15 (OBSERVED: 33 of 33 windows in the first read, 100 of 100 in the
  second).**
  - The epoch at the end of the slug (`btc-updown-15m-<epoch>`) equals
    `eventStartTime` in Unix seconds.
  - `endDate − eventStartTime` is exactly 900 s.
  - The question title "Bitcoin Up or Down - <Month D>, <h:mmAM/PM>-<h:mmAM/PM>
    ET", read in America/New_York time, equals `[eventStartTime, endDate]`.
    Every window observed was in EDT (UTC−4).
  - `Event.startTime` equals `Market.eventStartTime`.
  - `startDate` is 23.83 to 23.87 h before `eventStartTime`.
    `acceptingOrdersTimestamp` (and `clob-markets` `aot`) is 23.84 to 23.88 h
    before the open.
  - `startDate` is **not** Gamma's own `createdAt`: on all 33 windows,
    `createdAt` precedes `startDate` by 51.5 to 108.1 s. What `startDate`
    marks is undocumented (U-29).

  So trading opens about a day before the window it is about.

  A second read at 23:57Z (S-G09: the 100 most recently resolved windows,
  opening 2026-10-03T22:45Z to 2026-10-04T23:30Z) repeats all of this on 100
  of 100. The title range equals `[eventStartTime, endDate]`, the slug epoch
  equals `eventStartTime`, the window is 900 s, and `Event.startTime` equals
  `eventStartTime`. `startDate` is 23.825 to 23.864 h before the open, and
  `createdAt` precedes it by 66.9 to 110.4 s. With S-G08 (four windows, all
  inside S-G09's range), the two reads cover **115 distinct windows**. Every
  one was in EDT (UTC−4).

- **F-16 (rules text).** The rules define the window through the title: "of the
  time range specified in the title" (F-22). The ET title range is the rules'
  own statement of the window. `eventStartTime` and `endDate` are its
  machine-readable equivalents **by observation only**.

- **F-17 (OBSERVED).**
  - The 19 resolved TWAP-rule windows of the first read resolved 53 to 87 s
    after `endDate` (`closedTime`, `umaEndDate`).
  - The 100 resolved windows of the second read (S-G09, opening
    2026-10-03T22:45Z to 2026-10-04T23:30Z) resolved **53 to 152 s** after
    `endDate`, median 55 s: 72 within 60 s, 24 in 61-90 s, 2 in 91-120 s, and
    2 at 152 s (the windows opening 2026-10-04T17:15Z and 18:45Z).
    `closedTime` equals `umaEndDate` on all 100. S-G08 re-read four of them
    (18:00-18:45Z): 53, 88, 86 and 152 s.
  - So "one minute" fits the median, not the range. The latency is a
    dated observation, not a documented bound.
  - The two spot-rule windows of August 2026 resolved 18 to 21 s after
    `endDate`.
  - All 21 resolved windows of the first read, and all 100 of the second,
    carry `automaticallyResolved: true` and `umaResolutionStatus:
    "resolved"`.

**Answer to Q3.3.** The rules text names the title's ET range as the window,
so the title is the authority. By observation only, the window **open** is
`eventStartTime` (equal to `Event.startTime`, the slug's epoch and the title's
start), and the window **close** is `endDate` (open + 900 s, the title's end).
`startDate` is **not** the open. The documentation gives these fields' types
but not their meanings. To settle the semantics, Polymarket would have to
document them, or answer the clarification question in the settlement review
(§3.5).

Daylight saving: from 2026-11-01T06:00Z, ET is UTC−5. Converting the title by
America/New_York rules is an inference from EDT windows only; the first EST
window would confirm it. The title alone cannot identify every window on the
day the clocks go back. Computed with the IANA rules for America/New_York (not
observed: those markets do not exist yet):

- the 1:00-2:00 AM ET hour repeats;
- the windows opening at 05:00Z and 06:00Z would both read "1:00AM-1:15AM
  ET", and likewise 05:15Z and 06:15Z, and 05:30Z and 06:30Z;
- the window opening at 05:45Z runs from 1:45 AM EDT to 1:00 AM EST.

How Polymarket titles those windows is U-34. Admission should not take a
window's interval from its title alone on that day; the settlement seed halts
entries for any window whose title does not convert to exactly one 900 s
interval.

## A4. The trading delay and the tick size

Sources: S-D23, S-D65, S-D41, S-D85 (changelog), S-D14, S-D12, S-K01 … S-K05.

- **F-18 (DOCUMENTED, then OBSERVED absent).** S-D23 defines `secondsDelay` as
  "Delay, in seconds, before a newly placed marketable order can match."
  (line 877). The OpenAPI types it as a nullable integer (S-D70 lines
  703-705).
  - **OBSERVED:** the `secondsDelay` key is **absent** from all 33 Gamma
    markets of this series.
  - The undocumented CLOB `/markets/{condition_id}` returned `seconds_delay: 0`
    on all four windows read.

- **F-19 (DOCUMENTED, then OBSERVED true).** S-D65 defines `itode`: "Whether
  taker order delay is enabled for this market. When true, marketable orders
  are held for the 250 ms taker-delay window before synchronous processing.
  This field is omitted when false." (lines 125-130).

  S-D41: "**Taker delay:** used on selected crypto and finance up/down markets.
  The order is held for 250 ms, then validation runs again and the order is
  matched or placed on the book. … call the public CLOB endpoint
  `GET https://clob.polymarket.com/clob-markets/{condition_id}` and look for
  `itode: true`." (line 66).

  **OBSERVED:** `itode: true` on all four windows read (S-K01a … S-K04a).

- **F-20 (CONFLICT C-16).** The predictions changelog contradicts the 250 ms
  in F-19:
  - "**Higher taker delay**: The taker delay on crypto markets is now `150ms`,
    up from `50ms`. The change took effect on **September 4 at 14:00 UTC
    (10:00 AM ET)**." (S-D85 line 43)
  - "The taker delay on crypto markets is now `50ms`, down from `250ms`."
    (line 47; 2026-08-17)

- **F-21 (tick size).** DOCUMENTED:
  - `tick_size_change` is a "Market tick size update when price approaches
    limits" (S-D14 line 709).
  - "Always read the active value from the market rather than assuming a fixed
    increment." (S-D23 line 387).
  - The documented increments are 0.1, 0.01, 0.005, 0.0025 (World Cup only),
    0.001 and 0.0001 (S-D23 lines 376-383).
  - **The thresholds and the rule are UNDOCUMENTED** (U-28).

  OBSERVED:
  - The 11 windows not yet open, priced near 0.5, had `0.01`.
  - The window in progress at fetch time had `0.001`, with Gamma
    `outcomePrices` `["0.005","0.995"]`.
  - 20 of the 21 resolved windows had `0.001`; one (2026-10-04 20:00Z) had
    `0.01`.
  - For the window in progress, the documented `GET /tick-size` returned

**Answer to Q3.4.** Two per-market delay fields are documented: Gamma
`secondsDelay` (absent on this series) and CLOB `itode` (true). An exact-match
review should name **`itode`**, a boolean that the documentation says is
omitted when false. The delay's length is not a per-market field, and the
official pages disagree on it (C-16), so it must not be hard-coded. A missing

thresholds. A reviewed series should state the allowed values and the moment
they are checked, and the trader must follow `tick_size_change`.
