- **Labels.** Every statement carries one:
  - **DOC** quotes an official page, with its source id and line numbers;
  - **SDK** is the published npm package contents (§S), with a file and line in

**Headline consequences** (the migration plan maps them to code):

1. **Our series is still V1, and V2 is not visible on Gamma at all** (O.1,
   O.5). A V2 window of `btc-15m-updown` cannot be observed before it exists,
   so the migration packages must be built from the documentation and this
   round's fixtures, and re-verified against the first live V2 window.
2. **Three PAPER paths break when our windows become V2** (INF from F-38,
   F-43, F-70 and our code; plan class A):
   - admission reads only `clobTokenIds`;

   - the V2 resolution push (`market_resolved`) is unobserved (U-38).

   class B).
4. **Before any mode above PAPER, the SDK must move to 0.12.0 or later**

**F-42 (DOC). The Position ID layout.** S-D10 lines 104-176 ("## Polymarket
Protocol V2"):
- lines 113-114: `[moduleId | baseHash | arity | reserved | resolutionChain |
  conditionIndex | outcomeIndex]`, of 8, 128, 16, 64, 16, 16 and 8 bits; the
  field table gives `reserved` as bits "40 to 103".
- lines 129-133: module `1` BinaryModule, `2` NegRiskModule, `3`
  CombinatorialModule.
- line 165: "conditionId    = positionId with bits 0 to 7 cleared".
- lines 171-172: "The other binary outcome is derived by replacing
  `outcomeIndex` with `0` for YES or `1` for NO."
- S-D11 lines 122-126: "The first byte identifies the owning module, and the
  last byte identifies the outcome, with `0` for YES and `1` for NO. Treat the
  complete Position ID as an opaque decimal string in application code."

**F-43 (DOC). A V2 condition id has two widths.**
- S-D10 lines 152-155: "Polymarket Protocol V2 represents a Condition ID as
  `bytes31` and an Event ID as `bytes29`. Compatibility boundaries that accept
  or return `bytes32` use the same values right-padded with zero bytes."
- S-D04 line 54: "V2 `bytes31` condition ID. For a padded V2 `bytes32` value,
  validate its final byte is zero before narrowing."
- S-D12 line 216: "`conditionId` | 31-byte Polymarket V2 condition ID |
  Original 32-byte CTF condition ID".
- The documented Gamma V2 event (S-D17 line 281) carries
  `"conditionId": "0x017089ce3ba22aaa0a4cba8250b8c8e1eb0000000000000000000000000000"`:
  62 hex digits, the 31-byte form.
- The Data API defines `condition` as "`0x`-prefixed, 64 hex chars" (S-D26
  line 101).
- Which width each boundary takes is stated for no route individually (C-19).

**F-44 (OBS, computed). The observed ids match the layout.** Decoded locally

- The V2 ids `6635…625152`/`…625153` (S-L01) and `6198…204544` (S-L18) have

- Every V2 id observed is a 75-digit decimal string.

### S.4 Transport facts, for the SDK-adoption question

The migration plan's "Unified SDK adoption" section rests on these, read in the
0.12.0 sources:

- **No transport injection.** `createPublicClient` takes only `environment`,
  `apiKey` and `onRateLimitUpdate` (`PublicClientOptions`, `clients.ts` lines
  890-914; `createPublicClient`, lines 958-966). Each
  host is a `ServiceClient` built as `ky.create({ prefixUrl: root,
  throwHttpErrors: false })` (`ServiceClient.ts` line 79), with no `fetch`,
  `hooks`, `retry` or default `timeout`. A per-request `timeout` exists (lines
  168-174), but no public Gamma, CLOB or Data API read passes one.
- **ky's own defaults apply.** These were read from the repository's installed
  `ky` 1.14.3, the lockfile's version:
  - GET, PUT, HEAD, DELETE, OPTIONS and TRACE are retried up to 2 times, with
    a delay of `0.3 × 2^(n-1)` s (`distribution/utils/normalize.js` lines
    3-16);
  - the timeout is 10 000 ms, and `fetch` is `globalThis.fetch` unless one is
    passed (`distribution/core/Ky.js` lines 152-154);
  - INF: with `throwHttpErrors: false`, no HTTP status is retried, because the
    `HTTPError` the status retry acts on is thrown only when that option is
    set (`core/Ky.js` lines 58-60). A rejected `fetch` is still retried.
- **Raw bodies are not exposed.** A read returns the zod-parsed, normalized
  model. The `ServiceClient` getters `clob`, `gamma`, `data` and `secureClob`
  are `@internal` (`clients.ts` lines 140-190, 664-672) and absent from the
  `.d.ts`.
- **Normalized models drop fields.**
  - The Gamma `Market` keeps `version` and both ids but not `eventStartTime`,
    `makerBaseFee`, `takerBaseFee`, `restricted`, `automaticallyResolved`,
    `acceptingOrdersTimestamp` or `umaResolutionStatuses`. Our doors read
    several of these (plan §7.1, S1).
  - The raw `GammaMarketSchema` declares them, but `normalizeMarket` does not
    carry them (bindings `gamma/market.ts` lines 450-536).
  - Undeclared keys such as `resolutionStatus` are stripped.
- **The market WebSocket drops frames silently.**
  - `websockets/lifecycle.ts` lines 218-228: a text frame goes first to the
    heartbeat handler, which consumes `PONG`; non-JSON is dropped.
  - `websockets/clob/market.ts` lines 143-149: each event that fails
    `MarketEventSchema.safeParse` is skipped.
  - `websockets/clob/protocol.ts` lines 203-208: `market_resolved` reaches a
    subscriber only with `customFeatureEnabled` and an `assetIds` entry it
    subscribed to.
  - DOC S-D08 line 332 (`0.1.0-beta.18`): "Streams drop unknown or unreadable
    WebSocket frames instead of closing the connection."
- **Rate-limit headers** reach `onRateLimitUpdate` from the `clob` and
  `secureClob` clients only; the `gamma` and `data` clients are built without
  it (`clients.ts` lines 306-319, 553-589).
- **Tree-shaking does not help.** `createPublicClient(...)` ends in
  `.extend(allActions)` (`clients.ts` line 965).
- **Bundle cost (OBS).** Measured with the repository's esbuild 0.28.2

## H. ADR-033 D5's venue questions

ADR-033 D5 ("Before the ruling, a venue round") asks three things.

**H-1. Does the SDK now have a public order-heartbeat method? No (SDK).**
- In 0.11.0, 0.12.0 and the canary, a case-insensitive search for "heartbeat"
  across every client and bindings `.d.ts` finds 0 matches. The string
  "heartbeats" occurs 0 times in their shipped JS, and the README has none.
- The sources' "heartbeat" hits are WebSocket keep-alive code:
  `websockets/heartbeat.ts` and its users.
- DOC: S-D20's TypeScript and Python tabs for order heartbeats still read
  "Content coming soon." (lines 1568-1569).
- So C-12 stands: the handoff's "heartbeat orders" through the SDK alone
  cannot be met.

**H-2. Does the SDK publicly export the credential and signing primitives an
L2-signed request needs? Yes (SDK).**
- `buildHmacSignature(secret: string, timestamp: number, method: string,
  requestPath: string, body?: string): Promise<string>` is a root export in
  all three releases (`dist/index.d.ts` lines 224 and 226). Its doc comment
  reads: "The `secret` is expected to be base64-encoded and is decoded before
  signing. The returned signature is base64url-encoded with padding preserved."
- `SecureClient`'s own L2 header builder calls it (`clients.ts` lines
  815-837, `#createL2Headers`): `POLY_ADDRESS: this.account.signer`, `POLY_API_KEY:
  this.credentials.key`, `POLY_PASSPHRASE: this.credentials.passphrase`,
  `POLY_SIGNATURE: await buildHmacSignature(this.credentials.secret, timestamp,
  request.method, request.path, request.body)` and `POLY_TIMESTAMP`.
- `BaseSecureClient` has public getters `get credentials(): ApiKeyCreds` and
  `get account(): AccountIdentity` (0.12.0 `dist/types-B9F4CyS-.d.ts` lines
  6552 and 6556; 0.11.0 `dist/types-BE9qerqa.d.ts` lines 5018 and 5022).
- DOC: S-D35 lines 225-228 give the L2 algorithm: `message =
  clob_request_timestamp + method + request_path` and `clob_l2_signature =
  urlsafeBase64WithPadding(HMAC-SHA256(base64Decode(<clob_api_secret>),
  message))`. S-D20 lines 1518-1523 append the body for the heartbeat:
  `message = <clob_request_timestamp> + "POST" + "/v1/heartbeats" + body`.
  `buildHmacSignature` appends `body` when one is given (`src/hmac.ts` lines
  36-47).
- **What is not public.** An authenticated transport: `secureClob` is
  `@internal` (`clients.ts` lines 669-672). INF: option 1 would sign with
  public SDK exports, so it needs no hand-written signing. It would still send
  its own HTTP request.

**H-3. The documented route, and whether a success carries an id: the S-D17
versus S-D18 conflict.**
- **The guide** (S-D20 lines 1482-1571; byte-identical in substance to
  VENUE-3's S-D17): "Send an empty `heartbeat_id` to `POST /v1/heartbeats`",
  "Each successful response returns a new ID to use for the following
  heartbeat", and a `400` body `{"error_msg": "Invalid Heartbeat ID",
  "heartbeat_id": "<expected_heartbeat_id>"}`.
- **The API-reference page** (S-D23; footer-only change since VENUE-3's
  S-D18) renders `` ````yaml /api-spec/clob-openapi.yaml post /heartbeats ``
  (line 17). That is `POST /heartbeats`: no request body, a `200` with
  `{"status": "ok"}`, then `401` and `500`.
- **The CLOB OpenAPI itself** (S-O02, new to this conflict) documents **both**:
  - `POST /heartbeats` (line 4110), `operationId: sendHeartbeat`: no request
    body; `200` `HeartbeatResponse` requires `status`, example `ok`.
  - `POST /v1/heartbeats` (line 4152), `operationId: sendHeartbeatV1`, "Send
    heartbeat (v1)": "The first request should include an empty or initial
    heartbeat_id. The response will contain a new heartbeat_id that must be
    used in subsequent requests." The request body `HeartbeatRequest` requires
    `heartbeat_id`; `200` `HeartbeatV1Response` requires `heartbeat_id`
    (`format: uuid`), "The new heartbeat ID to use in the next request"; `400`
    `HeartbeatErrorResponse` requires `error` and `heartbeat_id`, example
    `error: Invalid Heartbeat ID`.
  - Both routes require the five L2 security headers.
- **The cancellation sentences.**
  - The guide's section opens with the timeout: "Once the first heartbeat is
    accepted, the CLOB expects the account to keep sending them. If a valid
    heartbeat is not received within 10 seconds, all open orders owned by
    those CLOB API credentials are canceled. The cancellation check runs every
    five seconds, so cancellation may occur up to five seconds after the
    timeout." (S-D20 lines 1485-1489). Its first step is "Send an empty
    `heartbeat_id` to `POST /v1/heartbeats`" (line 1497), and its second is
    "send the latest `heartbeat_id` back to the same route" (line 1536).
  - The OpenAPI gives both operations the same sentence: "If heartbeats are
    not sent regularly, all open orders for the user will be automatically
    canceled." (S-O02 line 4115 for `sendHeartbeat`, line 4162 for
    `sendHeartbeatV1`).
- **Result** (corrected in round 1).
  - On `POST /v1/heartbeats`, a success carries the next id: the guide and
    the OpenAPI agree.
  - **The 10-second cancellation is documented for `POST /v1/heartbeats`.**
    The guide ties its 10 s timeout to that route, and the OpenAPI's
    `sendHeartbeatV1` carries the cancellation.
  - On `POST /heartbeats`, a success carries `{status}` and no id. Its
    OpenAPI entry also promises automatic cancellation, but no page gives its
    timing ("not sent regularly"), or says whether it is the same mechanism as
    the `/v1` id chain.
  - The `400` body's message key is `error_msg` in the guide and `error` in
    the OpenAPI.
  - So the conflict is **resolved in part.** The route and the id of the
    guide's 10 s mechanism are documented: `/v1/heartbeats`. The API-reference
    page renders the OpenAPI's other operation, `sendHeartbeat`, so the two
    pages describe two documented routes. Still open: the `400` key (C-20),
    and `/heartbeats`' timing and whether it is the same mechanism as
    `/v1/heartbeats` (U-40).
- **Correction to the record.** `verified-2026-09-16.md` §5 called S-D18 "the
  OpenAPI page for `POST /v1/heartbeats`". VENUE-3's S-D18 and this round's
  S-D23 both read `post /heartbeats`, and the frozen reports stay as they are
  (ADR-033 Context 3).

## 15. Fixture verdicts

**New:** `test/fixtures/venue/protocol-v2/` holds 20 captures with provenance
sidecars (its `README.md` indexes them). They are 2 documentation examples, 15
raw responses, 2 redacted responses and 1 trimmed WebSocket session. The
41 files, sidecars and README included, total 62 907 bytes (59 979 in round 0).
- They use `.jsonc` and `.jsonl`, not `.json`.
  `apps/ops-cli/src/verify-venue/fixtures.test.ts` ("every fixture file on disk
  is claimed by exactly one check") would fail on any unclaimed `.json` under
  `test/fixtures/venue/` (as VENUE-SETL-1 measured, its §15). A check that
  claims them needs `apps/ops-cli/**`, which this round may not edit.
- In the Data API trade rows, wallets, names, pseudonyms, bios, profile images,
  transaction hashes and sizes are replaced with labelled synthetic values.
- **Round 1:** the trade rows' block timestamps, both pages'
  `pagination.next_cursor` and the cursor in the page-2 sidecar's `url` are
  synthetic too. A feed cursor carries the seek anchor of the last row (F-77),
  and the round-1 review found that one GET of the committed page-2 URL
  returned the unredacted page byte for byte. The sidecars list each
  replacement, and the real URL stays in the scratch fetch log.
- **What remains (stated accurately in round 1).** No personal data is
  committed, but the trades are still in Polymarket's own public feed. The
  rows were the market's newest trades at the sidecars' `fetched_utc`, and the
  feed pages newest first (OBS). A walk of the market's public
  `/v2/trades?condition=…` back to that time, matched on side, outcome and
  price, could find them with their real wallets. The redaction keeps personal
  data out of the repository; it does not make the trades unfindable.
- **A departure from the parent fixture rules** (recorded in round 1).
  `test/fixtures/venue/README.md` ("Sanitization rules") allows identifiers
  "already published as examples in the official documentation, or synthetic
  values", and monetary values that are "the documentation's example values or
  small round numbers". These captures keep live condition, token and position
  ids, slugs, and observed prices and times, because they pin live V2 shapes
  that no documentation example shows. The packet asked for sanitized
  captures of live markets and named personal data for replacement; it did not
  address the parent rules. `V2-9` amends the parent README, or replaces the
  values, when it claims this directory (plan §4).
