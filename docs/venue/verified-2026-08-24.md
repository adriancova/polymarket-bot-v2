## 2. Order request/response schemas, order types, expiration

Source: https://docs.polymarket.com/trading/place-orders (accessed 2026-08-24)

### 2.1 Request

SDK-level limit order fields: `tokenId`, `side` (`BUY`/`SELL`), `price`
(string, must conform to market tick size), `size` (string, must meet minimum
order size), optional `expiration` (unix seconds, GTD only), optional
`postOnly`, optional `builderCode`.

SDK-level market order fields: `tokenId`, `side`, `amount` (BUY, USD
notional) or `shares` (SELL), `maxPrice` (BUY) / `minPrice` (SELL), optional
`maxSpend`, `orderType` (`FAK` or `FOK`).

Raw API submission wraps a signed EIP-712 order struct (`salt`, `maker`,
`signer`, `tokenId`, `makerAmount`, `takerAmount`, `side` 0/1,
`signatureType` 0=EOA 1=Proxy 2=Safe 3=Deposit, `timestamp` unix ms,
`metadata`, `builder`) with top-level `deferExec`, `orderType`
(`GTC`/`GTD`/`FAK`/`FOK`), `expiration`, `owner` (CLOB API key), optional
`postOnly`. Maker/taker amounts are six-decimal integers. Price/size decimal
precision depends on tick size (tick 0.01 → price 2 dp; 0.001 → 3 dp;
0.0001 → 4 dp; size 2 dp).

### 2.2 Response

API JSON response: `success` (boolean), `errorMsg`, `orderID`, `status`,
`makingAmount`, `takingAmount`, `transactionsHashes[]`, `tradeIDs[]`.
SDK response: `ok`, `orderId`, `status`, `makingAmount`, `takingAmount`,
`tradeIds[]`, `transactionsHashes[]`, and `code`/`message` on failure.

Order statuses: `live` (resting on book), `matched` (matched immediately),
`delayed` (marketable but subject to a matching delay when
`market.trading.secondsDelay > 0`), `unmatched` (marketable but failed to
delay; placement still succeeded).

**Delayed-order semantics (verbatim from official docs):** "A `delayed`
response is accepted but has not matched yet. Its `makingAmount` and
`takingAmount` are `"0"`, and its `tradeIds` and `transactionsHashes` are
empty because no fills exist yet. Treat it as a pending order rather than a
fill."

### 2.3 Order types and expiration rules

- **GTC** — rests until filled or canceled; `expiration` `"0"` or omitted.
- **GTD** — expires at a unix-seconds timestamp; **"GTD orders expire one
  minute before their stated expiration as a security threshold"**; minimum
  stated expiration is ~3 minutes in the future (effective floor ~2 minutes
  after the 60-second offset); formula for an N-second lifetime:
  `now + 60 + N`.
- **FAK** — fills available liquidity immediately, cancels remainder.
- **FOK** — fills entirely and immediately or not at all.
- `postOnly` applies only to resting limit types (confirms handoff §23).

### 2.4 Error taxonomy (documented examples)

`ok: false` / `success: false` with `code`/`message`/`errorMsg`. Documented
causes include: "not enough balance / allowance"; price not conforming to tick
size; order size below `min_order_size`; GTD expiration less than 3 minutes in
the future. The full server-side error-code enumeration is not exhaustively
listed on the docs page; treat any unrecognized code as UNKNOWN and surface it
(do not invent codes). See §12 (UNVERIFIED items).

## 3. Market WebSocket channel

Source: https://docs.polymarket.com/market-data/websocket/market-channel (accessed 2026-08-24)

- URL: `wss://ws-subscriptions-clob.polymarket.com/ws/market`.
- Subscribe frame: `{"assets_ids": ["<token_id>"], "type": "market"}`;
  enhanced events require `"custom_feature_enabled": true`. Dynamic
  `{"operation": "subscribe"|"unsubscribe", "assets_ids": [...]}` frames are
  supported without reconnecting.
- Standard events: `book` (full snapshot with `bids`/`asks` arrays of
  `{price, size}` strings, `hash`, `timestamp`), `price_change` (batched
  `price_changes[]` with `asset_id`, `price`, `size`, `side`, `hash`,
  `best_bid`, `best_ask`), `tick_size_change` (`old_tick_size`,
  `new_tick_size`), `last_trade_price` (`price`, `size`, `fee_rate_bps`,
  `side`, `transaction_hash`).
- Enhanced events (`custom_feature_enabled`): `best_bid_ask` (`best_bid`,
  `best_ask`, `spread`) and lifecycle events `new_market` / `market_resolved`
  (`winning_asset_id`, `winning_outcome`).
- Heartbeat: **client sends the text frame `PING` every 10 seconds; the server
  replies `PONG`** (application-level heartbeat).
- **`price_change.size` semantics: the current docs page defines `size` as a
  `DecimalString` but does not explicitly state absolute-vs-delta semantics or
  that `size: "0"` removes a level.** Handoff §23 asserts absolute price-level
  changes with zero removal. See conflict C-1 in §11. Fixtures include a
  size-zero example consistent with the handoff assumption, flagged as
  pending explicit documentary or observational confirmation (WP-070).
- The docs do not state a maximum assets-per-subscription limit or the
  server-side timeout consequence of missed PINGs (see §12).

## 4. User WebSocket channel (authenticated)

Source: https://docs.polymarket.com/trading/realtime-order-updates (accessed 2026-08-24)
Source: https://docs.polymarket.com/market-data/websocket/user-channel (accessed 2026-08-24; the two pages describe the same channel)

- URL: `wss://ws-subscriptions-clob.polymarket.com/ws/user`.
- Subscribe frame carries CLOB API credentials
  (`auth: {apiKey, secret, passphrase}`), `type: "user"`, optional
  `markets: ["<condition_id>"]` filter. "Send the subscription frame
  immediately after connecting. The server may close a connection that remains
  unsubscribed." Dynamic market subscribe/unsubscribe frames are supported.
- Heartbeat: client sends `PING` every 10 seconds; server replies `PONG`.
- `event_type: "order"` events: `id`, `owner`, `market`, `asset_id`, `side`,
  `original_size`, `size_matched`, `price`, `outcome`, `status`, `timestamp`;
  `type` is `PLACEMENT` | `UPDATE` | `CANCELLATION`; statuses `LIVE`,
  `MATCHED`, `DELAYED`, `UNMATCHED`, `CANCELED`.
- `event_type: "trade"` events: `id`, `taker_order_id`, `market`, `asset_id`,
  `side`, `size`, `price`, `status`, `maker_orders[]`, `trader_side`
  (`TAKER`/`MAKER`), `timestamp`.
- Trade settlement states (asynchronous on-chain settlement, confirms handoff
  §23): `MATCHED` ("orders matched and the transaction was submitted for
  execution"; a pre-broadcast matched state also exists), `MINED` ("observed
  onchain but has not reached finality"), `CONFIRMED` (terminal success),
  `RETRYING` ("settlement failed temporarily and is being retried"),
  `FAILED` (terminal failure).
- Reconnect guidance (verbatim): "Real-time updates do not replace
  authoritative account reads or replay every change missed during a
  disconnection." Clients must refresh authoritative state via REST after
  reconnect — this validates the handoff requirement that reconnect always
  triggers reconciliation (WP-280/WP-290).

## 5. Order heartbeat, cancel, and query endpoints

Source: https://docs.polymarket.com/trading/manage-orders (accessed 2026-08-24)

- Heartbeat: `POST /v1/heartbeats` with body `{"heartbeat_id": "..."}`;
  success echoes `{"heartbeat_id": "..."}`. Cadence: **send every 5 seconds;
  server timeout window 10 seconds without a valid heartbeat; cancellation
  sweep runs every 5 seconds**, so venue-side cancellation can occur up to
  ~5 seconds after the timeout. Invalid/expired ID returns `400` with
  `{"error_msg": "Invalid Heartbeat ID", "heartbeat_id": "<expected>"}`.
  When heartbeats stop, "all open orders owned by those CLOB API credentials
  are canceled." Confirms handoff §23 resting-order safety.
- Cancels: `DELETE /order` (`{"orderID": "..."}`), `DELETE /orders`
  (array of 1–3,000 IDs, duplicates ignored), `DELETE /cancel-market-orders`
  (`{"asset_id": ...}` or `{"market": ...}`), `DELETE /cancel-all` (no body).
  All return `{"canceled": [...], "not_canceled": {"<id>": "<reason>"}}`.
- Queries: `GET /data/order/<order_id>`, `GET /data/orders` (filters `id`,
  `market`, `asset_id`), `GET /data/trades` (filters `id`, `market`,
  `asset_id`, `maker_address`, `after`, `before`). Authenticated reads use
  HMAC-SHA256 CLOB API credentials.

## 6. Fees and rewards

Source: https://docs.polymarket.com/trading/fees (accessed 2026-08-24)
Source: https://docs.polymarket.com/programs/maker-rebates (accessed 2026-08-24)
Source: https://docs.polymarket.com/programs/taker-rebates (accessed 2026-08-24)
Source: https://docs.polymarket.com/programs/liquidity-rewards (accessed 2026-08-24)

Snapshot as of 2026-08-24 — these are volatile program parameters:

- Fee formula: `fee = C × feeRate × p × (1 − p)` (C = shares, p = price);
  fees are charged in USDC, symmetric around p = 0.5, rounded to 5 decimal
  places, minimum charged fee 0.00001 USDC. **Makers pay no fees; only takers
  pay.** Taker feeRate by category: Crypto 0.07; Sports 0.05; Finance/
  Politics/Mentions/Tech 0.04; Economics/Culture/Weather/Other 0.05;
  Geopolitics 0 (fee-free).
- Maker rebates: funded from taker fees, distributed daily at midnight UTC in
  pUSD, minimum $1 pUSD accrual; rebate share of pool by category: Crypto 20%,
  Sports 15%, most other categories 25%; fee-equivalent weighting
  `C × feeRate × p × (1 − p)`; payout =
  `(your_fee_equivalent / total_fee_equivalent) × rebate_pool` per market.
- Taker rebates (program launched 2026-05-28): tiered by 30-day weighted
  volume `wV = size × (1 − entry price) × category weight × bonuses`
  (weights 1.0–2.3; Geopolitics 0). Tiers Bronze $2k/3% → Obsidian $10M+/50%,
  with level-up bonuses; daily pUSD payout, $1 minimum, no backfill; omnibus
  third-party wallets ineligible.
- Liquidity rewards: daily midnight-UTC payouts to maker addresses, $1
  minimum; one-minute sampling, 10,080 samples per weekly epoch; quadratic
  score `S(v,s) = ((v − s)/v)² · b`; scaling factor c = 3.0; single-sided
  liquidity scores at reduced rate for midpoint in [0.10, 0.90] and scores
  zero outside; per-market parameters `rewardsMinSize`, `rewardsMaxSpread`,
  and `clobRewards` allocations are exposed on the market object (see §7).
  Reward estimates are analytics, never realized PnL (handoff §9.16).

## 7. Per-market trading parameters

Source: https://docs.polymarket.com/market-data/market-details (accessed 2026-08-24)
Source: https://docs.polymarket.com/trading/place-orders (accessed 2026-08-24)

- **Tick size is dynamic and must always be read from the market**
  ("Always read the active value from the market rather than assuming a fixed
  increment"). SDK field `market.trading.minimumTickSize`; Gamma field
  `orderPriceMinTickSize`. Observed values range 0.1 down to 0.0001, with
  special 0.0025 ticks on certain sports market types. Tick-size changes are
  also pushed on the market channel (`tick_size_change`). Confirms handoff
  §23.
- Minimum order size: SDK `market.trading.minimumOrderSize` / Gamma
  `orderMinSize`; "orders smaller than this are rejected."
- Trading delay: SDK `market.trading.secondsDelay` / Gamma `secondsDelay` —
  "delay, in seconds, before a newly placed marketable order can match";
  drives the `delayed` order status.
- Negative risk: SDK `market.state.negRisk` / Gamma `negRisk`; augmented
  neg-risk additionally uses event-level `enableNegRisk` and
  `negRiskAugmented`. Neg-risk markets settle through the Negative Risk CTF
  Exchange contract and support converting one NO token into YES tokens of
  the event's other outcomes.
- Liquidity reward settings per market: `rewardsMinSize`, `rewardsMaxSpread`,
  `clobRewards[]` (with `rewardsAmount`, `rewardsDailyRate`, `startDate`,
  `endDate`).

## 9. Matching-engine restricted modes

Source: https://docs.polymarket.com/trading/matching-engine (accessed 2026-08-24)

- Restart: order-related endpoints return **HTTP 425 (Too Early)** during a
  matching-engine restart. Recommended client behavior: exponential backoff
  starting at 1–2 seconds. Restarts are announced (~2 days notice) on
  official channels.
- Post-restart: engine enters **post-only mode for 2 minutes**; cancels are
  accepted; new orders must set `postOnly: true`; others are rejected.
  Responses include `retry_after_seconds` (e.g. `"retry_after_seconds": 79`).
- Cancel-only mode: HTTP 503 with "Trading is currently cancel-only. New
  orders are not accepted, but cancels are allowed."
- Post-only mode: HTTP 503 with "post-only mode: only post-only orders and
  cancels are allowed" plus `retry_after_seconds`.
- Verbatim guidance: "Do not retry the same non-post-only order unchanged" —
  directly supports the WP-310 acceptance criterion.

## 10. Geographic restrictions, CTF position operations, Chainlink TWAP

### 10.1 Geoblock

Source: https://docs.polymarket.com/api-reference/geoblock (accessed 2026-08-24)

- Check endpoint: `GET https://polymarket.com/api/geoblock` (served from
  `polymarket.com`, not the CLOB API hosts). Response:
  `{"blocked": bool, "ip": string, "country": string (ISO 3166-1 alpha-2),
  "region": string}`.
- Three restriction tiers as of 2026-08-24: OFAC complete block (IR, SY, CU,
  KP, UA-43, UA-14, UA-09 — no new orders, positions cannot be closed);
  regulatory close-only enforced on frontend and API (35+ jurisdictions
  including US, GB, FR, DE, AU, BR, RU); regulatory close-only enforced on
  frontend only (IE, JP, MT, NL).
- Handoff/WP-320 requirement stands: the live path must perform the current
  geographic eligibility check before real entries, and an ambiguous result
  must block new live entries. Not exercised in WP-000 (PAPER-only).

### 10.2 Split / merge / redeem (CTF)

Source: https://docs.polymarket.com/trading/ctf/overview (accessed 2026-08-24)
Source: https://docs.polymarket.com/trading/positions/manage (accessed 2026-08-24; page organization overlaps the CTF overview)

- Split: convert pUSD into a YES/NO token pair. Merge: convert a YES/NO pair
  back into pUSD. Redeem: exchange resolved outcome tokens for their payout.
  "Every YES and NO pair is backed by exactly $1 of collateral locked through
  the CTF contracts." Confirms handoff §23 (buying consumes pUSD; selling
  requires outcome-token inventory; split/merge/redeem are first-class wallet
  operations).
- Position identifiers derive on-chain: `getConditionId(oracle, questionId,
  outcomeSlotCount=2)` → `getCollectionId(parentCollectionId, conditionId,
  indexSet∈{1,2})` → `getPositionId(collateralToken, collectionId)`.
- Neg-risk markets use the separate Negative Risk CTF Exchange and support
  NO→(other outcomes' YES) conversion.
- The docs page retrieved did not enumerate the current contract addresses
  inline; addresses must be taken from the official docs/SDK constants at
  WP-300 implementation time (see §12).

### 10.3 Chainlink TWAP over RTDS

Source: https://docs.polymarket.com/market-data/chainlink-twap (accessed 2026-08-24)

- URL: `wss://ws-live-data.polymarket.com` (RTDS).
- Topics: `crypto_prices_twap_thirty` (30 s window) and
  `crypto_prices_twap_sixty` (60 s window); subscribe with
  `{"action": "subscribe", "subscriptions": [{"topic": ..., "type":
  "update", "filters": "{\"symbol\":\"btc/usd\"}"}]}`. Symbols are
  lowercase slash-delimited pairs (e.g. `btc/usd`); omitting `filters`
  subscribes to all pairs.
- Update payload: `{symbol, value (number), full_accuracy_value (string
  integer), timestamp (unix ms), window_s}` wrapped in
  `{topic, type: "update", timestamp}`. The exact-decimal ingestion path
  must use `full_accuracy_value`, never the floating `value` (handoff
  numeric invariant).
- Stream behavior (verbatim): "Subscriptions start with the next update.
  There is no snapshot, history, or replay after a disconnect." Confirms the
  WP-100 acceptance criterion that no missing history may be fabricated.
- RTDS heartbeat: client sends text frame `PING` **every 5 seconds** (note:
  different cadence from the 10-second CLOB WebSocket heartbeat).

## 11. Conflicts between official docs and handoff §23

- **C-1 — `price_change` size semantics.** Handoff §23 states market data
  includes "absolute price-level changes" (i.e. `size` is the new aggregate
  size at the level and `"0"` removes it). The current market-channel doc
  defines `size: DecimalString` without stating absolute-vs-delta semantics
  or zero-removal. This is a documentation gap, not a direct contradiction.
  Resolution per handoff §1.1: the handoff's architectural assumption is
  retained provisionally; fixtures mark the zero-size removal example as
  handoff-derived; WP-070 must confirm the semantics against the official
  SDK's book-maintenance code and/or live observation before the order-book
  package (WP-150) treats it as truth. Escalated to the orchestrator via
  this report.
- No other §23 note conflicts with the current official documentation. The
  following §23 notes were positively re-confirmed: unified SDK supersedes
  archived clients; user-stream settlement states MATCHED/MINED/CONFIRMED/
  RETRYING/FAILED; asynchronous settlement; heartbeat-based resting-order
  safety; GTC/GTD/FOK/FAK with post-only limited to resting limit types;
  dynamic tick size; IP throttling plus per-signer order/cancel token
  buckets; HTTP 425 restart followed by a post-only period; cancel-only/
  post-only mode-aware behavior; pUSD collateral with split/merge/redeem;
  30 s and 60 s Chainlink TWAP over RTDS; geographic eligibility check
  requirement. (50/50 resolution is a resolution-process fact asserted by
  handoff §23; see UNVERIFIED item U-6.)
